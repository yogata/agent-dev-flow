# DEC-041: Wave 構成純度と実行並列上限の単一所有

## 背景

REQ-061-010 が Wave 同時実行上限を case-ready の構成安全境界として要求し、case-run が Epic Wave 実行モード（case-run(#epic)）で Wave 並列委譲 5 件を独自枠として持ち、case-auto Design が N 個の execution_unit 並列時の N×5 件の同時起動を許容していた。これは Wave 構成（意味的依存構造）と実行並列制御の二重並列制御を許容する契約上の不整合であり、RU-0131 で問題提起された。同一の意味的依存 DAG に対する Wave 構成が実行上限やファイル競合リスクによって変化しないこと（構成不変性）を保証するため、構成・実行・統合の契約と検証を横断して整合させる分離方針が RU-0131 の合議（2026-09-23）で確定した。

## 決定

1. **Wave 構成純度**: Wave は Epic 内の子 Issue 間の意味的依存 DAG のみから導出する。実行時並列数、同時実行上限、ファイル重複、統合制約を Wave 構成判断に混入しない。runtime 上の batch や一時直列化を Wave 分割として永続化しない。
2. **実行並列上限の単一所有**: 1 回の case-auto orchestration の stage 3 全体で active Issue task 数（1 active task = 1 Issue への実装実行委譲）の上限を共有する（現行 5、数値は case-auto Design が所有）。Epic、Wave、Standard Issue、case-run 呼出しごとの独立実行枠を設けない。case-run は与えられた単一 Issue の実行に専念し、legacy case-run(#epic) 経路に由来する独立実行枠を廃止する。Wave 構成の読み取り、fan-out/fan-in、子 Issue 並列起動の制御は case-auto が単一所有する。
3. **論理上限と harness 制限の切り離し**: active Issue task 数の論理上限は ADF 契約として所有する。harness の同時起動制限（bg task API 上限等）は adapter・実装制約（キューイング・バンドリング等）であり、論理上限の値の根拠としない。
4. **重複検出の用途転換**: 変更対象ファイル重複の検出は実行・統合時の競合リスク検出・調停（一時直列化、変更対象の調整、merge 順序、rebase、衝突解消担当）に用い、意味的依存の推定根拠・Wave 分離の理由としない。成果の成立順序への依存が確認された場合は意味的依存として Wave 構成へ反映する。
5. **Wave 収束と依存充足の区別**: Wave 収束（全子 Issue の実行結果確定）と後続 Wave の依存充足（意味的依存条件の成立、必要な統合・マージの完了を含む）を区別し、次 Wave の開始は両方の成立を条件とする。blocked、failed、delegation-unavailable は収束には該当し得るが依存充足とはみなさない。

## 代替案

- 本責務境界を DEC-039（authority 格子・直列化単位・冪等・並行性の一般モデル）へ統合する案: DEC-039 は一般モデルを所有し、本 Decision の具体の責務境界（Wave 構成純度・共有 active 枠・収束と充足の区別）を一般モデルへ埋め込むと一般モデルの粒度が損なわれる。本 Decision は DEC-039 の一般モデルの下で適用される具体決定として分離して記録する。
- 実行上限を Wave サイズへ反映し続ける案（現行契約の維持）: 構成不変性が破れ、実行上限の変化や harness 制限が意味的依存構造に影響するため採用しない。

## 結果、影響

- 正: 同一の意味的依存 DAG に対する Wave 構成が実行上限の数値に依存せず決定的になる（静的 DAG 比較で検証可能）。並列上限の単一所有により二重並列制御が解消され、空き枠補充・状態と復元・収束と充足の区別が runtime 制御の正規契約になる。
- 負: legacy case-run(#epic) 経路の廃止に伴う全呼出元・契約・Skill・テスト資産の同期更新が必要になる。文言修正だけでなく決定的回帰検証（構成不変性、共有上限、空き枠補充、収束・充足判定、再開、重複検出用途）の実装が要求される。
