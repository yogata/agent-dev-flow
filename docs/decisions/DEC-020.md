# DEC-020: GitHub Issue 共通管理単位の採用

## Status

proposed

## Context

ADF では、未解決事項（設計判断待ち、確認事項、判断保留中の問い）を発生から解決、正規成果物への反映確認まで育成・追跡する管理単位が存在せず、GitHub Issue は req/case パイプラインで実装対象となった作業単位（Case Issue）に限定されていた。

近接する既存系統はいずれも未解決事項の育成管理を担わない。

- Intake / Learning: AI 駆動開発の改善循環（検出事項、学びの取り込み）を扱う。
- Decision: 解決結果のうち判断理由を保持すべきものを扱う。解決後の正規化手段であり、未解決期間の追跡手段ではない。
- RU: 解決後に変更実施が必要と判断された場合の変更要求を扱う。

一方、未解決事項の管理には、検討経過の時系列保持、複数 workflow からの共通利用、操作手段の環境差異の吸収が求められる。

## Decision

GitHub Issue を、追跡Issue（課題、ToDo、アイデア、リスク等の未解決事項の育成管理単位）と Case Issue（req/case パイプラインの実行票）の共通管理単位とする。

- Issue は論理 role（tracking / case）により区別し、機械判定可能とする。
- 追跡Issueの論理スキーマ（role、kind、状態と状態遷移、物理マッピング、本文標準構造）は単一の skill Design（agentdev-issue-tracking）が一元所有する。
- Issue への I/O は GitHub I/O を担う Custom Tool（agentdev_gh）の操作契約へ集約する。ローカル版は同一の上位操作契約でローカルIssue（.agentdev/issues/）を読み書きする。

判断理由は次の2点である。

- 論理 role による追跡Issueと Case Issue の分離により、未解決事項の育成管理と実行の作業単位の混線を解消する。
- GitHub とローカルの I/O を Custom Tool 境界へ集約することで、リポジトリ外部依存と環境差異を統制下に置く。

## Consequences

- 未解決事項の状態管理、検討経過（Issue コメント）、反映追跡が Issue 基盤で一貫して行われる（REQ-049）。
- GitHub Organization 固有設定（Issue Type、Issue Fields）は必須前提とせず、利用可能な環境での物理写像として扱う。
- ローカル版の保存単位がローカルIssue（.agentdev/issues/issue-{NNNN}.md）へ一般化される（REQ-009）。
- 追跡Issueの管理に必要な操作が GitHub I/O を担う Custom Tool の操作契約へ追加される（REQ-011）。
- 追跡Issueは docs/ 配下の文書種別ではなく、管理単位・永続状態として扱われる（REQ-001）。
