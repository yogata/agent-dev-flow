# DEC-011: STEP resume point と会話記憶非依存

## 背景

現行の command 実装では、STEP 間の引き継ぎが会話コンテキストに依存している。compaction や中断再開時に
会話コンテキストが喪失すると、workflow の再開が困難になる。

## 決定

各STEP を resume point として定義し、STEP間 handoff は会話記憶を権威情報源とせず、永続情報から再開点を
再構成できる。

AgentDevFlow 配布契約は「安定したSTEP 識別子と永続情報から再開点を決定できる契約」のみを所有する。
ToDo の使用・compaction 検出・current STEP 選択の実処理は harness 固有機能とする
（DEC-001 context管理harness委譲、REQ-002-022 harness固有詳細禁止に整合）。

入力解決優先順位・STEP構造の詳細は Design（`docs/designs/workflows/step-reference-contract.md`・
`docs/designs/workflows/input-resolution-and-durable-state.md`）へ分離する。

## 結果、影響

- DEC-001 の永続状態・停止・再開責務を精製する。relates-to: DEC-001。
- proposed DEC-008（case-auto 固有 resume）と relates-to 関係を持つ。
- compaction 後の安全な再開が、会話コンテキストの保存に依存しなくなる。

## Inventory による裏付け（AG-001）

Workflow Architecture Inventory（`docs/designs/foundations/system.md`）が STEP resume point と durable state の実態を裏付ける。

- **durable state の二系統**: 全 Command が GitHub Issue/PR（公開状態）と `.agentdev/`（ドメイン状態: draft・RU・promoted・inbox・deferred・REQ・Decision・Design）を durable state とする。会話コンテキストは権威情報源としない原則が全 Command で一貫する。
- **resume point の実例**: `req-save` は読込時 commit hash と pull 後 hash の一致検証で再開点を検証する。`case-run` は3フェーズ（準備・委譲・クリーンアップ）のべき等性で再開点を構成し、PR番号・PR URL・Issue コメント（blocked/failed SSoT）から再開点を再構成する。`case-auto` は `case_auto_started_at`（JST）と L1 工程別タイムスタンプ内訳を durable state として保持し、停止時報告で再開点を明示する。`backlog-review`・`intake-promote`・`learning-promote` は分類確定状態と promoted/inbox/deferred の削除・残置状態で再開点を再構成する。
- **status frontmatter による再開点再構成**: `draft-data.status`（`req-save`/`design-save` で `saved`/Design消費済みフラグ）、Design `status`（draft/accepted/superseded）、RU frontmatter（`status`・`tentative_classification`）が、会話記憶を介さず再開点を決定する安定した識別子として機能する。
- **HITL 密度と resume**: 高 HITL Command（`req-define`・`case-open`・`intake-promote`・`learning-promote`・`backlog-review`・`inspect-promote`）は承認状態も durable state（draft status・分類確定・ユーザー承認）に保持し、compaction 後再開が可能である。
