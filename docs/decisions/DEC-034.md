# DEC-034: v4 の移行・release 標準境界（非破壊移行原則・v4.0.0-rc.1 cutover・self-hosting）

## 背景

実装を先行すると現行構造を別名で再生産する危険がある。また、ADF 自身と既存適用 Project の状態をその場で段階的に破壊する移行は、失敗時に巻き戻せない。開発 controller をいつ旧世代から新世代へ切り替えるかの公式境界も未定義であった。

## 決定

v4 Standard Operating Model が所有する移行・release の標準境界として次を決定する。

(1) ADF 自身および適用 Project の移行は、source をその場で段階的に破壊しない「Freeze source -> separate migration worktree -> semantic inventory/mapping -> canonical target paths への v4 state 構築 -> v4 validation -> cutover」を恒久原則とする。一時 staging を cutover 後に残さず、cutover 後の Project には canonical ADF state を一つだけ存在させる。

(2) v4.0.0-rc.1 を「旧世代によって新世代を作る段階から、新世代が新世代自身を継続開発する段階への公式境界（controller cutover）」とする。RC tag は v4.0.0-rc.N 形式で full validation 済みの exact candidate commit への annotated tag として付与・push し、detached HEAD を通常開発環境としない。

(3) 正式 v4.0.0 は self-hosting 成立と pilot migration の Evidence に基づいてのみ付与する。v4.0.0-rc.1 の成立条件（v4 model canonical 確定、Runtime、文書運用、req-define 相当入口、case-auto 相当 orchestration、work_type/scale/Epic/Wave、Collaboration Loop、Quality/Evidence/Gate、Traceability、Skill 再編、Extensions、adapter、migration mechanism、automated validation、self-hosting 開始可能）、RC cutover sequence、正式 v4.0.0 前の ADF 自己 self-hosting と複数既存 v3 適用 Project の RC pilot migration（semantic preservation、Project Contract 再構成、Loop continuity、Extensions migration、Quality 実用性、Traceability migration、req-define -> case-auto 実利用、context reconstruction、resume/recovery、rollback の検証。RC tag 明示、未タグ main を migration target としない）、v4.0.0 final tag の成立条件、後続 v4 Implementation Sequence（Foundation -> Runtime/lifecycle/state -> REQ/Decision/Design implementation -> req-define/case-auto UX -> work_type/scale/Epic/Wave -> Quality -> Traceability -> Skill restructuring -> Loop -> Extensions -> adapters -> migration implementation -> full validation -> v4.0.0-rc.1 -> self-hosting + pilot -> RC fixes -> v4.0.0）の依存順序は v4-migration-and-release Design が定義する（RC 前に migration と bootstrap self-hosting readiness を満たす）。

本決定は移行作業手順ではなく移行アーキテクチャの原則であり、作業手順は v4-migration-and-release Design が所有する。現行開発体制（v3 凍結・v4-dev branch 分離）の運用規範は本 Case の実行契約（realization_actions）が所有する。

## 結果、影響

後続の v4 実装・RC・pilot migration・final release の判断基準が確定する。v3 側は凍結運用とするため旧世代からの定期同期は原則不要とし、緊急修正が入った場合は個別に反映する。
