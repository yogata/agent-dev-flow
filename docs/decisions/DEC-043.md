# DEC-043: case-ready 実行構造判断への Jev 最終判断採用（Stage 2: 閾値ルーティング）

## 背景

Jev 有効性評価（Issue B、#3151。評価レポート: https://github.com/yogata/agent-dev-flow/issues/3151#issuecomment-5840241507）が観測 pool 45 JSON・242 判断（6系統、2026-09-22〜09-25）を分析し、判断単位ごとの Jev 単独利用可能性の材料を提示した。その結果、case-ready 実行構造判断（Standard/Epic 帰属・3軸判断）は是正率 2.9%（35判断中1件、唯一のは正も depends_on 機械的事実との突合由来）で最有力候補となり、構成欠陥除外後の閾値フロンティアでは T=0.9 で是正 0・カバレッジ 32.5%（系統内約76%）が示された。

2026-09-26、ユーザー承認（#3151 コメント https://github.com/yogata/agent-dev-flow/issues/3151#issuecomment-5840499327）により置換対象・採用閾値・段階実施が確定した（Issue C: #3156、元 Case #3143 OU-0002 / RU-0121）。

## 決定

1. **置換対象と基本契約**: case-ready の判断単位「Standard / Epic 確定（3軸判断の総合帰属）」について、Jev 先行評価の全 judgment の confidence が閾値 T = 0.9 以上の場合のみ Jev 結果を最終判断として採用する。1 judgment でも閾値未満の場合は判断単位全体を従来逐次経路（Jev 結果を情報として含む LLM 推論 → LLM 最終判断 → unchanged/corrected 記録）で処理する。閾値未満での Jev 単独採用を行わない（LLM fallback 必須）
2. **閾値の性格**: T = 0.9 は Issue B 評価結果から判断単位ごとに決定されユーザー承認された運用値であり、恒久確定ではない。将来の再評価・変更は別のユーザー承認による。Workflow 側で新規決定しない
3. **段階実施**: 6系統一括置換を行わない。本次は case-ready の当該判断単位のみ。他5系統と case-ready 残り2判断単位（Wave 構成判断、既存オープン Issue とのスコープ重複判定）は従来逐次経路（観測継続）を維持する
4. **観測契約**: Jev 結果・候補別確率分布・confidence・outcome は従来どおり独立した一次観測値として記録する。Jev 単独採用時は LLM 最終判断 field の追記を行わず部分レコード（recordState=partial）を正規の完了状態とする。これが置換経路の機械的識別子である。観測 schema の恒久改善（finalizer 区分 field 等）は Issue A 系（REQ-090 後続）の課題とし、本 Decision では現行 schema のまま運用する
5. **機構の再利用**: Jev 呼出し機構は Custom Tool `agentdev_jev` を再利用し、新規 Tool を作らない。Jev API 失敗時は自動 retry せず即座に従来 LLM 経路へ fallback し（REQ-090-003）、API key 未設定時は従来 LLM 経路のみで完了する（REQ-090-002）
6. **決定的検証の維持**: 構成検証（上限・依存維持・全割当）は決定的検証として Jev 置換対象外であり、Jev 単独採用時にも従来どおり適用する

## Jev 最終判断範囲と LLM 維持範囲

- Jev 最終判断範囲: case-ready「Standard / Epic 確定（3軸判断の総合帰属）」判断単位のうち confidence >= 0.9 の実行時のみ
- LLM 維持範囲: 上記判断単位の confidence < 0.9 の実行時、case-ready 残り2判断単位、他5系統（learning-promote、req-define、intake-promote、inspect-promote、backlog-review）の全判断単位

運用契約の正は配布 skill reference（`src/opencode/skills/agentdev-workflow-case-ready/references/execution-structure.md`「Jev 評価経路」節）が所有する。

## 代替案

- (a) 全系統一括置換 — 評価結果が系統ごとに有力差を示し（intake-promote 是正20% 等）、一括採用の根拠がないため不採用（段階実施は設計メモ §10.3 契約どおり）
- (b) margin（分布 top1−top2）併用の同時採用 — 評価レポートのフロンティア C で有望だが、ユーザー承認範囲外の設計拡張のため本 Decision では採用せず、将来の拡張候補として残す
- (c) 観測継続のみで置換を見送り — 承認された置換対象・閾値が存在し、着手条件（Issue B 評価結果と承認）が充足したため不採用

## 結果、影響

- 正: 当該判断単位の LLM 推論をスキップでき、処理時間・token 消費を削減できる。評価レポートの根拠（是正 0・カバレッジ約76%）の範囲で運用リスクを抑制する
- 負: Jev API 障害時・低 confidence 時は従来経路へ fallback するため、処理時間は置換前に比べて増加し得る（Jev 呼出し追加分）。confidence 0.9 未満の分布での Jev 単独行動は保証されない（fallback で LLM が担保する）
- 観測: 置換経路の実績（partial レコードの蓄積）により、将来の再評価（閾値変更・範囲拡大）の材料が追加蓄積される

## 再評価・撤回条件

- Jev 単独採用された構成判断に起因する構成不備が構成検証・実行で検出された場合は、当該事例を観測記録と共に整理し、閾値再評価または置換撤回をユーザー承認に付す
- 観測 pool の追加蓄積によりフロンティアが変化した場合も同様に再評価候補とする（機械的判定ではなくユーザー承認による）
