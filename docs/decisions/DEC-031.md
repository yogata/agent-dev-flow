# DEC-031: ADF v4 Standard Operating Model の採用とプロセス・実装の責務分離

## 背景

v3 は標準プロセスの概念と Command/Skill/checker/sidecar/OpenCode/GitHub 等の具体実装が結合しており、概念の本質と実装方式の変化が相互に拘束し合っていた。実利用は req-define -> case-auto、backlog-auto -> req-define -> case-auto に収束しつつある一方、内部状態機械の個別手動操作を公開 UX として扱う構造が運用負担となっていた。

## 決定

ADF を標準 Operating Model として再構成する。目的を「要件に基づいて AI エージェントと人間が協業し、継続的にソフトウェアを開発するための標準 Operating Model とその実行基盤」として定め、汎用ワークフローエンジン化を目的としない。標準プロセスの本質とその時点の実装方式の結合を解き、v3 系で蓄積した本質的概念（REQ、Decision、Design、work_type、scale、Epic、Wave、Case、Intake、Learning、Backlog、Quality/Verification/Evidence、Traceability、Project Extensions）を標準語彙として保持する。概念と実装の分離原則を、全モデル定義と実装の判断基準とする。

## 結果、影響

全成果物は概念モデル（Standard Operating Model）と実装（Runtime/adapter/配布物）の所属を明示して再編される。既存 v3 成果物の処遇は v3-v4-crosswalk が記録し、置換は後続段階（RU §24 Sequence）で実行する。
