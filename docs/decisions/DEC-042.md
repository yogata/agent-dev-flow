# DEC-042: case-auto 最大並列維持と同期逐次フォールバック禁止

## 背景

2026-09-24 の self-hosted case-auto 実行（RU-0122〜0133）で、stage 1 初回 background 委譲は 17〜25 秒間隔で複数子 session として並列起動された一方、以降の case-open 再試行が同期直列化し case-ready も同期実行に退化した。現行契約（REQ-034-025 の scheduling 語彙、REQ-034-028 の順次フォールバック許容、REQ-031-030 の同期再委譲）は運用合意（最大並列必須、障害後は durable state から並列再委譲を反復）と不一致であった。

## 決定

1. **並列必須と逐次完了禁止**: 各 orchestration stage は stage 内最大並列を維持する。実行環境由来の障害を理由とする同時1件の同期逐次実行（順次フォールバック）への切替を禁止する。並列起動が1件も成立しない場合は停止理由「並列起動不能」（原因断定を含まない）と再開可能性を報告して停止する。
2. **停止と staggered 反復再開モデル**: 再開時は durable state 照合により未完了対象のみを特定し、起動間隔契約に従う staggered background fan-out で並列再委譲する。反復に回数上限を設けない（設計意図）。停止報告には起動試行履歴（試行回数、起動成立数、最終成功起動時刻）を含め、操作者の再試行判断を支援する。
3. **弁別基準**: 並列起動不能（orchestration レベル）は当該 stage の起動可能対象集合に背景起動が1件も成立しない場合に限る。個別対象の起動失敗は delegation-unavailable として集約し、二重分類しない。一部起動成立時は部分継続原則（REQ-034-014、REQ-034-025）に従い稼働中対象と起動可能残対象の継続を妨げない。
4. **再委譲の確定条件**: background 再委譲の起動失敗継続時は Design の再試行計上契約に基づき delegation-unavailable へ確定する（fixed bound を要件へ固定しない）。
5. **適用対象外**: 必須依存・Wave 間・共有書き込み・単一書き手・実行安全上限による局所直列化、共有 active Issue task 枠の空き状況による可変並列度、コンフリクト解消 Level 2 再委譲（REQ-034-030）、bg task 破棄回復の親ループ代行（REQ-034-029）、親判断解決による下位 command の resume（REQ-034-032）。
6. **手段非固定**: staggered background fan-out は方針の規定であり、起動 API・実行基盤固有の並列化手段の固定ではない（REQ-034-036、DEC-041 決定3 と整合）。

## 代替案

- (a) 順次フォールバック許容の維持（現行）— 並列退化をマスクし観測性を損なうため不採用。
- (b) harness 起動 API 側の改善 — harness 責務であり本 Decision の対象外。
- (c) 反復に回数上限を設定 — 上限到達時の挙動が再び同期化または放置の二択となり目的を損なうため不採用（試行履歴報告で判断を支援）。

## 結果、影響

- 正: 並列退化の検出（対象別観測証跡）と回復（反復並列再委譲）が契約化される。
- 負: provider 障害持続時に完了までの所要時間が増加し得る（停止と再開の反復）。
