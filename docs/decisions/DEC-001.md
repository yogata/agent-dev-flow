# DEC-001: AgentDevFlow 憲章

## 背景

AgentDevFlow は、開発効率と品質を支える統制体系を蓄積してきた。
一方で、次の過剰・重複が生じていた。

- 配布 command の frontmatter `agent:` 固定など、harness 選定領域へ ADF core が踏み込む統制
- Design へ実装詳細（CLI 引数、report スキーマ、fixture 構成等）が侵出し、契約と実装が混在
- 特定時点の棚卸し検査と歴史経緯語彙検出が恒久 integrity rule 化
- 一時的な対応表が現行判断の入り口として参照され、作業成果物が恒久化
- 同じ意味空間を複数の Decision、REQ、Design が重複して所有

本 Decision は、これら過剰統制の削減、責務の限定と明確化、harness・model・project との責務分界の明確化、REQ/Decision/Design/command/skill/template/checker の重複削減、新規統制を安易に追加しない仕組みの確立を目的とする基準体系の再構築を定める。

過剰統制を是正するために巨大な新規統制体系を作っては本末転倒である。
本 Decision は基本原則を最小限の決定として定め、個別の統制追加・削除・統合判断をこの原則へ照らして行うための基準を提供する。

## 決定

### 決定1: ADF の中心責務

ADF は次を所有する。

- 要求の形成と合意
- 事実調査とユーザー意思決定の分離
- REQ/Decision/Design 等の成果物責任分界
- 実行可能な作業単位の形成
- Issue/PR/Case 間の工程接続
- SSoT の移行
- 承認境界
- 許可・禁止副作用
- 永続状態
- 依存、停止、再開、競合防止
- 受け入れ条件と完了証拠
- 実装中の発見の還流

### 決定2: ADF が所有しない領域

次の具体的実現方法は harness、AI モデル、適用プロジェクトへ委譲する。

- モデル選定、エージェント選定、サブエージェント階層
- skill の具体的な呼出し
- timeout、retry、context 管理
- TDD の具体的手順
- コードレビューエージェントの種類と構成
- デバッグ方法
- 実装計画の内部形式
- コード構造とテスト構造
- セッションの起動・終了
- バックグラウンド実行の具体的手段
- プロセス監視
- 生存確認

ADF は検証能力、回帰防止、独立レビュー等の「必要能力」と「標準方針」を定義してよい。
ただし特定のエージェント名、skill 名、起動 API、実行順序まで ADF core で固定しない。

### 決定3: hard governance の限定

hard governance（工程停止を要求する機械的強制）は、次の8点に限定する。

1. 状態破壊
2. 権限逸脱
3. ユーザー合意の偽装
4. 作業または永続情報の喪失
5. 二重実行、競合更新
6. 誤った成果物の正規化
7. 下流工程の実行不能
8. 後から検出・回復できない重大な失敗

文章品質、推奨する実装方法、分類の細部、改善候補は、原則として guidance または finding として扱い、工程停止条件にしない。

### 決定4: 新規統制追加の原則

新しい REQ、Design、Decision、command、skill、state、schema、gate、必須 field、checker を追加しないことを既定とする。

新規 hard control を提案する場合は、次の7条件を全て立証すること。

1. 再現可能または複数回観測された問題がある
2. 被害が hard control に値する
3. 削除、統合、interface 縮小、guidance 改善では防げない
4. 実際に機械的または運用上強制できる
5. 正規所有者が一つに定まる
6. 既存の何を削除または簡略化できるか説明できる
7. 将来の削除条件または再評価条件がある

「念のため」「将来必要かもしれない」「網羅性を上げたい」のみでは追加理由としない。

### 決定5: 管理方式

| 項目 | 取扱い |
|------|-------|
| 過去版の履歴基準 | tag `v2.11.0`（commit d1b4699）を変更しない履歴基準とする |
| 過去版の保守境界 | 過去版は修正せず、tag 参照に限定する |
| REQ/Decision 番号 | 現行文書は `REQ-001〜`、`DEC-001〜` の3桁IDを使い、過去版の文書は `v2:REQ-0119` 等の表記で区別する |
| docs ディレクトリ配置 | 現行配置（`docs/requirements\|decisions\|specs\|guides`）を維持 |
| Local backend | 必須範囲に維持。仕様は最小契約へ縮小 |
| draft 形式 | 承認済 change brief へ縮小。詳細は別途 REQ で定義 |

状態管理の分離: 基準文書と実装は Git、作業状態は GitHub Issue/Project、版間の履歴境界は Git tag、一時的な棚卸し対応表は非正規の作業成果物、実装差分は PR とする。
Issue/Project の状態を REQ/Decision/Design/draft へ複製しない。

### 決定6: リリース条件

リリース（main 統合と tag 付与）は、次の全てを満たした場合のみ行う。

1. 本憲章の決定1〜5を満たす
2. 基準文書が過去版を読まずに自足している
3. command、skill、template、checker が基準と整合する
4. Designが定義する10件の必須シナリオをすべて通過する
5. 互換範囲が明確
6. active な draft、RU、Issue の扱いが決着している
7. 一時成果物の引継ぎ漏れがない
8. リリースノートがある
9. main へ統合可能
10. tag を付与可能

## 代替案

1. **過去版からの逐語修正で表現**: 履歴境界が曖昧になり、過剰統制が温存されるため不採用。現行基準の再構成を許容する。
2. **現行の番号枠を設けず過去版から継続採番する**: 過去版と現行文書の区別が付きにくく、一時的な対応表が不要にならないため不採用。現行文書には `REQ-001〜`、`DEC-001〜` の番号枠を採用する。
3. **憲章を複数 REQ へ細分化**: 憲章の精神を個別要件へ分散させると原則判断の場が失われる。本 Decision で一括定義する。

## 結果、影響

- 配布物（command/skill/Design/template/script）から harness 固有記述を除去する個別判断は、本憲章の決定2へ照らして行う。
- 既存 Design から実装詳細を剥離する判断は、決定3（hard governance 限定）と決定4（新規統制追加抑制）へ照らして行う。
- 既存の v2:ADR-0136（harness 実行制御分離）、v2:ADR-0139（正規所有モデル）は本憲章の先駆的適用として維持する（relates-to）。
- 過去版の ADR 本文は書き換えず、tag 参照で維持する。
- 現行の REQ/Design は過去版を参照せずに自足させ、一時的な対応表を現行根拠にしない。
- 一時成果物は所定のライフサイクルに従って処分する。
