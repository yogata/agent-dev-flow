# 外部依存メジャーバージョン互換性管理ガイド

外部依存のメジャーバージョン互換性管理のガイド。`docs/specs/guides/` ドメインは存在しないため、執筆規約ドメイン（authoring）へガイド的性質の SPEC として配置する。依存追加・更新前の互換性事前確認手順、影響範囲スキャン方法、検査器と対象コードのバージョン整合要件を定義する。

本ガイドは執筆規約（authoring）に属し、コード変更を伴う全ての工程（case-run、case-update、メンテナンス作業）で参照する。 REQ や ADR を新設せず、guide 的性質の SPEC として運用する（AG-012）。

## 背景

外部依存のメジャーバージョンアップは互換性非整合を引き起こす事例がある。事後対応では影響範囲が拡大するため、依存追加・更新前に互換性を事前確認する必要がある。

- 具体例1: no-excuse 検査器が TypeScript 7 を要求するが対象コードは TypeScript 5.9（起動不能）
- 具体例2: zod v3 → v4 の `.refine` API 非互換

## 適用範囲

本ガイドの対象と対象外を以下に示す。

**対象**:

- 外部依存（npm パッケージ、CLI ツール、検査器等）のメジャーバージョン追加・更新
- 検査器（no-excuse、biome、tsc 等）と対象コード間のバージョン整合確認
- 依存追加・更新に伴う影響範囲スキャン

**対象外**:

- 同一メジャーバージョン内のマイナー・パッチ更新（互換性が前提されるため）
- 内部モジュール（リポジトリ内コード）のリファクタリング
- CI 実行環境（Node.js、Bun 等のランタイム）のバージョン選定（別課題）

## 用語

- **検査器**: 型検査、Lint、テスト等を実行するツール（no-excuse、tsc、biome、vitest 等）。対象コードとは独立にバージョン指定される場合がある
- **対象コード**: 検査器が検査対象とするリポジトリ内コード。対象コードが使用する言語機能や API バージョンを指す
- **メジャーバージョン**: SemVer の major 番号。メジャーバージョンアップは破壊的変更を含む可能性がある
- **互換性非整合**: 検査器要件と対象コード要件が矛盾し、検査器が起動しない、または正しく検査できない状態

## 依存追加・更新前の互換性事前確認手順

依存追加・更新前に以下のステップを順に実行する。いずれかのステップで不整合を検出した場合、ステップ5に従い依存追加・更新を停止する。

### ステップ1: 現行依存バージョンの確認

追加・更新対象の依存について、現行バージョンと更新後バージョンを確認する。

- `package.json`、`bun.lockb`、`package-lock.json` 等のロックファイルから現行バージョンを確認
- 更新後バージョンのリリースノート、CHANGELOG、Migration Guide を読む
- 破壊的変更（Breaking Changes）の有無を確認

### ステップ2: 検査器要件の確認

依存が検査器（または検査ツール）の場合、検査器が要求する言語バージョン、ランタイムバージョンを確認する。

- 検査器の `engines` フィールド、`peerDependencies` を確認
- 検査器のドキュメントに記載の前提条件（TypeScript バージョン、Node.js バージョン等）を確認
- 検査器が必要とする言語機能レベルを確認

### ステップ3: 対象コード要件の確認

検査対象となるリポジトリ内コードの要件を確認する。

- 対象コードが使用する言語バージョン（`tsconfig.json` の `target`、`lib` 等）
- 対象コードが依存する API バージョン（`package.json` の `dependencies`）
- 対象コードのランタイム（Node.js、Bun のバージョン）

### ステップ4: 整合性評価

ステップ2（検査器要件）とステップ3（対象コード要件）を突き合わせ、整合性を評価する。

- 検査器が要求するバージョン ≦ 対象コードが使用するバージョン であることを確認
- API 非互換（削除、シグネチャ変更、非推奨化）が対象コードに影響しないことを確認
- 影響がある場合、影響範囲スキャン（次節）を実施し、対応方針（コード修正、代替 API 移行等）を決定する

### ステップ5: 不合格時の扱い

整合性評価で不整合を検出し、対応方針が即時に決定できない場合、依存追加・更新を停止する。

- 即時対応可能な修正（型エラーの修正、非推奨 API の置換等）は同一 PR 内で実施する
- 対象コードの大規模修正が必要な場合、依存追加・更新を別 Issue に分割し、先にコード修正を実施する
- 依存追加・更新を強行しない（後追いで対応方針を決めることを禁止）

## 影響範囲スキャン方法

依存追加・更新に伴う影響範囲をスキャンし、互換性非整合箇所を特定する。

### スキャン対象

影響範囲スキャンは以下を対象とする。

- **API 使用箇所**: 更新対象依存の公開 API を使用するコード（`grep`, `ast-grep` で検索）
- **型参照**: 更新対象依存が提供する型を import するコード
- **設定ファイル**: 更新対象依存の設定ファイル（`tsconfig.json`、`.bazelrc` 等）

### 具体的コマンド例

依存の公開 API 名（例: `refine`, `parse`）でリポジトリ内を検索し、使用箇所を洗い出す。

```bash
# zod の .refine API 使用箇所の検索例
rg "\.refine\(" --type ts

# TypeScript の特定構文（例: satisfies 演算子）使用箇所の検索例
rg "satisfies " --type ts

# 依存の import 文の検索例
rg "from ['\"]zod['\"]" --type ts
```

ast-grep を使った構文ベースの検索（誤検出低減）も推奨する。

```bash
# ast-grep による .refine 呼び出しの検索例
sg -p '$X.refine($$$)' --ts
```

### 検出シグナル

影響範囲スキャンで以下のシグナルを検出対象とする。

- **API 非互換**: 削除メソッド、シグネチャ変更、引数変更
- **非推奨化**: `@deprecated` 付与、ドキュメント上の非推奨指定
- **型の非互換**: 型定義変更による型エラー、型推論結果の変化
- **ランタイム挙動の変化**: 同期→非同期化、例外送出条件の変更、戻り値の構造変更

スキャンで検出した箇所は、ステップ4（整合性評価）に基づき対応方針を決定する。

## 検査器と対象コードのバージョン整合要件

検査器と対象コードの言語バージョン整合は必須要件である。本節は TypeScript を具体例とするが、他の言語処理系（Python、Rust 等）にも同様に適用する。

### TypeScript バージョン整合（必須）

- 検査器が要求する TypeScript バージョンと対象コードが使用する TypeScript バージョンを一致させる、または対象コード側を上回る
- 検査器が新しい TypeScript 機能（例: TypeScript 7 の新構文）を要求する場合、対象コードが当該機能を使用しない場合でも検査器が起動しない可能性がある。この場合、対象コードの TypeScript バージョンを上げるか、検査器のバージョンを下げる
- 検査器が古い TypeScript しかサポートしない場合、対象コードが新しい構文を使用していると型エラーが発生する。この場合、検査器のバージョンを上げるか、対象コードの新しい構文使用を取りやめる

### 不一致時の扱い

検査器要件と対象コード要件が不一致の場合、依存追加・更新を停止する。不一致状態での依存追加・更新は以下の問題を生むため禁止する。

- 検査器が起動せず、CI が通っても実効性がない（false-positive green）
- 型検査が部分的にスキップされ、型安全性が損なわれる
- 開発者がローカルで検査を実行できず、検査結果の再現性が失われる

不一致を解消できない場合、依存追加・更新を断念し、代替手段（フォーク、別検査器の採用等）を検討する。

## 既知の事例

本ガイドの導入契機となった事例と、その対応方針を記載する。新たな事例が発生した場合は本節に追記し、ガイドの改良材料とする。

### TypeScript 7 を要求する no-excuse 検査器

- **事例**: no-excuse 検査器が TypeScript 7 を要求するが、対象コードは TypeScript 5.9 を使用。検査器が起動不能となった
- **対応方針**: 検査器の要求バージョンを下げる（TypeScript 5.9 サポート版）、または対象コードの TypeScript バージョンを 7 へ上げる。いずれも困難な場合、検査器の導入を延期する
- **教訓**: 検査器導入前にステップ2（検査器要件の確認）とステップ3（対象コード要件の確認）を必ず実施する

### zod v3 → v4 の `.refine` API 非互換

- **事例**: zod v4 で `.refine` API のシグネチャが変更され、既存コードが型エラーとなった
- **対応方針**: 影響範囲スキャンで `.refine` 使用箇所を特定し、新シグネチャへ機械的に移行する
- **教訓**: メジャーバージョンアップ時は影響範囲スキャン（前節）を必ず実施する
