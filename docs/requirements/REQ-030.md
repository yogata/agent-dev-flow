## 目的

case-open の実行契約を所有する。
case-open は ADF v4 公開運用モデル（DEC-033）において内部 lifecycle 段階である。
合意済み要件doc からの Root Case 確立、Definition Package の生成、canonical Definition に実変更がある場合の Definition PR 作成を扱う。
execution contract の確定、Standard / Epic の最終確定、Child Issue・Wave の作成、RU 削除、proposed Decision の受理評価は case-ready 実行契約 REQ が所有する。
マクロフェーズ構成と work_type 分類は REQ-005 が、execution contract の境界定義は REQ-017 が、Case 状態モデルは REQ-006 が所有し、本 REQ は case-open の実行オーケストレーションを所有する。

## 要件

| ID | 要件 |
|---|---|
| REQ-030-001 | case-open は合意済み要件doc を入力とし Root Case を GitHub Issue として確立し、対象要件（REQ 番号または Issue 内の合意済み要件）を Root Case 本文の対象範囲へ記載すること |
| REQ-030-002 | case-open は canonical Definition に実変更がある場合のみ、Case 単位で一つの Definition PR（GitHub Draft PR ではない通常 Pull Request）を作成すること。canonical Definition に実変更がない場合は Definition PR を作成しないこと |
| REQ-030-003 | case-open は壁打ち済み内容を Definition Package として生成し Root Case に関連付けること（Definition Package の構成は Design。Definition Package を独立した Issue 本文物項目として生成しない） |
| REQ-030-004 | case-open は機能要件、非機能要件、制約、対象外、受け入れ条件を新規に作成せず合意済み入力を反映すること |
| REQ-030-005 | case-open は新規 Decision を proposed のままにし accepted への状態遷移を実行しないこと |
| REQ-030-006 | case-open は要件が曖昧で Root Case を確立できない場合、停止すること |
| REQ-030-007 | case-open は draft / RU を削除しないこと |
| REQ-030-008 | case-open は execution contract を確定せず、Standard / Epic を最終確定せず、Child Issue、Wave を作成しないこと |
| REQ-030-009 | Root Case 確立後の状態は Case 全体の正規状態（実行継続）とし、実行契約の確定を条件とせずに実装開始を許可しないこと |
| REQ-030-010 | case-open は再実行時、既存 Root Case および既存 Definition PR を再利用し、不足分だけを処理して重複生成しないこと |
| REQ-030-011 | case-open は自工程で実観測した deviation を Split Rule で分類して intake/learning のいずれかへ保存すること（case-close への capture 委譲は廃止） |
| REQ-030-012 | case-open は STEP-5 冪等確認の実行時、draft の artifact_actions と未クローズ Case 群の主な変更対象（実行単位が所有する宣言）を機械的に比較し、2 以上の Case 間で同一パスが重複する場合、警告として投入者に提示すること。検出源の取得不能時は検出不能として報告すること |
| REQ-030-013 | 前行の検査は合意済み宣言の機械的比較に限定され、一般的な変更影響探索・依存関係探索（REQ-021-014）に該当せず、対象範囲を再決定せず、警告のみで Root Case の確立を自動阻止しないこと |
| REQ-030-014 | Epic を構成する投入では同一投入内（Epic 配下 Wave 内）の変更対象重複検出を子 Issue 確定後の検出（REQ-061-019）へ委譲し、二重検査としないこと。Epic をまたぐ Case 間の重複は本検査が検出対象とすること |
| REQ-030-015 | case-open は REQ 行追加を伴う Definition Package 生成時、検証スコープポリシー（traceability/policy.yaml）更新の追随要否を工程上明示し、必要なポリシー更新を Definition に含めること。ポリシー編集は実変更であるため Definition PR 経由以外の適用経路を取らないこと |
| REQ-030-016 | case-open は公開 command ではなく内部 lifecycle 段階として case-auto の orchestration から駆動されること。単独の手動起動を公開 UX の標準としないこと |
| REQ-030-017 | 並行して case-open を実行する場合、各 Case は専用 worktree で作業し、Definition branch は origin/main HEAD から独立して作成して兄弟 Case の commit を含むスタック構造を作らないこと。PR 作成前に merge-base と diff --stat により自 Case 差分のみであることを検査し、明示パス指定のステージングと git status による 1-writer 前提の侵害検知を行い、in-scope 外の書込みを検知した場合は直ちに停止（早期断念）すること。 |
| REQ-030-018 | case-open の preflight は deleteBranchOnMerge 設定を確認し、true でない場合と確認できない場合を区別した警告（設定無効 / 設定照会不能）として報告すること。当該設定理由だけでは case-open を blocked に停止しないこと。設定照会不能は実操作の安全性の証明ではなく、独立した実操作の安全性確認で認証・権限・必要な読取・書込み等の成立を確認できない場合は既存の安全契約に従って停止すること。ローカル版は設定確認をスキップする対象外とすること。確認手段の詳細は Design が所有する |
| REQ-030-019 | case-open は Definition Package の生成・確定において、合意済み入力の必須受け入れ義務（目的、対象範囲、禁止、対象外、受け入れ条件、必須検証義務）の欠落、縮小、反転がないことを、投影後の成果物だけの自己整合確認ではなく最新の合意済み入力との照合で確認すること。欠落・反転を検出した場合は Root Case の確定または実行へ進まないこと |
| REQ-030-020 | case-open は義務対応の確認で対応先の存在だけでなく元の義務の意味、評価範囲、禁止事項が保持されていることを確認し、どこにも対応しない受け入れ義務が存在する場合は非該当として扱わず投影不完全として処置すること |
| REQ-030-021 | case-open は Definition 確定後に投影不備が判明した場合、消費済み入力で実行契約を非公式に補完せず、正規の訂正経路での修復に向けた差し戻しを行うこと |

## 適用範囲

- 対象: case-open（Root Case 確立、REQ 番号埋め込み、Definition Package 生成、実変更時のみ Definition PR 作成、冪等再実行、自工程 deviation capture）
- 対象外: execution contract の確定、Standard / Epic の最終確定、Child Issue・Wave の作成、RU 削除、proposed Decision の受理評価（case-ready 実行契約 REQ）、マクロフェーズ構成と work_type 分類（REQ-005）、委譲時の判断と承認（REQ-003）、execution contract の境界定義（REQ-017）、Epic/Wave 実行モデルの実行規則（Epic と Wave 実行モデル REQ）、Definition Package の構成詳細（Design）、harness 固有詳細の配布物からの除去一般原則（REQ-002）
