## 目的

要件、技術判断、設計、案内、報告、索引、状態早見が、読み手の関心に沿って配置され、編集者が配置先を一意に定められる基準構造を維持する。
文書種別ごとの責務、識別子体系、配置規則、優先順位、ライフサイクルを一貫した基盤の上に成立させ、現行判断と履歴参照を明確に区別する。

## 要件

| ID | 要件 |
|---|---|
| REQ-001-001 | 文書種別（要件、判断記録、設計、案内、報告、索引、状態早見）ごとの責務は重複せず、各文書の配置基準が一意に定まること |
| REQ-001-002 | 要件文書は対象が満たすべき状態、振る舞い、制約、外部契約を記述し、詳細実装、内部パラメータ、作業手順を記述対象外とすること |
| REQ-001-003 | 設計文書は現在の内部構造、内部動作、責務分担、データ構造、処理方式、規則、パラメータを記述し、将来案、採用理由、却下理由、作業履歴、監査結果、評価結果、実測値、実装コードそのもの、検証実行結果を記述対象外とすること |
| REQ-001-004 | 判断記録文書は技術判断を含む意思決定のみを主題とし、削除、廃止、移行、統合といった作業手段を主題にしないこと |
| REQ-001-005 | 案内文書は人間向けの導線、案内、手順に限定し、必達要件の規範表現、詳細仕様、識別子注記を含めないこと |
| REQ-001-006 | 索引文書は探索入口を提供し、参照先文書の本文を重複して保持しないこと |
| REQ-001-007 | 状態早見文書は各状態項目ごとに状態、生成元、利用元、保持、削除条件を備えること |
| REQ-001-008 | 各要件、判断記録、設計は安定した一意の識別子を持ち、識別子は配置、分割、統合に依存せず不変であること。設計の識別子は文書配置パスにより一意に定まり、設計専用の識別子体系を導入しないこと |
| REQ-001-009 | 要件内の個別要件行は親識別子に連番を付与した形式で一意に識別できること |
| REQ-001-010 | 各永続文書は識別子、表題、作成日、更新日をメタデータとして備え、更新日は作成日以降であること |
| REQ-001-011 | 現行文書と廃止文書は配置、識別子、参照の扱いにおいて明確に区別されること |
| REQ-001-012 | 廃止文書は物理削除を第一選択肢とし、履歴参照に限定した運用を選ぶ場合も現行判断の根拠として引用しないこと |
| REQ-001-013 | 廃止識別子は再利用されず、廃止文書への参照は移行表、履歴節、置換連鎖による履歴参照に限定されること |
| REQ-001-014 | 現行文書の本文は過去前提、移行経緯、将来予定、未実装予定、検討過程、再編工程固有の識別子を含まず、現在契約を識別するための正式識別子のみを保持すること |
| REQ-001-015 | 履歴情報は版管理履歴、課題追跡、廃止文書で保持し、現行基準の本文では扱わないこと |
| REQ-001-016 | 現行文書の本文に取消線、見え消しを残さず、現行判断に必要な制約、例外、境界は現行文として記述すること |
| REQ-001-017 | 永続文書の本文は文意に基づく自然な日本語で記述し、内部処理段階名、抽象的な英単語修飾語、未定着の略語を露出しないこと |
| REQ-001-018 | 各記述の主たる文意は肯定文で記述し、否定文は肯定文で記述された主たる文意に対する境界条件、例外、補足として併記する場合に限り使用すること |
| REQ-001-019 | 主たる文意が否定文のみで構成された既存記述は、対応する肯定文へ書き換えること |
| REQ-001-020 | 文書間に矛盾がある場合、現行要件文書を最優先とし、次に承認済み判断記録、現行仕様の順で解決すること |
| REQ-001-021 | 判断記録は提案、承認、置換、非推奨の状態を持ち、承認状態の判断記録のみを現行根拠として使用すること |
| REQ-001-022 | 過去の判断を現行基盤から外す場合、新規判断記録ではなく既存判断記録の状態遷移で処理すること |
| REQ-001-023 | 新規判断記録は、旧判断を置き換える新たな意思決定が存在する場合に限り作成すること |
| REQ-001-024 | 判断記録の保存前には技術判断の存否を検証し、技術判断が不在の場合は保存を停止して理由を報告すること |
| REQ-001-025 | 設計文書は草案、承認の2状態を持ち、新規設計は草案として作成され、確定時に承認へ遷移すること。置換済み設計は現行設計ツリーへ保持せず、履歴は版管理、課題追跡、判断記録等の既存履歴手段から確認できること |
| REQ-001-026 | 設計の状態は単一の追跡情報源から視認でき、複数の索引で状態を重複管理しないこと |
| REQ-001-027 | 草案状態のまま放置される設計を機械的に検出できること |
| REQ-001-028 | 設計の新規追加、状態変更時には追跡情報源を実ファイルの状態と整合させ、登録漏れ、状態不一致を検出できること |
| REQ-001-030 | 永続文書の根拠参照は一時成果物の識別子を含まず、永続的な根拠のみを使用すること |
| REQ-001-031 | 配布成果物（実行時コマンド、スキル、テンプレート、判定処理）は自己完結し、リポジトリ内部の設計文書に依存せずに動作すること |
| REQ-001-032 | 配布成果物からは実行制御固有の詳細（実行者名、能力名、必須依存先、時間制限、再試行回数、文脈管理方式、検証手順）を除外し、必要能力と標準方針のみを記述できること |
| REQ-001-033 | 状態保持領域は永続的なドメイン状態であり、配布対象外であること |
| REQ-001-034 | 状態保持領域内の作業用ドラフトは正規のドメイン状態ではなく、コマンド間引き渡し用の中間成果物であること |
| REQ-001-035 | 課題、変更要求の状態管理は課題追跡系に一元化し、要件、仕様、取り込み成果物の本文で重複して管理しないこと |
| REQ-001-038 | 複数の関心領域にまたがる基盤設計は関心領域別に分類、体系化されること |
| REQ-001-039 | 新規設計の作成時には分類基準に従って配置先が決定されること |
| REQ-001-040 | 既存設計の分類変更時には旧配置と新配置の対応を追跡可能にし、旧参照を段階的かつ個別に更新すること |
| REQ-001-041 | 各要件、設計は文書統治、ワークフロー全体、配布成果物単位、成果物と実行時の責務、検証と検出、判断記録ライフサイクルのいずれかの分類に属し、関心対象の総体として説明できること |
| REQ-001-042 | 番号採番、識別子と配置の整合性確認、変更範囲の検証、配置先検索の決定的処理は、所有権を責務別に分離した正規所有者経由で実行すること |
| REQ-001-043 | 学習成果物、取り込み成果物から後続工程へ引き継ぐ分類根拠は、変更の性質、要件影響の有無、対象ステークホルダー、利用者から見える変更の有無、追記先の選択理由、根拠となる観測事実を含むこと |
| REQ-001-044 | 要件文書の健全性を要件行数、関心分類数、成果物種別数で定量化し、分割予兆を早期に検知して提案できること |
| REQ-001-045 | 現行要件、現行仕様の再構築時には完全性台帳により全要件行と全識別子なし規範記述を列挙し、分類確定、配置先確定、変更適用、配置先検証、内容算定の五状態が全て成立するまで完了扱いとしないこと |
| REQ-001-046 | 要件文書の標準構成は目的、要件、適用範囲の三区分とし、作業履歴、関連候補、出典記録の補助節を標準構成に含めないこと |
| REQ-001-047 | 変更の追跡は更新日フィールドのみで扱い、本文中に変更履歴節を設けないこと |
| REQ-001-048 | 要件行はステークホルダーを特定できること、ステークホルダーが得る成果または回避できる問題を説明できること、成果物内部を知らなくても達成を観測できること、内部構成を変更しても要求文が成立することの四妥当性基準を満たすこと |
| REQ-001-049 | 要件行は詳細実装の段階番号、手順番号を直接参照せず、機能名、段階名で参照すること |
| REQ-001-050 | 新規要件の作成は、既存要件に吸収できない独立した関心対象に限定されること |
| REQ-001-051 | 既存要件への追加は、既存セクションの内容を変えるか否かで追記または更新に分類されること |
| REQ-001-052 | 廃止候補は、バグ修正由来、移行完了状態、他要件への吸収済み、作業手段が主題の四類型で判定されること |
| REQ-001-053 | 作業種別はバグ修正、機能追加、保守、文書整備の四値に固定し、機能追加のみが規模を持つこと |
| REQ-001-054 | 実行経路は作業種別と規模から派生する値とし、独立した分類として管理しないこと |
| REQ-001-055 | 読者が現在の入力状態から次に実行すべき操作を選べる入口表を備えること |
| REQ-001-056 | accepted Decision を意味的に不変とし、明示承認済みの非意味修正と後継 Decision を必要とする意味変更を分離すること |
| REQ-001-057 | 直接更新可能な非意味修正は6分類体系として構成すること。各分類の具体的一覧は Design が正規所有すること |
| REQ-001-058 | 後継 Decision を必要とする意味変更は6分類体系として構成すること。各分類の具体的一覧は Design が正規所有すること |
| REQ-001-059 | 直接更新前に明示承認記録が存在すること。決定内容、範囲、制約、所有者、方式、観測結果の変更には後継 Decision が存在すること |
| REQ-001-060 | accepted Decision の過去版を無言で書き換えないこと。意味変更を表記修正として扱わないこと。Report へ規範要件または必達条件を移さないこと |
| REQ-001-061 | Decision と REQ は管理特性（重複排除、粒度管理）を分離すること。Decision は判断文脈の違い、再確認、後続判断との関係に意味があるため、意味的に近い複数 Decision の存在だけを理由として重複違反または自動統合対象としないこと |
| REQ-001-062 | Decision 間の意味的関係（関連、置換、再確認）を追跡可能とすること。具体的なフィールド名、enum、serialization 形式は Design の責務とする |
| REQ-001-063 | Decision の SPLIT / MERGE は固定件数のみで判断せず、意味的健全性（無関係な判断の混在、責務領域の過度な混在、判断境界の不明瞭化、accepted Decision 間の矛盾、関係付けされていない実質的な再確認・置換候補）を評価対象とすること |
| REQ-001-064 | Decision の健全性評価を REQ の重複・分割モデルと分離し、Decision 固有の意味境界・関係・矛盾を評価できること。類似性だけを根拠とする自動 MERGE を行わないこと |
| REQ-001-065 | 報告文書は監査、評価、観測、測定等の事実記録を専門とし、必達要件の規範表現を持たず、正規配置領域を設計文書と分離して持つこと |

## 適用範囲

- **対象**: 文書種別ごとの責務と配置基準、識別子体系、現行と廃止の区別、現行文書の記述品質、判断記録と設計のライフサイクル、文書間参照の健全性、配布成果物の自己完結性と実行時独立性、状態保持領域の位置づけ、正規所有モデルと配置一貫性、基盤設計の関心領域別体系化、要件文書の健全性指標と完全性台帳、要件行の妥当性基準、要件管理の追記、更新、廃止判定、作業種別と実行経路の分類
- **対象外**: 個別のコマンド実行手順、コード実装、各文書の具体的な本文内容、個別の閾値の数値、個別の整合性検査ルールの判定詳細、配布物の名前空間宣言の詳細、配布物内部の責務分界
