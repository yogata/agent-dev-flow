## 目的

要件定義プロセスは、既存REQ照合、操作分類、反映作業混入防止、ユーザー合意形成を含む一貫した契約である。
本 REQ は req-define、req-save、spec-save プロセスの横断基本契約を定義する。

## 要件

| ID | 要件 |
|---|---|
| REQ-004-001 | req-define はセッション履歴、現在コンテキスト、明示入力ファイル、RU、ユーザー対話を入力として受け入れること |
| REQ-004-002 | req-define は要件展開前に、リポジトリ上の REQ/Decision 実ファイル列挙に基づき現行 REQ を照合すること |
| REQ-004-003 | 文書記載の番号レンジと実ファイル一覧に乖離がある場合、文書修正または実ファイル確認により解消すること |
| REQ-004-004 | req-define は CREATE を選択する前に APPEND と UPDATE の可否を評価すること |
| REQ-004-005 | 同一関心対象の現行 REQ が存在する場合、要件追加は APPEND または UPDATE を既定候補とすること |
| REQ-004-006 | CREATE を選択する場合、既存 REQ に吸収できない理由を記録すること |
| REQ-004-007 | 現行 REQ は現在満たすべき状態、振る舞い、制約のみを保持すること |
| REQ-004-008 | 要件行は変更後に満たすべき振る舞い、制約、状態に限定すること |
| REQ-004-009 | 移行、変更、再定義、削除、改名、移管、除去、更新、移動、名称変更、参照修正などの作業手段は要件行の対象外とすること |
| REQ-004-010 | req-define は要件行候補を変更後仕様と反映作業に分類すること |
| REQ-004-011 | req-save は保存前に反映作業のみの要件行が残っていないか検査すること |
| REQ-004-012 | req-save は反映作業のみの要件行を検出した場合、保存を停止し、該当行、理由、移送先を報告すること |
| REQ-004-013 | req-save は REQ または Decision 保存後に README との整合性を確認すること |
| REQ-004-014 | req-define は複数の RU を同時に入力として受け入れること |
| REQ-004-015 | req-define は複数 RU 入力時に統合と分割を判断すること |
| REQ-004-016 | 同一主題、同一対象 REQ、同一変更理由に収まる RU 群は一つの REQ 操作に統合すること |
| REQ-004-017 | 対象 REQ、変更理由、受け入れ条件、対象外が分かれる RU 群は複数 REQ 操作として分割すること |
| REQ-004-018 | req-define は large または Epic 規模と判定した場合、scale と decomposition を記録すること |
| REQ-004-019 | REQ 間または子 Issue 間に順序制約がある場合、req-define は wave 候補または依存関係を記録すること |
| REQ-004-020 | req-define は Issue 階層そのものを確定しないこと |
| REQ-004-021 | req-save は REQ doc 保存時に Issue を作成しないこと |
| REQ-004-022 | req-define は実装フェーズの活動を実行しないこと |
| REQ-004-023 | req-define の要件行候補に実装指示を含めないこと |
| REQ-004-024 | 具体的なファイル編集内容、コード変更箇所の行番号指定、ステップバイステップの実装手順、テストコマンド、実装コード断片は要件行候補の対象外とすること |
| REQ-004-025 | REQ 要件行は満たす必要がある検証可能な要件に限定すること |
| REQ-004-026 | 推奨、任意、将来候補は REQ 要件行として扱わないこと |
| REQ-004-027 | 必達要件として再定義できない推奨相当の内容は、注記、SPEC、guide、backlog、report のいずれか適切な文書へ移すこと |
| REQ-004-028 | 任意相当の内容は原則として許容仕様、設計余地、将来候補として適切な文書に配置すること |
| REQ-004-029 | 主語、適用範囲、既存 REQ から一意に導ける再説明は現行 REQ の要件行の対象外とすること |
| REQ-004-030 | 既存要件の言い換えに過ぎず、新しい判定基準、例外、対象外、検査境界、優先関係を含まない文は要件行の対象外とすること |
| REQ-004-031 | REQ 要件行は、外部から見える責務、コマンド間契約、ドメイン状態の位置づけ、公開入口、安全境界、恒久的な文書体系制約を表す内容を含めること |
| REQ-004-032 | REQ 要件行は、当該行が存在しない場合に対象 REQ が何を満たすべきか不明になる内容に限定すること |
| REQ-004-033 | req-define および req-save は、要件行候補が REQ に記述すべき外部契約、状態要件であるか、SPEC 等に配置すべき詳細、内部パラメータであるかを保存前に判定すること |
| REQ-004-034 | req-define は壁打ち開始時、入力の構造を分析フレームで先行して整理すること |
| REQ-004-035 | req-define は個別論点の深掘り前に全体構造をユーザーに提示すること |
| REQ-004-036 | req-define は二項選択を求められた質問に対し、件数と根拠でいずれかを明示して回答すること |
| REQ-004-037 | req-define は修正の要否を検討する際、実装面と SPEC 面の両面を分析すること |
| REQ-004-038 | req-define は各面の修正対象と修正内容を明示すること |
| REQ-004-039 | req-define は片面のみの分析で修正要否を断定しないこと |
| REQ-004-040 | req-save は SPEC を編集しないこと |
| REQ-004-041 | SPEC 保存は spec-save の責務とすること |
| REQ-004-042 | req-define は Decision 判断が必要な要件について、Decision 判断確定前にアーキテクチャ確認ステップを実行すること |
| REQ-004-043 | req-define は Decision 番号を推測指定せず new:{topic-slug} 形式を使用すること |
| REQ-004-044 | req-save は Decision ファイル保存時に Decision 採番ルールで確定した番号を振ること |
| REQ-004-045 | req-save は draft 内の全 Decision 参照を当該確定番号で置換すること |
| REQ-004-046 | req-define は draft 保存後に auto_gate を確認すること |
| REQ-004-047 | auto_ready が false または unresolved_questions、unresolved_conflicts、out_of_repo_operations、stop_reasons が残る場合、壁打ちを継続して解消すること |
| REQ-004-048 | ユーザーが明示的に auto_ready false のまま標準フローで手動実行すると選択した場合のみ false を許容すること |
| REQ-004-049 | 当該選択は conflict_resolutions に記録すること |
| REQ-004-050 | 要件の適用対象を、信頼できない入力の構文解析、検証、解釈（パーサ、レクサ、デシリアライザ等）、権限、配布、trust 境界の enforcement、外部ネットワーク経路、アーカイブ展開等の外部攻撃面を持つ処理のいずれかに該当するか否かで判定し、判定基準を文書上で機械的に判定できる形で定義すること。適用対象とした場合はその前提を要件docに記録すること（適用外の場合の記録は強制しない） |
| REQ-004-051 | 適用対象の要件docにおいて、処理量の上限（時間計算量、処理ステップ数、または走査量の上限）、出力の上限（出力件数、証跡量の上限）、不正または曖昧な入力時の失敗挙動（fail-open か fail-closed か）の3項目を受け入れ条件として確定するまで壁打ちを継続すること |
| REQ-004-052 | 3項目への回答は検証可能な形式（上限は数値または計算量の形、失敗挙動は fail-open / fail-closed のいずれか）を要求し、形式不定の回答や形式的な記述を許容しないこと。数値上限の記述は既存の test strategy 数値閾値ガイドおよび pass_criteria 記述ガイドの規範に従うこと |
| REQ-004-053 | 非機能受け入れ条件の確認は work_type に関わらず常に実行される要件展開工程の一部として実行し、adversarial-review の発動条件に依存しないこと。adversarial-review の動的レビュー戦略における検出観点は第二の網として助言に留め、新規の統制ゲートを構成しないこと。確定した受け入れ条件は既存の投影契約（SPLIT 後は case-open 実行契約 REQ の該当行〔分割元 REQ-006-004〕、REQ-017-002）により下流へ運搬し、draft-data スキーマ、要件docテンプレート、QG、正規成果物種別を本件のために変更しないこと |

## 適用範囲

**対象**:

- req-define コマンド
- req-save コマンド
- spec-save コマンド
- 要件形成プロセス全体
- ユーザー合意形成プロセス

**対象外**:

- Case 実行プロセス
- Intake と Learning lifecycle
- コード実装
- テスト実行
