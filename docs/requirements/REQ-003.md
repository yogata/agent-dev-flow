## 目的

委譲時の最終判断、ユーザー承認、永続化、外部更新、制御された副作用の発動契約を所有する。
親エージェントと委譲先（サブエージェント、外部エージェント）の間で、判断、承認、副作用の権限とタイミングの一意性を担保する。
本 REQ は許可、禁止、承認の境界のみを定義し、配布成果物の責務分界、委譲契約の詳細（category 選定基準、MUST NOT DO 一覧、result state machine）、git 操作の手順詳細は所有しない。

## 要件

| ID | 要件 |
|---|---|
| REQ-003-001 | 親エージェントは次工程への進行判断、永続化、外部システム更新、commit、push、merge、ユーザー確認を保持すること |
| REQ-003-002 | 委譲先（サブエージェント、外部エージェント）は判定結果、調査結果、助言のみを返し、永続化、外部システム更新、commit、push、merge、ユーザー確認を行わないこと |
| REQ-003-003 | 委譲先の返却は副作用の有無を示す情報を含めること |
| REQ-003-004 | 成果物本文（Issue 本文、PR 本文、commit message、保存対象ファイル本文、テンプレート成果物）は原文のまま返し、判定結果、調査過程、中間ログは要約、根拠、親判断事項、capture 候補へ圧縮して返すこと |
| REQ-003-005 | intake 候補、learning 候補は保存せず capture 候補として親エージェントへ返すこと |
| REQ-003-006 | 委譲時最小契約は入力、副作用境界、出力契約、capture 引継ぎを中心に構成されること |
| REQ-003-007 | 外部アーキテクチャ助言は確定事項として扱わず、親エージェントが確定事項、推定事項、ユーザー確認事項、ブロッカーへ分類すること |
| REQ-003-008 | 親エージェントは裏付けのない助言内容を要件本文、REQ、ADR、SPEC へ確定事項として混入させないこと |
| REQ-003-009 | 外部アーキテクチャ助言が必要な条件で助言確認が利用不可の場合、ブロッカーとして報告し、静かにスキップしないこと |
| REQ-003-010 | 外部助言にブロッカーが含まれる場合、または未決事項が解消されず残る場合、要件確定へ進まず壁打ちへ差し戻すこと |
| REQ-003-011 | case-run への実行委譲契約は結果4状態（completed-pr、blocked、failed、delegation-unavailable）、永続化先、禁止事項（作業ツリー外変更、Issue 完了判定、capture 直接書込、外部実行手段中間成果物の永続状態化）のみを規定すること |
| REQ-003-012 | 実行担当サブエージェントは completed-pr、blocked、failed、delegation-unavailable のいずれか1状態を case-run へ返すこと |
| REQ-003-013 | ハーネスの実行計画確認は QG-3（実装差分確認）、QG-4（完了条件最終評価）のいずれの代替にもならないこと |
| REQ-003-014 | 外部実行手段の中間成果物の内部構造を ADF 永続状態として扱わないこと |
| REQ-003-015 | コンフリクト解消は機械的解消のみを許可し、実装変更を伴う解消を禁止すること |
| REQ-003-016 | case-close はマージ時コンフリクトの機械的解消を担い、解消不能時は case-auto へエスカレーションすること |
| REQ-003-017 | case-auto はコンフリクトエスカレーションを受領し、コンフリクト文脈を付けて case-run へ再委譲すること |
| REQ-003-018 | コンフリクト解消の再委譲は上限回数を設け、上限を超えた場合はマージ競合の停止条件を満たすこと |
| REQ-003-019 | case-close とマージ手順を分離せず、完了処理とマージ時コンフリクト機械的解消を単一責務として維持すること |
| REQ-003-020 | subagent 委譲プロンプトは委譲先責務と意味的距離を評価した category 選定と、スコープ外作業を明示した禁止事項セクションを必須とすること |
| REQ-003-021 | promote/review 系コマンドのヒューマンインザループは「判断の確定」に限定すること |
| REQ-003-022 | 判断確定後の保存、移動、prune、削除、commit、push は対象範囲、保存先、除外条件、証跡保存条件が明確な場合に自動実行を許可すること |
| REQ-003-023 | 破壊的変更、未コミット変更、矛盾解消、要件仕様スコープ変更は明示承認を維持すること |
| REQ-003-024 | 学習成果物のうち deferred、未処理は自動削除対象から除外すること |
| REQ-003-025 | case-open は draft、RU 削除後に即時 push し、後続工程での引き継ぎ失敗を防止すること |
| REQ-003-026 | case-close は squash merge 後のローカル先行 commit を検出し、重複を解消して後続の pull 失敗を防止すること |
| REQ-003-027 | case-open は子 Issue 本文に前工程完了度を記録し、後続工程が前工程の完了状態を確認できること |
| REQ-003-028 | ADF 可観測壁時計タイムスタンプ（全体開始終了、構成工程開始終了、結果状態確定時刻、停止時点工程別経過）を ADF 配布物の所有対象とすること |
| REQ-003-029 | ハーネス内部メトリクス（timeout、推論時間、queue 待機、retry 単位、context 圧縮時間、監視間隔）は ADF 標準の管理対象外とすること |
| REQ-003-030 | 委譲された批判的検証結果を自動的に採用せず、対象案側が根拠、前提、対象範囲、影響を吟味する契約を維持すること |
| REQ-003-031 | 対象案側が妥当でない批判へ根拠付きで反論し、批判側が反論を受けて自身の批判を撤回、維持、限定、修正、部分合意、解決不能のいずれかを判断できる往復契約を維持すること |
| REQ-003-032 | 関連コンテキストから判断可能な限り自律審議を継続し、意見不一致だけを理由にユーザー確認へ進まないこと |
| REQ-003-033 | エージェント間で解決不能な争点のみをユーザーへ返し、回答後に審議状態を引き継いで影響を受ける争点から議論を再開すること |
| REQ-003-034 | 合意が形式的全会一致ではなく本質的争点単位で管理され、対象案側の反論と批判側の再検討を経て閉じること |
| REQ-003-035 | 明示呼び出しによる任意のレビュー手段（Deep Review）がユーザー承認、および commit/push/merge/ファイル保存/Issue・PR 更新の副作用権限を代行しないこと |

## 適用範囲

- **対象**:
  - 親エージェントが保持する最終判断、承認、副作用権限
  - 委譲先（サブエージェント、外部エージェント）への委譲時最小契約
  - 永続化操作、外部システム更新、GitHub Issue/PR 更新、commit、push、merge の発動契機
  - コンフリクト解消時の副作用発動と責務割当
  - promote/review 系コマンドのヒューマンインザループ境界
  - 委譲時観測タイムスタンプの所有範囲
- **対象外**:
  - 配布成果物の責務分界（REQ-002 が所有）
  - 委譲契約の詳細（category 選定基準、MUST NOT DO 一覧、result state machine）（SPEC が所有）
  - git 操作、rebase 手順の詳細（SPEC が所有）
  - ハーネス内部メトリクス、サブエージェント起動、実行制御パラメータ（harness 責務）
  - QG-3、QG-4 の評価と更新（完了報告と成果物品質ゲートが所有）
  - 実装担当サブエージェントの起動方法、エージェント構成（harness 責務）
  - intake、learning、RU のライフサイクル本体（一時成果物ライフサイクルが所有）
