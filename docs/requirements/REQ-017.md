## 目的

case-ready と case-run の実行契約責務境界を所有する。
case-ready は canonical Definition 確定後に合理的に確定可能な execution contract を完成させ、
Issue を case-ready 成功後の後続工程に対する SSoT として引き渡す。
case-run は execution contract を新規設計せず、既確定契約に基づく実装、実行時観測、
検証を担当する。実装時に契約変更、scope 拡大が必要と判明した場合は
blocked および req-define 再合意を経た case-revise 経路へ移行する。
case-ready、case-run、case-revise は ADF v4 公開運用モデル（DEC-033）において内部 lifecycle 段階であり、case-auto の orchestration から駆動される。

artifact-specific quality control の適用判定と Issue contract への投影は
case-open の責務であり、個別 Skill/Design は適用条件定義と品質基準を所有する。
共通ルーティング規則は Design（artifact-quality-control-routing）が所有する。

工程接続のプロトコル層（マクロフェーズ、SSoT 遷移、work_type 分類、scale 評価）は
REQ-005 が、Case実行オーケストレーション mechanism は REQ-006 が、
一時成果物 lifecycle は REQ-008 が所有し、本 REQ は execution contract 境界定義を
所有する。

## 要件

| ID | 要件 |
|---|---|
| REQ-017-001 | case-ready は canonical Definition の確定後に、対象範囲（対象要件、主な変更対象、対象外）、関連 REQ/Decision/Design への必要な参照、実現方針（再判断してはならない合意がある場合のみ）、完了条件（条件、検証方法、合格条件、達成状態の各項目と必要な品質検証の統合）を Issue 本文の対応する章へ確定すること。ユーザー明示 review 発動契約、work_type、scale、Issue 構成の分類を Issue 本文の正規契約として確定しないこと |
| REQ-017-002 | case-ready は機能要件、非機能要件、制約、対象外、受け入れ条件を新規作成せず、合意済み要件doc を実行契約の各要素へ投影すること（現行の投影契約は REQ-030-004 が正規所有する） |
| REQ-017-003 | Issue の完了条件は各項目が条件、検証方法、合格条件、達成状態を読み取れる形式で保持し、必要な品質検証を完了条件へ統合すること。テスト戦略、必須品質統制等の別章を設けないこと。必須条件をすべて検証し、不合格、証拠不足、検証不能、未処理を未達とし、未達が残る限り完了させないこと。項目固有の処置が合意されている場合だけ、その条件へ記載すること。実行手段と検証手段は検証方法と合格条件に分離して記録すること。必須品質能力の呼出自体が利用者要求でない限り、Skill 呼出を完了状態として扱わないこと |
| REQ-017-004 | 変更予定成果物の種別から必須品質統制を導出できる場合、その適用要否を case-run に委ねず、case-ready が完了条件の検証方法と合格条件へ反映すること。artifact type と quality control の対応は個別 command に散在させず共通規則として管理すること |
| REQ-017-005 | document、Skill、Command の各変更に対し、それぞれ文書品質査読能力、Skill 品質査読能力、Command 品質査読能力に相当する必須検証を case-ready が完了条件へ事前確定すること。同一成果物が複数能力を必要とする場合は全て展開すること |
| REQ-017-006 | 共通ルーティング規則（artifact type → 必須品質能力）は個別 Skill/Design が所有する適用条件定義を再定義せず、合成と投影契約のみを所有すること。ルーティング先は能力キーで表現し現在の提供 skill を参照情報として扱うこと |
| REQ-017-007 | case-run は既確定の実行契約（対象範囲、実現方針、完了条件）を実行契約として扱い、完了条件の不足、曖昧さ、矛盾、実現不能を検出した場合は自律補完せず blocked とすること |
| REQ-017-008 | case-ready は関連 Decision の拘束条件を実行契約確定前に特定し、必要な制約を実現方針または完了条件へ反映すること。case-run は既確定 Decision への適合を確認し、新たな拘束 Decision の必要性検出時は blocked とすること |
| REQ-017-009 | Issue の予定変更内容から事前判定可能な追加検証条件（関数削除時の全利用箇所検査等）は case-ready が完了条件の検証方法へ展開すること。case-run は記録済みの検証方法を新規設計せず実行すること |
| REQ-017-010 | case-ready は実行契約確定前に変更影響候補を探索し、scope、完了条件に影響する候補を実行契約へ反映すること。case-run は既存 scope 内の内部実装上の影響を処理可能とし、scope 拡大が必要な場合は blocked および req-define 再合意を経た case-revise 経路に移行すること |
| REQ-017-011 | case-run は実行契約を再設計して実行契約または workflow を変更しないこと。metadata、構造、実態の矛盾検出時は停止し、Root Case 指定による正規再開経路を使用すること |
| REQ-017-013 | 変更後の形式を唯一の現行形式とすること。旧形式を恒久的に読み続ける互換層、旧別名の受理、形式判別のための専用スキーマ版を残さないこと。新形式内の章読み取りと Issue 構造の判別は、新旧併存のための形式判定とは区別すること |
| REQ-017-015 | case-ready は runtime-only 判断（worktree 状態、現行性、実 diff、実装結果、test 実行結果）を事前確定しようとせず、これらを case-run の安全検査として維持すること |
| REQ-017-016 | case-ready 成功後の case-run は req_draft を参照して不足契約を補完せず、Issue/Epic を SSoT として処理すること（REQ-008-036, 037 参照） |
| REQ-017-017 | case-ready は draft-data の realization_actions を Issue / Epic の実現方針へ投影すること（realization_actions の内部属性一式は転記しない）。case-ready 成功後は case-run が Issue 本文だけで変更責務、変更意図、検証方針を取得できること。case-run は realization_actions に記録済みの実現面の変更方針を再決定せず、その範囲内の内部実装方針（関数配置、命名、データ構造、実現順序、具体的 diff）だけを決定すること |
| REQ-017-018 | Issue 監査値には計測基準（基準 commit または時点）が記録され、第三者が監査値の現行性を検証できること |
| REQ-017-019 | case-run から実行担当サブエージェントへの委譲 prompt は、structured_context の作業内容・purpose を Issue 本文の目的・対象範囲または正規 REQ から抽出して生成すること。会話コンテキスト由来の推定や波及解釈を注入しないこと。委譲 prompt 生成時に Issue 番号と対象成果物パスの一致を検査すること |
| REQ-017-020 | case-run / case-auto は、正典から導出可能な補助情報（対象一覧・操作サマリ等）を委譲 prompt へ含める場合、当該補助情報を正典と機械突合可能な形式で記述すること。委譲を受けた実行側は補助情報と正典の不一致を検出した場合、正典を優先し、補助情報を根拠とした対象判断・本文更新を行わないこと（REQ-017-019 の抽出制約の正典導出補助情報への拡張） |

## 適用範囲

- **対象**:
  - case-ready の実行契約確定責務（対象範囲、実現方針、完了条件と検証方法・合格条件、必須品質統制の完了条件への統合、impact candidate の投影）
  - case-run の実行契約消費責務（契約実行、blocked 遷移、req-define 再合意を経た case-revise 経路連携、runtime-only 判断維持）
  - artifact-specific quality control の case-open 事前確定と共通ルーティング規則の所有境界
  - 変更後の形式を唯一の現行形式とする運用（旧形式恒久互換の不存在）
  - 委譲 prompt 生成側の structured_context 抽出制約と Issue 番号×対象成果物パス突合（消費側 SSoT 要件 REQ-017-016 の生成側対偶）
- **対象外**:
  - Case実行オーケストレーション mechanism（Epic/Wave 制御、状態機械、execution_unit 並列モデル）（REQ-006）
  - 一時成果物 lifecycle、draft/RU 構造化契約（REQ-008）
  - workflow プロトコル層（マクロフェーズ、SSoT 遷移、work_type 分類）（REQ-005）
  - artifact-specific quality control の個別品質基準（各 authoring Skill/Design）
  - 共通ルーティング規則の詳細実装（Design artifact-quality-control-routing）
  - QG-2 実行時投影の詳細実装（Design agentdev-quality-gates）
  - runtime-only 判断の実装詳細（worktree、staleness check、実 diff 検査等）（REQ-006）
