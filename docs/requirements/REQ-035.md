## 目的

Epic Issue を実行順序の SSoT（唯一の情報源）とする Epic/Wave オーケストレーションモデルを所有する。
子 Issue の実行状態ライフサイクル、Wave 状態の導出、execution_unit 定義、Epic Issue 本文の単一書き手排他制御、別 Epic 分割許容、コンフリクト解消モデルを扱う。
Wave 構成の生成は case-ready 実行契約 REQ が、Epic 進捗追跡テーブルの更新手続きは agentdev-epic-tracker が所有する。

## 要件

| ID | 要件 |
|---|---|
| REQ-035-001 | Epic Issue 本文（実行構成を含む）の更新は per-Epic の単一書き手として排他制御されること。子 Issue の実行結果の確定（completed、blocked、failed）に応じた実行構成への状態反映と全体条件評価の更新は同一の排他制御の下で Epic Issue 本文へ書き込むこと。running 段階の並列実行と orchestration 段階は実行構成の状態反映を除き Epic Issue 本文を更新しないこと（orchestration が完走する場合は closing 段階へ委譲し closing 段階の実行主体が書き込む） |
| REQ-035-002 | Epic 実行では Epic の実行構成を実行順序の SSoT とし子 Issue の実行状態と整合させること |
| REQ-035-003 | 子 Issue の状態は実行結果の確定（completed、blocked、failed）に応じて Epic 実行構成へ反映されること |
| REQ-035-004 | 子 Issue の永続状態は pending、completed、blocked、failed の4値とし、実行状態ライフサイクルとして扱うこと。スキップを終了状態として採用せず、ready、running、Wave 状態、状態別件数を Issue 本文へ保存しないこと。blocked と failed は未完了の停止状態であり Issue としての終了を意味しないこと。継続条件が成立し旧実行の終了が確認できた対象は pending へ戻して再試行でき、試行履歴管理を追加しないこと。通常の再開で completed を未完了へ戻さないこと。合意変更による成果の再評価は通常再開とは区別すること。pending は新規起動許可を意味せず、再開時の起動判断には実行の生存状況と成果物を照合し、実行中・状態不明を未着手と扱わず、状態不明のまま同一 Issue を再起動しないこと |
| REQ-035-005 | Wave 状態は永続化対象ではなく Wave 内 Issue 状態から導出すること |
| REQ-035-006 | execution_unit は standard issue または epic issue とし Wave は execution_unit に含めないこと（Wave は Epic 内の依存関係と並列実行可能性を表す実行スケジューリング単位であり、Epic Issue 本文から読み取る内部構造である） |
| REQ-035-007 | 複数 execution_unit 並列実行時 Epic Issue 本文の単一書き手は Epic Issue 本文単位で維持されること |
| REQ-035-008 | 必須依存があっても事前契約、依存先 Epic 完了、Epic サイズ推奨範囲調整のいずれかを満たす場合は別 Epic 分割を許容すること |
| REQ-035-009 | 並列実行時に PR マージコンフリクトが発生した場合後続 PR を main 基準で rebase により機械的解消すること |
| REQ-035-010 | コンフリクト解消モデルは rebase による機械的解消、文脈付き再実行、オーケストレーション級判断の段階的エスカレーションで構成すること（各レベルの詳細は Design） |
| REQ-035-011 | Git 上の変更を伴う並列処理では、処理単位を worktree で隔離すること。依存関係上独立した処理単位は並列実行可能とすること。並列処理の一部が失敗・中断した場合、完了済み処理を未完了へ戻さず、全体の次状態を規則に従って判定し、必須処理単位が揃っていない状態で後続処理へ進まないこと |
| REQ-035-012 | Epic 親へ子 Issue の主な変更対象パスを重複保存しないこと。同一 Epic 内の比較は子 Issue の宣言を使い、Epic 単位の横断比較は必要時に子 Issue 宣言を集約すること。変更対象の重複検出は子 Issue 確定後の検査へ寄せ、旧工程での検査を保存するためだけの複数宣言元切り替えを作らないこと。比較不能を無変更・無重複とみなさず検出不能として報告すること。ファイル重複のみを理由として Wave 分離を行わず、重複検出結果は実行時の一時直列化、変更対象の調整、merge 順序、rebase、衝突解消担当の判断に用いること。コンフリクト解消モデル（Level 1〜3）と execution_unit 間並列可否の判定軸（必須依存の連結成分のみ）を維持すること。mergeable 作成時状態のみで Wave の安全性を判断しないこと |
| REQ-035-013 | Epic Case では Root Case を Case 全体、Definition 参照、対象範囲、全体制約、実行構成（子 Issue、Wave、意味的依存、子状態を含む）の orchestration SSoT とし、各 Child Issue を各 case-run が消費する実行契約の execution SSoT とすること |
| REQ-035-014 | 各 Child Issue は親 Root Case の自由記述に依存せず、その Issue 単独で対象範囲（対象要件、主な変更対象、対象外）、実行に必要な合意内容、実現方針、完了条件を取得できること |
| REQ-035-015 | Standard Case では Root Case 自身を単一 execution unit とし、儀式的な Child Issue を作成しないこと |
| REQ-035-016 | Wave 収束とは当該 Wave の全子 Issue の実行結果が確定し、未処理・実行中・状態不明の子 Issue が残らないこと。blocked、failed、delegation-unavailable は実行結果が確定していれば収束に該当し得るが、依存条件の充足としては扱わないこと |
| REQ-035-017 | 後続 Wave の開始条件は現 Wave の収束と後続 Wave に必要な全ての意味的依存条件の成立の両方を満たすこと。意味的依存条件の成立には必要な統合・マージの完了を含み、実装 task の完了（PR 作成）と依存充足を区別すること |
| REQ-035-018 | 子 Issue 間に成果の成立順序への依存（一方が作成する成果を他方が利用する等）が確認された場合、それを意味的依存として Wave 構成に反映すること |
| REQ-035-019 | Epic の実行構成は子 Issue、Wave、意味的依存、子状態を一つの表として保持すること。実行構成は Issue 本文に一つだけ存在し、分解表と実行順序表の二重保持を行わないこと。表の物理構成（列構成等）は Design が確定すること |
| REQ-035-020 | 依存先の作業終了と、依存する成果を利用できる状態を区別すること。blocked または failed を依存充足とみなさないこと |

## 適用範囲

- 対象: Epic と Wave モデル（Epic の実行構成（子 Issue、Wave、意味的依存、子状態を一つの表で所有する実行順序 SSoT）、子 Issue 実行状態ライフサイクル（pending/completed/blocked/failed の4値、再試行、起動判断）、Wave 状態の Issue 状態導出、execution_unit 定義、単一書き手排他制御、別 Epic 分割許容、コンフリクト解消モデル、子 Issue 確定後の変更対象重複検出モデル（実行構成の生成手順は case-ready 実行契約 REQ が所有））
- 対象外: 実行構成の生成（case-ready 実行契約 REQ）、Epic 実行構成更新手続き（agentdev-epic-tracker、Design）、execution_unit 並列モデルの内部パラメータとコンフリクト解消レベルの詳細手順（Design）、処理単位の一級概念定義（DEC-036、REQ-011）
