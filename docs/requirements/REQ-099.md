## 目的

ADFの共通原本（業務・安全・品質契約）とホスト別接続（OpenCode、Senpi）を分離し、既存契約を維持したまま OpenCode＋OmO v4.19.4 と Senpi＋OmO Native v5 の併存利用を可能にする。ホスト選択とバックエンド選択（GitHub、ローカルIssue）を独立した軸として扱い、過渡期に両ホストへの配置を可能とし、実際に使用するインターフェースはユーザーが選ぶ。本要件は既存契約の実現手段と配布対象の追加を所有し、業務契約の緩和や新しい実行基盤の新設を所有しない。配布成果物の種別責務と原本配置の宣言は REQ-002 が、同期・導入基盤は REQ-009 が所有し、本要件はマルチホスト併存に起因する追加要件を所有する。適用は検証した組合せに限定する。

## 要件

| ID | 要件 |
|---|---|
| REQ-099-001 | 業務Skill等の原本を host 非依存の共通原本領域（src/common/）に整理し、OpenCode／Senpiの公開入口が同じ業務契約を参照すること。ホスト別コピーの業務手順を独立編集する構造を持たないこと |
| REQ-099-002 | src/opencode/ と src/senpi/ はホスト固有の接続領域（公開入口、Tool登録、plugin/hookまたはextension、引数・結果・実行contextの変換）に限定すること。Workflow本文にホスト版別の条件分岐や二重手順を散在させないこと。ホスト固有の起動API、category／agent選定、通知・継続・取消の扱い、品質実行入口は限定された実行設定・referenceに集約し、OmOのバージョンだけでホストを推測しないこと |
| REQ-099-003 | 両ホストから req-define、case-auto 等の既存の業務名と引数の意味で利用できること。名前空間・呼出し構文が異なる場合は対応表と展開テストを提供し、同じWorkflowへ到達すること。Commandの名前空間やホスト固有の呼出し構文の完全一致は要件としないこと。公開Skill名・Tool名・操作契約は原則維持すること |
| REQ-099-004 | 親と子のSkill読込、同梱reference・template・scriptの参照、実行時workspaceの解決を両ホストで成立させること |
| REQ-099-005 | agentdev_gh、agentdev_jev、agentdev_third_party 等の既存Tool契約と検証・読戻しを維持し、必要なホスト接続を追加すること。操作契約の接続境界は Custom Tool 操作契約（GhRunner 型）に限定し、新たなバックエンド抽象層と GitHub 互換ローカルサーバを導入しないこと（REQ-009-035 維持） |
| REQ-099-006 | GitHubバックエンドとローカルIssueバックエンドの双方を両ホストで利用可能とし、バックエンド選択とホスト選択を独立した軸として扱うこと。選択したバックエンドに接続し、意図しない二重登録を避けること。両ホストへの配置と、同じTool名で両バックエンドを同時有効化することを混同しないこと（REQ-009-037 の同居対象外宣言と、Custom Tool の Local 実現への差し替えは同居に非ずの既存解釈を維持） |
| REQ-099-007 | OpenCode×GitHub、OpenCode×ローカルIssue、Senpi×GitHub、Senpi×ローカルIssueの全組合せで、対象バックエンドの操作契約・成果物検証・Workflow接続の試験結果を記録すること。配置のみをもって対応完了としないこと |
| REQ-099-008 | 既存ローカルIssue資産の読込・更新・状態写像・採番を維持すること。ホスト変更だけを理由とするデータ再作成を要求しないこと。必要な移行がある場合は Design が明示し、既存契約との適合と移行試験を行うこと |
| REQ-099-009 | ローカルIssueの採番・状態写像・読み書きのホスト別重複を実装しないこと。共通の操作契約と検証engineに各バックエンドを接続すること。バックエンドの具体配置、選択・切替の設定方法、共有module境界は Design が定めること |
| REQ-099-010 | installer の単一公開入口と check／dry-run／apply の3モードを維持し、OpenCodeのみ、Senpiのみ、両方への配置を選択可能とすること。配置対象選択の詳細（新規導入・既存導入更新の選択肢と既定、self-sync の投影整合）は multi-host-canonical-model.md と runtime-package-boundary.md が所有する |
| REQ-099-011 | CLI未導入でも配置可能とし、配置検査と実行環境の診断を区別すること。未導入・未検証を実行対応済みと報告しないこと。対応済みのADF／adapter／ホスト／OmO版の組合せを報告可能とすること。OmO版を診断・互換確認にのみ使用し、配置対象の自動振分けに使用しない制限を含む実行詳細は multi-host-canonical-model.md が所有する |
| REQ-099-012 | 共通原本への投影は同一ADF版に整合させ、ホスト別の管理範囲を分離すること。片方のホスト投影の更新・除去が他方を壊さず、repo-local資産とユーザー設定を保護すること。既存consumerの更新時に古い投影・参照を安全に更新し、再実行の冪等性を確認すること |
| REQ-099-013 | guardはホスト固有の編集解釈と共通判定を分けること。入力キーの機械的な変更だけで編集意味論を同一と扱わないこと。ホストのwrite／edit／patch等の対応編集と生の書込み経路について、拒否時に副作用が発生せず、正常操作を正しく許可すること。検査不能を成功扱いしないこと |
| REQ-099-014 | 配布用とADF自己ホスト用のguard適用範囲を維持して両ホストへ接続すること。編集操作のホスト固有の意味を解釈し、同じ安全・品質判定を副作用前に適用すること |
| REQ-099-015 | 必須Tool、guard、親・子のSkill読込、工程委譲、background状態解釈、指定workspace隔離、品質ゲートを満たす実行経路を対応環境で確認すること。必須能力が不足する場合、対象工程を実行可能と判定せず、guard無効化、工程の勝手な親インライン化、禁止された同期逐次fallback、mainへの作業先変更で吸収しないこと |
| REQ-099-016 | taskの終了とADF工程の成功を区別すること。通知重複、状態不明、取消、中断に対して既存の成果物検証と回復契約を維持すること。単一実行内の重複起動防止・回復は維持すること（新たなホスト間競合防止機能の要求ではない） |
| REQ-099-017 | ユーザーが旧実行を停止し永続状態を確認した前提下で、永続成果物を確認して他ホストへ切替・復帰できることを試験すること。生きたtask移送やクロスホスト同時実行の機械的防止を実装しないこと。同一Caseを両ホストで同時処理しないこと、切替前の停止・永続状態確認は運用責任であることをガイドに明記すること |
| REQ-099-018 | 対応を確認した版の実値・組合せ、バックエンド、Command対応表、導入・切替手順の所有先はガイド（consumer-project-setup.md・multi-host-operations.md）であり、記録義務と検証済み組合せ限定の保証を保持すること |
| REQ-099-019 | 共通原本化に伴う参照、配布検査、テスト、ガイドの更新と、既存consumerの更新互換を対象に含めること |
| REQ-099-020 | installer・release archive 生成系（package-release-archive、consumer archive install、同梱 README、archive レイアウト規定、trusted-distribution-gate）は共通原本構成（src/common/ とホスト接続領域）を前提として動作すること。旧 src/opencode 単一前提の収集定義・境界検査・投影対象を残さないこと |

## 適用範囲

- **対象**: 共通原本領域とホスト別接続領域の分離構造、Command業務名互換と対応表、バックエンド×ホストの全組合せ接続と試験記録、ローカルIssue資産互換、installer配置対象選択と過渡期運用（投影整合・冪等・保護・診断区別）、Tool・guard・Skill読込・workspace解決の両ホスト接続、実行契約の適合確認と回復・切替・復帰、運用ガイドの整備
- **対象外**: 工程、責務、進行・停止条件、品質ゲート、副作用境界、result契約、永続状態からの回復という既存ADF業務契約の緩和（REQ-005、REQ-030〜REQ-034、REQ-061、REQ-062 が所有）。OmO／Senpi本体の機能移植、モデルルーティングの内部実装、会話session形式の変換。ADF独自のqueue、heartbeat、session管理等の実行基盤の新設。ホストをまたぐ同一Caseの競合検出、排他ロック、実行中台帳、起動拒否機構。生きたsessionやtaskの別ホストへの移送。ユーザーのモデル、認証情報、個別のOmO設定の自動変更・移行、CLIの自動導入。任意の将来のOmO／ホスト版への無条件の互換保証（対応済み宣言は検証した組合せに限定）。Commandの名前空間やホスト固有の呼出し構文の完全一致
