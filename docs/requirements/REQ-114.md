## 目的

backlog-auto の backlog 整理サイクル（inspect-docs → 昇格3系統 → backlog-review）で承認確定した RU 一式を、単一の公開コマンド起動で要件定義・実装・検証・統合・一式全体の完了判定・パッチリリース作成まで接続して実行する（一気通貫実行）。既存の依存判断・並列実行機構・個別工程の実装を再定義せず、不足している接続部分のみを所有する。

## 要件

| ID | 要件 |
|---|---|
| REQ-114-001 | `/agentdev/backlog-auto` の単一起動で、backlog 整理サイクル、RU 一式の要件定義、実行、検証、統合、一式全体の完了判定、パッチリリース作成までを接続して実行すること。既存の承認・安全境界に基づく利用者判断（backlog-review の RU 承認、req-define の壁打ち、リリース条件・公開権限の確認）は維持し、単に次の工程を開始するためだけの手動コマンド入力を要求しないこと |
| REQ-114-002 | 一式の対象は当該 backlog-auto 実行における backlog-review で承認確定した RU 一式とし、一式の必須の要求と受け入れ義務のスナップショット、RU・要件doc・operation_unit・実行単位の対応表（統合・分割を含む）、基準点情報、進捗を set-state として記録・維持すること。統合・分割後も元の要求と後続対象の対応を維持し、一式と無関係な既存 RU・ドラフト・Issue を取り込まないこと |
| REQ-114-003 | 一式は単一の req-define 実行（入力は一式の RU の明示列挙）で処理し、結果を単一の要件doc に確定すること（複数 RU の統合・分割は operation_units 構造で表現）。実行は当該要件doc を明示指定した単一の case-auto 実行として接続し、引数なし全件処理および個別ドラフトごとの複数 case-auto 起動を用いないこと |
| REQ-114-004 | 一式から複数の独立した実行可能 Issue が生じた場合、既存の共有 active Issue task 上限と横断補充（REQ-034-027、REQ-034-040）に従って Issue および Epic・Standard を横断して並列実行すること。一式を複数グループへ分断し、実行可能な Issue が残っているのに先行グループの全完了を待つ逐次化を行わないこと |
| REQ-114-005 | req-define の壁打ちで利用者が一式の複数要件docへの分割を判断した場合、当該判断を一式の構成変更（再スコープ）として set-state に記録し、分割後の各一式はそれぞれ独立した一気通貫ライフサイクル（基準点確定から）で扱うこと |
| REQ-114-006 | RU 生成後・要件定義後・Issue 生成後・実行中のいずれで中断しても、set-state から同じ一式の対象と進捗を復元し、未完了部分から再開すること。完了済みの操作を重複実行しないこと。backlog-auto の再実行は set-state から完遂済み Case を検出し、全体完了判定以降の段階から再開できること（case-auto 単独の再開入口契約 REQ-034-038 は変更しない） |
| REQ-114-007 | 一式全体の完了は、元 RU 一式の必須の要求と受け入れ義務が、要件定義・実行対象・検証結果に過不足なく対応し、必要な範囲の検証結果がすべて成立した場合にのみ判定すること。個別の Issue 終了・PR merge のみで一式全体の完遂としないこと。突合の正は set-state の義務スナップショットと対応表とすること（RU・要件docの削除契約 REQ-008-010、REQ-061-025 は変更しない） |
| REQ-114-008 | 実行開始時に、最後の正式リリース（版番号規則は Decision `DEC-059` に従う）と開始時点のコミット ID を確定すること。一式全体の完遂前に新規のタグ・リリースを作成しないこと |
| REQ-114-009 | 一式全体完遂後、リリース時点の正規情報を確認し、最後の正式リリースからパッチ番号を1つだけ進めた版を確定し、リリース対象コミット（一式の全マージ完遂時点の main HEAD）にタグを付与すること。タグ付与前に開始コミットから対象コミットまでの差分と一式分の実変更の突合を行い、無関係コミットの混入を検出した場合は報告して利用者判断を求めること。major/minor への自動振り分け、同一実行での二つの版番号の消費、既存タグの移動を行わないこと |
| REQ-114-010 | 正式リリースは、一式全体の完遂、リリース条件（Decision `DEC-059` の適用規則）、公開操作の権限がすべて成立した場合に限り、対象プロジェクトの採用方式に従って作成すること。少なくとも正式バージョン、リリース対象コミット、タグ、リリース内容が確認可能であること。追加の公開成果物は対象プロジェクトの採用方式に従い、ADF本体では版タグ（正式 SemVer タグと RC タグを含む）ごとにタグ名と一致する GitHub Release を1件だけ対応させ、対応する Release のない版タグには草稿を作ること。既存の Release の本文と公開状態を変えず、草稿を自動公開しないこと（公開は、草稿作成とは別に利用者が明確に認めた場合に限る） |
| REQ-114-011 | 公開途中の失敗・中断時は、既存の結果を読み戻し、タグの移動・再作成、第二のパッチ番号の消費なしに未完了部分から再開すること |
| REQ-114-012 | RU 0 件またはリリース対象となる実変更がない場合はリリースを作成せず報告すること。正式なバージョン基準がない場合は対象プロジェクトの採用済み初期バージョン規則を確認し、確認できない場合は初期バージョン番号を決定せず停止して利用者判断を求めること。公開方式・権限・必要な環境が不足する場合も対象と理由を報告し、リリース完了としないこと |
| REQ-114-013 | ADF本体、GitHub 接続型適用プロジェクト、ローカルIssue適用プロジェクトの各採用形態で、実際の公開コマンド入口からの共通の E2E 挙動が確認可能であること。リリース公開先・配布物は対象プロジェクトの採用方式に従い、並列実行・中断再開も各形態で実測すること。必要な環境・権限がなく確認できない条件は合格ではなく未検証として扱うこと |
| REQ-114-014 | 既存の利用者判断境界（req-define の壁打ち、backlog-review の RU 承認、リリース条件・公開権限の確認）を自動化しないこと。REQ-039-001（backlog-review はユーザー承認を経て RU を生成する。プロジェクト知識候補は docs/knowledge/ への知識文書保存〔REQ-056〕を RU と同等の正規完了経路とする）は backlog-review のスコープ制約として維持し、backlog-auto による req-define 起動は req-define 自体の壁打ち・承認境界を保存する接続であること |
| REQ-114-015 | REQ-041 の完了扱い・全体報告に係る行は backlog 整理サイクル部分に係るものであり、一気通貫全体の完遂判定と最終報告は本 REQ が所有すること |
| REQ-114-016 | リリース工程における GitHub Release の作成・読み戻しは、ADF が認めた経路（Custom Tool 操作契約のカタログ）だけで行い、生コマンド実行でカタログ外の書き込み経路を迂回しないこと。版タグと Release の対応を GitHub から読み戻して確認するまでリリース工程を完了とせず、草稿作成に失敗した場合はタグを移動・再作成せず、Release が欠けているため工程を完了できない旨を報告して停止すること。再開時は既存のタグと Release を使い、同一タグへ二つ目の Release を作らないこと。Release 記録の補完は版番号の消費とタグの作成・移動を伴わない記録操作であり、REQ-114-008 の完遂前の新規リリース作成禁止の対象外であること |
| REQ-114-017 | リモートに存在しない既存の版タグは、注釈付きの元のタグを上書きしない通常の push で送り、リモートとローカルでタグ識別子が一致することを確認した上で対応する Release 草稿を作ること。RC 版タグの Release は草稿かつプレリリースとして作ること（版番号の基準から RC を除く規則は変更しない） |

## 適用範囲

- **対象**: backlog-auto の単一起動による一気通貫実行（backlog 整理サイクル後の RU 一式の要件定義・実行・検証・統合・全体完了判定・パッチリリース作成の接続）、set-state による一式の運搬体、実行前後の版管理とパッチリリース、既存機構の接続部分
- **対象外**:
  - learning・intake・inspect の評価ロジックの全面再設計
  - Epic/Wave 構成規則、共有並列上限、依存判断、並列実行アルゴリズムの再定義
  - 個別の要件定義・実装・検証工程の重複実装
  - 新規の汎用工程管理基盤・恒久台帳の一律導入
  - 配布形式の統一
  - major/minor バージョンの自動判定
  - 本番環境への自動配備
