## 目的

GitHub Issue を、追跡Issue（課題、ToDo、アイデア、リスク等の未解決事項の育成管理単位）と Case Issue（req/case パイプラインの実行票）の共通管理単位として運用する。

要件定義、方式設計、実装、レビュー、検証、外部確認等で生じた未解決事項を、発生から検討、保留、解決、正規成果物への反映確認まで継続して追跡できるようにする。

追跡Issueと Case Issue の役割分離、論理スキーマの一元管理、自然言語操作入口、Tool 操作契約経由の I/O を確立し、各 workflow がこれらを再実装しない基盤を提供する。

課題管理は、Intake / Learning 等の AI 駆動開発における改善循環とは別系統として扱う。

## 要件

| ID | 要件 |
|---|---|
| REQ-049-001 | GitHub Issue は、人または Agent が検討、判断、実行、追跡する必要のある事項の永続的な管理単位であること。要件定義、方式設計、実装、レビュー、検証、外部確認等で生じた未解決事項の正規管理先は追跡Issueとし、未解決事項は発生から検討、保留、解決、正規成果物への反映確認まで継続して追跡できること |
| REQ-049-002 | Issue は論理 role により追跡Issue（tracking）と Case Issue（case）に区別され、role は機械判定可能であること。追跡Issueの kind は少なくとも problem、idea、task、risk の意味を表現できること |
| REQ-049-003 | 追跡Issueの状態は少なくとも起票、検討中、保留、実行準備完了、解決済み、クローズ済みの6状態を区別できること。解決済みは結論の確定を意味し、クローズ済みは必要な反映の完了または反映不要の確認完了を意味すること |
| REQ-049-004 | Issue が存在すること自体を Agent の実行許可としないこと。追跡Issueを実行票へ直接変質させないこと |
| REQ-049-005 | 追跡Issueで実行が確定した場合、req-define 等の正規要件化・設計経路を経由し、case-open が追跡Issueとは別の Case Issue を作成すること。追跡Issueと生成された Case Issue の関係は後から追跡できること |
| REQ-049-006 | GitHub Organization 固有設定（Issue Type、Issue Fields 等）を利用必須条件としないこと。追跡Issueの論理スキーマは最低限、リポジトリ単位の Issue、ラベル、本文、状態で表現でき、利用可能な環境では GitHub Issue Type / Issue Fields を物理写像として使用できること |
| REQ-049-007 | 追跡Issueの論理スキーマ（role、kind、状態と状態遷移、件名、内容、背景、影響、関連成果物、選択肢、判断材料、不足情報、owner・期限・優先度等の任意メタデータ、保留理由、再評価条件、解決結論、反映先と反映状態、追跡Issueと Case Issue の関連、物理マッピング、本文標準構造）の正は一元管理 Design が所有すること。同一のラベル名、kind、状態、本文フォーマットを複数の Command / Skill / Template が独自定義しないこと |
| REQ-049-008 | 物理マッピング（role、kind、状態とラベル等の物理値の対応表）の所有は一元管理 Design とし、論理値と物理値の変換（写像表の機械適用）は Tool 内実装とすること。Tool は写像表の機械適用のみを行い、写像の意味判断を新規に所有しないこと |
| REQ-049-009 | /agentdev/issue を追跡Issueの自然言語操作入口とすること。起票、検索・参照、更新、コメント追加、保留、再評価、実行準備完了、解決、反映確認、クローズ、再オープンを、自然言語入力と会話文脈から判断して実行できること |
| REQ-049-010 | 追跡Issue操作の利用に、サブコマンド、ラベル名、Issue Type、Field 名等の GitHub 実装詳細の把握をユーザーに要求しないこと |
| REQ-049-011 | 新規起票時は、現在の作業で解決できる事項を先に解決し、既存追跡Issueを検索して重複を避けること。ユーザー合意が必要な設計判断を課題管理側だけで確定しないこと |
| REQ-049-012 | 検討経過は Issue コメントを正規の時系列履歴とすること。Issue 本文は現在状態の理解のための要約・構造化情報を中心とし、本文内へ独自の追記専用ログを二重保持しないこと |
| REQ-049-013 | 保留状態の追跡Issueは、現在判断できない理由と再評価の成立条件を識別できること。再評価後は、結論の確定、理由と不足情報を更新した保留継続、対応不要という結論での解決、解決結果の正規成果物への反映のいずれかとして処理できること |
| REQ-049-014 | 解決済みの追跡Issueは結論を保持すること。クローズは必要な反映の完了または反映不要の確認を条件とすること。反映先の成果物更新はその成果物を所有する能力へ委譲できること |
| REQ-049-015 | 追跡Issueの操作能力は特定の単一 workflow に閉じず、要件定義、設計、レビュー、実装、検証等の複数 workflow から利用できること。各 workflow は追跡Issueのスキーマ定義や GitHub I/O を再実装しないこと |
| REQ-049-016 | GitHub 版の追跡Issue管理は、リポジトリ内に課題ファイルを作成し、commit しないこと |
| REQ-049-017 | ローカル版は .agentdev/issues/ のローカルIssueにより、通常版と同一の Tool 操作契約経由で追跡Issueの操作能力を提供すること。ローカルIssueの保存構造は REQ-009 が所有すること |
| REQ-049-018 | 旧課題管理方式から追跡Issueへの移行情報は、現在有効な論点（未解決の判断事項、判断材料、保留理由、再評価条件、再分析事項）のみを含み、旧課題 ID、旧保存方式、移行に至った経緯を含まないこと。移行起票は case 側の実施事項とし、本要件は移行内容の性質のみを規定すること |
| REQ-049-019 | 追跡Issueは docs/ 配下の文書種別ではなく、管理単位・永続状態として扱うこと。docs/ 配下に課題ファイルの文書種別を設けないこと |

## 適用範囲

### 対象

- 追跡Issue管理機構（共通管理単位、role と kind、状態と状態遷移、論理スキーマの一元管理、物理マッピングの所有と機械適用の分担、/agentdev/issue 自然言語入口、追跡Issue操作能力の共通提供、反映追跡とクローズ条件）
- 追跡Issueと Case Issue の役割分離と関係追跡、実行確定時の要件化経路への引き継ぎ
- ローカル版における追跡Issue能力の Tool 操作契約経由での提供
- 旧課題管理方式から追跡Issueへの移行情報の性質

### 対象外

- Intake / Learning パイプラインへの統合
- すべての追跡Issueを Decision 化すること
- 追跡Issue起票時点で反映先を固定すること
- 課題管理から直接実装を開始すること
- ユーザーに課題管理用 CLI 構文の暗記を要求すること
- GitHub Issue 操作の I/O 手続き（REQ-011 が所有）
- ローカルIssueの保存構造、採番、role 条件付きスキーマの詳細（REQ-009 が所有）
- ラベル、kind、状態の具体的値域、本文フォーマット、状態遷移表、状態の三段写像、追跡Issueと Case Issue の参照形式の詳細（Design が確定する事項）
- 移行起票の実施、旧課題管理方式の実装とその除去（case 側の実施事項）
