## 目的

AIエージェントが過去の会話や消費済みの RU・ドラフトに依存せず、Case Issue・Epic と参照先の恒久文書から最新の合意、現在地、次の行動を判断できるようにするため、Case Issue の本文・コメント・Case Epic の記録構造、記録契機、記録主体の責務、記録の整合性維持を定める。担当交代、停止・再開、判断撤回、並列実行が生じても、古い条件による実行、未検証の完了扱い、記録の食い違いを防ぐ。

記録モデルの物理様式は workflows/issue-lifecycle-records Design が正となり、workflow-templates Design はテンプレート投影規約を所有する。

## 要件

| ID | 要件 |
|---|---|
| REQ-101-001 | Case Issue の本文は最新の合意・現在地・結果の最新状態の提示を担い、Issue コメントは時系列の経過と判断理由の記録を担い、Case Epic は子 Issue の状態集約と全体条件の評価を担うこと。子 Issue の完了と Epic 全体の完了を区別して扱うこと |
| REQ-101-002 | Case Issue の本文は目的、対象・対象外、完了条件、適用する合意・規律への参照、現在地、結果の構成で保持すること（各セクションの物理様式は Design が確定する） |
| REQ-101-003 | 現在地は工程、進行状態、次の行動、担当役割、停止・待機理由、最新記録参照を読み取れる内容とすること |
| REQ-101-004 | 結果は成果物、最終判定とその根拠、残件の扱いを読み取れる内容とすること |
| REQ-101-005 | 工程、進行状態、完了判定を分離して記録すること。工程は ADF 工程に結び付け、必要な内部区分のみを加えること。表示上の進行状態は未着手、実行中、待機、終了の4値とし、待機には理由と次の行動を、終了には完了・中止の区別を付すこと。実行中表示は生存保証を意味せず、観測不能な場合は停止と断定せず観測不能であることを明示すること。進行状態は Root Case ライフサイクル状態（REQ-006-112）等の正規状態と記録契機から写像（導出）される表示であり、独立して更新・判断される第二の進行管理を構成しないこと（英語識別子と写像規則は Design が確定する） |
| REQ-101-006 | 記録契機は着手、引き渡し、停止、再開、判断変更、完了とすること。委譲要求を実着手と同一視しないこと。工程終了を待たず、途中で確定した停止・判断待ちを報告・反映できること。内部の全手順、全ツール実行、思考、定期投稿を記録契機に追加しないこと。短い複数の変化はまとめて記録でき、停止の通知を遅らせないこと |
| REQ-101-007 | 記録コメントは記録種別、対象工程、事実・結果、理由・根拠、次の行動、関連合意・成果物を基本項目とし、非該当項目は省略できること。停止には再開条件、判断変更には撤回対象、引き渡しには残作業と受取役割、完了には判定根拠を必須とすること。検証詳細は成果物を参照し、本文・コメント・PR 本文へ重複して記載しないこと |
| REQ-101-008 | 記録の取りまとめ責務（本文・コメント・Epic への反映、読み戻し確認、引き渡し、未反映の回復）は case-auto 等の進行スキルとコードが担うこと。専用の管理エージェントと公開コマンドを追加しないこと。実行担当は事実・結果・停止・変更影響を報告し、case-close 等の判定主体は完了条件と証拠を照合し、実行の申告だけで完了扱いとしないこと。同一のエージェントが複数役割を担う場合も責務を区別すること |
| REQ-101-009 | 合意変更は記録、受領、実行への適用を区別して扱うこと。影響対象を特定して継続・停止・再実行を判断し、最新条件を作業担当へ渡し、担当による作業への適用方針の報告まで確認すること。影響しない作業を一律停止しないこと。通常の現在地更新によって目的・対象範囲・完了条件を変更しないこと |
| REQ-101-010 | 同一 Issue/Epic 本文への競合更新のみを局所的に直列化し、独立した作業は並列実行すること（直列化単位と一般原則は DEC-039 と Runtime 実行モデル Design に従い、本要件は再定義しない）。直列化は実際の書込み経路（ワークフロー、手動・代替経路、Epic 内処理）を横断して確認すること |
| REQ-101-011 | 更新失敗・結果不明を成功扱いにしないこと。コメントのみ成功、本文のみ成功、Epic のみ未反映等の部分成功を区別し、読み戻し後に不足分を再試行すること。中断・担当交代で未反映情報を失わず、重複投稿・重複実行を防ぐこと。進捗表示の失敗だけで稼働中の処理を強制終了しないこと。未反映の重要条件に基づく新作業開始を許可しないこと。成果の確定と記録・終了処理の完了を区別すること |
| REQ-101-012 | RU・ドラフト消費後は Case Issue・Epic と参照先の恒久文書を作業の正規情報源とし、消費済みの RU・ドラフトから不足する契約を補完しないこと。本文の簡素化を制約、検証方針、依存関係等の実行条件を落とす根拠にしないこと。必要情報の永続化・確認前に RU・ドラフトを削除しないこと |
| REQ-101-013 | 更新回復用のローカル記録は未反映内容と識別情報等に限定し、第二の作業定義・恒久状態源として扱わないこと |
| REQ-101-014 | 取りまとめは記録契機（着手、引き渡し、停止、再開、判断変更、完了）に応じて子 Issue の本文・コメントと Case Epic 本文への反映を完了させること。Epic 本文への反映が完了するまでの間は子 Issue 本文の現在地が最新の情報として読み取れること（この読み取り規律は Epic 反映責務の代替ではない）。Epic 本文の書き込みは per-Epic の単一書き手として排他制御されること |

## 適用範囲

### 対象

- Case Issue（Root Case・Child Issue）と Case Epic Issue の本文・コメント・進行記録の構造と記録契機
- 記録主体の役割責務（実行担当・取りまとめ・判定主体）と報告・反映・確認の論理契約
- 記録の競合直列化の適用、部分成功の区別と回復、重複防止
- RU・ドラフト消費後の情報源としての Issue/Epic の読み取り契約（読み取り優先順位を含む）
- 記録契機に応じた Epic 本文反映の実現に必要な Epic 書き手契約・書き込み時機の変更（REQ-035-001 の更新、agentdev-epic-tracker Design の更新）

### 対象外

- execution contract の確定と消費（REQ-017）
- case-auto/case-ready/case-run/case-close/case-revise 等の各工程実行契約とその内部状態機械（REQ-034/REQ-031/REQ-032/REQ-061/REQ-062）
- Epic/Wave 実行モデルの実行制御（Wave 構成、収束判定、実行順序 SSoT、Wave 状態の導出、全 Wave 完了後の一括確定反映）（REQ-035-002/003/005/007/013/016、agentdev-epic-tracker Design の追跡テーブル更新手続き）
- Root Case 状態モデルと resume_command（REQ-006）
- 追跡Issueの本文構造と論理スキーマ（REQ-049、agentdev-issue-tracking Design）
- RU・ドラフトの削除契約自体（REQ-008-010/011、REQ-061-025）
- 過去 Issue の一括遡及更新、常時監視・定期投稿、全ログの GitHub 複製、別の状態管理基盤の新設、専用管理エージェント・公開コマンドの新設
