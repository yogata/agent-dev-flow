## 目的

AIエージェントが過去の会話や消費済みの RU・ドラフトに依存せず、Case Issue・Epic と参照先の恒久文書から最新の合意、正規の状態、継続条件を判断できるようにするため、Case Issue の本文・コメント・Case Epic の記録構造、記録対象、記録主体の責務、記録の整合性維持を定める。担当交代、停止・再開、判断撤回、並列実行が生じても、古い条件による実行、未検証の完了扱い、記録の食い違いを防ぐ。

記録モデルの物理様式は workflows/issue-lifecycle-records Design が正となり、workflow-templates Design はテンプレート投影規約を所有する。

## 要件

| ID | 要件 |
|---|---|
| REQ-101-001 | Case Issue の本文は最新の合意・結果の最新状態の提示を担い、Issue コメントは停止・失敗の理由、重要な判断変更、完了済み Issue の検証証拠、自明でないレビュー上の判断など後工程が必要とする判断理由と証拠の記録を担い、Case Epic は子 Issue の状態集約と全体条件の評価を担うこと。子 Issue の完了と Epic 全体の完了を区別して扱うこと |
| REQ-101-002 | Case Issue の本文は目的、対象範囲（対象要件、主な変更対象、対象外を含む）、実現方針（再判断できない合意が確定している場合のみ設ける）、完了条件、進行状況、結果（完了・中止の確定時のみ）の構成で保持し、子 Issue は本文冒頭に親 Epic への参照を持つこと（各セクションの物理様式は Design が確定する）。該当しない章を本文に設けないこと |
| REQ-101-003 | 進行状況は Root Case の正規状態と開始・終了日時のみを記録すること。開始日時は最初の実着手時に設定し以後更新しないこと。終了日時は完了または中止の確定時に設定すること。子 Issue の本文は状態を持たず（子 Issue の状態モデルの所有は REQ-035-004）日時のみを記録すること。第二の進行管理、現在工程、次の行動、担当役割、最新記録参照を本文項目として保持しないこと |
| REQ-101-004 | 結果は成果物、最終判定とその根拠、残件の扱いを読み取れる内容とし、完了または中止が確定した時点でのみ本文に設けること |
| REQ-101-006 | Issue コメントの記録対象は停止・失敗の理由と再開条件、重要な判断の変更（撤回対象を含む）、完了済み Issue の検証証拠、自明でないレビュー上の判断に限定し、着手・引き渡し・再開の定型的な報告コメントを生成しないこと。コメントの削減で判断理由と証拠の記録を失わせないこと |
| REQ-101-007 | 記録コメントは対象、事実・結果、理由・根拠、次の行動（停止の場合は再開条件を含む）、関連合意・成果物を基本項目とし、非該当項目は省略できること。検証詳細は成果物を参照し、本文・コメント・PR 本文へ重複して記載しないこと |
| REQ-101-008 | 記録の取りまとめ責務（本文・コメント・Epic への反映、読み戻し確認、未反映の回復）は case-auto 等の進行スキルとコードが担うこと。専用の管理エージェントと公開コマンドを追加しないこと。実行担当は事実・結果・停止・変更影響を報告し、完了条件チェックボックスの更新は case-close が専任として行い（完了条件評価の契約は REQ-032 が所有する）、実行の申告だけで完了扱いとしないこと。同一のエージェントが複数役割を担う場合も責務を区別すること |
| REQ-101-009 | 合意変更は記録、受領、実行への適用を区別して扱うこと。影響対象を特定して継続・停止・再実行を判断し、最新条件を作業担当へ渡し、担当による作業への適用方針の報告まで確認すること。影響しない作業を一律停止しないこと。通常の進行状況更新によって目的・対象範囲・完了条件を変更しないこと |
| REQ-101-010 | 同一 Issue/Epic 本文への競合更新のみを局所的に直列化し、独立した作業は並列実行すること（直列化単位と一般原則は DEC-039 と Runtime 実行モデル Design に従い、本要件は再定義しない）。直列化は実際の書込み経路（ワークフロー、手動・代替経路、Epic 内処理）を横断して確認すること |
| REQ-101-011 | 更新失敗・結果不明を成功扱いにしないこと。コメントのみ成功、本文のみ成功、Epic のみ未反映等の部分成功を区別し、読み戻し後に不足分を再試行すること。中断・担当交代で未反映情報を失わず、重複投稿・重複実行を防ぐこと。進捗表示の失敗だけで稼働中の処理を強制終了しないこと。未反映の重要条件に基づく新作業開始を許可しないこと。成果の確定と記録・終了処理の完了を区別すること |
| REQ-101-012 | RU・ドラフト消費後は Case Issue・Epic と参照先の恒久文書を作業の正規情報源とし、消費済みの RU・ドラフトから不足する契約を補完しないこと。本文の簡素化を制約、検証方針、依存関係等の実行条件を落とす根拠にしないこと。必要情報の永続化・確認前に RU・ドラフトを削除しないこと |
| REQ-101-013 | 更新回復用のローカル記録は未反映内容と識別情報等に限定し、第二の作業定義・恒久状態源として扱わないこと |
| REQ-101-014 | 取りまとめは反映が必要な記録（停止・失敗とその再開条件、重要な判断変更、完了・中止の確定）に応じて子 Issue の本文・コメントと Case Epic 本文への反映を完了させること。Epic 本文への反映が完了するまでの間は子 Issue の本文・コメントが最新の情報として読み取れること（この読み取り規律は Epic 反映責務の代替ではない）。Epic 本文の書き込みは per-Epic の単一書き手として排他制御されること |
| REQ-101-015 | 進行状況・結果に実作業時間、試行ごとの記録、着手・引き渡し・再開の履歴を保持しないこと。判断理由と証拠の記録はこの限りでないこと |
| REQ-101-016 | 廃止した本文項目・コメント種別・管理情報を、別名、補助的なメタデータ、コメント、管理ファイルによって再導入しないこと。判断理由と証拠の記録は維持すること |

## 適用範囲

### 対象

- Case Issue（Root Case・Child Issue）と Case Epic Issue の本文・コメント・進行記録の構造と記録対象（本文構成、進行状況の日時規則、コメント記録対象、結果の設置条件）
- 記録主体の役割責務（実行担当・取りまとめ・判定主体）と報告・反映・確認の論理契約（完了条件チェックボックス更新の case-close 専任を含む）
- 記録の競合直列化の適用、部分成功の区別と回復、重複防止
- RU・ドラフト消費後の情報源としての Issue/Epic の読み取り契約（読み取り優先順位を含む）
- 反映の実現に必要な Epic 書き手契約・書き込み時機の変更（REQ-035-001 の更新、agentdev-epic-tracker Design の更新）

### 対象外

- execution contract の確定と消費（REQ-017）
- case-auto/case-ready/case-run/case-close/case-revise 等の各工程実行契約とその内部状態機械（REQ-034/REQ-031/REQ-032/REQ-061/REQ-062）
- Epic/Wave 実行モデルの実行制御（Wave 構成、収束判定、実行順序 SSoT、Wave 状態の導出、全 Wave 完了後の一括確定反映）（REQ-035-002/003/005/007/013/016、agentdev-epic-tracker Design の追跡テーブル更新手続き）
- Root Case 状態モデルと再開入口（REQ-006）
- 子 Issue 状態モデルと実行構成表の構成（REQ-035-004/019。実行構成の生成は REQ-061-007）
- 追跡Issueの本文構造と論理スキーマ（REQ-049、agentdev-issue-tracking Design）
- RU・ドラフトの削除契約自体（REQ-008-010/011、REQ-061-025）
- 過去 Issue の一括遡及更新、常時監視・定期投稿、全ログの GitHub 複製、別の状態管理基盤の新設、専用管理エージェント・公開コマンドの新設
