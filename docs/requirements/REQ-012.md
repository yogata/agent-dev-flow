## 目的

AgentDevFlow の Traceability Information Model（TIM）を、汎用成果物グラフではなく、要件を中心とした最小の対応モデルとして定義する。
各要件について、要件に関わる Design 文書、実装成果物、検証手段、Decision 文書を明示的に対応付け、対応漏れと不整合を決定的に検査できることを目的とする。
トレーサビリティ標準機能として agentdev-traceability（coverage、impact、check）を提供し、AgentDevFlow を導入するプロジェクトが自プロジェクトの要件管理のために利用できる標準機能とする。AgentDevFlow 自身のトレーサビリティデータも本機能で管理・検査する（自己適用）。
対応関係の保存は、inline 対応宣言（ADF-COVERS）とリポジトリルート直下の traceability/ 配下の sidecar に分離する。inline 宣言は producer 側成果物のための直列化形式とし、標準実装は正規成果物の直接走査によって対応関係を解決する。
検証対応要否はトレーサビリティポリシー（traceability/policy.yaml）が所有する。
外部標準（SysML、OSLC、OpenFastTrace）は概念上の参照元とし、日本語本文の正式用語は「対応関係」「対応付け」を用いる。
旧 Artifact Graph（汎用グラフ、派生索引、旧公開API）は移行完了後に撤去する（DEC-017）。

## 要件

| ID | 要件 |
|---|---|
| REQ-012-026 | TIM の要件単位は REQ 文書全体ではなく、個別の要件行（`REQ-{NNNN}-{MMM}`）とすること |
| REQ-012-027 | TIM の標準コア関係は、成果物が要件へ明示的に対応する対応関係（covers）のみとすること |
| REQ-012-028 | 要件へ対応する成果物の役割は、decision、design、implementation、verification の4種を標準とすること。design と implementation は必須対応の役割、decision は任意対応の役割、verification はトレーサビリティポリシーが定める検証対応要否に従う役割とすること |
| REQ-012-029 | 各現行要件について、その要件を実現する実装成果物が1件以上明示的に対応付けられていること |
| REQ-012-030 | 各現行要件のうち検証対応必須の要件行について、その要件を検証する検証手段が1件以上明示的に対応付けられていること。検証対応要否はトレーサビリティポリシー（リポジトリルート直下の traceability/policy.yaml）が所有し、未指定の要件行は検証対応必須として扱うこと。検証対応を任意とする要件行はポリシーへの明示登録によってのみ宣言できること（検証手段と検証実行結果の分離は REQ-021） |
| REQ-012-031 | 各現行要件について、その要件の設計を記述する Design 文書が1件以上明示的に対応付けられていること。Definition 保存時点での Design 対応の未成立は保存を阻害せず、工程ゲートによる Design 対応の確立は REQ-021 が所有すること |
| REQ-012-032 | 実装成果物および検証手段は要件へ直接対応付けること。Design 文書との対応関係を経由して、要件に対する実装または検証が成立したものと推定しないこと |
| REQ-012-033 | 1つの成果物が複数の要件へ対応できること。1つの成果物が複数の役割を持てること |
| REQ-012-034 | implementation はソースコードという物理種別ではなく、要件を実現する永続成果物の役割として扱うこと |
| REQ-012-035 | verification は要件を検証する永続的な検証手段を表すこと。個々の検証実行結果を TIM に保持しないこと |
| REQ-012-036 | Decision は ADF の正式文書として維持し、TIM の標準成果物役割 decision の対応対象とすること。Decision 対応の欠落を対応関係の完全性の不合格として扱わないこと |
| REQ-012-037 | 一般的な文書参照、Markdown リンク、言及を、TIM の意味的なトレース関係として扱わないこと |
| REQ-012-038 | 関係ごとの変更影響方向を TIM の正規データとして保持しないこと |
| REQ-012-039 | 分解、具体化、依存、実現、実装、検証などの多数の関係型を、標準 TIM へ持ち込まないこと |
| REQ-012-040 | 任意の成果物型や関係型を追加する汎用拡張機構を、最小 TIM の必須機能としないこと |
| REQ-012-041 | TIM は派生索引、グラフDB、物理保存形式を規定しないこと |
| REQ-012-042 | coverage / covers は機械識別子または外部標準との対応説明で使用できるが、日本語本文の正式用語は「対応関係」「対応付け」とすること |
| REQ-012-043 | トレーサビリティ標準機能の配布スキル名は `agentdev-traceability` とし、artifact-graph を新しい標準機能名として引き継がないこと |
| REQ-012-044 | 標準公開能力は coverage、impact、check を基本とすること |
| REQ-012-045 | coverage は、要件を指定して対応する Design 文書、実装成果物、検証手段、Decision 文書を役割付きで取得でき、成果物を指定してその成果物が対応する要件を役割付きで取得できること。sidecar と inline の対応宣言は同一の論理対応関係として正規化して返すこと。明示された対応関係を全件返し、候補数上限、ランキング、探索深度によって黙って切り捨てないこと |
| REQ-012-046 | impact は、要件を起点に当該要件へ明示的に対応する成果物を、成果物を起点にその成果物が対応する要件を経由して同じ要件へ対応する他の成果物を、変更時の再確認候補として取得できること。任意深度のグラフ探索を行わず、成果物 ↔ 要件 ↔ 成果物の範囲を超えて探索せず、impact の空結果を「影響なし」の証明として扱わないこと |
| REQ-012-047 | check は、少なくとも sidecar とトレーサビリティポリシーの構文不正、未知の成果物役割、存在しない要件への参照、対応先パスの解決不能、Design 対応の欠落、実装対応の欠落、検証対応の欠落（検証対応必須の要件行のみ計上）、ポリシー参照の不正、同一対応関係の重複宣言の不整合を決定的に検査できること。Decision 対応の欠落を不合格として扱わないこと |
| REQ-012-048 | 標準実装は正規成果物（inline 対応宣言を保持する producer 側文書、およびリポジトリルート直下の traceability/ 配下の sidecar とトレーサビリティポリシー）を直接走査し、対応関係をその場で解決できること。`.agentdev/graph/` のような派生 Graph を標準動作の必須入力または必須生成物とせず、派生索引の鮮度判定、再生成、生成バージョン、設定ダイジェスト等を必須契約としないこと |
| REQ-012-049 | neighbors、path、provenance、related、dependency、implementation、diagnostics の旧公開動作との互換性を必須としないこと。一般文書探索、任意経路探索、構造診断、依存関係探索を agentdev-traceability の責務へ取り込まないこと。OpenFastTrace、Eclipse Capra、専用グラフDBを標準実行依存として導入しないこと。性能について数値の受け入れ基準を設けないこと |
| REQ-012-050 | 将来、直接走査が実運用上の問題として観測された場合、coverage、impact、check の外部契約を変えずにキャッシュまたは索引を追加できる構造とすること。対応宣言の具体的な表記は Design で確定し、要件では文字列形式を固定しないこと。旧 Artifact Graph の互換層、移行専用の恒久例外台帳、旧要件だけを除外する legacy モードを移行完了後に残さないこと |
| REQ-012-051 | 検証対応要否はトレーサビリティポリシーの登録状態のみから導出すること（未登録 = 検証対応必須）。検証対応要否の中間状態、分類状態のみを保持する独立した台帳、REQ frontmatter 項目、派生索引を新設しないこと |
| REQ-012-052 | トレーサビリティ標準機能（agentdev-traceability）は、AgentDevFlow を導入するプロジェクトが自プロジェクトの要件トレーサビリティのために利用する標準機能として提供されること。AgentDevFlow 自身のトレーサビリティデータも本機能で管理・検査すること（自己適用） |
| REQ-012-053 | 配布対象成果物（製品ソース）の対応関係は、リポジトリルート直下の traceability/ ディレクトリ配下に component または package 単位で配置する sidecar に宣言できること。sidecar の最小データは対応対象成果物のリポジトリ相対パス、役割、要件行 ID とし、専用の成果物 ID、関係 ID、リビジョン、ダイジェストを必須としないこと。sidecar の YAML スキーマ詳細とファイル命名規則は Design が所有すること |
| REQ-012-054 | inline 対応宣言（ADF-COVERS）は producer 側成果物のための直列化形式に位置づけること。sidecar と inline の対応宣言は、coverage、impact、check において同一の論理対応関係として扱うこと |
| REQ-012-055 | 対応関係の宣言と検査は、成果物の物理種別と拡張子に依存しないこと。sidecar から参照できる永続成果物を種別を問わず対応対象とできること |
| REQ-012-056 | check は、対応宣言またはトレーサビリティポリシーの解決が実行不能な場合、対応完全性の合格として扱わず不合格として扱うこと |
| REQ-012-057 | agentdev-traceability 配布スキルは、トレーサビリティの知識と手順を提供し、個別プロジェクトの対応関係データ、sidecar、トレーサビリティポリシーを配布内容に含めないこと。対応関係データは各プロジェクトの正規成果物として管理されること |

## 適用範囲

**対象**: 最小 TIM（要件行単位、covers、decision/design/implementation/verification の4役割、対応関係の完全性規則、用語政策）、トレーサビリティ標準機能としての一般化と自己適用、sidecar とトレーサビリティポリシーによる対応関係の保存、agentdev-traceability 標準配布スキル（coverage、impact、check、正規成果物の直接走査、対応宣言の解析・検査）、旧機能撤去の最終状態（互換層なし、恒久例外台帳なし、legacy モードなし）

**対象外**: ADF ワークフロー統合の工程割り当て（REQ-021）、成果物区分（開発管理成果物 / 製品ソース / 配布成果物）の所有と配布閉包純度の不変条件（REQ-002、REQ-029）、sidecar の YAML スキーマ詳細とファイル命名規則（Design）、一般文書探索、任意経路探索、構造診断、依存関係探索、意味類似検索、ソースコード依存解析、実行順序やワークフロー依存の表現、Decision の理由探索、個々の検証実行結果の保存、グラフDB、派生索引とその鮮度管理、OpenFastTrace 等の本番依存化、性能の数値基準、LLM による対応関係の自動確定、既存要件の棚卸し移行作業の実行計画（case-open が決定）
