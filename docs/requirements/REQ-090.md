## 目的

ADF の6系統 Workflow の意味判断に typesafe/Jev による先行評価を逐次経路で組み込み、Jev と LLM 最終判断の関係を実運用で観測可能にすること。Jev は最終判断者ではなく、後段の LLM 推論への追加情報として扱うこと。観測契約は一次事実（1 semantic evaluation = 1 observation）を中心に構成し、confidence 閾値による LLM 推論の省略・Jev 結果の直接確定 routing を行わないこと。本要件は観測可能化（Stage 1 / Issue A）までを対象とし、有効性の最終結論（Issue B）と LLM 推論の Jev 置換（Issue C）を含まないこと。

## 要件

| ID | 要件 |
|---|---|
| REQ-090-001 | ADF は Jev 先行評価を提供する Custom Tool を備えること。Tool の公開契約は provider・SDK のいずれにも依存せず、初期実装の Vercel AI Gateway 接続（model ID typesafe-ai/jev、credential AI_GATEWAY_API_KEY）は adapter 内部実装として隠蔽し、SDK 固有の名称・型・格納位置を Workflow 層と公開スキーマへ漏らさないこと。Tool は API 呼出し、入出力形式の検証、provider・接続設定の解決、結果・確率分布・確実性の正規化、呼出し失敗の構造化、機械的処理時間の計測を担い、判断対象の意味、評価基準、Jev を呼ぶべき箇所、最終判断を所有しないこと。質問型と boolean/choice/score の対応づけは adapter mapping であり意味契約の変更としないこと。 |
| REQ-090-002 | Jev 先行評価はデフォルトで有効であり、feature flag や opt-in 手続きを必要としないこと。利用可否は AI_GATEWAY_API_KEY の設定有無で決まること。API key 未設定時は Jev を呼び出さず従来 LLM 経路（reasoning model のみ）で Workflow を完了させること。未設定を Jev API 失敗に含めず、未設定および評価入力の事前検証失敗では semantic evaluation observation を生成しないこと。 |
| REQ-090-003 | Jev API 呼出し後の失敗（timeout、429、5xx、network error、response validation error 等）に対して自動 retry を行わず即座に従来 LLM 経路（reasoning model のみ）へ fallback すること。failure observation は実際の evaluator 呼出し開始後の失敗のみを対象とすること。観測の保存のみに失敗した場合、Workflow の正規処理結果を維持し（fail-open）、rollback・再実行・擬似再生成を行わず、識別可能な warning を報告すること。Jev 経路の障害によって既存 ADF の正規状態を破損しないこと。 |
| REQ-090-004 | learning-promote、req-define、Epic/Wave 構成判断、intake-promote、inspect-promote、backlog-review の6系統 Workflow は、閉じた意味判断ごとに基本判断経路「Jev 先行評価 → 評価結果・候補別確率分布・取得できた confidence を判断材料として含む LLM 推論（従来の判断材料も参照）→ LLM による最終判断」を実行できること。evaluator API 呼出し失敗・未設定・評価入力の事前検証失敗のいずれの場合も LLM（reasoning model）のみで最終判断まで到達し Workflow を継続できること。confidence 閾値による LLM 推論の機械的省略・Jev 結果の直接確定 routing を行わないこと。判断単位と質問形式の割当ては各 Workflow/Capability Skill が所有し、その初期割当て（適用対象19件）と適用可否を本 Case 内で確定する3件の判断結論を該当 Workflow の reference へ文書化すること。Jev へ渡す state は Workflow が構成した閉じた判断入力とし、候補探索用の repository 全文を渡さないこと。 |
| REQ-090-005 | 1件の semantic evaluation（複数 judgment を含み得る）につき独立した1 observation を生成すること。provider/evaluator が実際に返した confidence は evaluation 単位でのみ保存し、judgment 単位への複製および probability distribution からの代替 confidence の生成・永続化を行わないこと。provider が confidence を返さない evaluation では confidence を保存しないこと。inputTokens は provider が返す場合のみ保存すること。 |
| REQ-090-006 | 観測記録は .agentdev/jev-observations/ を正式な永続 domain state（git 管理対象）の保存先とし、1 semantic evaluation につき1 observation（1 JSON）として保存すること（1 Workflow 実行単位の JSON 集約を行わない）。各 observation から実行元 Workflow と semantic evaluation の種別を一意に識別できること。観測の一次事実は evaluator 返却結果、候補別確率分布、provider 返却 confidence、入力再構成情報（具体的 source revision、再構成可能入力は参照と request digest、再構成不能入力のみ最小 snapshot）、reasoning model の最終判断結果、差異理由分類、呼出し時間、input token 数（provider 返却時のみ）、失敗分類と最小 diagnostic に限定すること。source revision から一意に導出できる provider・requested model 等の情報を観測ごとに必須保存しないこと（非導出の identity 差異が実行時観測された場合のみ保持できる）。観測 filename、個別 field 名、snapshot 物理表現、operation 構成は実装設計時の自由度であり、本項の意味契約を変更しない範囲で定めること。 |
| REQ-090-007 | Epic/Wave 構成の正規判断所有者は case-ready であり、docs/designs/workflows/references/execution-unit-construction.md 内の旧 case-open 所有表現（6箇所）および docs/designs/README.md 横断 Design 一覧の当該行が case-ready 実行契約へ整合して更新されていること。 |
| REQ-090-008 | Jev 実装開始直前の最新 main に v4.0.2 tag が存在すること。Jev を無効化した場合（API key 未設定を含む）、既存 Workflow の挙動を基準点時点と同等に維持できること。 |
| REQ-090-009 | Jev 導入のために、投機実行、background LLM 化、rollback 機構、投機状態管理、Jev 専用の durable state、汎用意味判断基盤、汎用依存グラフ基盤、汎用 provenance graph、汎用 replay engine、Jev 専用サブエージェントを新設しないこと。 |
| REQ-090-010 | 既存 Command / Workflow Skill / Capability Skill の責務境界を維持すること。Custom Tool は機械処理のみを担い、判断の意味・基準・Jev 呼出し位置・LLM 最終判断は Workflow/Capability Skill が所有すること。Command は公開契約上必要な範囲のみを更新し、Jev 固有の手順を不必要に重複記述しないこと。 |
| REQ-090-011 | adapter の score 形式マッピングは、gateway スキーマが questions[].score.criteria に必須要求する空でない文字列配列を満たす形で criteria を構成すること。水準ラベル（scale）を criteria の文字列配列として渡す実装とし、choice 形式の criteria 構成と対称であること。adapter パッケージの単体テストに score 形式のマッピング検証を含め、boolean/choice/score の全質問形式のマッピングが検証されていること。マージ前に AI_GATEWAY_API_KEY 設定環境で実 gateway へ score 形式 1 問の実呼出し検証を 1 回行い、成否・inputTokens・confidence を実行記録に残すこと。観測 JSON スキーマ、Workflow 側の質問構成方法、credential 供給経路は対象外とすること。 |
| REQ-090-012 | Jev 先行評価の choice 形式質問は、正解となり得る操作クラス（REQ 操作なし等の非操作正解クラスを含む）を候補集合が網羅するように構成し、NULL 候補（該当なし等）を含めるか否かを構成時に明示判断すること。候補集合の欠落に由来する判断是正は質問構成側の欠陥として分類し、判断器精度の劣化要因として集計しないこと。 |
| REQ-090-013 | agentdev_jev の evaluate は evaluator 成功後・reasoning model（LLM 推論）へ進む前に、当該評価の一次観測の永続化を試みること。永続化成功後の中断でも一次観測が失われないこと。reasoning model の最終判断結果は evaluator 成功観測へ反映し、failure observation への重複保存を要求しないこと。永続化自体の失敗は観測保存失敗契約（fail-open）に従うこと。観測の永続化経路の物理構成（操作分割、完了状態の表現）は実装設計時の自由度とすること。 |
| REQ-090-014 | canonical result は provider 固有表現に依存せず、boolean は真偽、choice は候補、score は scale level として扱うこと。評価入力の各質問と各結果を1対1で対応付けられ、各質問について evaluator result と候補別確率分布の双方を保持できること。 |
| REQ-090-015 | evaluator 成功かつ reasoning model が最終判断した場合の観測に final result を保持できること（failure observation への重複保存を行わないこと）。evaluator result と final result が異なる場合のみ、差異理由の分類（evaluation_input_defect / semantic_disagreement / deterministic_override / unknown）を保持できること。 |
| REQ-090-016 | failure observation は実際の evaluator 呼出し開始後の失敗のみを対象とし、失敗分類（timeout、429、5xx、network error、response validation error の5分類）と最小 diagnostic を保持すること。運用メトリクスとして実評価の呼出し時間を比較可能な形で保持し、input token 数は provider 返却時のみ保存すること。 |
| REQ-090-017 | 既存の v1 観測（1 Workflow 実行 = 1 JSON 形式）は履歴として保持し、migration・変換・読み取り互換を要求せず、新契約の現行 observation として誤解釈可能な扱いをしないこと。recordState、outcome、llmTreatment、unchanged/corrected、finalizedBy、direct-finalization marker、fallback reason、not_configured/invalid_input observation を新契約観測の必須要素としないこと。 |

## 適用範囲

### 対象
- Jev 先行評価 Custom Tool（provider・SDK 非依存の公開契約、初期 Vercel adapter、失敗の構造化、confidence 正規化）
- 6系統 Workflow（learning-promote、req-define、Epic/Wave 構成判断、intake-promote、inspect-promote、backlog-review）への逐次経路追加
- 観測 domain state .agentdev/jev-observations/（1 semantic evaluation = 1 observation、一次事実となる必須観測項目、入力再構成）
- Epic/Wave 所有表現の case-ready 整合修正（execution-unit-construction.md、docs/designs/README.md）
- v4.0.2 tag 基準点の作成
- REQ-089 欠番に伴う採番整合（欠番記録3ファイル、採番スクリプトの最小修正、新規 REQ は REQ-090）

### 対象外
- Jev 有効性の最終結論（Issue B: 一定量観測後の評価）
- LLM 推論の Jev 置換（Issue C: confidence 閾値に基づく最終判断の置換）
- 投機実行、background LLM 化、rollback 機構、投機状態管理
- 汎用意味判断基盤、汎用依存グラフ基盤、汎用 provenance graph、汎用 replay engine の新設
- opencode.db を使った本格分析
- Jev だけを理由とする独自外部送信制限の新設
- 観測 JSON の filename、個別 field 名、snapshot 物理表現などの具体 schema 規定（実装設計時の自由度として合意済み）
- 課金開始後の実験継続条件の判断（本 Case の失敗条件としない）
- confidence 閾値による routing 統計量・routing engine・汎用 threshold 管理（margin、Workflow 別 threshold 体系を含む）の新設
