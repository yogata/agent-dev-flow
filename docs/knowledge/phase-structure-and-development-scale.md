# 工程の共通責務と構成選択―小規模一気通貫と段階開発の両立

## 知識内容

### 工程の責務と工程構成は同じではない

要件を明らかにし、実現方式を検討し、実装・構築して、必要な範囲を検証するという責務は、工程を何段階に分けるかとは独立して考えられる。要件定義、基本設計、詳細設計等を別々の作業として扱う場合も、一つの有限作業で連続して扱う場合も、責務の内容と必要な検証は消えない。

工程を細かく分けると、中間成果物を確認・確定して別の担当者や後続作業へ渡しやすい。一方で、工程間の受け渡し、成果物の作成・管理、再確認の負担が増える。小さな変更にすべての詳細工程と独立した文書を要求すれば、変更の実質より管理が大きくなる。逆に工程を一つに固定すれば、実装を伴わない設計確定や、別の期間・主体が担当する後続工程への引継ぎが難しくなる。

ADFが目指したのは、詳細工程を一律に採用することでも、一気通貫だけを許すことでもない。工程の共通責務を保ちながら、プロジェクトが採用した工程・成果物の構成に応じて実行できることである。

### 開発規模と、作業の起点・終了境界を分ける

変更駆動と工程駆動は、小規模と大規模をそのまま分ける分類ではない。変更駆動は一つの要求・障害等を起点に、必要な要件・設計・実作業・検証へ連続して進む単位であり、複数のIssueや依存作業を含む場合もある。工程駆動は、採用した工程内で検討と成果物形成を反復し、利用者の判断で次工程へ引き継ぐ単位であり、小さな設計確定だけを扱う場合もある。

入口を一本化すれば操作や説明を減らせる一方、工程状態の設定やテーマ作成まで全変更に要求すると、軽量な変更の負担になる。入口を分けても、要求・設計・実装・検証の正本や証明義務を別々に所有する必要はない。これは2026-10-15の棚卸しで整理した得失であり、過去の会話でこの比較どおり採否が決まったという記録ではない。双経路併存の正式な決定はDEC-058が所有する。

### 先行知見を使うことと、必要な結果を減らすことは別である

2026-10-12の議論統合ノート第18・19章には、開発プロセスやプロジェクト管理の先行知見と既存ADF能力を先に検討し、足りない外部AIとの受渡し・正規反映・工程間接続に固有の仕組みを設ける方針が合意として記録されている。一般的な工程や品質の概念を独自に再定義すると、既存の知見との対応説明や維持管理の負担が増えるためである。特定規格への全面準拠・認証や、標準の項目をそのまま公開操作へ写すことを意味しない。

簡素化の対象は実現手段であり、必要な成果、安全境界、検証義務ではない。既存成果物やGit履歴から根拠を確認できるなら専用の台帳を省けるが、根拠を確認できない状態を「軽量化したから合格」とは扱えない。新しい仕組みは、既存手段ではどの必要な結果を達成できないかが具体化したときに、追加負担と比較して再検討できる。規格の本文や個別条項を今回確認したという主張ではない。

### 過去に対象外とした方向と理由

- **基本設計・詳細設計・環境定義などを全案件の必須工程とすること**：工程を分ける必要性は案件によって異なり、軽量な変更に過大な負担を生む。
- **各設計責務について独立したDesign文書を一律に要求すること**：設定ファイルや既存成果物で設計内容と根拠が確認できる場合、別文書の存在自体は設計の妥当性を証明しない。ただし、プロジェクトが独立設計書を必須とした場合の欠落は別問題である。
- **工程の成立をIssueや進捗管理の有無で測ること**：追跡・分割・委譲にIssueが有用でも、工程の成果と要求充足を代理しない。
- **大規模な段階開発のための管理機能を、すべての小規模案件に先回りして適用すること**：多様な規模に対応できる構造と、常時その複雑さを負担させることは異なる。

これらは当時の適用範囲を判断した理由であり、将来の全案件に通用する禁止事項ではない。

### 新しい提案を評価する観点

工程や文書を追加する提案が出た際は、まず、その分離によって誰が何を確認・確定・引継ぎできるようになるのかを考える。独立した確認や引継ぎに意味がなく、同じ証拠を既存成果物から取得できるなら、工程や文書を増やす必要性は弱い。

一方、複数主体による段階確定、承認を要する中間成果物、異なる期間にまたがる作業などが現れれば、当初は省いた工程分離や成果物管理を再検討する価値がある。過去に「不要」とした理由と、現在の前提が一致するかを利用者へ示すことが判断材料となる。

## 適用条件

- v5.0.0・v5.1.0の工程構成、工程間の責務、成果物の確定単位を検討・改訂する場合
- 小規模の一気通貫実行と、段階的な開発・工程単独実行の両立を評価する場合
- 新たな必須工程、独立文書、Issue管理を提案する際に、その追加価値と負担を比較する場合

## 適用対象

ADF自身の工程駆動・変更駆動の設計検討、要件・設計レビューにおける非規範的な判断材料。ADF導入先のプロジェクトにこの知識文書全体を配布する必要はない。

## 根拠

- 2026-10-07〜08のChatGPTにおける工程分解・工程責務・一気通貫と大規模段階開発の議論。小規模開発を主な実験対象としながら大規模にも適用可能な構造を残し、過剰な作り込みを避けるという利用者の判断。
- REQ-104（共通責務、任意の詳細工程、単独・連続実行）、REQ-105（設計責務と独立文書の分離）、REQ-108（有限作業とIssue必要時利用）。
- DEC-053（v4で生じた工程・独立Design文書の一律必須化の問題とv5での選択）、DEC-055（工程独立実行の採用理由）。

- 2026-10-15の補強では、利用者提供の `adf-domain-knowledge-discussion-note-v07.md` 第2・3・7章と、`adf-v5.1-discussion-synthesis-2026-10-12-standards-agreed.md` 第1.1・15.2・17〜19章を参照した。これらは議論の整理記録であり、今回元の全会話を取得したものではない。双経路併存はREQ-111・DEC-058とも照合した。追加の得失整理と再評価例は、同日の棚卸し提案に対する利用者承認を経た今回の分析であり、過去の逐語的な採否記録とは区別する。
