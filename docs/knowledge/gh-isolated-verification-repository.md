# GitHub 版隔離検証環境の事前準備と常備方針（管理者側の用意前提）

## 知識内容

GitHub 版検証を必要とする完了条件・test strategy 項目がある場合、その検証環境は実行時の repo 作成ではなく、管理者による事前準備の隔離検証リポジトリの常備で用意する。Custom Tool `agentdev_gh` の操作カタログは repo 作成相当の操作を追加しない。この方針は既存の操作カタログ不拡張決定（DEC-045 決定3前半）の維持を含む。本書は検証環境の構築・運用・利用終了時の返却・クリーンアップの手順と責務を検証環境前提として記録する。方針の正は REQ 文書（`docs/requirements/REQ-116.md`）であり、本書はその実現面（用意前提の文書化）を記録する。

### 方針の判断根拠（検証方法の格下げをしない）

- GitHub 版検証を別手段（ローカル版のみの検証、代替の構造的等価性の主張）へ置き換えない。検証方法の格下げは既存規律と整合しないため選択しない。格下げを拒む根拠は3つある。合意済み検証方法の変更には同等以上の観測能力と未証明範囲不増を要求する規律（`docs/requirements/REQ-032.md` の REQ-032-037）。production-equivalent verification の定義（`docs/requirements/REQ-055.md`）。代替の構造的等価性を同等以上と認めない既存判断
- gh-write guard の fail-closed 拒否自体の緩和は解決手段としない。guard は生 gh 書込み迂回を fail-closed で拒否する契約を維持し、検証環境の用意は guard の迂回や緩和によらず行う
- 検証環境の用意は管理者による repo 外操作である。実行担当サブエージェント・workflow が repo を作成しない

### 構築手順と責務（管理者）

1. 検証専用の隔離リポジトリを管理者が GitHub 上に作成する（agentdev_gh を経由しない repo 外操作）。作成場所と命名は既存の隔離検証リポジトリ運用に従う。production リポジトリと分離する
2. 作成した repo の認証情報を、検証実行環境の正規の認証経路（実行環境側の非対話認証設定）で参照可能にしておく。設定手順の参照先は `docs/knowledge/git-noninteractive-auth.md` である
3. 作成日時・目的・担当を検証記録へ残し、以後の運用とクリーンアップの起点とする

### 運用手順と責務（検証実行者）

1. 検証実行前に、隔離リポジトリの存在と参照可否を読み取り操作（repo meta 照会等）で確認する。不在の場合は検証せず、管理者への用意依頼を再開条件として停止報告する
2. 検証の書込み操作は Custom Tool `agentdev_gh` 正規経路のみで行い、対象 repo を隔離リポジトリへ限定する。検証の実行記録（検証差分）へ用いた検証環境（隔離リポジトリの識別）を記録する
3. 隔離リポジトリへ production データ・資格情報の値を書き込まない

### 利用終了時の状態復旧と返却条件（検証実行者）

常備環境は個別作業の終了時に環境全体を削除せず、次の条件を満たして返却する。

1. 検証由来の残存物（test branch、test issue 等）の有無を確認し、残存物の報告と整理を行う。実行担当側で整理できる残存物は実行担当が整理し、実行担当側では整理できない残存物は管理者の後続処置の対象として明示して報告する
2. 常備環境を初期状態へ復旧する必要がある場合は、管理者へ状態の初期化依頼を返す。初期化の実施は管理者の後続処置であり、実行担当は依頼と現状の報告を完了する
3. 返却の成立は、管理者への通知だけでは成立と扱わない。受け手（管理者）、対象（隔離リポジトリ）、状態、残る処置、権限と、受領または既存の常設受入条件への適合を確認して成立させる
4. 後片付けの実施結果、確認根拠、未処理事項を既存の作業記録経路（検証差分、PR 本文等）へ返す。実行したという申告だけで返却の成立を認めない

管理者の後続処置（残存物の整理、状態の初期化、削除判断）が残る場合でも、実行担当の返却責任（残存物の報告と整理、初期化依頼、成立条件の確認）は別に成立する。両者を区別する。新しい確認フォームや毎回の人間の応答を一律に要求しない。

### クリーンアップ手順と責務（管理者）

1. 検証完了後、隔離リポジトリの状態を検証記録とともに確認し、検証由来の残存物（test branch、test issue 等）を管理者が整理する。検証実行者から報告された残存物と状態の初期化依頼は、管理者の後続処置の起点である
2. 常備を継続する場合は状態を初期化し、不要となった場合は管理者が削除判断する（削除は repo 外操作）

### 検証再開先

- 検証環境の用意後の再開入口は case-close とする。再開対象は、GitHub 版部分の検証を保留して完了できていない項目のうち、当該検証環境を前提とするものである。具体は Case #3779 完了条件2（TS-007）と Epic #3803 の TS-008・TS-010 の GitHub 版部分。本書の再開先記述は上記案件の識別子であり、本書を作成した Case の完了条件とは別案件である
- 検証環境の用意が外部要因（管理者側の準備不能）で不能な場合は、req-define へ差し戻して再評価する

## 適用条件

- GitHub 版検証を必要とする完了条件・test strategy 項目が存在する Case の実行時
- 隔離検証リポジトリの不在が検証継続を阻む場合の停止報告と再開判断時

## 適用対象

- GitHub 版検証を担う検証実行者（workflow・実行担当サブエージェントを含む）
- 隔離検証リポジトリの構築・クリーンアップを担う管理者
- 検証環境不在時の再開入口（case-close）と差し戻し先（req-define）の判断者

## 補足

- 本書は検証環境の用意自体を実行する手順書ではなく、検証環境前提の記録と接続先の正である。検証対象の完了条件・test strategy 項目側から本書を参照して前提を確認する
- 操作カタログ拡張（repo create 相当）、gh-write guard の緩和、admin による実際の repo 準備の実施は、当該方針（REQ-116）の対象外とする後続判断領域である
