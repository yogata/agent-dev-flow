# ADR-003: req_draft ソフトコントラクト原則

## 背景

req-define が生成するコマンド間ドラフト（req_draft）の取り扱い方針として、ソフトコントラクト原則を採用する。
ソフトコントラクトとは、提供側が意味付けを定め、利用側が LLM 推論で解釈する基準である。
後続コマンド（req-save、spec-save、case-open、case-auto、case-run、case-close）は構造化フィールドを LLM 推論で読み、機械的な schema 検証を行わない。

この原則を維持する。
一方で、req_draft 形式が工程間合意、Wave 構成、実行順序、artifact_actions 等、複数の役割を担って肥大化している。
憲章（ADR-001）は決定4で新規統制の追加を抑制し、決定5で draft 形式を縮小形式へ統一することを定めた。
縮小形式は合意内容の伝達に集中するため、完成本文、Wave 構成、実行順序、artifact_actions を req_draft から外す。

本 ADR は、ソフトコントラクト原則を基準として確立し、縮小形式との組合せで req_draft の責務を合意内容の伝達に限定する。
厳格 schema の導入は憲章決定4 の新規統制追加にあたり、本 ADR は採用しない。

## 決定

req_draft をソフトコントラクトとして設計する。
後続コマンドは構造化フィールドを LLM 推論で解釈し、機械的な schema 検証を行わない。

縮小形式を採用し、req_draft が持つセクションを次の8つに限定する。

- **背景**：要件に至る文脈
- **問題**：解決対象の課題
- **合意済要求**：ユーザーと合意した要求事項
- **制約**：実装、運用、文書上の制約
- **対象外**：本 req_draft が扱わない事項
- **受入条件**：要件の受け入れ基準
- **重要決定**：実装、設計、運用上の決定事項
- **入力参照**：RU、promoted 成果物、関連 REQ/ADR の参照

次のセクションは廃止する。

- artifact_actions（完了本文相当の実行指示）
- 完成本文
- Wave 構成
- 実行順序
- 未解決事項なし

これらは下流工程（case-open、case-run、case-auto）の SSoT が所有する情報であり、req_draft の合意内容ではない。
未解決事項は req-define の完了を持って解消済とし、req_draft には持ち込まない。

## 結果、影響

形式の縮小により、req-define の出力と後続コマンドの解釈責務が分離する。
req_draft は合意内容の伝達に専念し、実行計画は下流工程の SSoT が所有する。

次のリスクを受入れる。

1. **QG 決定性との矛盾**：運用フィールド（受入条件、制約等）が LLM 推論で非決定的に解釈される可能性がある。同じ req_draft でも実行や LLM バージョンごとに判定が変動し得る。
2. **提供側と利用側の暗黙のズレ**：schema バージョン管理をもたないため、req-define の出力進化時に利用側へ破壊的変更の信号が伝わらない。
3. **テスト困難性**：req_draft 解釈の決定的単体テストが困難である。LLM 呼出または並行するパーザ試験 harness が必要になる。
4. **デバッグ不透明性**：不正解釈時の根本原因が曖昧になる。プロンプトや命名の調整で対応し、schema 編集では対応できない。

軽減策として、docs-check と integrity-check は主要フィールド名の存在をズレ検出の対象とする。
厳格な検証器ではなく、ドリフト検出として運用する。
提供側基準の詳細は SPEC（`docs/specs/responsibilities/artifact-contracts.md`）が定義し、フィールド進化時の参照点を提供する。

憲章決定4 との整合：厳格 schema は新規 hard control にあたるため、本 ADR はソフトコントラクトにより追加統制を回避する。
フィールド追加、名称変更、セクション構成の調整は SPEC（artifact-contracts.md）の改訂で扱い、本 ADR の改訂を要しない。
ただし意味的変更（ソフトコントラクトの放棄、縮小形式の破棄）は新規 ADR を作成して本 ADR を置き換える。
