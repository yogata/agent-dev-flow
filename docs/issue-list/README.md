# 課題管理（docs/issue-list/）

`docs/issue-list/` は課題ファイルの正規配置先である。
要件定義、方式設計、HLD、LLD、パラメータ設計、実装、レビュー、検証、外部確認等で生じた未解決事項を、発生から検討、保留、解決、正規成果物への反映確認まで継続して追跡する。

課題ファイルは永続的な git 管理対象の正規成果物であり、`.agentdev/` 配下の一時成果物とは扱いを区別する。
操作（検知、新規起票、検索・参照、更新、検討経過の追加、保留、再評価、解決、反映確認、クローズ、再オープン）は課題管理 Capability Skill（`agentdev-issue-tracking`）が提供する。本 README は配置基準と運用規則を定め、形式の詳細（状態別必須項目、記述形式、テンプレート）は当該スキルの参照資料（`references/issue-file-format.md`）を正とする。

## 他系統との分離

課題管理は次の系統とは別系統の責務である。未解決事項の保持をこれらの系統へ代行させない。

| 系統 | 責務 | 課題管理との違い |
|---|---|---|
| Intake / Learning | AI 駆動開発の改善循環（検出事項、学びの取り込み） | 改善循環であり、未解決事項の追跡ではない |
| GitHub Issue | req/case パイプラインの作業単位 | 実装対象となった作業単位であり、未解決期間の問いの保持を目的としない |
| Decision | 判断理由を保持すべき解決結果 | 解決後の正規化手段であり、未解決期間の追跡手段ではない |
| RU | 変更要求 | 課題解決後に変更実施が必要と判断された場合の成果物であり、課題そのものではない |

## 課題 ID とファイル命名

| 項目 | 規約 |
|---|---|
| ID 形式 | `ISL-NNN`（`ISL` は `docs/issue-list/` に由来する接頭辞、`NNN` は3桁ゼロ埋めの通番） |
| 採番規則 | 既存課題 ID の最大番号に 1 を加えた番号。廃止済み番号は再利用しない（欠番維持） |
| ファイル名 | 課題 ID + `.md`（例: `ISL-001.md`） |
| GitHub Issue 番号との識別 | GitHub Issue 番号は `#NNNN` 形式の純数字参照であり、`ISL-` 接頭辞とハイフンを持つ課題 ID とは機械的にも人間にも混同できない |

## 状態

状態は各課題ファイルの frontmatter `status` が保持する。1課題1ファイルとし、状態が変わってもファイルを移動しない。解決済み、クローズ済みの課題も本ディレクトリに残置し、同一体系内で履歴として追跡する。

| 保存値 | 意味 |
|---|---|
| `open` | 未着手 |
| `in-progress` | 検討中 |
| `on-hold` | 保留（判断保留の理由と再評価条件を保持） |
| `resolved` | 解決済み（結論が出た状態。対応不要を含む） |
| `closed` | クローズ済み（必要な反映または反映不要の確認まで完了した状態） |

`resolved`（結論が出た）と `closed`（反映まで確認した）は区別する。

## 保持情報

各課題は次の情報を保持できる。課題にとって不要な項目は省略できる。

- frontmatter: 課題 ID（`id`）、件名（`title`）、状態（`status`）、起票日（`created`）、最終更新日（`updated`）、関連成果物（`related_artifacts`）、担当（`owner`）、期限（`due`）、再評価条件の要約（`reevaluation`、保留状態で必須）
- 本文: 課題内容、背景、影響、関連成果物、現時点の選択肢、判断材料・証拠、不足情報、再評価条件、検討経過（追記専用）、結論、反映先、クローズ確認

保留状態の課題は、なぜ現在判断できないか（判断保留の理由）と、何が成立すれば再評価するか（再評価条件）を本文「再評価条件」セクションで識別できるようにする。解決済みの課題は結論を保持し、クローズ時は反映先または反映不要の理由を確認できる。

## 検査区分

課題ファイルは検討経過を保持する履歴系文書であり、文意品質検査（`agentdev-doc-writing`）における現行文書基準の適用対象外とする。検討経過の追記は履歴記録であり、追記時点の現行文書品質基準（一文一行の整形、用語の統一等）での全面書き直しを求めない。

本 README（形式定義と運用規則）は現行文書として文意品質検査の適用対象である。

## 運用規則

- 課題起票時点で反映先を決め打ちしない。反映先は解決時点で確定し、課題ファイルの「反映先」に記録する。
- 課題の解決結果は Decision、REQ、HLD、LLD、その他の Design、パラメータ設計、RU、実装、検証方法、対応不要のいずれにもなり得る。課題の対象を特定の粒度に限定しない。
- 正規成果物への反映は当該成果物を所有する ADF 能力へ委譲する。課題管理側は結論、反映先、反映状況の追跡に徹する。
- 課題をクローズする前に、必要な反映が完了していること、または反映不要であることを確認する。解決済みで反映が未完了の課題はクローズしない。
- 課題ファイルの変更は、実施中の工程の成果物コミットに含めて永続化する。

## 到達機構

すべての ADF コマンド実行時に本ディレクトリの全文を読み込むことを要求しない。
課題の検索・一覧には課題管理 Capability Skill の決定的スクリプト（`scripts/src/list.ts`）を用いる。同スクリプトは各課題ファイルの frontmatter（最初の `---` ブロック）のみを解析し、状態（`--status`）、関連成果物（`--related`）、課題 ID（`--id`）で必要な課題へ到達できる。保留課題の再評価条件は frontmatter `reevaluation`（要約）と本文「再評価条件」セクション（詳細）で保持し、`--status on-hold` で到達する。
