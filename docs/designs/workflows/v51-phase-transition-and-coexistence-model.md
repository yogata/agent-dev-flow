# ADF v5.1 工程遷移・独立レビューと双経路併存モデル

## 目的と適用範囲

本 Design は REQ-111 が定める工程遷移、独立レビュー、有限作業、変更駆動との併存に関する内部設計の要綱を示す。公開操作の最終名（phase-tasks-create、phase-tasks-update、phase-artifacts-update、phase-review、phase-transition）と保存方式（.agentdev/phase/ 配下の保存状態）は実装・公開済みである。Capability Skill 等の具体的なスキル構成の分担と個別 command Design の整備は確定していない部分であり、外部動作と検証義務を保つ範囲で後続設計に委ねる。

## 工程遷移

工程の完了・遷移は利用者が判断する。遷移操作は確定した工程関係と既知義務を次工程へ渡し、前工程を完了済みの過去工程として一回だけ記録する。利用者が取消した場合は現在工程を維持する。工程の解決不能、永続化失敗、中断後の再実行では成立済みの状態を正規記録から復元し、未成立の技術処理を成功として扱わない。

採用済み工程関係に後続工程がない場合は終端として扱う。後続が1件なら一意に選び、複数件なら利用者の選択を求める。複数の前置工程がある場合は既知義務と未確認範囲を保持して引き継ぐ。遷移後の初回テーマ形成は遷移成立と独立させる。

採用済み工程関係に後続工程がない終端の遷移は、架空の後続工程を作らない記録形式で遷移記録へ保存する。終端の記録形式（後続不在を表す toPhase の表現を含む）は phase-transition 配下の決定的処理 script が所有する schema が定め、保存された記録から終端であることを再構成できる。

終端の遷移後、当該工程の工程駆動の保存状態（テーマ正本、識別状態、遷移記録）は参照専用として保持する。参照専用の保持は、完了済み過去工程の正規改訂（REQ-111-008）と変更駆動経路による作業を妨げない。テーマ正本のテーマ状態（active、merged、deprecated）に完了状態を追加せず、テーマの消化をもって工程の完了を記録・証明しない。

遷移記録の保存は、同一識別キーで遷移の意味内容（対象範囲・遷移元・遷移先）が一致する要求のみを既存の成立済み遷移の復元（duplicate）として扱う。いずれかが異なる要求は同一の成立済み遷移として復元せず、成立済み遷移の記録を上書き・置換せず、不一致を報告して記録を保存しない（fail-closed）。記録ファイル名は識別キーから決定的に生成されるため、同一キーの異内容を別記録として保存すると既存記録の上書き消失を招く。記録時刻（recordedAt）は記録メタデータであり、同一遷移の正当な再実行でも一致しないため内容照合の対象に含めない。内容同一性照合の規律は外部戻り入力の受理（agentdev-phase-theme-collaboration の receive）で実証済みの「同一断定禁止・fail-closed」規律を、固定フィールド構造（key、scope、fromPhase、toPhase、recordedAt）にはフィールド値直接比較として転写して適用する。

遷移記録領域または既存記録の読取が技術的に失敗する場合（記録領域の列挙・読取が存在確認不能に失敗する場合を含む）は記録不在として扱わず、確認不能（error）として報告し、確認不能な既存状態の上へ遷移記録を保存しない。記録領域自体の不存在のみを記録不在として扱う。既存記録ファイルの読取失敗・JSON 破損・schema 違反を error として扱う既存契約は維持する。

遷移後の現在工程の特定・再開は、遷移記録と現在工程の識別状態（identity）を照合し、矛盾を検出した場合は遷移記録に依存する操作を保留して矛盾を報告する。次工程の初回テーマ形成が未実施・失敗でも、別セッション再開でも、成立済み遷移と既知義務は遷移記録から再取得する。

工程遷移の引渡しは、採用済み事項・上流の制約・未決事項・参考候補を区分して引き渡し、遷移先の次工程で各区分を区別して再取得できる。前置工程が複数ある場合は各前置工程の区分を欠落なく統合する。参考候補を正式な採用済み要求へ変換せず、未決事項を自動解消せず、別取組・別版の情報を区分外へ混入させない。

## 独立レビュー

独立レビューは既定要求、対象成果物、検証証拠と照合し、確定違反、証拠不足、推測、未採用改善候補を区別して所見を示す。テーマの解消や構造上の成立だけで要求充足・工程完了を認定しない。レビューを工程完了の必須ゲートとせず、レビューの深さも必須基準にしない。

## レビュー所見の成果物修正への引き継ぎ

phase-review が提示した所見のうち、利用者が明示的に採用した対象のみを成果物更新の正規経路へ引き継ぐ。採用範囲と判断根拠を維持し、未採用・採否不明の所見を修正確定済みの要求として扱わない。所見の自動採用と独立レビューの必須工程化は行わない。

引き継ぎでは、対象成果物、参照する要求、元の指摘内容、判断根拠を誤転記や意味変更なく利用する。対象箇所の特定に行番号だけを依存条件としない。実際の修正前に最新の正規成果物を照合し、指摘内容が現在も成立することを確認する。誤所見、既に解消済みの所見、対象を一意に特定できない所見は、そのまま修正に使わない。

同時に採用された複数所見の一部が不成立・衝突・未確認でも、独立して安全に修正できる部分を反映し、保留部分の理由と必要な確認を区別して報告する。反映結果は実際の成果物変更と照合して反映済み・未反映・保留を確認し、修正指示の生成・作業開始・保存操作の成功だけを反映完了の証拠としない。

一部反映後に中断した場合は、現在の成果物と採用済み所見を照合して残る必要な修正だけを継続する。所見の反映状況は、元の所見、採用判断、正規成果物、実際の変更事実から再構成し、第二の管理台帳を作らない。採用後の修正は既存の正規成果物管理経路（phase-artifacts-update と各成果物管理スキル）に接続し、新しい承認段階を一律に要求しない。

## 有限作業と実装接続

利用者が要件確定または設計確定だけを求めた場合は、その有限作業と正規成果物・技術的根拠を確定して終了する。Issue、PR、後続実装を一律に要求しない。利用者が確定済み詳細設計、有限な実装対象、既存検証条件を示した場合は、最新の実リポジトリ、対象、依存、証拠を確認して実装・検証へ接続する。未検証結果は未検証として報告する。

「有限作業と実装接続」節への追記（target_area: 有限作業と実装接続）。採用した工程構成に基づく
単独工程・連続実行の実行接続: (1) 単独工程の実行境界 — 要件確定のみ・設計確定のみ・確定済み設計
からの実装・検証のみの各単独工程は、採用規約の解決結果（REQ-104-009 の接続）を実行基準として
参照し、対象作業に必要な成果物と検証の成立を確認して独立完了する。後続実装・Issue・PR の一律
要求と要件定義への無条件復帰を実行経路に組み込まない。(2) 一気通貫実行 — 採用規約で詳細工程を
必須としない小規模案件は、正規利用経路（req-define → case-auto、または工程駆動の連続利用）で
要件から検証まで連続実行し、不要な工程・独立文書・Issue を生成しない。完了判定は各段階の検証
証拠に基づく。(3) 中断・再開の実行境界 — 採用済み・未決・試作・成立済み作業を含む状態での再開は
REQ-108-006 の既有義務に従い、実際の正規状態から必要な範囲だけ継続する。既存の実行主体と責務境界
（case 系 workflow、実行担当 subagent、harness）は変更しない。

実行接続の実装所在（反映確認）: 上記 (1)(2)(3) の実現面の接続先は、case-auto orchestration の実行境界を case-auto workflow 実装本体（`agentdev-workflow-case-auto` スキル「v5 有限実行モード」節。モード契約の「単独工程の独立完了」「v5 小規模連続実行モード」「再開」「変更駆動能力群の維持と横断検証義務」各条項）が所有し、実装・検証のみの単独工程の実行は case-run 委譲契約（`agentdev-workflow-case-run` スキル「単独工程からの実装・検証接続」節）を再利用し、要件確定のみの単独工程の入口接続は req-define command（不変条件の要件確定のみの単独工程条項）が所有する。対応関係の正は repository top-level `traceability/` 配下 sidecar が保持し、本 Design は実装所在を重複定義しない。

## 過去工程の改訂と影響伝播

完了済み過去工程の改訂における下流の更新・再検証の完遂確認は、次の経路で行う。差分・影響評価の能力と出力契約は agentdev-traceability Design「relied-diff（依拠版に基づく差分・変更影響 CLI）」節の第1段階共通能力を利用し、本 Design は工程管理側の消費と完遂確認を所有する。
- 全下流の列挙: phase-artifacts-update による完了済み過去工程の改訂では、採用した工程間関係（隣接工程間対応）に沿って、変更起点から影響し得る必要な全下流工程を列挙する。中間工程の更新不要の評価で列挙と後続評価を打ち切らない。正味差分ゼロ・明示対応関係空の下流も列挙から黙って除外しない（REQ-106-005、REQ-106-007、REQ-106-012）。
- 影響評価の入力: 各下流工程の影響評価は、第1段階共通能力の出力（依拠版基準の影響分類、旧証拠の上流整合、fullyPropagated、propagationRequired、未確認事項）を入力として取得して行う。共通能力を再実装せず、工程開始時点の版を無条件の比較基準としない（REQ-106-001、REQ-106-011、REQ-111-008）。取得失敗・比較基準解決不能は未確認として扱い、完了側に含めない（REQ-106-003、REQ-106-010）。
- 完了判定: 影響分類ごとに必要な処理を実行し（更新必要→更新と再検証、更新不要→現行上流との整合を示す根拠の確認、作成→作成と検証、未確認→確認の解消または完了側からの除外）、実際の成果物・検証結果と照合して変更反映完了を判定する（REQ-106-013、REQ-106-016）。判定の材料（影響分類、実施した更新内容、検証結果、残る未確認事項）を実際の成果物・検証結果と照合できる形で保持する。既存の変更・検証記録、正規成果物、Git履歴を利用し、全成果物の版台帳・汎用依存グラフ・専用履歴データベース・第2の管理台帳を新設しない。
- 再開: 一部成立での中断後は、実際の成果物と検証結果から各下流対象の成立状態を再構成し、未成立の処理だけを継続する。成立済み更新の再適用による内容の重複を生じない（REQ-106-015）。処理失敗時は現在工程までの全反映完了を宣言せず、再開に必要な情報を示す（REQ-111-008）。
- 通知の時点区分: 正規反映の前の事前通知、実行中に新たな影響が判明した場合の追加通知、反映後の結果説明を、改訂の実行記録から時点を区別して確認できる形で行う（REQ-111-026）。通知の内容義務と通知と承認の区別は REQ-108-014〜REQ-108-023 の既有義務に従い、本 Design は時点区分の確認可能性を追加する。時点区分の確認に用いる実行記録の所在と形式は、本 Design の運用規律と既存の工程駆動の保存状態の範囲で定める。
- 承認範囲: 改訂は有効な承認の対象・内容・範囲に従って実行し、承認されていない内容を改訂に含めない。実行記録から、適用した承認の範囲と実際の変更内容の対応を確認できる（REQ-111-025）。現在工程を巻き戻さない規則（REQ-111-008）と、無影響部分の無条件な再生成・変更発生のたびの全成果物再生成の対象外規定（REQ-106 適用範囲）を維持する。

「通知の時点区分」項への追記（target_area: 過去工程の改訂と影響伝播）。時点区分の確認に用いる実行記録の所在と形式を次のとおり確定する。実行記録は改訂実行記録（1改訂1ファイル、JSON）として .agentdev/phase/revisions/ へ保存する。保存先・様式の正は領域契約テンプレート（templates/phase-readme.md）の「revisions/ の様式」である。時点区分の語彙は pre（正規反映前の事前通知）/ in-progress（実行中の追加通知）/ post（反映後の結果説明）とし、同一区分の複数回を許容する。実行中の追加通知は、新たな影響が判明するたびに複数回行い得るため、記録側で回数を上限化しない。語彙外の区分と記録参照の空は決定的処理 script が非ゼロ終了で拒否する。変更反映完了の判定、完了側に含めない対象、再開に必要な情報は同一の script から決定的に導出する。判定の機械規則は Capability Skill agentdev-phase-theme-collaboration の scripts（lib/revision-record.ts）に実装する。機械規則の内容は、影響評価の入力が未解決の場合に全下流対象を完了側から除外すること、更新実施・作成実施に検証結果を必須とすること、更新不要に現行上流との整合根拠を必須とすること、旧証拠の適用可能性が stale・unconfirmed の対象を完了側から除外すること、未処理・処理失敗を再開対象として列挙すること、承認範囲の記録が空の場合は記録を確定させないこと、である。

## 外部検討結果の受入経路との分離

phase-review の所見と外部AIからの戻り入力は別の概念として扱う。外部AIから受領した入力を intake inbox へ自動投入しない。採用する場合は根拠を示す受理経路を通し、Learning / Intake の既存責務と混同しない。

## 双経路併存と移行

変更駆動（req-define → case-auto）と工程駆動（4操作と利用者判断による工程遷移）は独立した正規利用経路として併存する。変更駆動は工程駆動の操作・遷移を前置必須とせず、従来の外部的な作業結果と検証義務を維持する。旧コマンド名や旧内部構造の一致は合否条件としない。後継経路の実現・検証・正式採用が成立するまでは REQ-108-012 に従って現行経路を正として扱う。設計PR の作成・マージだけでは、後継経路の実現・検証・正式採用を満たさない。

「双経路併存と移行」節への追記（target_area: 双経路併存と移行）。両経路の実行接続と切替の設計補強:
(1) 5操作の実行接続 — GitHub 版と Local 版の各公開入口は 5操作（phase-tasks-create、
phase-tasks-update、phase-artifacts-update、phase-review、phase-transition）を同一の操作契約で
接続し、入力・状態・判断・保存結果（.agentdev/phase/ 配下の保存状態、正規成果物への反映、遷移記録）
の扱いが両環境で意味上同等になることを確認する。(2) 双方向の再利用 — 工程駆動で形成した正規成果物
の変更駆動での改訂と再利用、および逆方向は、既存の保存・確定経路の所有境界（case-ready/case-revise
と phase-artifacts-update、各成果物管理スキルへの委譲）を通し、更新結果を他経路が古い状態のまま
参照しない（正規成果物の現行版からの再読み出し）。(3) 切替時の情報保全 — 後継経路への切替は
REQ-109 の意味保存・検証の契約に従い、有効な正規情報・必要な参照・未処理情報の継続性を切替前状態と
照合する。(4) Local 版の結果確認 — 実装を伴う作業では実行報告と実際の Git 取り込み結果の独立照合
を実行手順に組み込み、成功報告単独での取り込み完了判定をしない。既存の「双経路併存と移行」節の
権威継続の記述（REQ-108-012、後継経路採用まで現行経路が正）は変更しない。

## 実行主体と責務境界

| 操作 | 実行主体分類 | 責務境界 |
|---|---|---|
| 独立レビュー | Workflow Skill と GitHub／Local の公開入口 | Skill が所見区分と意味評価を担い、入口は両版の正規利用経路へ接続する。レビューは工程完了ゲートにしない |
| 工程遷移 | 公開操作（command／adapter）と harness の状態保存 | 利用者が遷移を決定し、操作は正規状態の一回記録、再開、失敗報告を担う |
| 確定済み設計からの実装接続 | case 系 workflow、実行担当 subagent、harness | 既存 case 実行契約を再利用し、最新リポジトリの実変更と検証証拠を確認する |

公開名（phase 系 5 公開操作）と保存実装（.agentdev/phase/ 配下の保存状態）は確定済みである。既存 case 系実行契約および REQ-009/106/107/109 の契約を重複定義しない。
