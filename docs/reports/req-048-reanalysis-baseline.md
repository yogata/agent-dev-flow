# REQ-048 再分析比較基線と再分析手順

REQ-048（ADF 実行効率第1次改善）実施後の再分析に用いる比較基線と再分析手順を記録する観測記録である。
識別情報の記録契約の正規仕様は workflow-contracts Design「ADF 実行識別情報の記録契約」が、テンプレートセクション形式は agentdev-workflow-templates Design「実行識別情報・検証差分のテンプレートセクション形式」がそれぞれ正である。
本資料は既存正規成果物（Report）への保存であり、識別情報記録専用の新規成果物種別や実行履歴 DB を新設しない（DEC-017 準拠）。

## 目的

本要件の実施後に ADF 実行を再分析した際、改善前の分析と同一の定義で指標を算出し、改善前後を比較できる状態を保証する。
改善前分析で用いた定義を本資料に保存し、再分析手順が当該定義から逸脱しないことを機械的に確認可能にする。

## 比較基線（改善前分析の定義と実測値）

### 分析対象とデータ源

改善前分析は、分析時点（2026-08-22）から直近30日間の ADF 実行を OpenCode の永続セッションデータから分析した。
出所は RU-0001（消費済み）第2節・第4節である（git 履歴 `git show 55853b4f:.agentdev/backlog/req-units/RU-0001.md` で参照できる）。

### 用語の定義

| 用語 | 定義 |
|---|---|
| 論理実行単位 | ADF の1実行に対応する集計単位。委譲起動を単位とする親子セッション群を1単位とする。改善前分析では read を伴う実行を計上対象とした（97単位）。再分析では委譲単位識別子 `DEL-{N}-{seq}` で機械的に区分する。導入前の実行は委譲 prompt を含むセッション境界からの従来区分を併用する |
| 正規化 path | source（`src/opencode/...`）と projection（`.opencode/...`）の対応する双方の経路を同一 path へ対応させる正規化規則。改善前分析では167正規化 path を検出した |
| 集計方法 | 期間内の全セッションを論理実行単位へ区分し、単位ごとに token（input、output、cache read、cache write の総計）、tool call（read の対象 path）、子セッション間の重複を集計する。token、model、tool call 等の詳細履歴は OpenCode 側のデータのみを用い、ADF 側へ複製保存しない |

### 指標と改善前実測値（基線値）

| 指標 | 改善前実測値 | 再分析での算出方法 |
|---|---|---|
| 論理実行単位当たり token | 総計約 67.9 億トークン（49,157 回のモデル呼出し。大半を cache read が占めた）を97単位へ配分 | 論理実行単位ごとの token 総計を集計し、単位当たり値と分布を算出する |
| token 分布 | 大半を cache read が占める集中分布 | 単位ごとの token を順位付けし、集中度（上位単位の占める割合）と cache 構成比を算出する |
| 同一 path 再読込 | 97単位中78単位で同一 path の複数回読込 | 同一論理実行単位内で同一 path への read が複数回発生した単位数を計上する |
| 子セッション間の同一 path 再読込 | 97単位中68単位で子セッションをまたぐ同一 path 読込 | 親子セッションをまたいで同一 path が read された単位数を計上する |
| source / projection 重複参照 | 35単位で双方の経路が参照され、167正規化 path、931 read が該当 | 正規化 path が同一の source と projection の双方へ read された単位数、正規化 path 数、read 数を計上する |
| 工程間の同種検証 | case-run 側と case-close 側で同じ種類の検証が行われる実態を確認 | 検証種別（bun test、distribution boundary gate、docs-check 等）ごとに、同一 Case の複数工程での実施有無を対応付けて計上する |
| 新規・修正・既出 finding | 構造化されていない（自由文から再構成） | PR 本文・Issue コメントの検証記録から新規、修正済み、既出を分類する。5分類（撤回・無効を含む）の機械化は検証差分セクション導入（Area4）後に行う |
| 対応付け率 | 改善前は全 Case を安定して集計できる専用識別情報なし（自由文再構成のみ。機械対応付け率は実質 0%） | 期間内の論理実行単位のうち、対象 Case、GitHub Issue、GitHub PR、実行単位、ADF 工程を識別情報（`adf_` key、委譲識別情報ブロック）のみで対応付けできた単位の割合を算出する |
| 構造化された文脈引き継ぎの利用状況 | 委譲 prompt に統一された構造化契約なし | 委譲 prompt・工程間引き継ぎに構造化契約（委譲識別情報ブロック、構造化文脈）を含む論理実行単位の割合を算出する（構造化文脈は Area2 実装後に有効化） |

## 再分析手順

1. 期間を設定する。改善前分析と同一の期間長（30日）とする。
2. OpenCode の永続セッションデータから message、part、tool call、token 生成元情報を読み取り専用で抽出する。書き込み、スキーマ変更、形式変換を行わない。
3. 論理実行単位へ区分する。識別情報セクションまたは委譲識別情報ブロック（`DEL-{N}-{seq}` 形式）を含む実行は当該識別子で機械区分する。導入前の実行は委譲 prompt の特徴による従来区分を併用する。
4. 指標を定義表と同じ定義で算出する。定義から逸脱が必要になった場合は、逸脱内容と理由を再分析記録に明記する。
5. 本資料の基線値と比較し、比較表として再分析記録に残す。

手順を手順書として整備し、集計スクリプトを新設しない。
OpenCode 内部構造（永続データの物理形式）への依存を配布物に持ち込まないためである。
将来の機械化は、本資料の定義を変更せずに手順2〜4をスクリプト化する形で行える。

## 境界（横断制約の記録）

- 本資料の整備と識別情報の記録は、サブエージェント数、並列度、REQ、Decision、Design、Skill、reference 等の文書、case-run の検証、case-close の検証、独立レビューを削減しない。削減要否は再分析の観測結果から判断する。
- 再分析は OpenCode の永続セッションデータを読み取り専用で使用する。OpenCode 本体、harness 内部の context 管理方式、provider の token 計測または課金方式、OpenCode DB スキーマの変更を条件としない。
