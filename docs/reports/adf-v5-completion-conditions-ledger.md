# ADF v5 完遂条件台帳（様式・作成・更新手続き）

本台帳は REQ-110（ADF v5 完遂判定の強制）と DEC-057 の実現面として、完遂条件体系（G0〜G10、4領域構成）の判定・証拠対応を保存する監査記録（Report）である。正規原本は docs/requirements/REQ-110.md、docs/decisions/DEC-057.md、docs/designs/quality/v5-completion-judgment.md（「G4 反例カタログ（期待挙動表）」「完遂条件台帳の様式」節）である。

本台帳は Report（docs/reports/）であり、Design インデックスの管理対象外である。恒久台帳を新設しない（REQ-103-017）。判定・証拠の確定記入は完遂判定（case-close QG-4 最終完了判定）の実行時に本台帳の手続きに従って行う。本台帳自体が管理機構としての継続更新義務を所有せず、確定記入は QG-4 実行ごとの監査記録として保存される。

初回整備は Wave-1 Issue #3578（親 Epic #3575、委譲識別子 DEL-3578-1）が行った。本 Issue は様式・作成・更新手続きと反例投入の実行基盤までを所有し、48項目すべての判定・証拠の確定記入は対象外である。

## 台帳の様式

各台帳項目は次の記録要素を持つ。

| 記録要素 | 内容 |
|---|---|
| 条件ID | `G{N}-{NN}`（ゲート番号 N は 0〜10、条件番号 NN はゲート内 2 桁連番） |
| 領域 | 工程・成果物／差分・影響・追跡／実行・改善循環／移行 の 4 領域 |
| 対応要件行 | `REQ-NNN-MMM`。REQ-104〜109 の全義務行（本 Case による追加行を含む）。1 行が少なくとも 1 つの台帳項目へ対応する |
| 判定 | pass / fail / blocked / not applicable の 4 値 |
| 証拠参照 | PR・Issue コメント・監査記録・実行ログの所在 |
| 判定時刻 | 判定を行った日時 |
| 判定主体 | 判定を行った工程・委譲単位の識別子 |

判定値と Gate 判定値（pass / warn / fail / partial）への写像は v4-quality-gate-model Design「判定値と遷移接続」節の正規所有契約に従う。完了条件単位の pass / warn / fail / partial への写像では必須条件の未達・未証明を Gate 全体の warn で通過させない。完遂条件台帳の判定（pass / fail / blocked / not applicable）と Gate 判定値は別物であり、本台帳は Gate 判定値の定義を所有しない。

## 作成・更新手続き

1. **確定記入**: QG-4 最終完了判定の実行時に、各条件IDへ判定・証拠参照・判定時刻・判定主体を記入する。判定の根拠は QG-4 の既存証拠チャネル（QG-4 結果コメント・suite 実行ログ・SSoT コメント）と PR 本文検証差分セクションへ到達できること。
2. **合意文書照合**: 台帳確立時に合意文書本文（session:2026-10-09-adf-v5-completion-conditions、RU-0195 の合意の正投影）との照合機会を設ける。本文が入手可能な場合、各ゲートの定義本文と 48 受け入れ条件の確定列挙を本文と逐語照合したうえで条件行へ展開する。照合を実施した日時と入手した本文の所在を証拠参照へ記録する。
3. **条件行の展開**: ゲート行（G0〜G10）を親として、条件行 `G{N}-{NN}` を追加する。条件行の追加は合意文書照合と QG-4 実行時の記入のいずれかを契機とし、追加した行に対応要件行を割り当てる。
4. **追加行への対応**: 本 Case 以降に REQ-104〜109 へ追加された義務行は、少なくとも 1 つの台帳項目へ対応付ける。対応のない義務行が発生した場合、QG-4 実行時に欠落として検出されなければならない。
5. **反例検証の実行記録**: 反例投入ハーネス（後述）の実行ごとに、反例識別子・期待挙動・判定・証跡参照・判定時刻・判定主体を「G4 反例投入の実行記録」節へ追記する。
6. **偽陽性の記録**: 検証器偽陽性を検出した場合、対象機能の判定ではなく検証器側を fail として扱い、「検証器偽陽性の確認記録」節へ記録する（REQ-110-003）。

### 反例識別子と期待挙動

反例識別子 `G4-X01〜X14` は v5-completion-judgment Design「G4 反例カタログ（期待挙動表）」の行順に対応する。期待挙動の値は次の 4 値とする。

| 期待挙動値 | 意味 |

| reject | 拒否。入力を合格としない |

| recover | 回復。正規入力からの再開・冪等経路の確認を経て継続する |
| verifier-fail | 検証器側を fail として扱う |

### 隔離環境の実行規則

- 反例投入は隔離環境（OS 一時ディレクトリに構築した模擬環境）で実行し、リポジトリの正規状態へ書き込まない（REQ-110-002）。
- ハーネスの識別規則は Design の期待挙動表と REQ の義務行から導出し、実装の実行結果から生成しない。
- ランタイム経路自体で test 再現できない反例（workflow 実行の実測、外部副作用を伴うもの）は、検証ハーネスとして分離した手続きで投入する。本ハーネスは構造的に test 再現可能な反例を bun test で実行する。
- 偽陽性確認は同一ハーネスで実行する。合格とすべき正常系投入と反例投入の双方で、不合格の合格化と正常系の誤不合格化の双方の有無を確認する。偽陽性を検出した場合、検証器側を fail として扱い本台帳へ記録する（REQ-110-003）。
