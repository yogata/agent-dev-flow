# 構造再編と過去工程改訂

`phase-artifacts-update` が構造再編または完了済み工程の改訂に進む場合の分岐手順。

## 構造再編

対象成果物と項目、分割・統合・移動の別が明示された場合のみ受理する。対象・権限が不明なら保留して候補と不足を示す。内容変更は別に許可された場合のみ行う。専用モードを新設せず、成果物種別ごとの管理スキルへ既存の採番・配置・照合・状態規則で委譲する。分離・統合される内容は元の status を引き継ぐ。

| 確認段 | 完了条件 |
|---|---|
| 適用前 | 識別子衝突、移動先不明、項目重複を検出し、該当部分を保留・報告 |
| 適用後 | 識別子・件数・参照を機械的に突合し、内容の同等性、参照と索引の整合を別に確認 |
| 再開 | 記録と実ファイルで成立済みと未成立を確認し、未成立部分だけを適用 |

件数一致や保存成功だけで完了としない。重複・消失・誤改番があれば当該適用を止め、成立状態と差分を報告する。

## 完了済み過去工程の改訂と影響伝播

1. **承認範囲**: 有効な承認の対象・内容・範囲を確認する。不明・範囲外は承認の再確認まで保留する。遷移記録を取り消さず、現在工程を巻き戻さない。
2. **下流列挙**: 採用された工程間関係から影響し得る全下流を列挙する。中間の更新不要、正味差分ゼロ、明示対応の空集合を理由に後続を除外しない。
3. **依拠版の評価**: 下流が実際に依拠した版を正規成果物・承認・検証記録・Git 履歴から特定し、`agentdev-traceability` の公開 `relied-diff` CLI に渡す。工程開始時の版を一律に指定したり独自に再計算したりしない。版不明・取得失敗は未確認とし、空の変更集合にしない。
4. **処置と再検証**: 更新必要・更新不要・作成・未確認を理由とともに区別する。必要な変更と再検証は既存経路で実施する。更新不要は現行上流との整合を確認する。旧証拠の再利用は対象ごとに対象・版・条件への適用可能性を記録する。適用不能・再検証失敗・転用先不在・未確認を完了に含めない。
5. **記録と再開**: 影響分類、実際の更新・検証と結果、未確認事項、承認範囲、通知の時点（事前・追加・事後）を記録する。Capability Skill の改訂実行記録生成へ `relied-diff` 出力と処置結果を渡し、`.agentdev/phase/revisions/` へ1改訂1ファイルで保存する。承認記録なしでは確定しない。中断後は実成果物・検証結果から成立状態を復元し、未成立部分だけを続ける。未完了なら残件と再開条件を報告する。

無影響部分を一律再生成せず、既存の証跡と正規成果物から再構成する。専用の版台帳・依存グラフ・履歴 DB や第2の管理台帳を作らない。
