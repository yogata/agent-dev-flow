# phase-artifacts-update workflow スキル

反映指示、貼付・指定ファイルの外部戻り入力または利用者の直接提示を受け取り、採用済みの内容だけを現行の正規成果物へ反映する。GitHub・Local とも同じ契約を用いる。テーマ正本・工程遷移は変更しない。対話内で完結し、STEP model の resume point / export / import は持たない。再投入は記録と実ファイルから再開する。

| 工程 | 実行・判定 |
|---|---|
| 1 | 指示と正規状態から取組・対象版・現在工程を特定する。一意に特定できなければ書き込まず、候補と不足を返す |
| 2 | `agentdev-phase-theme-collaboration` の決定的処理で外部戻り・直接入力を同じ規律で受理する |
| 3 | 利用者の明示判断または有効な正規決定を採用根拠とする。外部AIの承認自己申告や会話からの推論は証拠にしない。採否不明の部分だけを確認に返す |
| 4 | 最新の正規成果物と内容を照合し、増分更新・新規作成・構造再編・保留を選ぶ。ファイルが見つからないことだけで新規作成を選ばない |
| 5 | 下記の保存前 gate を満たして反映する。重要変更の通知は反映より先に行う |
| 6 | 実ファイルと照合し、反映済み、衝突、未確認、保存失敗を区別して報告する。独立して安全な項目は先に進める |
| 7 | 入力経路に応じた記録を保存し、反映先・記録先・機械検証の結果（または未実行）を報告する。返却後に処理を残さない |

## 反映先の照合と書込み

先行合意と矛盾する部分は保留し、無断で置換・再編しない。有効な既存成果物へは増分反映し、内容上の照合で適切な成果物が存在しなければ必要な種類だけ新規作成する。変更駆動・工程駆動は互いの現行成果物を再読取して利用し、各経路の保存・確定の権限を維持する。

REQ・Decision・Design 操作は各成果物管理スキルへ委譲する。所有先判断（既存REQ照合の判定基準を含む）も委譲先の共有の成果物管理スキルの基準に従い、本経路独自の照合基準を導入しない。採番・配置・初期状態・参照・索引の規律を維持し、関連更新と整合性確認が済むまで完了にしない。

保存直前に `agentdev-artifact-validation` の引用要件行 ID 実在検証を適用後本文に対して実行する。同じ変更内の REQ 要件行テーブルの適用後本文も渡し、保存順ではなく適用後状態で評価する。`ok: false` は保存せず、修正対象の ID と箇所を報告する。増分反映では変更差分と下流影響を評価し、旧検証証拠の対象・版・条件を照合する。

| 条件 | 詳細参照 |
|---|---|
| 独立レビュー所見、部分失敗・再投入、記録の保存 | [入力・部分反映・記録](references/input-and-records.md) |
| 利用者が対象と実施を明示した分割・統合・項目移動 | [構造再編と過去工程改訂](references/restructure-and-revise.md) の構造再編 |
| 遷移記録で完了済みの過去工程の成果物を改訂 | [構造再編と過去工程改訂](references/restructure-and-revise.md) の影響伝播。現在工程と遷移記録を巻き戻さない |

## 記録の保存

外部戻り入力がある場合は `.agentdev/phase/received/` に1受領1ファイルで保存する。直接採用時は `.agentdev/phase/adoptions/` に採否記録のみを1採用1ファイルで保存し、外部受領を装わない。採否記録の様式・生成は `agentdev-phase-theme-collaboration` が所有する。

採否記録は受領記録と同じ証跡規律に従う。由来（provenance）と正式な採用根拠（adoptionBasis）を区別し、曖昧・不正な入力は確定しない（fail-closed）。同日の複数採用は連番で区別して既存記録を上書き・消失させない。保存先と様式は領域契約文書の「adoptions/ の様式」から発見できる。

## 領域契約文書の非破壊実体化

対象の特定後、保存の前に `.agentdev/phase/README.md` を確認する。存在しない場合のみ `.opencode/skills/agentdev-phase-theme-collaboration/templates/phase-readme.md` から実体化し、テンプレートと一致させる。既存文書を上書きしない。不在を検査失敗として扱わない。実体化した場合は保存先一覧に含める。

## 重要変更の通知と結果説明

重要性の識別は変更の意味と影響に基づく本スキル自身の判断責務である。ファイル数や行数だけで決めない。反映の実行（工程5）より前に、変更する理由、予定内容と方法、想定影響、確定している事項と未確認の事項を利用者へ提示する。過去工程の成果物なら現在工程との関係と想定される後続影響を通知に含める。反映の実行より先に通知を出力した事実は採否記録と完了報告に残す。反映実行後の初回提示を事前通知として扱わない。

採用判断（利用者の明示判断）と反映作業（委譲された裁量）の既存境界を変更せず、採用済みの反映を通知後に実行する。実行中に判明した未反映の重要変更は反映前に、反映済みのものはその事実を区別して通知する。実際の変更、見込みとの違い、残る影響を報告する。差分・影響評価と現在工程を巻き戻さない規則を維持し、通知で代替しない。共通報告と正本の優先度は `agentdev-workflow-lifecycle` に従う。
