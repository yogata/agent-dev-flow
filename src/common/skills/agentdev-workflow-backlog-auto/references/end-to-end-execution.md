## set-state 永続化契約

### 配置

- set-state は `.agentdev/backlog-auto/end-to-end/<一式識別子>/set-state.json` に配置する
- `.agentdev/` 配下でありながら req-units と draft の配置外とする。ドラフト残存・RU 残存を検証するクリーンアップ検証ゲートの対象外である
- 全体完了とリリース完了まで保持する。リリース完了後の削除可否は結果報告に記録する

### 形式

set-state は次の要素を記録する。

| 要素 | 内容 |
|---|---|
| 一式識別子 | 実行開始時刻（JST）由来の一意 ID。分割時は後継一式に新しい一式識別子を発行し、対応表に旧新対応を記録する |
| 義務スナップショット | 元 RU 一式の必須の要求と受け入れ義務のスナップショット（RU 本文から抽出）。完了突合の正の一つである |
| 対応表 | RU・要件doc・operation_unit・実行単位（Case Issue / Issue / Epic）の対応（統合・分割を含む）。統合・分割後も元の要求と後続対象の対応を維持する |
| 基準点情報 | 実行開始時に確定した最後の正式リリース（版番号、タグ名、タグ対象コミット）と開始コミット ID |
| 進捗 | stage 別の完了状態（stage 4: 要件定義済み、stage 5: 実行済み、stage 6: 完遂判定済み、stage 7: リリース状態） |
| リリース状態 | 未着手／基準点確定済み／保留理由（リリース条件・権限・公開途中失敗の区別と内容）／完了（版番号、タグ名、対象コミット、公開成果物の確認情報、公開実行形態。公開実行形態は workflow 実行／代行／利用者手動の3区分で区別して記録し、workflow 実行の場合は承認根拠（承認した HITL 質問 ID・回答の記録参照）を含める） |

### 単一書き手規則

- set-state への書込みは同一 backlog-auto 実行に限定する
- backlog-auto の二重起動に対しては既存の single-flight 保護に準じて排除する。進行中の実行を示す set-state（完了か保留か中断を確定できない状態）を検出した後行起動は、新規実行を開始せず既存実行の状態確認と再開（`/agentdev/backlog-auto` 再実行の案内）へ切り替える

## STEP-7: set-state 初期化・基準点確定

### Purpose

承認確定した RU 一式を一式として set-state に登録し、実行前の基準点（最後の正式リリースと開始コミット ID）を確定する。

### Input Resolution

1. SSoT 再構成: `.agentdev/backlog/req-units/` の承認確定 RU 一式（当該 backlog-auto 実行の backlog-review が生成した RU。実行前から存在した無関係 RU を含まない）、set-state 実ファイル（再開時）
2. identifier 保持: 一式識別子
3. 最小 scalar: 基準点情報（最後の正式リリース、開始コミット ID）
4. runtime artifact: set-state

### Preconditions

- stage 3（backlog-review）が正常完了し、承認確定 RU 一式が存在する（0 件の場合は STEP-6 へ。対象なし報告）
- 基準点が未確定である（再開時は既存 set-state の基準点情報を再利用する）

### Procedure

基準点確認手続に従い基準点を確定し、set-state を作成する。

基準点確認手続:

1. 正式 SemVer タグの列挙: リポジトリのタグから正式 SemVer タグのみを列挙する（rc タグ、非 SemVer のベースラインタグは基準から除外する）
2. 祖先到達判定: リリース対象となりうるコミット（開始時点では現行 main HEAD）から到達可能な正式タグに限定する
3. 最大版算出: 到達可能な正式タグのうち最大版を SemVer 順序比較（major.minor.patch の数値比較。辞書式比較を用いない）で算出する
4. 到達可能 0 件の取扱い: 正式タグが存在するが到達可能なものが 0 件の場合は、既存正式タグとの方針（版番号後退の回避を含む）を利用者判断に求めて停止する。初期バージョン番号の自動決定は行わない
5. 初期状態の取扱い: 正式なバージョン基準が存在せず、対象プロジェクトの採用済み初期バージョン規則も確認できない場合は、実行開始前の基準点確定時に停止し、利用者に初期バージョンの判断を求める
6. 開始コミット ID の記録: 現行 main HEAD のコミット ID を開始コミット ID として set-state に記録する

set-state の作成は義務スナップショットと対応表の初期登録を含む。

- 義務スナップショット: 元 RU 一式の必須の要求と受け入れ義務を RU 本文から抽出して登録する。完了突合まで RU 削除の影響を受けない（RU・要件doc の削除契約は変更しない）
- 対応表: 初期状態では RU →（未確定）の対応のみ。stage 4 以降で要件doc・operation_unit・実行単位の対応を追記する

基準点確定不能（初期状態・到達不能正式タグ）の場合は stage 4〜7 を開始せず、停止理由と利用者判断要求を報告して STEP-6 へ進む。

### Result

- set-state の作成（一式識別子、義務スナップショット、対応表、基準点情報、進捗初期状態）
- 基準点確定結果（最後の正式リリースと開始コミット ID）または基準点確定不能の停止

### Evidence

- set-state のパスと基準点情報の値、列挙した正式タグ一覧と到達判定の根拠

### Completion Verification

- 基準点が確定できた場合のみ set-state に基準点情報が記録されていること
- 基準点確定不能の場合に stage 4〜7 が開始されていないこと

### Resume-Idempotency

- 再開時は既存 set-state の基準点情報を再利用し、基準点確認手続を再実行しない。set-state 不在で進行痕跡がある場合は基準点確認手続から再実行する（確定不能工程は未完了扱い）

## STEP-8: stage 4: 要件定義接続

### Purpose

一式 RU を単一の req-define 実行へ接続し、単一の要件doc に確定する。工程内部の手続き（壁打ち対話、Decision 判断、ドラフト生成）は `agentdev-workflow-req-define` が正規の処理主体である。

### Input Resolution

1. SSoT 再構成: set-state の義務スナップショットと対応表、`.agentdev/backlog/req-units/` の一式 RU 実ファイル
2. identifier 保持: 一式識別子
3. 最小 scalar: stage 4 の開始時刻、終了時刻、結果状態
4. runtime artifact: 要件doc（draft）

### Preconditions

- STEP-7 で set-state が作成され基準点が確定している（再開時は set-state から復元）
- stage 4 が未完了と判定されている（要件doc 確定済みの場合は STEP-9 へ）

### Procedure

`agentdev-workflow-req-define` を権威情報源として req-define を1回だけ実行する。入力は一式 RU の明示列挙である（引数なし全件処理を用いない）。

- req-define 自体の壁打ち・承認境界は req-define 側の所有として維持する。本接続は req-define の壁打ちを保存する接続であり、自動化しない
- 複数 RU の統合・分割は operation_units 構造で表現する（複数の要件doc を生成しない）
- req-define の壁打ちで利用者が一式の複数要件docへの分割を判断した場合、当該判断を一式の構成変更（再スコープ）として set-state の対応表に記録する。分割後の各一式はそれぞれ独立した一気通貫ライフサイクル（基準点確定から）で扱う。現在の実行は、判断に含まれる対応する一式の処理のみを継続する
- req-define が blocked / failed の場合は stage 5 以降を開始せず、set-state に進捗を記録して STEP-6 へ（停止報告）

要件doc が確定した場合、set-state の対応表に RU・要件doc・operation_units の対応を追記し、進捗を要件定義済みへ更新する。

### Result

- 単一要件doc の確定、set-state 対応表の更新
- stage 4 実行結果（正常完了 / blocked / failed / 再スコープ記録）

### Evidence

- 確定した要件doc のパス、set-state 対応表の更新内容、blocked / failed 時はその理由、分割判断時は再スコープの記録

### Completion Verification

- 一式全体が単一の req-define 実行で処理されていること（個別ドラフトごとの複数起動が存在しないこと）
- 要件doc 確定後に set-state の対応表が更新されていること

### Resume-Idempotency

- 再開時は set-state の進捗と要件doc の実在から stage 4 の完了を判定し、完了済みの場合は req-define を再実行しない

## STEP-9: stage 5: 実行接続

### Purpose

確定した要件doc を明示指定した単一の case-auto 実行へ接続する。実行内部の手続き（case-open〜case-close、並列実行制御、再開制御）は `agentdev-workflow-case-auto` が正規の処理主体である。

### Input Resolution

1. SSoT 再構成: set-state の対応表（要件doc パス、実行単位）、確定済み要件doc 実ファイル
2. identifier 保持: 一式識別子
3. 最小 scalar: stage 5 の開始時刻、終了時刻、結果状態
4. runtime artifact: なし（実行内部の過程は case-auto 側の durable state が所有）

### Preconditions

- STEP-8 で単一要件doc が確定している
- stage 5 が未完了と判定されている（実行完了済みの場合は STEP-10 へ）

### Procedure

確定した要件doc を明示指定して case-auto を1回だけ起動する。

- 一式から複数の独立した実行可能 Issue が生じた場合の並列実行は、case-auto 側の既存の共有 active Issue task 上限と横断補充に従う。一式を複数グループへ分断して先行グループの全完了を待つ逐次化を行わない
- 本接続は個別ドラフトごとの複数 case-auto 起動を用いない
- case-auto が blocked / failed の場合は stage 6 以降を開始せず、set-state に進捗を記録して STEP-6 へ（停止報告）。停止報告には case-auto 単独の再開入口（Root Case 指定の再開）に加えて一式再開経路（backlog-auto 再実行）を併記する
- case-auto の正常完了（全 Issue の完了、中断なし）を受領した場合、set-state の進捗を実行済みへ更新する。実行単位（Case Issue / Issue / Epic）を対応表へ追記する

### Result

- 単一 case-auto 実行の完了または停止、set-state 進捗・対応表の更新

### Evidence

- case-auto 実行の完了報告（実行単位一覧）、blocked / failed 時はその理由と再開入口

### Completion Verification

- 一式が単一の case-auto 実行へ写像されていること（複数起動が存在しないこと）
- case-auto 完了後に set-state の進捗が更新されていること

### Resume-Idempotency

- 中断時の再開は case-auto 単独の再開入口契約（Root Case 指定の再開）を利用する。本 STEP は実行の起動と結果受領のみを管理し、実行内部の再開点を再構成しない。再開時は set-state から実行未完了を判定し、case-auto の再開を1回だけ再接続する

## STEP-10: stage 6: 全体完了判定

### Purpose

set-state の義務スナップショットと対応表を正として、要件定義・実行対象・検証結果の突合により一式全体の完遂を判定する。

### Input Resolution

1. SSoT 再構成: set-state（義務スナップショット、対応表、進捗）、確定済み要件doc、実行単位の完了状態と検証証跡
2. identifier 保持: 一式識別子
3. 最小 scalar: 完遂判定結果（完遂 / 未完遂）
4. runtime artifact: なし

### Preconditions

- stage 5 が完了している、または再開時に set-state から実行済みと確定している

### Procedure

全体完了突合手続に従い突合を実行する。

全体完了突合手続:

1. 義務の対応確認: 義務スナップショットの各必須要求・受け入れ義務が、確定済み要件doc の要求行と実行対象（実行単位）に過不足なく対応していることを対応表で確認する。統合・分割後も元の要求と後続対象の対応が維持されていることを含める
2. 検証結果の成立確認: 実行単位の検証証跡（品質ゲート、test strategy 項目の検証結果等）が、義務に対応する必要な範囲ですべて成立していることを確認する
3. 判定: 1 と 2 がともに成立する場合にのみ一式全体の完遂と判定する。個別の Issue 終了・PR merge のみで完遂としない
4. 未成立時: 不足する義務対応または検証結果を特定し、完遂とせず報告する（不足内容と再開経路を含める）

突合の正は set-state の義務スナップショットと対応表であり、RU・要件doc が削除済みでも突合は set-state から復元して実行する。完了判定と最終報告は一気通貫実行の REQ が所有し、backlog 整理サイクルの完了扱い・全体報告とは分離する。

完遂と判定した場合、set-state の進捗を完遂判定済みへ更新する。未成立の場合は STEP-6 へ（全体完遂不成立の報告。全体完了として扱わない）。

### Result

- 完遂 / 未完遂の判定と根拠、set-state 進捗の更新

### Evidence

- 突合結果（義務ごとの対応、検証結果の成立一覧）、未成立時は不足内容

### Completion Verification

- 義務・検証結果が過不足なく対応した場合のみ完遂と判定されていること
- Issue 数の一致、PR merge 状態のみで完遂と判定していないこと

### Resume-Idempotency

- 突合は set-state と実行単位の完了状態から再実行可能であり、副作用を持たない。完遂判定済みの set-state が存在する場合は突合を再実行せず STEP-11 へ進む

## STEP-11: stage 7: リリース

### Purpose

完遂した一式に対し、パッチリリース規則の Decision に従って版番号を導出し、対象コミットへタグを付与し、採用方式に応じた追加公開成果物（GitHub Release）の草稿作成と読み戻し確認、結果記録を行う。

### Input Resolution

1. SSoT 再構成: set-state（基準点情報、対応表、リリース状態）、リリース時点の正規情報（main HEAD、タグ一覧、差分）
2. identifier 保持: 一式識別子
3. 最小 scalar: 導出版番号、対象コミット、タグ名
4. runtime artifact: git タグ、Release 草稿

### Preconditions

- STEP-10 で完遂と判定している（完遂済み・リリース保留からの再開を含む）
- リリース条件と公開権限が確認済みである（未確認の場合は確認を利用者判断として要求する）
- 公開権限確認の HITL 選択肢文言は本節の定義を一元的に使用し、workflow の実行能力と一致させる: 「草稿を作成する（公開はしない）」は workflow が履行できる草稿作成経路（release_create）の存在を前提とし、「草稿を作成して公開する（承認根拠を記録する）」は workflow が履行できる公開経路（release_publish。承認根拠必須の入力契約）の存在を前提とする。workflow が履行できない選択肢（カタログに存在しない操作の実行を約束する文言等）を提示しない

### Procedure

リリース手順シーケンスに従い、順に実行する。

1. 基準点再確認: リリース時点で正式 SemVer タグを再確認する。開始時基準より新しい正式タグが存在する場合は、その最大版から版番号を導出し直す。既存タグとの衝突、タグの移動、二重採番は行わない
2. 版番導出: 最後の正式リリースからパッチ番号を1つだけ進めた版を確定する（major/minor への自動振り分け、同一実行での二つの版番号の消費を行わない）。導出版と同一のタグが既に存在する場合は衝突として報告し、版番号を再消費せず停止する
3. 対象コミット確定と無関係コミット混入検知: リリース対象コミット（一式の全マージ完遂時点の main HEAD）を確定する。開始コミット..対象コミットの差分と、set-state の対応表から導出する一式分の実変更（一式の実行単位が生んだマージ済み変更）を突合し、一式に帰属しない無関係コミットの混入を検出した場合は報告して利用者判断を求める（タグ付与の可否は利用者判断）
4. タグ作成: リリース対象コミットに導出版のタグを作成する。タグ作成済みを検出した場合は作成を省略し、タグの移動・再作成を行わない
5. 追加公開物（Release 記録）: 対象プロジェクトの採用方式が追加公開成果物（GitHub Release）を要求する場合、次の Release 記録手順を Custom Tool 操作カタログ（release_create、release_list、release_read、release_publish）経由で実行する。公開（draft の解除）は公開権限の確認で利用者が草稿作成とは別に明確に承認した場合に限り release_publish（承認根拠必須）で実行する（「公開操作の実行経路」節）
   1. 版タグ列挙: 対象プロジェクトの版タグ（正式 SemVer タグと RC タグ）を列挙する。非 SemVer のベースラインタグは対応対象から除外する
   2. 対応確認: release_list で全 Release を読み取り、版タグごとの対応（同名 Release の有無、draft・prerelease 状態）を確認する。既存 Release がある版タグは作成を省略する（同一タグへの二つ目の Release を作らない）
   3. 欠落タグの補完（該当時のみ）: リモートに存在しない既存版タグは、注釈付きの元のタグを上書きしない通常 push で送り、git ls-remote --tags でリモートとローカルのタグ識別子が一致することを確認してから草稿を作る。force push による解消を行わない
   4. 草稿作成: 対応のない版タグへ release_create で草稿を作成する。RC 版タグは prerelease: true で作成する。Release タイトルは版タグ名とする。作成に失敗した場合はタグを移動・再作成せず、Release が欠けているため工程を完了できない旨を報告して停止する
   5. 読み戻し確認: release_list（必要に応じて release_read）で全版タグと Release の 1:1 対応を再読取して確認するまで、Release 記録工程を完了としない。同一タグ名の Release が2件検出された場合は削除せずに読み戻し結果を報告して停止する
   6. 承認時公開: 公開権限の確認で利用者が公開を明示承認した場合、release_publish（承認根拠〔承認した HITL 質問 ID・回答の記録参照〕付き）で対象版タグの Release を公開（draft の解除）し、読み戻しで draft=false・published_at が確認された場合のみ公開完了とする。already-published（draft=false）を検出した場合は重複実行せず記録完了扱いとする。未承認の場合は公開を実行せず、Release 草稿が draft 状態のまま保持されていることを確認する
6. 結果記録: set-state のリリース状態を完了へ更新し（版番号、タグ名、対象コミット、Release 対応の確認情報、公開実行形態を含める）、結果を報告する。公開実行形態は workflow 実行（承認根拠の参照を含む）／代行／利用者手動の3区分で区別して記録する。未承認であるのに公開済み（draft=false）を検出した場合は不整合として完了とせず報告する

各段階の中断・失敗時は既存結果の読み戻しにより未完了段階から再開する（タグ不移動・再作成なし・第二番号なし）。公開途中の失敗・中断時は、タグの存在（ローカル・リモート）と Release 草稿の状態（release_list による版タグと Release の対応）を読み戻し、読み戻し再開可能な状態で報告する。再開時は既存のタグと Release を使い、同一タグへ二つ目の Release を作らない。

リリース条件・公開権限が不成立の場合は、タグ・リリースを作成せず「完遂済み・リリース保留（理由記録）」として報告する。backlog-auto 再実行はリリース段階から再開する。

### Result

- タグ作成、Release 草稿作成・読み戻し確認、承認時の Release 公開（該当時）、set-state リリース状態の更新（公開実行形態を含む）、リリース結果または保留理由

### Evidence

- 導出版番号と根拠（基準タグ、到達判定）、対象コミット、差分突合結果、タグ作成の実行記録（既存省略時はその検出根拠）、Release 対応の読み戻し結果（版タグごとの対応と draft・prerelease 状態、欠落タグ補完時は識別子一致確認）、公開実行形態の記録（workflow 実行時は承認根拠の参照と公開後の読み戻し結果 draft=false・published_at を含む）、保留時は理由

### Completion Verification

- 完遂前の段階で新規のタグ・リリースが作成されていないこと（本 STEP 以前の set-state 進捗とタグ一覧の観測で確認する）
- 差分突合で無関係コミット混入を検出した場合に利用者判断なしでタグ付与が行われていないこと
- 中断・失敗後に再開した場合、タグの移動・再作成と第二の版番号の消費が発生していないこと
- Release 記録は読み戻し確認（全版タグと Release の 1:1 対応）まで完了していること。読み戻し確認前の段階では Release 記録工程を完了としない
- 公開完了検証は set-state の公開実行形態記録を判定鍵とする条件化である。公開実行形態が未記録（未承認）の場合: 公開操作（draft の解除）が実行されておらず、Release 草稿は draft 状態のまま保持されていること。公開実行形態が workflow 実行の場合: 対象 Release の読み戻しで draft=false・published_at が確認され、set-state に承認根拠の参照が記録されていること。公開実行形態が代行・利用者手動の場合: set-state の記録と Release の実状態（draft 状態）が一致していること。未承認であるのに公開済み（draft=false）を検出した場合は不整合として完了とせず報告する

### Resume-Idempotency

- 各段階は set-state のリリース状態と実環境の読み戻し（タグ一覧、Release の対応）から未完了段階を判定して再開する。完了済み段階を再実行せず、既存のタグ・版番号を消費しない
- Release 記録の再開時は既存のタグと Release を使い、既存 Release がある版タグの作成を省略し（重複防止）、同一タグへ二つ目の Release を作らない

## 公開操作の実行経路

- 最小公開形は git タグの作成であり、ローカルリポジトリで完結できる。リモートへの push は Git 操作の非対話認証経路の契約に従う（対話認証を待機せず、資格情報の値を解析証拠やログへ出力しない）
- GitHub Release の作成・読み戻し・公開は Custom Tool 操作カタログの Release 操作（release_create、release_list、release_read、release_publish）経由でのみ行う。release_create の入力契約に公開モード（draft の解除、publish 相当フィールド）は含まれず、契約外の公開指定フィールドを含む要求は副作用発生前に入力契約違反として拒否される。公開（draft の解除）は release_publish の入力契約（タグ名と公開承認の根拠を必須とする）経由で、利用者が草稿作成とは別に明確に承認した場合に限り実行する。承認根拠を欠く要求は副作用発生前に入力契約違反として拒否される（fail-closed）。生 gh コマンドによる Release 書き込み（カタログ外書き込み経路）を迂回しない
- 公開権限の確認で利用者が公開を明示承認した場合、workflow は release_publish を実行し、読み戻し（draft=false・published_at）で公開状態を確認するまでを workflow 実行として完了する。承認後の公開を利用者側実施へ転嫁しない（代行・利用者手動は例外経路として set-state に区別して記録する）
- 公開方式・権限・必要な環境が不足する場合は、対象と理由を報告し、リリース完了としない（「異常系の取扱い」節）

## 異常系の取扱い（対象なし・初期状態・公開不能）

| ケース | 取扱い |
|---|---|
| RU 0 件 | stage 4〜7 を開始せず、一式不在の旨を報告する。リリースは作成しない |
| リリース対象となる実変更なし | 完遂判定の結果、一式に対応する実変更（マージ済み変更）が存在しない場合はリリースを作成せず報告する |
| 正式なバージョン基準なし（初期状態） | 対象プロジェクトの採用済み初期バージョン規則を確認する。確認できない場合は初期バージョン番号を決定せず基準点確定時に停止し、利用者判断を求める |
| 到達可能な正式タグ 0 件 | 正式タグ存在下で到達可能 0 件の場合は停止し、既存正式タグとの方針（版番号後退の回避を含む）を利用者判断に求める |
| 公開方式・権限・環境の不足 | 対象と理由を報告し、リリース完了としない。完遂済み・リリース保留（理由記録）として扱う |
| Release 草稿作成の失敗 | タグを移動・再作成せず、Release が欠けているため工程を完了できない旨を報告して停止する。再開時は既存のタグと Release を使い、同一タグへ二つ目の Release を作らない |
| 同一タグ名の Release が2件検出 | 削除・変更せずに読み戻し結果を報告して停止する（重複解消は利用者判断） |
| 未承認の公開済み検出 | 公開権限の確認で未承認であるのに対象 Release が draft=false（公開済み）を検出した場合は不整合として完了とせず、読み戻し結果（タグ、set-state の公開実行形態記録と実状態の差異）を報告して停止する |
| 欠落タグの push 失敗または識別子不一致 | force push による解消を行わず、失敗内容と識別子の差異を報告して停止する（草稿は作成しない） |

## 一式再開経路

- stage 4〜7 のいずれで中断しても、backlog-auto 再実行により set-state から同じ一式の対象と進捗を復元し、未完了部分から再開する
- 完遂済み Case を検出した場合、全体完了判定（stage 6）以降の段階から再開する。実装を再実行しない
- stage 5 の実行中断は case-auto 単独の再開入口契約（Root Case 指定の再開）でも再開できる。case-auto 単独の再開入口契約は変更しない
- 停止報告には case-auto 単独の再開入口に加えて一式再開経路（backlog-auto 再実行）を併記する
