# 既存REQ照合、整合性チェック、マージ競合対応

本ファイルは `agentdev-req-file-manager` SKILL.md の補助資料であり、req-define での既存REQ照合方法論、Issue/Decision/README との整合性チェック、REQ更新失敗時のマージ競合対応パターンを扱う。
SKILL.md 本文では要点のみを提示し、照合の判定要素、操作分類の5軸評価、マージ競合パターン別解決方法は本ファイルを参照する。

## 既存REQ照合方法論

req-define（壁打ちフェーズ）で既存REQファイルとユーザーの要件を照合する方法論を定義する。

### 照合の実行タイミング

壁打ちの意図把握後、要件展開の前に実行する。
照合結果は要件展開に反映される。

### 照合の判定要素

| 判定要素 | 重み | 説明 |
|----------|------|------|
| タイトル | 高 | 要件の主題とREQのタイトルの意味的類似性 |
| 目的セクション | 高 | REQの「目的」セクションとユーザー要件の目的の意味的重複 |
| 要件内容 | 中 | REQの要件テーブル内容とユーザー要件の具体的な重複、包含関係 |

### 正規情報の取得と取り扱い

照合と要件展開に用いる正規情報は、REQ・Decision・Design の実ファイルから必要な範囲を取得する。

- 正規ファイルの実内容と判断に用いた情報を照合し、現行と廃止済みの情報、採用済みと未採用・未決の内容を区別なく判断材料へ混入させない
- 実在するREQの見落としや正規情報の取得に失敗した場合を該当なしとして扱わず、判断を保留して失敗の内容と不足している情報を報告する（fail-closed）
- 取得できた情報の範囲で成立する判断と、取得の失敗のために確定できない判断を区別して扱う。確定できない部分を取得結果から勝手に補完しない
- 取得に失敗した正規情報の内容が照合・操作分類の判断に必要である場合、その判断は「取得の失敗のために確定できない判断」であり、操作分類を確定しない（照合結果の分類「保留」を適用する）。取得に失敗した成果物の内容を、インデックス題目・投入要求等の取得済み情報から補完する操作分類（欠損 REQ 番号へ新規作成する CREATE を含む）で確定しない。欠損の処置（再作成・番号の扱い・索引是正・復旧の要否）は候補と不足している判断材料を報告し、保留の解除は利用者の処置による
- 取得済み実ファイルの内容のみに依存して独立に成立する判断は、他に取得失敗があっても継続する。取得失敗の影響を受けない判断のために一律の停止や質問を行わない

### 照合結果の分類

| 状況 | 操作分類 | 説明 |
|------|----------|------|
| 同じ関心領域のREQが存在し、内容を修正する場合 | `UPDATE` | 既存REQのセクション内容を変更 |
| 関連するREQが存在し、新しい要件を追加する場合 | `APPEND` | 既存REQに要件行を追加 |
| 同じ関心領域のREQが存在しない場合 | `CREATE` | 新規REQファイルを作成 |
| 既存の要件行の規定だけで要求が成立する場合 | 変更不要（REQ操作なし） | REQ操作を実行せず、重複する要件行を追加しない |
| 所有先を一意に決定できない場合 | 保留 | 操作分類を確定せず、候補と不足している判断材料を報告する |

※ SPLIT（要件の分割）が検出された場合は、requirements review/ follow-up 候補として扱い、保存操作の対象外とする。

### 操作分類の判定軸

関連REQ特定後の CREATE/APPEND/UPDATE の選択では、要求の持続的な目的・関心と既存REQの目的・所有範囲との対応を主軸として評価する。
判定軸は次の5軸である。「目的の連続性」と「独立目的の有無」の2軸が主軸であり、対象コンポーネントと対象スコープの一致は主軸の判断を補強する補助材料である。

| 判定軸 | 位置づけ | 説明 |
|--------|----------|------|
| 目的の連続性 | 主軸 | 既存REQの目的に対する追加、補強、調整か。要求の持続的な目的・関心と既存REQの目的・所有範囲が対応するか |
| 独立目的の有無 | 主軸 | 既存REQとは独立した目的を持つ新規要件か |
| 対象コンポーネント | 補助材料 | 同じUI部品、画面、機能単位への変更か。主軸の判断を補強する材料であり、一致だけでは統合を決定しない |
| 対象スコープ | 補助材料 | 同じ利用者操作、業務範囲、表示範囲への変更か。主軸の判断を補強する材料であり、一致だけでは統合を決定しない |
| 要件行追加可能性 | 補助材料 | 既存REQの要件テーブルへ自然に新規行として追加できるか |

**判定フロー**:

1. 照合で関連REQを特定後、主軸（目的の連続性、独立目的の有無）で評価する
2. 既存REQの目的に対する追加、補強、調整であり、既存の要件行の規定だけでは要求が成立しない → APPEND
3. 既存REQの目的、要件行、適用範囲の内容修正 → UPDATE
4. 独立した目的を持つ新規要件 → CREATE
5. 既存の要件行の規定だけで要求が成立する場合 → 変更不要（REQ操作なし）とし、重複する要件行を追加しない
6. 所有先を一意に決定できない場合 → 操作分類を確定せず保留とし、候補と不足している判断材料を報告する
7. CREATE 選択時は req-define コマンドの `create-rationale` フィールドに理由を記録

**判定の禁止事項**:

- 不具合修正や一時作業という作業種別を理由に、独立した目的を持つ要求を既存REQへ統合しない
- 実装部品の一致（同じUI部品、画面等への変更であること）だけを根拠に統合を決定しない
- 個別投入か一括投入かという入力の体裁だけを根拠に、既存REQへの統合の要否やREQ変更の要否を決定しない

### 照合時の壁打ち反映

関連REQが特定された場合、以下を壁打ちコンテキストに即時反映する: 該当REQの目的セクション、既存要件テーブル、適用範囲。
これにより重複や矛盾を防ぐ。

### REQファイルの照合用情報記述規則

将来の APPEND/UPDATE 判定で参照できるよう、REQファイルの既存セクションに照合用情報を明示する。
frontmatterへの新規フィールド追加は行わない。

| セクション | 記述内容 | 例 |
|-----------|----------|-----|
| title | 対象コンポーネント、対象領域を含める | "AgentDevFlow コマンドプロトコル" |
| 適用範囲（対象） | 対象コンポーネント、対象画面、対象操作、対象スコープを含める | "req-defineの既存REQ照合プロセス" |
| 適用範囲（対象外） | 明示的に対象外とするスコープを含める | "並列実行の依存分析" |

## 関連情報管理

REQ間の関連、依存はREQ本文内に記載する（frontmatterフィールドは使用しない、REQ標準構成 `## 目的`/`## 要件`/`## 適用範囲` 以外に専用セクションは仮定しない）。
記述規約は numbering-and-validation.md「REQ本文内メタデータ規約」参照。

- **置き換え**: 旧REQを新REQに置き換える場合に記載
- **関連**: 独立要件だが変更が競合する可能性がある場合に記載
- **分割元/分割先**: SPLIT操作による分割関係

## 整合性チェック

### Issue ↔ REQ

- REQファイルはIssueから一方向参照（Issue本文にREQ番号を記載）。REQファイルからIssueへの逆参照は行わない

### Decision ↔ REQ

- Decisionが必要な要件は、REQ本文内に `Related ADRs` 形式でDecision番号を記載する（専用セクションは仮定しない、記述形式は numbering-and-validation.md「REQ本文内メタデータ規約」参照）
- Decisionが存在しない場合、Decision作成を推奨（要件がアーキテクチャ判断を含む場合）

### README.md ↔ REQ

- `docs/requirements<README>.md` のインデックスに全REQが記載されているか確認
- インデックスに記載されているがファイルが存在しないREQを検出
- ファイルが存在するがインデックスに未記載のREQを検出

エントリ存在確認は `agentdev-artifact-validation` が所有する決定的スクリプト `check-entry-existence.ts` が担当する。
本 skill は公開検証契約へ委譲する。

## マージ競合対応パターン

### REQファイル更新時のマージ競合対応

#### 1. 競合リスク状況

| 状況 | リスクレベル |
|------|-------------|
| 複数ユーザーが同時に同じREQを編集 | 高 |
| REQ保存（Definition 保存内部責務）と手動編集が競合 | 中 |
| APPENDとUPDATEが同時に実行 | 中 |

**競合予防**: 更新前に `git pull --ff-only` で最新を取得し、`git status --porcelain` でローカル変更を確認。

#### 2. frontmatter競合の解決

- `created`: 古い日時を維持（変更禁止）
- `updated`: 最新の日時を採用
- `title`: 手動で統合

解決後は frontmatter バリデーションを実施（id/ファイル名一致、created ≤ updated）。

#### 3. 本文セクションの競合解決

| 競合パターン | 解決方法 |
|-------------|----------|
| 異なる要件行の追加 | 両方の要件行を追加（行順は要件番号順） |
| 同じ要件行の内容変更 | 手動で統合 |
| 要件行IDの重複 | 再採番（最大番号 + 1） |

目的セクション、適用範囲セクションの競合: 両方の内容を手動で統合し、意図が矛盾する場合は要件の分割、統合を検討。

**重要**: 自動的な競合解決は禁止。
必ず手動解決をユーザーに依頼する。

#### 4. REQ更新失敗時の報告フォーマット

REQ更新時に競合やエラーが発生した場合:

```markdown
## REQ 更新失敗エラー

**REQ番号**: REQ-{NNNN}
**操作モード**: {CREATE/APPEND/UPDATE}
**失敗理由**: {競合発生 / file write error / etc}
**ユーザーアクション**: 手動で競合を解決してください
```
