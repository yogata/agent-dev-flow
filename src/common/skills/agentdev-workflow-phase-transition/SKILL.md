# phase-transition workflow スキル

phase-transition command の workflow 実装本体である。
利用者の遷移判断を受け、採用済みの工程関係から後続工程を解決し、確定した遷移を正規状態へ一度だけ記録する制御構造を所有する。
本スキルは利用者の工程完了判断と技術的な状態切替を分離し、技術的失敗を成功として扱わない。

phase-transition command は公開 interface（入出力契約・ガードレール）と本スキルへの dispatch のみを持ち、本スキルが workflow 実装本体を提供する。

## 入力

- phase-transition command から渡される遷移の指示（自然言語。対象工程、遷移意図、取消の意図を含む）
- 現在の会話コンテキスト

## 出力

- 遷移の記録結果（記録先、後続工程の解決結果、前工程の過去工程化の伝達、前置工程の既知義務と未確認範囲）
- 解決不能・保存失敗・中断後再実行では、未成立部分と再開可能な情報を分離した報告

本操作は遷移記録の保存を行う操作であり、保存先の一覧には遷移記録の保存先を含める。取消時は記録しない旨を報告する。機械検証は遷移記録の照会・後続候補の判別を機械的に実行した場合のみその結果を報告し、実行していない場合はその旨を報告する。返却時点で裏で継続している処理はない（次工程の初回テーマ形成への接続は案内のみである）。

完了報告は、次を必須要素として含める。操作の性質に応じて値が変わり、保存を行わない操作では保存しない旨を、機械検証を実行していない場合はその旨を、完了報告に含める:

- 保存した成果物・記録の保存先の一覧
- 実行した機械検証とその結果
- 操作の返却時点で裏で継続している処理の有無

採用内容の範囲が未決事項と重なる場合はその旨を、検討方向の差し替えを受領する場合は旧方向が持っていた前提の行き先（継承または破棄）を、完了報告に含める。採用・採用根拠の判断自体は既存の採用根拠の規律が担い、この報告は判断を代理確定しない。

機械検査の合格は意味品質の保証ではなく、必要条件であって十分条件ではない。

## 副作用

- 遷移記録（`.agentdev/phase/transitions/` 配下）の作成・読取。遷移記録の削除は行わない
- Decision、REQ、Design 等の正規成果物は更新しない

## workflow model（STEP model 対象外）

本スキルは対話操作完結型の workflow であり、STEP model の対象外である。
resume point / export / import を持たない。各遷移操作が1完結単位であり、遷移記録自体が durable state（永続状態）であるため、中断後の同一要求再実行では遷移記録から現在状態を再構成する（下記「中断後の再実行と復元」）。
工程一覧のラベルは順序ラベルであり resume point ではない。

| 工程 | 名称 | 内容 |
|---|---|---|
| 1 | 対象工程と遷移意図の特定 | 指示と会話文脈から遷移対象の現在工程と遷移意図（進行・取消）を特定する。正規情報から採用済みの工程関係を解決する。解決不能な場合は遷移を実行せず、不足する情報と再開条件を報告する |
| 2 | 遷移判断の受領 | 遷移の完了判断をユーザーから受け取る。参考の懸念は具体的な事実と推測を区別して必要な場合だけ再確認し、ユーザーが続行を選べば推論だけで遷移を止めない。ユーザーが取消を選んだ場合は「取消時の現在工程維持」へ進む |
| 3 | 後続工程の解決 | 採用済みの工程関係から後続工程を解決する（下記「後続と前置の解決」） |
| 4 | 前置工程の情報収集 | 前置工程が複数ある場合は、前置工程の既知義務と未確認範囲を収集して遷移の報告に含める |
| 5 | 遷移の記録 | 遷移記録の保存を実行する（下記「遷移の記録と一度実行の制御」） |
| 6 | 報告と次工程への接続 | 前工程の過去工程化、後続工程の解決結果、前置工程の既知義務と未確認範囲を報告する。次工程の初回テーマ形成への接続を案内するが、形成の実行を遷移の記録と結合しない |

ファイル検索・内容検索・ディレクトリ列挙は実行基盤の内蔵ツール（ファイル検索、内容検索、読み取り）を使用し、bash 内蔵コマンド（grep、ls 等）を標準手順としない。ただし遷移記録の保存・読取は下記の決定的処理 script の呼出しであり、この限りではない。

## 遷移判断の受領

遷移の完了判断はユーザーの単独操作による。本スキルは次の規律に従う。

- ユーザーの遷移判断なしに遷移を記録しない。会話の流れからの推論で遷移を確定しない
- 参考の懸念は具体的な事実と推測を区別して提示し、必要な場合だけ再確認を求める。再確認の要求を遷移の前置必須条件としない
- ユーザーが続行を選んだ場合、未解決の懸念を理由に遷移を止めない（未採用改善候補・推測は遷移の妨げにならない。確定違反を検出した場合は遷移の記録の前にユーザーへ提示し、判断を求める）

## 後続と前置の解決

採用済みの工程関係は正規情報から解決する。優先順は次のとおりであり、解決の根拠を遷移の報告に含める。

1. 採用済み規約（採用済み工程・工程間関係の宣言。解決の機械的部分は Capability Skill `agentdev-adopted-conventions` の決定的解決器を利用できる）
2. 既存の有効な実効規約（宣言がなく実効運用がある場合の現行運用）
3. 会話で利用者が明示した工程関係（上記で解決できない場合の利用者指定）

採用済みの宣言が読み取れない場合は判断を留保し、解決不能として報告する（未採用参照の欠落を誤判定の根拠にしない）。

| 後続工程の条件 | 取扱い |
|---|---|
| 後続0件 | 終端として扱う。架空の工程を作らず、前工程を完了済みの過去工程として記録する遷移のみを実行する |
| 後続1件 | 一意に解決する。ユーザーへ選択を求めず、解決した後続工程を遷移先とする |
| 後続複数件 | 解決せず、候補一覧を提示してユーザーの選択を求める。選択を受けた後続工程のみを遷移先とする |

前置工程が複数ある場合は、各前置工程の既知義務と未確認範囲を収集して遷移の報告に含める。既知義務の欠落や未確認範囲の省略により遷移を中止しない（義務と未確認範囲は引き継ぎ情報であり、前置必須条件ではない）。

後続候補の0/1/複数の判別と、前置工程の既知義務・未確認範囲の収集は正規情報の読み取り判断である。判別の機械的部分は下記の決定的処理 script（後続解決）が担う。

## 遷移の記録と一度実行の制御

遷移記録は `.agentdev/phase/transitions/` 配下の domain state とする（工程駆動の状態領域。テーマ正本・識別状態と共通の `.agentdev/phase/` 配下配置方針に従う）。遷移記録の物理形式・操作契約は本スキル配下の決定的処理 script が所有する。

終端の遷移（採用済みの工程関係に後続工程が存在しない遷移）は、架空の後続工程を作らない記録形式で保存する。終端の記録は toPhase に後続不在を表す表現（`null`）を記録し、保存された記録から終端であることを再構成できる。記録形式の正は決定的処理 script が所有する schema であり、I/O 契約の詳細は `scripts/README.md` を参照する。

記録の手順:

1. **既存記録の検出**: 対象遷移を識別する冪等キーで既存の遷移記録を検索する。決定的処理 script の照会操作を使う
2. **二重実行の防止**: 既存記録が存在する場合は保存を実行せず、既存記録の内容を復元して報告する（下記「中断後の再実行と復元」）
3. **保存の実行**: 既存記録が存在しない場合のみ保存を実行する。保存の成否は script の実行結果で判定する
4. **保存失敗の扱い**: 保存の書込みが失敗した場合は遷移の成功報告を出さない。失敗内容と再実行可能な条件を報告し、ユーザーの遷移判断は維持したまま再実行を可能にする

遷移記録の削除は本スキルの操作に含めない（取消は記録の実行前に完了する。記録後の遷移の正規改訂は正規改訂の経路に従う）。

## 取消時の現在工程維持

ユーザーが取消を選んだ場合、遷移記録の保存を実行せず、現在工程を維持する。
取消の報告では、維持された現在工程と取消の根拠を伝える。取消によって既存の遷移記録・正規成果物を変更しない。

## 初回テーマ形成との独立性

遷移の記録の成立は次工程の初回テーマ形成から独立する。

- 初回テーマ形成が未実施でも、遷移記録と現在工程・既知義務の参照は維持される
- 初回テーマ形成が失敗しても、遷移の記録を取り消さない。形成の失敗は形成の再実行条件として報告する
- 本スキルは初回テーマ形成を実行しない（形成は独立した公開操作。遷移記録の成立後に案内するのみ）

遷移後に確定済み設計から実装・検証へ接続する場合の接続先は、確定済み詳細設計と有限な実装対象・既存検証条件を正規入力として実装・検証へ接続する case 系実行経路（`/agentdev/case-auto`）である。接続の実行は遷移の記録から独立し、本スキルは実装・検証を実行しない。

## 中断後の再実行と復元

中断後に同一の遷移要求が再実行された場合、次の手順で復元する。

1. 既存の遷移記録を冪等キーで検索する
2. 記録が存在する場合は、確定した遷移だけを記録から復元して報告する。遷移を再記録せず、二重実行を防ぐ
3. 記録が存在しない場合は未成立として通常の手順で遷移を実行する
4. 技術的失敗（工程特定の失敗、書込みの失敗）と利用者の工程完了判断を分離して報告する。技術的失敗を成功として報告せず、未成立部分を明示する

## GitHub 版と Local 版の両対応

本スキルは GitHub 版・Local 版のいずれの正規利用経路からも単独起動できる（対応する command 定義が共通原本から両版へ投影される）。
遷移記録は `.agentdev/phase/transitions/`（両版共通の domain state 配置）に保存し、backend の物理表現に依存しない。
Local 版で遷移後の作業が実装作業を伴う場合は、既存実行経路の突合契約（ローカル記録と実 Git 取り込み結果の独立突合。成功報告だけでは確定しない）に従い、本スキルは突合を実行しない。

## 決定的処理 script（公開操作契約）

遷移記録の保存・照会・後続候補の判別は、本スキル配下 `scripts/` の決定的処理 script が担う。

| script | 操作 | 入力 | 出力 |
|---|---|---|---|
| `scripts/src/lookup.ts` | 遷移記録の照会 | `--dir`（遷移記録ディレクトリ）、`--key`（冪等キー） | 記録の有無と内容（JSON） |
| `scripts/src/apply.ts` | 遷移記録の保存（冪等） | `--dir`、`--input`（遷移記録 JSON パス。`-` で stdin） | 保存結果（新規記録・既存検出を区別した JSON） |
| `scripts/src/resolve-successor.ts` | 後続候補の判別 | `--input`（候補 JSON パス。`-` で stdin） | 終端・一意・複数の判別結果（JSON） |

実行は bun 起点で `bun ./.opencode/skills/agentdev-workflow-phase-transition/scripts/src/apply.ts ...` 形式（配布投影側）または原本パス直指定で実行する。script の I/O 契約の詳細は `scripts/README.md` を参照する。

## 共通制約

- 遷移判断の代理確定をしない。ユーザー合意が必要な設計判断を本スキルで確定しない
- 正規成果物（Decision、REQ、Design 等）を直接更新しない
- decision 成果物は、工程をまたぐ意思決定・未解決課題の管理・方式選択を記録する成果物である。正本の優先度（source-of-truth priority）は `inspect-docs` コマンド定義「不変条件」を、decision の記録内容の規定は document-model Design「責務マトリックス」を参照する（定義本文は複製しない）
- 遷移記録は最小情報に限る。進行度・完了率・残作業を記録する恒久台帳を設けない
- project extension（`.agentdev/extensions/skills/agentdev-workflow-phase-transition.yaml`）が存在する場合は読み込み、破損していれば無視して標準動作で続行する（fail-open）
