# backlog 一括整理（一気通貫実行）

backlog 整理サイクル（inspect-docs による文書診断、learning、intake、inspect の3昇格系統、backlog-review による統合と RU 生成）を1回の起動で一巡させ、さらに承認確定した RU 一式を、要件定義・実行・検証・統合・一式全体の完了判定・パッチリリース作成まで接続して実行する（一気通貫実行）。
要求入口の1つ（backlog-driven の要求蓄積入口）であり、検出事項と採用済み成果物を統合して RU として要求を蓄積する。一気通貫実行では、承認確定した RU 一式を単一の req-define 実行と単一の case-auto 実行へ接続し、一式全体の完遂判定とパッチリリースまで進める。既存の利用者判断境界（backlog-review の RU 承認、req-define の壁打ち、リリース条件・公開権限の確認）は維持され、次工程開始のためだけの手動コマンド入力を要求しない。

## 入力

- なし（対象状態は各子コマンドの永続状態と set-state から解決する）

## 出力

- 各子コマンドの既存出力（`.agentdev/inspect/inbox/` の検出事項、各 promoted/、`.agentdev/backlog/req-units/RU-*.md` 等、子コマンド公開契約どおり）
- backlog-auto 全体の実行結果報告（工程別結果、停止理由、再開コマンド提示を含む共通実行契約形式）
- 一気通貫の実行結果報告（工程別結果、全体完了判定結果、リリース結果または保留理由、再開経路を含む共通実行契約形式）

## 副作用

- 各子コマンドの既存副作用（`.agentdev/` 配下の成果物作成・削除、git commit/push、ユーザー対話）を子コマンド公開契約どおりに発生させる
- set-state の作成・更新（`.agentdev/` 配下、req-units と draft の配置外）
- git タグ作成・push（リリース時。版番号・リリース条件・公開操作はパッチリリース規則の Decision に従う）
- 追加公開成果物の対応（ADF本体では GitHub Release の草稿作成・読み戻しと、公開権限の確認で利用者が公開を明示承認した場合の公開（カタログ内操作 release_publish。承認根拠必須・draft 解除のみ）までを Custom Tool カタログ経路で実行する。公開は利用者が草稿作成とは別に明確に認めた場合に限る）

## HITL 境界

- 各子ワークフローの既存 HITL 境界（backlog-review の RU 承認、req-define の壁打ち・承認等）を維持する。既存境界の自動化は行わない
- 一気通貫実行の利用者判断境界: 開始時基準点確認（初期状態・到達不能正式タグの場合の停止）、リリース条件確認、公開権限確認
- 複数系統が判断待ちの場合はユーザー対話を直列化し、対象子ワークフローを識別可能に表示する

## 停止条件

- inspect-docs が blocked / failed の場合、下流工程を開始せず停止する
- 昇格3系統に blocked / failed / 未完了が残る場合、backlog-review を開始せず停止する
- 一気通貫実行の停止条件: 基準点確定不能（初期状態・到達不能正式タグを含む）、要件定義・実行の blocking 停止伝播、全体完遂不成立、リリース条件・権限不成立（完遂済み・リリース保留として報告）、公開途中失敗（読み戻し再開可能な状態で報告）
- 再実行時は子ワークフローの既存再開契約と set-state による一式再開経路に従う

## workflow

本コマンドは workflow 実装本体を `agentdev-workflow-backlog-auto` スキルへ委譲する（DEC-{N}、REQ-{NNNN}-{NNN}）。
工程、分岐、状態遷移、再開、停止などの高水準の実行構造、子ワークフロー（inspect-docs、learning-promote、intake-promote、inspect-promote、backlog-review、req-define、case-auto）の権威情報源と読込主体の割当ても同スキルの制御平面（control plane）が所有する。
backlog-auto は子ワークフロー内部の分類、評価、昇格、RU 生成ロジック、並列実行アルゴリズムを再実装しない。一気通貫実行（set-state 永続化、基準点確認、全体完了突合、リリース手順と再開経路）の実行構造も同スキルが所有する。

## 不変条件

工程上の選好を反映した肯定形の不変条件:

- 実行順序は inspect-docs、昇格3系統（learning-promote、intake-promote、inspect-promote）、backlog-review の順とし、工程間の開始条件ゲートを制御する。inspect-docs が正常終了する前に昇格3系統を開始せず、昇格3系統すべてが正常完了または対象なしで終了する前に backlog-review を開始しない
- 昇格3系統相互に先行依存を設けない。1系統の blocked、failed で独立して進行可能な他系統を停止しない
- 同一作業ツリーに対する競合する Git 操作、共有成果物への競合書き込み、ユーザー対話を直列化する。ユーザー対話は対象子ワークフローを識別可能に表示する
- 各子ワークフローの HITL 境界、安全境界、停止条件、自動昇格 opt-in を子ワークフロー側の所有として維持する。通常の backlog-auto 実行で inspect-promote の `--auto` を暗黙的に有効化しない
- 対象なし終了を正常終了として扱う。昇格3系統で新規 promoted が0件でも全系統正常終了後に backlog-review を実行し、実行前から存在する promoted を処理対象にできる
- 一気通貫実行の対象は backlog-review で承認確定した RU 一式に限定し、一式と無関係な既存 RU・ドラフト・Issue を取り込まない
- 一式は単一の req-define 実行（入力は一式 RU の明示列挙）で処理して単一の要件doc に確定し、実行は当該要件doc を明示指定した単一の case-auto 実行として接続する。引数なし全件処理と個別ドラフトごとの複数 case-auto 起動を用いない
- 一式から複数の独立した実行可能 Issue が生じた場合の並列実行は、case-auto 側の既存の共有 active Issue task 上限と横断補充に従う。一式を複数グループへ分断して先行グループの全完了を待つ逐次化を行わない
- 一式全体の完遂は、set-state の義務スナップショットと対応表を正として、要件定義・実行対象・検証結果の過不足ない突合と必要な範囲の検証結果の成立によってのみ判定する。個別の Issue 終了・PR merge のみで完遂としない
- 一式の実行開始時に最後の正式リリース（版番号規則はパッチリリース規則の Decision に従う）と開始時点のコミット ID を確定し、一式全体の完遂前に新規のタグ・リリースを作成しない。完遂後はタグ付与前に差分と一式分の実変更の突合を行い、無関係コミットの混入を検出した場合は報告して利用者判断を求める
- RU 0 件またはリリース対象となる実変更がない場合はリリースを作成せず報告する。正式なバージョン基準がなく採用済み初期バージョン規則も確認できない場合は、初期バージョン番号を決定せず停止して利用者判断を求める。公開方式・権限・環境が不足する場合も対象と理由を報告し、リリース完了としない
- 中断・再実行時は set-state から同じ一式の対象と進捗を復元し、未完了部分から再開する。完了済み操作を重複実行せず、backlog-auto の再実行は set-state から完遂済み Case を検出して全体完了判定以降の段階から再開できる
- 公開途中の失敗・中断時は既存結果を読み戻し、タグの移動・再作成、第二のパッチ番号の消費なしに未完了部分から再開する
- 中断、再実行時は子ワークフローの既存再開契約を利用する。inspect-docs は中断時に先頭から再実行する
- 既存5コマンドを従来どおり単独実行できる。backlog-auto は子ワークフローの公開契約を変更しない（子ワークフロー自身の契約変更は各コマンドの正規変更経路による）

## ガードレール

否定規則は破壊的操作、state 破壊等の硬い境界に限定する:

- 子ワークフロー内部の分類、評価、昇格、RU 生成を代行しない（各子 Workflow Skill の責務）
- inspect-promote の `--auto` を明示 opt-in なしに有効化しない
- capture 系コマンド（learning-capture、intake-capture、intake-from-github）と inspect-skills を自動起動しない
- req-define と case-auto は一気通貫実行の接続工程（要件定義接続、実行接続）として workflow 委譲経由でのみ起動する。接続工程を外れた自発的な起動を行わず、GitHub Issue / PR 作成を直接実行しない（Issue / PR 作成は case-auto 実行の内部責務）
- req-define の壁打ち・承認境界、backlog-review の RU 承認、リリース条件・公開権限の確認を自動化しない
- 版番号の major/minor 自動判定、同一実行での二つの版番号の消費、既存タグの移動、本番環境への自動配備を行わない
- 子ワークフローの定義ファイルと公開契約を変更しない（子ワークフロー自身の契約変更は各コマンドの正規変更経路による）
