# 課題管理

開発過程で生じた未解決事項を追跡Issueとして管理する人間向け公開入口。
ユーザーは自然言語で意図を伝え、現在の会話文脈、対象追跡Issue、状態から必要な操作（起票、検索、参照、更新、検討経過追加、保留、再評価、実行準備完了、解決、反映確認、クローズ、再オープン）を判断して実行する。

追跡Issueは GitHub Issue を Case Issue（req/case パイプラインの実行票）と共有する管理単位であり、論理 role により区別される。Case Issue の操作（case-open、case-run、case-close、case-update）は本コマンドの対象外。
サブコマンド、引数、ラベル名等の操作文法や GitHub 実装詳細をユーザーに要求しない。内部実装で明示的な操作種別を持つことは禁止しない。

## 入力

- ユーザーの自然言語による指示（例: 「この論点を課題として残して」「未解決の課題を確認したい」「保留していた課題を再検討して」）
- 現在の会話コンテキスト（対話中の未解決事項、対象追跡Issue、状態）

## 出力

- 追跡Issueの作成・更新（書き込み操作時）
- 検索・参照結果、操作結果の報告（セッション内テキスト出力）

## workflow

本コマンドは workflow 実現本体を `agentdev-workflow-issue` スキルへ委譲する。
工程、分岐、判定（操作種別判定、課題化判定、Capability Skill と Tool 操作契約への委譲、完了報告）は同スキルの control plane が所有する。

## 不変条件

工程上の選好を肯定形の不変条件として示す:

- ユーザーは自然言語で意図を伝え、課題管理側が会話文脈、対象追跡Issue、状態から必要な操作を判断する。サブコマンド、引数、操作文法の暗記を要求しない
- 追跡Issueの読み書きは GitHub I/O を担る Custom Tool（`agentdev_gh`）の操作契約経由のみ。上位層で物理ラベルへの写像を再実装しない
- 課題管理能力の利用に本コマンドの明示実行を必須としない。各 workflow は未解決事項を認識した場合に課題管理 Capability Skill（`agentdev-issue-tracking`）の知識を直接利用できる
- 課題化は「現在の作業で解決できず、かつ将来の設計、実装、検証、合意等に影響する未解決事項」に限定する。正規成果物の確認等でその場で解決可能な疑問は、課題化前に解決を試みる。既存追跡Issueを検索して重複を避ける
- 正規成果物または現在の会話で結論が確定している事項は、その結果を追跡Issueへ反映できる。ユーザー合意が必要な設計判断を課題管理側で勝手に確定しない
- 課題の解決結果の正規成果物への反映は、当該成果物を所有する ADF 能力へ委譲する。課題管理側は結論、反映先、反映状況の追跡に徹する
- 追跡Issueの存在を実行許可としない。実行が確定した場合は req-define 等の正規要件化・設計経路へ引き継ぎ、Case Issue の生成は case-open が行う

## ガードレール

硬い境界（破壊的操作・state 破壊等の否定規則）に限定する:

- 追跡Issueの読み書きは Custom Tool（`agentdev_gh`）の操作契約経由のみ（リポジトリ内の課題ファイルやローカルIssue保存先の直接読み書きは禁止）
- GitHub 版でリポジトリ内に課題ファイルを作成し、commit しない
- GitHub 実装詳細（サブコマンド、ラベル名、Issue Type、Field 名等）の把握をユーザーに要求しない
- Decision、REQ、Design 等の正規成果物を直接更新しない（反映は当該成果物を所有する ADF 能力への委譲による）
- ユーザー合意が必要な設計判断を代理確定しない。既存の承認、判断境界を迂回しない
- 課題起票時に反映先を決め打ちしない
- 解決済みの追跡Issueを反映完了または反映不要の確認なしにクローズしない
