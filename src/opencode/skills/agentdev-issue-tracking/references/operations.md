# 課題管理の操作手順（operations）

本ファイルは `agentdev-issue-tracking` SKILL.md から遅延読み込みされる、11操作の実行手順と反映追跡の委譲規則である。
課題ファイルの形式（frontmatter、セクション、状態保存値）は [issue-file-format.md](issue-file-format.md) を正とする。

## 1. 検知

要件定義、方式設計、HLD、LLD、パラメータ設計、実装、レビュー、検証、外部確認等の作業中に未解決事項を認識した場合、課題化候補かどうかを判定する。

判定基準:

- 現在の作業で解決できず、かつ将来の設計、実装、検証、合意等に影響する未解決事項を課題化候補とする。
- 正規成果物の確認等によってその場で解決可能な疑問は、課題化前に解決を試みる。
- すべての疑問、TODO、一時エラーを無条件に課題化しない。

正規成果物または現在の会話で結論が確定している事項は、その結果を課題へ反映できる（ユーザー合意が必要な設計判断を課題管理側で勝手に確定しない）。

## 2. 新規起票

1. `docs/issue-list/` 配下の既存課題 ID の最大番号に 1 を加えて課題 ID を採番する。
2. [issue-file-format.md](issue-file-format.md) §7 のテンプレートで `docs/issue-list/ISL-{NNN}.md` を作成する。起票時点で反映先を決め打ちしない。
3. frontmatter の `related_artifacts` に関連成果物（パスまたは ID）を記録する。関連成果物がない場合は空リスト `[]` を記録する。
4. 検討経過に起票エントリ（`- YYYY-MM-DD: 課題を起票した`）を記録する。
5. 変更は実施中の工程（workflow）の成果物コミットに含めて永続化する。

作成後、スクリプトの形式検証（`--validate`）で frontmatter と必須セクションを確認できる。

## 3. 検索・参照

検索、一覧、参照には `scripts/src/list.ts` を使用する。全課題ファイルの本文に目を通すことを前提としない。

| 目的 | 実行 |
|---|---|
| 全課題の一覧と状態別件数 | `--root .` |
| 保留課題と再評価条件の要約 | `--root . --status on-hold` |
| 作業対象（関連成果物）に関連する課題 | `--root . --related <パスまたはID>` |
| 特定課題の参照 | `--root . --id ISL-{NNN}` で対象を特定し、当該課題ファイルのみ本文まで読む |

保留理由と再評価条件の詳細が必要な場合は、`--status on-hold` で対象を特定し、当該課題ファイルの `## 再評価条件` セクションを読む。

## 4. 更新

1. 対象課題ファイルを開き、該当セクションを更新する。
2. frontmatter `updated` を更新日へ変更する。
3. 状態が変わる場合は `status` を変更し、検討経過に遷移と理由を追記する。
4. 更新は実施中の工程の成果物コミットに含めて永続化する。

## 5. 検討経過の追加

検討に進展があった場合（選択肢の追加、判断材料の入手、不足情報の解消等）、`## 検討経過` に1エントリ1行で追記する。既存エントリは書き換えない。frontmatter `updated` を更新する。

## 6. 保留

結論を出せず判断を先送りする場合:

1. `status` を `on-hold` に変更する。
2. `## 再評価条件` セクションを追加し、`### 判断保留の理由`（なぜ現在判断できないか）と `### 再評価条件`（何が成立すれば再評価するか）を記述する。
3. frontmatter `reevaluation` に再評価条件の要約（1文）を記録する。
4. frontmatter `updated` を更新し、検討経過に保留と理由を追記する。

保留した課題は保存して忘れない。関連する作業、設計、レビュー、分析を行う際に `--status on-hold` と `--related` で条件成立を確認する。

## 7. 再評価

保留課題の再評価条件が成立した場合、または関連作業で条件成立が確認された場合に再評価する。再評価後は次のいずれかを選択する。

| 状況 | 処理 |
|---|---|
| 結論が出た | §8「解決」へ進む（`status` を `resolved` に変更） |
| まだ判断できない | `### 判断保留の理由` と `### 不足情報` を更新し、`on-hold` を継続する |
| 課題自体が消滅した | 対応不要という結論で解決する（§8） |
| 必要な変更が確定した | 解決し、反映先へ反映する。変更が要件レベルの場合は RU 化を検討する（§9） |

再評価の実施と結果は検討経過に追記し、frontmatter `updated` を更新する。

## 8. 解決

課題に対する結論が出た場合:

1. `status` を `resolved` に変更する。
2. `## 結論` セクションに結論を記述する。対応不要の場合は対応不要という結論と理由を記述する。
3. 結論を正規成果物へ反映する必要がある場合、`## 反映先` セクションを追加し、反映先と反映内容、状況（`未反映`）を記録する。反映不要の場合は反映不要の理由を記録する。
4. frontmatter `updated` を更新し、検討経過に解決と結論の要約を追記する。

解決結果は Decision、REQ、HLD、LLD、その他の Design、パラメータ設計、RU、実装、検証方法、対応不要のいずれにもなり得る。解決済みは結論が出た状態であり、反映の確認まで完了した状態ではない。

## 9. 反映確認

`## 反映先` に未反映の項目がある場合、反映を進める。

1. 反映先の種別に応じ、当該成果物を所有する ADF 能力へ更新を委譲する（§12）。
2. 反映が完了したら `## 反映先` の該当行の状況を `反映済み` に変更する。
3. frontmatter `updated` を更新し、検討経過に反映完了を追記する。

変更が要件レベル（新規要件、要件変更）に及ぶ場合は、要件パイプライン（要件の壁打ちから保存、Case 化）または RU 化の経路へつなげる。RU 化が必要な変更は intake パイプライン（`agentdev-intake-pipeline`）で取り込み、`/agentdev/backlog-review` による RU 生成に委譲してよい。

## 10. クローズ

反映の確認まで完了した場合にクローズする。

1. 前提を確認する: `status` が `resolved` であり、`## 反映先` の全行が `反映済み` または `反映不要` であること。未反映の行がある場合はクローズせず、§9「反映確認」を完了させるか、反映不要の確認を取る。
2. `## クローズ確認` セクションに反映先ごとの確認結果と確認日を記録する。
3. `status` を `closed` に変更し、frontmatter `updated` を更新し、検討経過にクローズを追記する。

クローズ済みの課題も `docs/issue-list/` 内に残置し、履歴として同一体系内で追跡する。形式検証（`--validate`）により、`resolved` に必要な `## 結論`、`closed` に必要な `## 反映先` と `## クローズ確認` の欠落を機械的に検出できる。

## 11. 再オープン

クローズ済みの課題を再検討する必要が生じた場合:

1. `status` を `open` に戻す。
2. 検討経過に再オープンの理由と経緯を追記する。
3. frontmatter `updated` を更新する。
4. 必要に応じて `## 結論`、`## 反映先`、`## クローズ確認` の内容を残したまま、再検討の状況を各セクションへ追記する。既存の検討経過、結論の記録は書き換えない。

## 12. 反映追跡と委譲

課題管理能力自身は Decision、REQ、Design 等すべての成果物の更新責務を直接所有しない。何が結論となったか、どこへ反映すべきか、実際に反映されたかを課題ファイルで追跡し、成果物の更新は当該成果物を所有する ADF 能力へ委譲する。

| 反映先の種別 | 委譲先 |
|---|---|
| Decision（判断理由を保持すべき結論） | `agentdev-decision-file-manager` |
| REQ（要件行の追加、変更） | `agentdev-req-file-manager`（要件パイプライン経由） |
| Design（HLD、LLD、その他の Design、パラメータ設計） | `agentdev-design-file-manager` |
| RU（変更要求の要件化） | intake パイプラインで取り込み、`/agentdev/backlog-review` で RU 生成 |
| 実装、検証方法 | 当該変更の Case（req/case パイプライン）へ反映し、GitHub Issue は `agentdev-issue-management` の手続きで扱う |
| 対応不要 | 委譲不要。結論と理由を課題ファイルが保持する |

委譲先での更新が完了した事実は、委譲元の課題ファイルの `## 反映先` 状況と `## クローズ確認` に記録して追跡を完結させる。
