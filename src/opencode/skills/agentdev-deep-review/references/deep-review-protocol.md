## 対象と役割

深掘りレビューは、対象成果物の主張を五つの独立したレーンで検討し、根拠付きの報告を親エージェントへ渡す助言手順である。
親エージェントはレビュー範囲を定め、各レーンの結果を統合し、必要な DELTA を実装責任者へ渡す。
レビューサブエージェントは割り当てられたレーンを読み取り専用で確認し、訂正や承認を行わない。
本プロトコルの結果は助言であり、ユーザー承認、実装実行、又は強制的な統制判定にはならない。

## 五つの標準レーン

初回レビューでは、次の五つのレーンをすべて独立して実行する。
標準レーン以外を既定のレーンとして追加しない。

| レーン | 確認する内容 | 必要な証拠 |
|---|---|---|
| `目的・制約` | 目的、明示された制約、非対象の整合 | 対象の要求、範囲記述、利用者が示した制約 |
| `設計・責務境界` | 主体の責務、入出力、決定権限、副作用境界の一貫性 | 設計記述、契約、責務を示すソース |
| `統制・ガバナンス` | 判断権限、例外処理、承認の扱い、停止条件の明示 | 適用方針と権限又は例外を示すソース |
| `履歴・追跡性` | 由来、先行判断、変更理由の主張の追跡可能性 | 主張の出所、変更記録、参照先 |
| `証拠・検証可能性` | 結論、測定、検証済みという主張の再確認可能性 | 確認手順、実行記録、読み取り可能な結果 |

各レビューサブエージェントは一つのレーンだけを担当する。
初回レビューでは、他レーンの途中報告を入力に含めない。

## レビュー入力と証拠

親エージェントは、対象、確認目的、対象範囲、読み取り可能なソース、各レーンに必要な確認をレビュー入力に含める。
各必須確認には、同じレビュー状態で一意な `check_id` と確認基準を付ける。
レビュー対象に関係しないソースを、結論を補強するためだけに追加してはならない。

有効な証拠は、レビュー時点で実際に読み取れる対象ファイル、閲覧可能な記録、又はレビュー入力に含まれる確認可能な指示である。
証拠はソースの識別子、確認した箇所、そこから導く主張を対応付ける。
リポジトリ内のソースを示す場合は、前方スラッシュのリポジトリ相対パスを使う。
テスト出力又はコマンド出力を引用する場合は、実際の実行記録、実行対象、結果を読み取れる形で確認する。

validator の結果を引用する場合は、実行識別子、対象範囲、終了状態、対象変更に起因する検出事項、既存又は無関係な検出事項を分けて記録する。
repository 全体の終了状態だけを、対象変更の `FAIL` 根拠にしてはならない。
対象変更との関係を確認できない場合は `PARTIAL` とする。

存在を確認できない先行承認、先行判定、テスト出力、コマンド出力を証拠として記載してはならない。
ソースへ解決できない引用、記憶だけに依存する要約、推測で補った由来を証拠として記載してはならない。
対象が先行承認又は先行判定を主張しながら確認可能な出所を示さない場合、その主張自体を根拠に `履歴・追跡性` の `FAIL` とする。
必要なソースが実際に利用不能であり、対象がその不在を事実として主張していない場合だけ、該当レーンを `PARTIAL` とする。

## finding 契約

各レーンは、検出事項又は肯定的な証明を source-grounded finding として親エージェントへ返す。
`PASS` の報告にも、必須確認を完了したことを示す肯定的な claim と evidence を含める。

| フィールド | 内容 |
|---|---|
| `lane` | 報告を作成した標準レーン名 |
| `id` | 同一 review-state で追跡できる一意識別子 |
| `check_id` | 対応する必須確認の識別子 |
| `target` | 確認した成果物又は読み取ったソースの範囲 |
| `claim` | 証拠から導く確認結果又は矛盾の内容 |
| `evidence` | 実在し読み取り可能なソース、その箇所、観測内容 |
| `severity` | 適合証明は `none`、不適合又は改善事項は影響度としての `high`、`medium`、`low` |
| `confidence` | 証拠の直接性としての `high`、`medium`、`low` |
| `verdict` | レーン判定へ与える `PASS`、`FAIL`、`PARTIAL` の効果 |
| `recommended_action` | 維持、最小 DELTA、又は必要な証拠の取得 |
| `notes` | 前提、未確認範囲、再レビュー条件 |

`evidence` にソースと観測内容を記録できない finding は無効である。
無効な finding を `FAIL` の根拠に使ってはならない。
必要な確認を完了できない原因が必要なソース又は必要なレーンを担当するレビューの利用不能であれば、無効な finding を作らず `PARTIAL` の理由を記録する。

### 必須確認の網羅表

各レーンは finding に加えて、すべての必須確認を次の網羅表で報告する。

| フィールド | 内容 |
|---|---|
| `check_id` | 入力で付与された必須確認の識別子 |
| `status` | `verified`、`failed`、`unavailable` のいずれか |
| `finding_ids` | この確認を証明する finding の id |

`PASS` は、すべての `check_id` が `verified` であり、各項目に一つ以上の有効な finding が対応する場合だけに使う。
`failed` が一つでもあれば `FAIL` とする。
`unavailable` が一つでもあり `failed` がなければ `PARTIAL` とする。

## 判定規約

各レーンは `PASS`、`FAIL`、`PARTIAL` のいずれか一つを返す。

| 判定 | 条件 | 親エージェントの扱い |
|---|---|---|
| `PASS` | 全必須確認の完了、読み取り可能な証拠、適合の肯定的な証明 | レーンの証明を保持 |
| `FAIL` | 読み取り可能な証拠で確認したブロッキング矛盾 | finding を DELTA の入力にする |
| `PARTIAL` | 必要な証拠又は必要なレーンを担当するレビューの利用不能 | 利用不能な対象の明記と利用可能後の再レビュー |

`PASS` は `FAIL` が見つからなかったことを意味しない。
`PASS` は、必須確認が完了したという積極的な証明を必要とする。
`FAIL` は、未確認の懸念、好み、又は推測だけでは成立しない。
`PARTIAL` は、時間不足、判断の保留、又は修正待ちの言い換えとして使わない。

## 読み取り専用の委譲契約

委譲の実行方法は、起動主体、実行モデル、実行基盤に依存しない。
具体的な委譲では、親エージェントが各レーンに同じ対象パケットを渡し、レーン固有の確認だけを追加する。

### inputs

| 入力 | 内容 |
|---|---|
| `review_target` | 確認対象と対象範囲 |
| `lane` | 五つの標準レーンのうち一つ |
| `required_checks` | そのレーンで完了が必要な確認 |
| `readable_sources` | 実際に読み取ることができるソースと所在 |
| `prior_review_state` | 再レビュー時に保持すべき earlier finding と earlier verdict |
| `delta` | 再レビュー時の訂正内容と影響を受ける前提 |

### side_effect_boundary

レビューサブエージェントは読み取りと報告だけを行う。
レビューサブエージェントはファイルを編集しない。
レビューサブエージェントは commit、push、Issue 又は PR の作成を行わない。
レビューサブエージェントはユーザー承認を取得又は主張しない。
レビューサブエージェントは DELTA を適用しない。

### output_contract

`required_checks` は `check_id`、確認基準、必要な証拠を含む。

レビューサブエージェントは、担当レーン名、一つのレーン判定、finding 契約に従う報告、必須確認の網羅表、根拠のない主張を含まない要約を返す。
`PASS` の場合は肯定的な証明を返す。
`FAIL` の場合はブロッキング矛盾と最小 DELTA の候補を返す。
`PARTIAL` の場合は利用不能な証拠又はレーンのレビューと、再開条件を返す。

### capture_handoff

親エージェントは各報告を受け取り、finding、判定、参照したソース、前提、再レビュー条件を review-state に保持する。
レビューサブエージェントは報告を対象成果物へ直接反映しない。
親エージェントは報告を統合しても、レーンの `FAIL` 又は `PARTIAL` を `PASS` へ変更しない。

### 委譲依頼の構成

各レビュー依頼には、次の情報をこの順序で含める。

1. 担当レーンと確認対象を示す。
2. 必須確認と読み取り可能なソースを示す。
3. finding 契約と判定規約を示す。
4. 再レビュー時は前回の review-state と DELTA を示す。
5. 読み取り専用の副作用境界を示す。

この構成は実行環境の呼び出し形式を規定しない。

## 親エージェントによる統合

親エージェントは、五つのレーンから独立した報告を受け取ってから統合する。
親エージェントは、各 `evidence` が実在し読み取り可能なソースへ解決することを確認する。
親エージェントは、重複する finding をまとめて表示できるが、元のレーン、判定、証拠を失わない。
親エージェントは `FAIL` 又は `PARTIAL` を `PASS` に上書きできない。

全体の `PASS` は、五つのレーンがすべて `PASS` の場合に限る。
一つでも `FAIL` があれば、全体の結果は `FAIL` である。
`FAIL` がなくても一つでも `PARTIAL` があれば、全体の結果は `PARTIAL` である。
全体の結果はユーザー承認又は実装完了を表さない。

## DELTA による訂正

`FAIL` が出た場合、親エージェントは最小の DELTA を定義する。
`PARTIAL` が出た場合、親エージェントは利用不能な証拠の取得又はレビュー担当の利用回復を先に試みる。
`PARTIAL` の原因が対象成果物の不足にある場合に限り、その不足を最小の DELTA として定義する。
DELTA は finding を解消するために必要な変更だけを含める。
DELTA は無関係な改善、再構成、又は追加機能を含めない。

| DELTA の要素 | 記録する内容 |
|---|---|
| `source_finding` | 対応する `FAIL` 又は `PARTIAL` の id |
| `change` | 削除、修正、又は証拠取得の最小内容 |
| `rationale` | finding を解消する理由 |
| `impacted_lanes` | 変更された前提を再確認すべき標準レーン |
| `unchanged_premises` | 影響を受けない `PASS` レーンの前提 |

親エージェントが DELTA を適用する。
親エージェントは実装責任者を兼ね、レビューサブエージェントは DELTA の提案だけを返し、適用しない。
親エージェントは DELTA と impacted_lanes の対応を review-state に追加する。

## セッション継続と再レビュー

訂正後は、以前に `FAIL` だったレーンと DELTA の前提に影響を受けるレーンを再レビューする。
以前に `PARTIAL` だったレーンは、必要な証拠又はレーンのレビューが利用可能になった後に再レビューする。
変更されていない `PASS` レーンは、DELTA がその前提に影響しない限り有効のままとする。

継続できるレビューセッションが利用可能な場合は、同じレビューセッションへ DELTA と前回報告を渡して再レビューする。
同じレビューセッションを利用できない場合は、earlier finding と earlier verdict を保持する portable review-state summary を新しいレビュー担当へ渡す。
portable review-state summary は少なくとも対象範囲、各レーンの判定、必須確認の網羅表、finding、証拠、validator の対象変更との関係、前提、DELTA、impacted_lanes、再レビュー条件を保持する。
本プロトコルは review-state の永続化先を定義しない。

再レビューの担当は、前回の `PASS` を無条件に再判定してはならない。
再レビューの担当は、DELTA が前回の `PASS` の前提を変えた場合だけ、そのレーンを再確認する。
再レビューの報告は、以前の finding と verdict を置き換えず、どの DELTA により変化したかを追記する。

## 自律ループ

親エージェントは、全レーンが `PASS` になるまで次のサイクルを自律的に繰り返す。

1. `FAIL` 又は `PARTIAL` の finding を集約する。
2. 各 finding へ対応する最小の DELTA を定義する。
3. DELTA を適用する。
4. 影響を受けるレーンだけを再レビューする。
5. 再レビューの結果を review-state へ追記する。

再レビューの対象は、以前に `FAIL` 又は `PARTIAL` だったレーンと、DELTA により前提が変更されたレーンだけである。
以前に `PASS` だったレーンで、DELTA がその前提に影響しないものは再レビューしない。

### ユーザー判断への委譲

`FAIL` の原因が親エージェントの権限を超える場合は、自律ループを中断し、ユーザーへ報告する。
ユーザー判断が必要な例は次のとおり。

- 設計上の分岐選択（例: 正規所有者の確定、処分の確定）。
- ユーザー承認事項（`[UA]`）の解決。
- 存在しない証拠の外部取得。

中断時は、残る finding、適用した DELTA、再レビュー結果、ユーザーへ問うべき判断事項を報告する。
ユーザーが判断を提供した後、親エージェントは自律ループを再開する。

## 完了報告

親エージェントは、各レーンの最終判定、根拠付き finding、適用した DELTA、再レビュー範囲、全体の判定を報告する。
全体が `PASS` になるまで、深掘りレビューは完了として報告しない。
全体が `FAIL` 又は `PARTIAL` の場合は、残る finding 又は利用不能な証拠を明示する。
完了報告は、ユーザー承認、実装完了、又は強制的な統制通過を主張しない。
