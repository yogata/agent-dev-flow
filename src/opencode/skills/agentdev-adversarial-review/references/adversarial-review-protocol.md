## 対象と論理的役割

本プロトコルの対象は、要件、設計、規格・仕様、計画、実装を標準対象とする。
完成済み文書に限定せず、ドラフト、構造化提案、検討中の選択肢を含む。

審議は Orchestrator、Reviewer、Reviewee の3論理的役割で構成する。
論理役割は物理エージェント構成を固定しない。

| 役割 | 責務 |
|------|------|
| Orchestrator | 審議全体の進行、状態管理、合意候補管理、完了判断を担う。ただし自身は本質的争点の正解を判断せず、相互反証が収束する状態を確認する |
| Reviewer | 対象案を正しいと仮定せず、未発見の破綻条件、欠落、矛盾、不成立な前提、問題のある設計判断、実装方針、トレードオフを探索し反証を試みる |
| Reviewee | Reviewer の finding を未検証の主張として扱い、根拠、前提、対象理解、適用範囲、影響、方法論を反証する |

Reviewer と Reviewee の双方が自身の以前の主張を撤回、限定、修正できる。
一方に恒常的な正解権限を与えない。

本プロトコルの結果は助言であり、ユーザー承認、実装実行、強制的な統制判定にはならない。

## 動的レビュー戦略の構成

評価前に Orchestrator が対象、目的、制約、技術領域、想定失敗条件を整理し、初期レビュー戦略を構成する。
固定された観点集合の全項目実行をレビュー成立条件、完了条件としない。

レビュー戦略の構成要素:

| 構成要素 | 内容 |
|----------|------|
| 何を疑うか | 対象のどの部分、判断、前提、依存関係を検証対象とするか |
| どの立場から評価するか | 利用者、運用者、実装者、攻撃者、保守者等の立場の選択 |
| どの既存知識・方法論を使うか | 既存 Decision、Design、外部の adversarial review 方法論等、方法論の選択 |
| 何を証拠とするか | 関連コンテキスト、参照可能なソース、検証可能な事実の範囲 |
| どの意味単位へ分解して検証するか | 要件行、設計判断、契約、前提、コンポーネント等の分解単位 |

レビュー戦略自体も未検証の判断として扱い、Reviewer と Reviewee が不足、過剰、誤適用、前提不成立を指摘できる（「戦略メタ反証」参照）。
審議中に新しい証拠や争点が生じた場合、観点、立場、方法論を追加、削除、再構成する。

外部知見を権威として自動採用せず、対象への適合性を評価する。
実行時の外部サービス・外部リポジトリへの必須依存にせず、必要な知見を ADF 側の配布可能なレビュー知識として保持する。

## 振る舞いプロトコル（状態遷移）

審議は次の状態遷移で進行する。
各段階の詳細は後述各節を参照。

```
strategy -> challenge -> counter-challenge -> convergence -> convergence audit
```

- **strategy**: Orchestrator が対象と文脈を整理し初期戦略を構成する。戦略メタ反証を受けて修正できる。
- **challenge**: Reviewer が対象案を正しいと仮定せず、finding を提示する。
- **counter-challenge**: Reviewee が finding を反証し、Reviewer が再評価する。
- **convergence**: 本質的争点について相互反証が収束したものを合意候補として形成する。
- **convergence audit**: 合意候補と成立根拠を再度対論的に検証する。新たな本質的争点が見つかれば当該争点の対論を再開する。

## 対称的反証プロトコル

### challenge（Reviewer の finding 提示）

Reviewer は対象案を正しいと仮定せず、未発見の破綻条件、欠落、矛盾、不成立な前提、問題のある設計判断、実装方針、トレードオフを探索する。
finding は可能な限り次の要素を明示する。
単なる懸念や指摘を finding としない。

| 要素 | 内容 |
|------|------|
| 判定 | 何が問題かの判定 |
| 根拠 | 判定の妥当性を支える証拠、参照先 |
| 前提 | finding が依存する前提条件 |
| 適用範囲 | 対象案のどの部分、要件、設計、判断に対するものか |
| 適用条件 | どのような条件の下で成立するか |
| 反証条件 | どのような条件が示されれば finding を撤回、限定、修正するか |

反証条件を持たない抽象的懸念は、原則として本質的争点とならない（「本質的争点と非本質的批判の判定」参照）。

### counter-challenge（Reviewee の反証と Reviewer の再評価）

Reviewee は finding を未検証の主張として扱い、根拠の確認可能性、前提の妥当性、目的・制約・対象外との整合、充足済か、修正しない場合の影響、好み・理想論・過剰要求・スコープ外でないか、他の finding との重複を吟味し、反証する。

反証は finding の根拠、前提、対象理解、適用範囲、影響、方法論のいずれかを対象とする。

Reviewer は反論を再評価し、当該 finding を次のいずれかに遷移させる。
一方が恒常的な正解権限を持たないため、妥当な反論を受けて Reviewer も自身の finding を撤回、限定、修正する。

| 再評価状態 | 意味 |
|------------|------|
| 撤回 | 反論により finding が妥当でなかったと確認し、取り下げる |
| 維持 | 反論によっても finding が妥当であることを確認し、維持する |
| 限定 | 適用範囲を限定し、限定された範囲で finding を維持する |
| 修正 | 内容、前提、対象範囲を修正して再提示する |
| 部分合意 | 反論の一部を受容し、残る部分で finding を維持する |
| 解決不能 | 反論と finding のいずれも妥当と確定できず、自律審議では解決できない |

妥当な finding を対象案を守ることだけを目的として拒否しない。
妥当でない finding をレビュー結果であることだけを理由に受け入れない。

## 初期 challenge の独立 stream

初期 challenge は最低2系統の独立した論理 review stream で実施する。

### 独立性の定義

独立性は物理 agent 差やモデル差ではなく、初期 finding 生成時の兄弟 stream の finding 非共有によって定義する。
各 stream は初期 finding 生成完了前に兄弟 stream の finding を参照しない。

### 共有許容範囲

対象・目的・制約・確定済み review strategy は stream 間で共有を許容する。
共有対象は審議の入力条件であり、finding そのものではない。

### 初期 challenge 完了後の統合

初期 challenge 完了後に各 stream の finding を統合し、duplicate を整理して既存 counter-challenge / convergence へ進む。
duplicate 統合の詳細は「サブエージェント利用と重複統合」節を参照。

### 独立性判定

| 観点 | 判定 |
|------|------|
| stream 数 | 最低2系統であること |
| finding 非共有 | 初期 finding 生成完了前に兄弟 stream の finding を参照しないこと |
| 共有範囲 | 対象・目的・制約・確定済み review strategy の共有は独立性を損なわない |
| 物理 agent 差・モデル差 | 独立性の要件ではない（論理的分離が要件） |

## 戦略メタ反証

レビュー戦略自体を未検証の判断として扱い、Reviewer と Reviewee は戦略の次の問題を指摘し、戦略を修正できる。

| メタ反証種別 | 内容 |
|--------------|------|
| 不足 | 想定失敗条件、立場、知見、証拠源が不足し、特定の破綻を検出できない |
| 過剰 | 対象、目的、制約と無関係な観点が含まれ、審議を浪費する |
| 誤適用 | 対象種別に合わない方法論、立場、分解単位を適用している |
| 前提不成立 | 戦略が依存する前提（対象の性質、制約、利用可能証拠等）が成立しない |

戦略の修正は審議中に随時行える。
新しい証拠や争点が生じた場合、観点、立場、方法論を追加、削除、再構成する。

## 争点状態遷移

争点は次の状態を持つ。
状態遷移の物理的保存形式、スキーマは Design 所有対象外とし、配布スキル実装へ委譲する。

| 状態 | 意味 |
|------|------|
| 起原型 | 未検証の反証候補、初期 finding |
| 審議中 | Reviewer と Reviewee が反証と再評価を往復している状態 |
| 合意候補 | 相互反証が一時的に収束した暫定状態。convergence audit 待ち |
| 撤回 | 提起者が反証を取り下げた状態 |
| 限定合意 | 適用範囲を限定した上で合意した状態 |
| ユーザー質問中 | 自律解決不能でユーザーへエスカレーションした状態 |
| 完了 | convergence audit を経て最終的に閉じた状態 |

遷移の主流は `起原型 -> 審議中 -> 合意候補 -> convergence audit -> 完了` である。
審議中からは撤回、限定合意、ユーザー質問中へ分岐でき、ユーザー質問への回答後は影響を受ける争点から審議を再開する。

重複する反証は同一争点へ統合する。
解決済み争点は、新しい証拠、新しい前提、異なる具体的破綻条件、未評価の適用範囲が示されない限り再開しない。

## finding lifecycle

各 finding を個別に識別し、次の要素を意味的に区別して追跡する。

| 要素 | 内容 |
|------|------|
| 主張 | finding が主張する判定内容 |
| evidence | 判定を支える証拠、参照先 |
| assumptions | finding が依存する前提条件 |
| scope / applicability | 対象案のどの部分、要件、設計、判断に対するものか |
| falsification condition | どのような条件が示されれば finding を撤回、限定、修正するか |
| 現在状態 | 起原型、審議中、合意候補、撤回、限定合意、ユーザー質問中、完了のいずれか |
| 直近 disposition | Reviewer の再評価結果（撤回、維持、限定、修正、部分合意、解決不能） |
| 解決根拠 | finding が閉じた場合の成立根拠または撤回根拠 |
| duplicate 関係 | 他 finding との重複、統合元、統合先の関係 |

### 状態遷移の主流

finding の状態遷移の主流は `起原型 -> 審議中 -> 合意候補 -> convergence audit -> 完了` である。
審議中からは撤回、限定合意、ユーザー質問中へ分岐でき、ユーザー質問への回答後は影響を受ける争点から審議を再開する。

### 永続 schema 非導入

finding 状態は審議中の一時状態とし、新しい正規 artifact または永続 schema を導入しない。
具体的 field 名、保存形式、内部データ構造は配布スキルの実装詳細とする。

### finding 識別と duplicate 判定

複数 stream や複数 round で生成された finding について、同一実質の finding を duplicate として統合する。
duplicate 判定は主張、evidence、assumptions、scope の意味的照合で行う。
表面的に類似していても falsification condition または scope が異なる finding は独立した finding として扱う。

## 審議進展の意味状態判定と semantic stagnation 制御

審議の進展を文章表現や単純 round 数ではなく、finding の意味状態の変化で判定する。

### 進展なしと判定する条件

| 条件 | 内容 |
|------|------|
| 言い換え | 同一の主張、根拠、前提を異なる表現で反復しただけの場合 |
| 同一 evidence 反復 | 既に提示済の evidence を再提示しただけの場合 |
| 根拠のない同一 finding 再起票 | 新証拠、新前提、異なる failure condition、未評価範囲のいずれも伴わない同一 finding の再起票 |

### 意味状態の進展として認識する条件

| 条件 | 内容 |
|------|------|
| 新 evidence の提示 | 未参照の証拠が新たに提示された場合 |
| scope / applicability の変更 | 対象範囲の拡大、縮小、限定が生じた場合 |
| assumption の変更 | finding が依存する前提条件が変更された場合 |
| falsification condition の変更 | finding の反証条件が変更された場合 |
| finding の撤回・限定・修正 | finding の状態遷移が生じた場合 |

### stagnation 検出時の自律解決

stagnation（進展なし状態）を検出した場合、直ちにユーザー質問へ遷移せず、次の自律解決を試みる。

| 手段 | 内容 |
|------|------|
| duplicate 統合 | 同一実質の finding を統合し、重複を解消する |
| 非本質論点の終了 | 本質的争点に該当しない finding を閉じる |
| 追加 evidence 探索 | 関連コンテキストから未参照の証拠を取り出す |
| scope 限定 | finding の適用範囲を限定し、限定的な妥当性を確認する |

### 収束条件

固定 round 数を収束条件としない。
timeout や最大 round は実装詳細として設定可能とする。

## 合意候補管理と convergence audit

### convergence（合意候補の形成）

本質的争点について相互反証が行われ、利用可能な証拠から維持すべき本質的反論が残らない状態に至った争点を合意候補として形成する。
合意は形式的全会一致、多数決、Reviewer と Reviewee が同じ文言を返した状態ではなく、本質的争点の収束として判断する。

合意結果は次のいずれも許容する。
中間案への機械的妥協を要求しない。

- 元案維持
- 元案修正
- 部分修正
- finding 撤回
- 適用範囲限定
- 代替案採用

### convergence audit（合意候補再検証）

Reviewer と Reviewee が合意候補とその成立根拠を再度対論的に検証する。
合意候補を形成しただけでは完了としない。
再検証で新しい本質的争点が見つかった場合、当該争点について対論を再開する。

convergence audit は合意候補に新しい欠陥が混入した場合にこれを検出する最終関門である。
合意候補の成立根拠、前提、適用範囲、他争点との整合を再検証する。

## finding と正規結果の形式

finding は単なる懸念や指摘ではなく、判定、根拠、前提、適用条件を伴う。
次のいずれも正規結果として扱い、問題を発見すること自体をレビューの成功条件としない。

| 正規結果 | 意味 |
|----------|------|
| 問題が確認された | finding の判定、根拠が成立し、対象案への反映が必要 |
| 限定条件下のみ成立 | 適用範囲を限定した場合のみ finding が成立する |
| 検証の結果成立しなかった | 反証により finding が妥当でないことが確認された |
| 証拠不足で判定不能 | 利用可能な証拠から判定できず、追加証拠またはユーザー判断を要する |
| 十分な反証を試みても問題を確認できなかった | 明確な破綻を確認できず、finding を捏造しない |

明確な破綻を確認できない対象では、finding を捏造せず「問題未確認」「証拠不足で判定不能」等の正規結果を返す。

## 本質的争点と非本質的批判の判定

次のいずれかに該当する指摘は、原則として本質的争点としない。

- 具体的破綻・実害を示せない指摘
- 目的・制約・対象範囲と無関係な改善
- 好み・理想論のみの指摘
- 過剰要求
- スコープ外
- 解決済みの再提出
- 表現変更のみの同一批判
- 反証条件を持たない抽象的懸念
- 継続目的化した指摘

Reviewee が一方的に本質的でないと確定せず、反論と Reviewer の再検討を経て争点を閉じる。

## 自律審議とユーザー質問

関連コンテキストと取得可能な証拠から判断可能な限り自律審議を継続する。
意見不一致だけを理由にユーザーへ返さない。

審議の継続時、未解決争点を閉じるために次の手続きを試行する。
順不同で適用し、複数を組み合わせてもよい。
審議の進展判定と停滞（stagnation）検出時の自律解決は「審議進展の意味状態判定と semantic stagnation 制御」節を参照。

| 手続き | 内容 |
|--------|------|
| 前提確認 | 反証の前提、対象案の前提、審議の暗黙前提を照合し、前提の相違を特定する |
| 根拠確認 | 反証の根拠、対象案の根拠、関連コンテキストの証拠を照合し、根拠の不足または誤読を特定する |
| 誤解解消 | 表現、意図、対象範囲の誤解を対話により解消する |
| 適用範囲の限定 | 反証の適用範囲を対象全体から部分へ限定し、限定的な妥当性を確認する |
| 部分合意の探索 | 反証のうち妥当な部分と妥当でない部分を分離し、妥当な部分について部分合意を形成する |
| 代替案の比較 | 複数の解決案を比較し、目的、制約、対象範囲への整合で優位な案を特定する |
| 追加証拠による再評価 | 関連コンテキストから追加証拠を取り出し、争点を再評価する |
| 反証内容の再構成 | 反証を本来の対象、目的、破綻条件へ再構成し、本質的争点と非本質的批判を分離する |

技術的に決着できない優先判断、ユーザー固有の目的・価値判断、両立不能要求、必要情報不足等、自律解決できない争点のみをユーザーへ返す。
ユーザー回答後は影響を受ける争点から審議を再開し、必要な再検証を行う。

ユーザー質問時は、未解決争点、エージェント間で解決できない理由、合意済み範囲、対立選択肢、選択肢ごとの差異・影響、推奨案と根拠、ユーザーに確定してほしい判断、回答後に再開する争点を明確にする。

## サブエージェント利用と重複統合

Reviewer と Reviewee は双方とも、必要に応じて複数のサブエージェントを利用できる。
大規模対象では観点、コンポーネント、failure mode、仮説、証拠源等の意味的に独立した単位へ分解し、ワークフロー化、並列化できる。
小規模対象では物理的な複数サブエージェントを必須としない。

初期 challenge の独立 stream（「初期 challenge の独立 stream」節参照）で生成された finding の統合にも本節の重複統合アルゴリズムを適用する。

複数サブエージェントの結果は多数決しない。
同一 finding の報告数を証拠の強さとして扱わず、重複統合、共通原因抽出、根拠・前提確認を行い、本質的争点へ正規化する。

重複統合アルゴリズム:

1. 複数サブエージェントの finding を意味的対象（対象案の同一部分、同一前提、同一破綻条件）ごとに束ねる。
2. 報告数を加重せず、同一争点へ統合する。
3. 共通原因、共通前提、共通根拠を抽出する。
4. 差異部分（適用範囲、前提の違い）を分離し、独立争点として扱うか限定合意へ回す。

物理的なエージェント数、並列数、DAG 構造、モデル選択、timeout、最大ラウンド数、物理的状態保存形式は Design 所有対象外とし、配布スキル実装へ委譲する。

## 完了条件

審議全体の完了は、形式的全会一致や固定観点全 PASS ではなく、次の本質的合意条件で判断する。
固定観点全 PASS や形式同一判定を完了条件としない。

1. 本質的争点がすべて閉じていること
2. 妥当と合意した finding が元案へ反映されていること
3. 撤回または棄却された finding が元案へ混入していないこと
4. 部分 finding の採用範囲と非採用範囲が明確であること
5. ユーザー判断事項が残っていないこと
6. 合意候補の再検証（convergence audit）が完了していること
7. 再検証後に新たな本質的争点が残っていないこと
8. 対論を継続すること自体を目的とした議論だけが残っていないこと

## 出力契約

審議完了時には次を確認可能な形で返す。

| 項目 | 内容 |
|------|------|
| 合意済最終案または方針 | 合意済みの対象案の最終版または方針 |
| 採用した主要 finding と根拠 | 採用した主要な finding とその根拠 |
| 撤回・棄却した主要 finding と理由 | 撤回または棄却した主要な finding とその理由 |
| 限定 finding と適用範囲 | 適用範囲を限定した finding とその範囲 |
| 主要なレビュー戦略と方法論 | 用いた主要な戦略、立場、方法論 |
| 残留リスク・前提・不確実性 | 合意後も残るリスク、前提条件、不確実性 |
| 未解決事項 | 未解決の争点、ユーザー判断待ち事項 |

レビュー終了後、レビュー結果の対象への反映、ファイル保存等を必要に応じて追加指示できることをユーザーへ明示的に促す。
ただしその促し自体を理由に本スキルが後続操作を実行しない。

## 副作用境界

本スキルは次の副作用を行わない。

| 禁止 | 内容 |
|------|------|
| ファイル保存 | 対象案、審議状態、出力結果をファイルへ保存しない |
| commit | git commit を行わない |
| push | git push を行わない |
| merge | git merge を行わない |
| Issue・PR 操作 | Issue、PR の作成、更新、コメント追加を行わない |
| レビュー結果の自動適用 | 審議結果を対象へ自動反映しない |
| ユーザー承認代行 | ユーザー承認を代行しない |
| その他の外部状態変更 | データベース、外部サービス、実行環境の状態を変更しない |

レビュー結果保存用の新しい正規成果物種別を導入しない。

## 審議状態の保存形式（実装詳細）

審議状態の物理的保存形式、スキーマ、最大ラウンド数、並列数、タイムアウトは Design 所有対象外とし、配布スキル実装へ委譲する。

本プロトコルは次の実装詳細を規定しない:

- 審議状態の保存先（インメモリ、ファイル、データベース等）
- 争点、finding、反証、合意候補のデータスキーマ
- 審議の最大ラウンド数、最大争点数
- Reviewer、Reviewee の並列起動数
- 各手続きのタイムアウト

これらは配布スキルの実装が AGENTS.md、実行環境の制約に従い決定する。

## 呼出元との契約

本プロトコルは adversarial-review Design「adversarial-review caller integration 共通契約」節が定める共通契約に従う。
共通契約の正規所有者は Design であり、本ファイルは審議プロトコル実装の観点からの補完のみを提供する。

### 再 review の発動と停止

審議プロトコル内の争点再開条件（「争点状態遷移」節）と caller integration 側からの再 review 発動条件は同一基準に従う。
呼出元は finding 反映の結果、review 対象の意味内容が変更され、新たな本質的争点が生じ得る場合にのみ再発動する。
新証拠、新前提、異なる failure condition、未評価範囲のいずれも伴わない同一 finding の再起票をしない。

再 review の停止条件は次の4点とする。

1. 新しい本質的 finding がないこと
2. 新たに提示された finding が全て撤回、解決、限定合意のいずれかで処理済みであること
3. 残った争点がユーザー判断を必要とするため既存の HITL または blocker 扱いへ移行したこと
4. 変更後も候補の意味内容が変化しておらず、再 review の対象がないこと

### 呼出失敗時の取扱い

本プロトコルの実行前、実行中に起動異常、timeout、スキル不在が発生した場合は silent skip を禁止する。
審議プロトコルは結果を返せない旨を呼出元へ明示し、呼出元は従来フローと既存 QG/HITL を維持する。
プロトコル内部のリトライ、復旧は審議状態の物理的保存形式（「審議状態の保存形式（実装詳細）」節）に属し、本節の対象外とする。
