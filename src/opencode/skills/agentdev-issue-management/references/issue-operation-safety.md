# Issue 操作安全性手順

GitHub Issue の作成、更新、リンク、確認を安全に行うための手順。
本書は Custom Tool `agentdev_gh`（書き込みは Tool 内部の読み戻し検証で完了）と連携し、Issue 操作特有の安全性要件を補完する。
各手順の読み取りは Custom Tool `agentdev_gh` の読み取り操作に従うこと。

## 委譲接続点と本文受け渡し

case-open がサブエージェントへ本文生成を委譲する接続点（Step 2/6/8/9）では、本文候補をメッセージ本文ではなくファイルパスで受け渡す。

- サブエージェントは生成した本文候補をファイルへ保存し（UTF-8 BOM なし・LF。ファイル I/O の実装詳細は Custom Tool `agentdev_gh` が所有）、親エージェントへはファイルパスを返す
- 親エージェントは受領したファイルの内容を変更せず Custom Tool `agentdev_gh` の操作引数として渡す。本文テキストをメッセージ本文で再送、再構成（空行圧縮、見出し前後のスペース化、改行正規化）してはならない
- これにより、サブエージェント→親エージェント間のメッセージ本文圧縮、Markdown レンダリング正規化による LF・空行欠損を構造的に排除する
- 親エージェントが本文修正（変数置換漏れ、前工程完了度属性の埋め込み等）を行う場合も、修正後の本文を改めてファイル保存し、そのファイルをファイル経由で渡す（同一のファイル経由規定）

## Issue 作成後の内容反映確認

`agentdev_gh` の issue_create 操作実行後、Issue番号を取得し、本文が正しく反映されたかを確認する。

1. `agentdev_gh` の issue_create 操作の戻り値から Issue番号（`#N` または Issue URL）を取得する。
Issue番号を取得できない場合は作成失敗とみなし、再作成前に既存 Issue の有無を確認する（読み取り系）。
2. 作成した Issue の本文を `agentdev_gh` の issue_read 操作で取得する。
3. 書き込み元テキストと読み戻しテキスト（`agentdev_gh` の成功応答は読み戻し検証済み）を以下の観点で確認する。
 - **(a) エンコーディング検証**: 日本語文字列の一致、制御文字の混入有無
 - **(b) Markdown 構造検証**: テーブル列数、チェックボックス、コードブロック、リスト階層
 - **(c) テンプレート必須セクション検証**: `【必須】` マーカー付き見出しの存在
 - **(d) リポジトリ参照リンク検証**: 相対パス、裸パスの混入がないか
4. 検証失敗時は3段階リトライ（同一内容リトライ → 内容再生成 → 停止、ユーザー報告）に従う。

## Parent/Child Issue リンク確認

子 Issue の本文先頭に `Parent: #{epic_number}` を配置した場合、双方向のリンク整合性を検証する。

1. 子 Issue の本文を安全な読み取り手順で取得する。
2. 本文冒頭のメタ情報行に `Parent: #{epic_number}` が存在するか確認する。
3. `{epic_number}` が実際の Epic Issue 番号と一致するか確認する。
`#{TBD}` や `#{TBD_Wn}` 等のプレースホルダーが残存している場合はリンク未完了とみなし、実番号への置換を行ってから再検証する。
4. Epic Issue 側の本文に、子 Issue 番号（`#{child_number}`）が正しく記載されているか逆方向も確認する。
5. 双方向のリンク（子 → 親 の `Parent: #N`、親 → 子 の番号記載）が揃っていることを完了条件とする。
片方向のみの確認で完了扱いにしないこと。

## Epic Issue ステータス追跡テーブル更新

Epic Issue 本文内のステータス追跡テーブル（総数、進行中、完了）を更新する場合、更新前後でテーブル構造と数値の整合性を保つ。

**単一書き手制約**: Epic Issue 本文ステータス追跡テーブルの更新は **case-close のみ**が実施する。
case-run は Epic Issue 本文を読み取るのみ（書き込まない）。
case-auto は Wave 反復制御のみを行い、Epic Issue 本文に直接書き込まない。
last-write-wins 競合防止は case-close の単一書き手で維持される。

1. Epic Issue の現状本文を安全な読み取り手順で取得し、ステータス追跡テーブルの行数、列数を記録する（更新前スナップショット）。

2. 子 Issue の作成、ステータス変更に合わせて、テーブルの総数、進行中、完了を更新する。
テーブル行を追加、削除する場合は列数を維持する。

3. `#{TBD}`/ `#{TBD_Wn}` プレースホルダーを実番号に置換した場合、置換漏れがないか Epic 本文の全文検索で確認する。

4. 総数 = 進行中 + 完了 +（未着手）の数値整合性が取れているか確認する。

5. 更新後、`agentdev_gh` の issue_read で本文を再取得し、テーブル構造（列数、行数）が保持されているか、Markdown 構造が崩れていないか検証する。
テーブル列ずれは VERIFY (b) の検証項目。

## Issue 更新時の前後内容比較

`agentdev_gh` の issue_update 操作で既存 Issue を更新する場合、更新前の本文を保存し、更新後に差分を比較する。

1. 更新前に Issue 本文を `agentdev_gh` の issue_read 操作で取得し、一時ファイル（実行時作業領域配下）に保存する（更新前スナップショット）。
2. 更新内容をマージした新しい本文を生成し、`agentdev_gh` の issue_update 操作で書き込む。

3. 更新後、再度本文を取得し、更新前スナップショットと比較する。
意図した差分のみが反映され、意図しない削除、文字化け、セクション欠落が発生していないか確認する。

4. 読み戻し本文についてエンコーディング、Markdown 構造、テンプレート必須セクション、リポジトリ参照リンクを検証する。
5. 検証完了後、更新前スナップショットの一時ファイルを削除する。

## Issue 内容検証（`agentdev_gh` 読み戻し連携）

Issue 作成手続き/ `agentdev_gh` の issue_update 操作を使用する場合、ファイル内容と反映内容の一致を検証する。
本手順は Custom Tool `agentdev_gh` の操作と連携する。


1. `agentdev_gh` の issue_create / issue_update 操作で本文を書き込む。
文字コード・一時ファイル等の実装詳細は Tool 内部に隠蔽される。

2. Issue 作成手続き/ `agentdev_gh` の issue_update 操作を実行する。

3. Issue 本文を `agentdev_gh` の issue_read 操作で取得し、書き込み元テキストと比較検証する。

4. 検証失敗時は3段階リトライ（同一内容リトライ → 内容再生成 → 停止、ユーザー報告）に従う。
リトライ上限到達時は自動的な代替手段を実行せず、ユーザーに差分内容、試行段階、リトライ回数を報告して停止する。
5. 実行完了後、一時ファイルを削除する。

## 禁止事項

- GitHub Issue 操作は Custom Tool `agentdev_gh` へ委譲（gh コマンド直接記述禁止、REQ）
- Issue番号を確認せずに後続操作へ進むこと禁止
- Parent/Child リンクの片方向のみ確認して完了とすること禁止（双方向確認が必須）
- Epic テーブル更新後に VERIFY 操作を省略すること禁止
- `#{TBD}`/ `#{TBD_Wn}` 等のプレースホルダーが残存している状態で Issue 作成、更新を完了とすること禁止
- 更新前スナップショットを取得せずに `agentdev_gh` の issue_update 操作を実行すること禁止
- **Epic Issue 本文ステータス追跡テーブルの更新を case-close 以外のコマンド（case-run、case-auto）が直接行うこと禁止**（単一書き手制約）。case-run は読み取りのみ、case-auto は Wave 反復制御のみとし、Epic Issue 本文への書き込みは case-close に限定する
