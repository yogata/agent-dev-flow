## ユーザーストーリー

「[誰]が[何]を[なぜ]する」形式で記述する。

- 明確な主体（ユーザー、システム、外部サービス等）
- 具体的なアクション
- ビジネス価値、目的

## 完了条件

Given-When-Then形式で記述し、測定可能であること。

- **Given**: 事前条件、前提状態
- **When**: 実行するアクション、イベント
- **Then**: 期待される結果、状態変化

客観的な完了判定が可能であること。

## 境界条件

正常系、異常系、エッジケースを網羅する。

- **正常系**: 期待されるフロー
- **異常系**: エラー、例外、拒否パターン
- **エッジケース**: 境界値、空入力、同時実行等

## 必達要件記述ガイダンス

要件行は検証可能な必達要件として記述する。推奨、任意、将来候補は要件行に含めない。

**記述ルール**:
- 各要件行は「満たす必要がある検証可能な要件」として記述する
- 禁止、停止条件、完了不可条件は自然文で記述する（「〜禁止」「〜停止する」「〜完了扱いにしない」等）
- 曖昧な表現（「適切に」「効率的に」等）は、具体的な測定可能な条件に置き換える

## 状態要件と反映作業の分離基準

要件行候補を「状態要件（変更後仕様）」と「反映作業」に分類する判断基準（050）。

**状態要件（要件行として採用）**:
- システムが満たすべき振る舞い、制約、状態の宣言
- 「〜すること」「〜を禁止」「〜しない」等の検証可能な記述
- 変更後に満たされるべき条件

**反映作業（要件行として不採用、移送候補）**:
- 既存成果物への操作: 更新、削除、移動、名称変更、参照修正、移行、再定義、改名、移管、除去、廃止、置換
- 作業手順の記述（ステップバイステップの実行指示）
- 既存文書の修正内容そのもの

**混合候補の処理**:
- 状態要件の記述を含み、かつ反映作業も含む場合 → 要件行として採用（反映作業部分は移送候補としてマーク）
- 反映作業のみの場合 → 要件行として不採用、後続工程への移送候補として振り分け

**移送先**:
- 反映作業は case/ Issue/ 受け入れ条件/ 作業記録で扱う
- 現行 REQ の title/ 目的/ 要件行/ 適用範囲に作業手段語を混入させない（007）

## REQ/SPEC 境界判定基準

状態要件と判定された要件行候補を、REQ に記述する内容と SPEC 等に配置する内容に振り分ける判断基準（-069, -055）。「状態要件と反映作業の分離基準」と併用する。

**REQ に記述する内容（外部契約、状態要件）**:
- システム、コマンドが満たすべき状態、振る舞い、制約の宣言
- 外部から見える責務、公開 command 名、公開入口
- ドメイン状態の位置づけ、他 command との接続契約
- 安全境界、停止条件の大枠、利用者に見える分類体系
- 恒久的な文書体系制約

**SPEC 等（SPEC/ rule catalog/ command reference/ skill reference/ test docs）に配置する内容（詳細、内部パラメータ）**:
- schema field、enum 値一覧、route/category/status 詳細判定表、file pattern、template variant、report format
- fixture detail、regression test 条件、checker 個別ルール、false positive 抑制方式
- retry 回数、token 目安、行数上限、Step 番号、Phase 番号、内部アルゴリズム
- 作業履歴、Case/RU/Issue/PR/OU 由来の作業記録

**安定契約例外**: 要件行候補がパラメータ、分類、値の形式をとる場合であっても、公開 command 名、公開入口、ドメイン状態の位置づけ、他 command との接続契約、利用者に見える分類体系、安全境界、停止条件の大枠、後続工程が依存する安定した外部契約のいずれかに該当する場合は、REQ に要約として記述する。詳細な値一覧、判定表、内部処理条件は SPEC 等に配置する。

**必要性テスト**: 「当該行が存在しない場合、対象 REQ が何を満たすべきか不明になるか？」を問う。不明になる場合は REQ 行として残し、対象 REQ の必達要件の理解に寄与しない場合は SPEC 等へ移送する。

**記述形式**: 主たる文意は肯定文で記述する（-066 準拠）。否定文は境界条件、例外、補足として併記する場合に限る。

**判定タイミング**: req-define/ req-save は保存前に REQ/SPEC 配置判定を行う。QG-1 の観点 6（REQ/SPEC 配置判定）がこれを担保する。

**SPEC 候補の分離経路**: req-define は SPEC 等に配置すべきと判定した要件行候補を REQ 要件行に残留させず、ドラフト内の `## SPEC候補` 補助セクションと `draft-meta.spec-candidates`（SC-ID、content、intended_spec、classification、source）に分離する。各 SPEC 候補には想定配置先 SPEC（既存 SPEC ファイル名または新規 SPEC 候補）と分離根拠（SPEC分離基準の該当種別）を記録する。この分離経路により、SPEC 相当行が REQ ファイルへ混入することを構造的に防止する。req-save は REQ ファイル保存時に SPEC候補セクションを除去し、内容は spec-save が `docs/specs/**/*.md` へ保存する。

## 用語定義

要件内の専門用語を明確化する。

- ドメイン固有の用語
- 技術的な前提条件
- 業務用語、略語の統一定義

## 分析フレーム選択基準

壁打ち（req-define Step 3）の開始時、入力（RU、セッションコンテキスト、明示入力ファイル）の構造を、入力データの性質に応じた分析フレームで先行して整理する（AG-001、-083）。個別論点の深掘りに進む前に全体構造をユーザーへ提示し、論点漏れ、手戻りを防ぐ。

**フレーム選択**: 入力データの性質に応じて以下のフレームから選択する。推奨例であり、入力に応じて適切なフレームを選択する。

| 入力データの性質 | 推奨フレーム |
|---|---|
| 複数RU・複数改善候補 | 対象×変更種別の二軸マトリクス |
| 既存要件との照合が必要 | 既有件化/未要件化/SPEC配置の3分類表 |
| 修正要否の判定 | 実装面/SPEC面の両面分析表 |

**先行提示の原則**:
- 分析フレームは個別論点の深掘りに先行して提示する
- 全体構造を提示してから「未決分岐の抽出と整理」の依存順解消（目的 → 対象 → 対象外 → 責務境界 → 粒度 → 永続化 → 判定基準）に進む

## 実装/SPEC両面分析規定

修正の要否を検討する際、実装面と SPEC 面の両面を分析し、各面の修正対象と修正内容を明示する（AG-003、-085）。片面のみの分析で修正要否を断定しない。

**分析対象**:

| 面 | 対象 |
|---|---|
| 実装面 | ソースコード、スクリプト、スキル定義ファイル等の変更 |
| SPEC 面 | SPEC 文書の変更 |

**記述要件**:
- 各面の修正対象（対象ファイル、対象セクション）を明示する
- 各面の修正内容（変更の要点）を明示する
- 一方の面で修正が不要な場合も、分析を実施した上で「修正不要」であることを明示する

## チェックボックス品質基準

Issue本文のチェックボックスが満たすべき品質条件。

### 測定可能

完了/未完了が客観的に判定できること。

- ❌ 「処理を最適化する」
- ✅ 「レスポンス時間を200ms以下にする」

### 一意

1つのチェックボックス = 1つの要件。複合要件は分割する。

- ❌ 「認証機能の実装とテスト」
- ✅ 「認証APIの実装」「認証フローのテスト」

### 実装可能

1つのチェックボックス = 1つのPRで実装可能な粒度。

- ❌ 「システム全体のリファクタリング」
- ✅ 「ユーザーモジュールのリファクタリング」「決済モジュールのリファクタリング」

## ADR閾値判定ブリッジ

技術判断がADR閾値に達するかの基準。

### ADRが必要な判断

- アーキテクチャ変更: システム全体の構造、主要コンポーネント間の関係に影響
- 複数システム影響: 技術スタック選択、データモデル、認証スキームなど
- 長期間有効な決定: 将来の開発、運用に長期的影響を与える
- 取り返しがつかない変更: 後で変更するコストが高い、困難

### ADR閾値未満

- 単一モジュール内の実装選択
- ライブラリのマイナーバージョン選択
- コーディングスタイル、命名規約

### ADR参照

ADRが必要と判定された場合 → `agentdev-adr-guidelines` スキルを参照する。ADR候補記録までを責務とし、ADRファイル作成は req-save + `agentdev-adr-file-manager` に委譲する。
