# 構造化データ操作の設計原則（語彙一致・構造前提の明示・静的破壊の防止）

## 背景

同一概念の識別子を複数モジュールで独立定義し、テーブル構造を暗黙前提として実装した結果、語彙外値の静的破棄・形式追加時の既存列破壊という静的なデータ破壊（silent data loss）が2件で観測された。いずれも fixture 駆動の実経路確認で検出され、回帰テスト新設で解消されたが、未検出のまま永続化すれば記録データの喪失に至る潜在被害がある（影響度 5）。

## 問題

(1) 記録契機語彙が record-comments.ts（start/handoff/halt）・records-report.ts / epic-reflect.ts（start/handover/stop 系）で3経路に分岐し、epic-reflect は語彙外行を parse 失敗として applied=true で静かに破棄、既存エントリ削除済みの本文を適用していた。(2) tracking-table.ts の replaceChildStatus が旧4列形式（ステータス列=最終列）前提の正規表現で新4列形式（# / Issue / ステータス / 内容）の内容列まで置換対象に含め、内容列を破壊した（列数同じで列数では判別不能）。

## 望ましい変更

構造化データ操作の設計原則として次を Design へ反映する: (a) 同一概念の識別子は単一モジュールで定義し export 共有する、または語彙一致の機械検査（3経路一致回帰テスト等）を併設する、(b) 語彙外・解析不能な入力は静的破棄せず applied=false 等で明示失敗する防御を持つ、(c) テーブル等の構造操作は列位置を暗黙前提とせずヘッダー列名を情報源に列を特定する、(d) 複数形式世代の共存を前提とした回帰テストを併設する。前例の「存在チェックと能力検証の分離」原則と同系の実装パターン原則として整理する。

## 元learning item / 根拠

- **要約**: 識別子・テーブル構造の暗黙前提による静的データ破壊（記録契機語彙 3経路分岐の静的破棄・列位置前提正規表現の内容列破壊の2件）
- **根拠**: Case #3391・Wave 2 #3399・TS-006 の F-1/F-2 検出・PR #3406（語彙を RECORD_KINDS へ統一・語彙検証と applied=false 防御・3経路一致テスト新設、ヘッダー列名特定へ変更・内容列保持回帰テスト追加）
- **再発条件**: 同一概念の識別子を複数モジュールで独立定義し語彙差異検出の機械検査がない場合、複数形式世代が共存するデータへ列位置前提の置換を実行する場合
- **横展開可能性**: 識別子共有・構造化データ操作を持つ実装全般
