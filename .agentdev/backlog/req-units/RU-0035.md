# case-ready導入後のcase-auto orchestration再整合

## 背景

標準ワークフローへ `case-ready` を追加したことで、主フローは次の状態遷移へ再構成された。

`case-open → case-ready → case-run → case-close`

また、再合意済み Definition 変更では `case-open` の代わりに `case-revise` を入口として `case-ready` へ接続する。

`case-ready` の追加そのものは、Root Case 確立と Definition 確定・実行準備完了の責務を分離するための変更である。

一方、case-auto への反映では、旧来の orchestration 構造を新しい主フローから再導出せず、既存 stage へ `case-ready` を追加する形で整合した。この結果、複数対象実行における stage 構造、並列性、stage 完了条件、中断再開、cleanup、Epic / Wave との接続について後付けの補正が必要となった。

さらに、その是正過程で `stage 1a / 1b` や「対象群全体への barrier」といった、本来のワークフローに必須ではない概念が導入され、case-auto の制御モデルが複雑化した。

本RUでは、個別の縦切り実行不具合だけを修正するのではなく、`case-ready` 導入後の case-auto orchestration 契約を主フロー全体から再整合する。

## 問題

現在の case-auto orchestration には、少なくとも以下の構造的問題がある。

1. `case-open` と `case-ready` を `stage 1a / 1b` として扱っているが、両者を一つの stage の下位区分として扱う意味的根拠がない。
2. `case-open`、`case-ready`、`case-close` を stage 単位で直列実行する契約があり、本来並列化可能な独立対象まで直列化している。
3. 一方で対象単位に `case-open → case-ready → case-run → case-close` と縦切りで進行すると、stage 単位の進行順序が崩れる。
4. 「stage barrier」という独立概念が導入されたが、必要なのは各 stage 内の分散実行と、その完了結果の合流であり、別の状態管理モデルを追加する必要はない。
5. stage 全体を直列化することで、共有書き込みなど本当に直列化すべき局所処理と、並列化可能な処理が区別されていない。
6. `case-ready` 成功時に draft / RU が削除されるため、中断再開時に case-auto 起動時の対象集合を維持できなければ、正しい進行位置を再構成できない。
7. `case-ready` が blocked / failed / 中断した場合には draft / RU が保持されるため、cleanup 判定を単純な「残存有無」とすると正常な保持まで異常扱いする。
8. Epic / Wave は内部に独自の反復制御を持つため、command 名だけで case-auto の stage を分類すると外側の orchestration と内部状態遷移を混同する。
9. case-open / case-ready が持つ横断依存検査は、対象を並列実行した場合でも対象間の検出漏れを発生させてはならない。
10. case-ready 導入後の変更が REQ、Design、Workflow Skill、command projection、reference に横断しているため、局所修正では旧契約が残存する。

チャット内で以下に合意した。

* case-ready 導入自体ではなく、その追加に伴う case-auto 全体の orchestration 再設計が不十分だったことを問題の中心とする。

  * stage 1: `case-open`
  * stage 2: `case-ready`
  * stage 3: `case-run`

* 各 stage の対象が収束した後に次 stage へ進む。
* 全 stage 共通の固定並列上限は新設しない。

* stage cursor を新しい正規状態として保存しない。
* 中断再開に必要な場合は、起動時対象集合の安定識別子だけを既存のローカル一時実行状態として保持できる。

* 物理的な一時状態の保存形式やパスは要件で固定しない。
* Epic / Wave の内部実行モデルは再設計せず、case-auto の外側 stage と正しく接続する。
* case-ready の cleanup は stage 2 正常完了対象についてのみ評価し、blocked / failed / 中断により正当に保持された draft / RU を cleanup 違反としない。
* 過去の Report / Decision 等の履歴文書は現行契約への参照として使用されていない限り書き換えない。

## 統合理由

今回確認された問題は、個別の `case-open` 並列化不足や縦切り実行だけではない。

`case-ready` の追加により主フローの状態遷移が変わったにもかかわらず、case-auto の orchestration を新しい主フローから再導出しなかったことが共通原因である。

stage 番号、stage 内並列性、stage 間進行、中断再開、cleanup、Epic / Wave 接続は相互依存しており、一部だけを修正すると別の補正規則が必要になる。

したがって、本件を「case-ready 導入後の case-auto orchestration 契約の再整合」という一つの Requirement Unit として扱う。

## 要件化の方向

### 1. 4-stage 構造

case-auto の通常経路は次の4 stage とする。

1. stage 1: `case-open`
2. stage 2: `case-ready`
3. stage 3: `case-run`
4. stage 4: `case-close`

`case-open` と `case-ready` を `stage 1a / 1b` として下位分類しない。

再合意済み Definition 変更では stage 1 を `case-revise` とし、stage 2 以降は通常経路と同じとする。

### 2. stage 内最大並列

各 stage は、当該 stage の開始時点で実行可能な対象を fan-out し、安全上または依存関係上直列化が必要な処理を除いて最大限並列実行する。

「最大限並列」は無制限並列を意味しない。

以下の既存制約を満たす範囲で並列化する。

* 必須依存関係
* 当該工程固有の実行安全上限
* 同一正規成果物や共有状態への競合書き込み
* 単一書き手契約
* 実行基盤側の安全制約
* その他、既存契約に明示された直列化要因

全 stage 共通の新しい固定並列数は導入しない。

### 3. stage 間の進行

stage 内の全対象が当該 stage について収束した後に、次 stage を開始する。

対象単位で `case-open → case-ready → case-run → case-close` を先行する縦切り実行を行わない。

stage の収束結果には少なくとも以下を区別する。

* 正常完了
* blocked
* failed
* delegation-unavailable
* その他既存 workflow が定める継続不能または再実行待ち状態

後続 stage へ渡す対象は、その stage を正常完了し、後続工程の開始条件を満たす対象とする。

blocked / failed 等で後続不能になった対象の存在だけを理由として、独立した正常対象の後続進行を停止しない。

未実行、実行中、状態不明、再実行待ち等を正常完了として扱わない。

### 4. stage 1: case-open

複数対象の `case-open` を一律順次実行しない。

独立して実行可能な Root Case 確立、Definition Package 生成、Definition PR 準備等は最大限並列実行する。

ただし、横断依存検査等、対象群全体の情報が必要な処理は並列実行によって兄弟対象を見落とさないこと。

そのために必要な全対象確立後の横断評価、起動時対象集合の利用、その他の実現方法は Design で決定する。

並列化を理由として既存の横断依存検査能力を弱めない。

### 5. stage 2: case-ready

複数対象の `case-ready` を一律順次実行しない。

Definition 忠実性確認、品質確認、構造計算等、対象単位で安全に実施できる処理は最大限並列化する。

Definition PR merge、canonical Definition 更新、共有正規成果物更新等で競合する書き込みについては、その共有書き込み部分だけを局所的に直列化する。

局所的な直列化を理由として、stage 2 全体を対象単位で順次実行してはならない。

各対象は自身の Definition 確定後、最新 canonical Definition を再取得する既存契約を維持する。

### 6. cleanup

stage 2 の対象群が収束した後、stage 3 開始前に cleanup 検証を行う。

cleanup 検証では、stage 2 を正常完了した対象について draft / RU が削除されていることを確認する。

blocked / failed / 中断等により stage 2 を正常完了していない対象について、既存 lifecycle 契約に従って保持された draft / RU を cleanup 違反として扱わない。

### 7. stage 3: case-run

case-run は既存の並列実行モデルと実行安全上限を維持する。

case-auto は stage 3 の全対象を対象とし、既存上限の範囲で可能な対象を継続的に fan-out する。

並列上限によって複数 batch に分かれても、それを別 stage として扱わない。

stage 3 の全対象が収束する前に stage 4 を開始しない。

### 8. stage 4: case-close

複数対象の `case-close` を一律順次実行しない。

PR 情報取得、Issue / PR 読取、完了条件事前評価、検証、capture 候補抽出等、安全に独立実行できる処理は最大限並列化する。

以下のような共有状態を変更する部分だけを必要な単位で局所的に直列化する。

* main へ影響する merge / 同期
* 同一 Epic Issue 本文への更新
* 単一書き手対象
* 同一共有 `.agentdev` 状態への競合更新
* その他同時書き込みによって整合性を失う処理

per-Epic 単一書き手のように競合範囲が対象単位で限定される場合、無関係な別 Epic まで全体直列化しない。

### 9. Epic / Wave

Epic / Wave の既存内部実行モデル自体は変更しない。

case-auto は Epic execution_unit の内部反復を、当該 execution_unit の stage 3 完了判定として扱う。

Epic / Wave 内部で利用される個別 command 名を理由に、外側 case-auto の stage 4 開始と誤認しない。

Epic execution_unit の stage 3 完了条件は、既存 Epic / Wave workflow が返す execution_unit 完了状態を基準とする。

case-auto に Epic / Wave 内部ロジックを複製しない。

### 10. 中断再開

case-auto は stage cursor を新たな正規状態として保存しない。

再開時は以下を使用して現在位置を再構成する。

* case-auto 起動時に確定した対象集合
* 各対象の Issue / PR / Case 等の正規状態
* Epic / Wave の正規状態
* 正規成果物から再構成できない最小限のローカル一時実行状態

起動時対象集合が draft / RU 削除によって失われる場合、その安定識別子を中断再開に必要な期間だけローカル一時実行状態として保持できる。

完了済み stage の処理を再実行せず、現在 stage の未完了対象だけを再開する。

全対象が終端状態になった後の対象集合一時状態の恒久保持は要求しない。

物理保存パス、ファイル名、データ形式は要件で固定しない。

### 11. 用語整理

case-auto 固有の独立概念としての `stage barrier model` を廃止する。

`barrier` を case-auto の状態管理モデルや新しい制御抽象として使用しない。

必要な制御は以下で表現する。

* orchestration stage
* stage 内 fan-out
* stage 完了時の fan-in
* stage 完了条件
* 局所的な直列化

`stage 1a / 1b` の表現を現行規範面および実行時投影から除去する。

## 作業仮定

* fan-out / fan-in の具体的実行機構は harness に依存し得るが、どの対象を並列可能と判断し、どの処理を局所直列化するかという業務契約は ADF が所有する。
* stage 内の局所直列化を実現する具体的な lock、queue、スケジューラ方式は外部契約を変更しない内部 Design として決定できる。
* 既存の case-run 安全上限、Epic / Wave 並列上限、単一書き手契約は、本RUで明示的に変更しない限り維持する。

## 受け入れ条件

### AC-01 4-stage 構造

通常経路が以下の4 stage として定義されていること。

`stage 1 case-open → stage 2 case-ready → stage 3 case-run → stage 4 case-close`

active な規範文書および実行時投影に `stage 1a / 1b` が残存しないこと。

### AC-02 stage 1 最大並列

独立した対象 A / B / C が存在する場合、A の `case-open` 完了を待ってから B を開始するような一律逐次実行を行わず、安全上の制約がない A / B / C を並列実行できること。

### AC-03 stage 1 の合流

A の `case-open` が先に完了しても、B / C の stage 1 が未収束である間は A の `case-ready` を開始しないこと。

### AC-04 case-open 横断検査

A / B / C の case-open を並列化しても、同一起動対象群内の兄弟対象が横断依存検査からタイミング依存で欠落しないこと。

### AC-05 stage 2 最大並列

stage 2 の A / B / C について、Definition 確定前の独立した検査・準備処理を最大限並列実行できること。

共有正規状態への書き込みが必要な部分だけが局所直列化され、その理由で stage 2 全体を対象単位の逐次実行へ退化させないこと。

### AC-06 canonical 再取得

並列 stage 2 において各対象が Definition を確定した後、各対象が最新 canonical Definition を基準として後続処理を継続すること。

### AC-07 cleanup

stage 2 の対象群収束後かつ stage 3 開始前に cleanup 検証を実施すること。

stage 2 正常完了対象に draft / RU が残存している場合は既存契約どおり停止すること。

blocked / failed / 中断対象に正当に保持された draft / RU は cleanup 違反としないこと。

### AC-08 stage 3 既存並列上限

stage 3 に既存安全上限を超える対象が存在する場合、上限内で継続的に並列実行すること。

先行 batch の完了だけで stage 4 を開始せず、stage 3 全対象の収束後に stage 4 へ進むこと。

### AC-09 stage 4 最大並列

複数 case-close の読み取り、検証、事前評価等の独立処理を最大限並列実行できること。

merge、main 同期、同一 Epic 本文更新、共有 domain state 更新等の競合部分のみ必要な単位で直列化すること。

### AC-10 局所直列化

一つの共有資源への競合を理由として、その共有資源と無関係な対象まで stage 全体で直列化しないこと。

異なる Epic への per-Epic 単一書き手処理は、他の Epic と競合しない限り相互に並列実行可能であること。

### AC-11 部分失敗

同一 stage の B が blocked / failed となり、A / C が正常完了した場合、当該 stage の結果集約後に B を後続対象から除外し、A / C の後続 stage を進行できること。

### AC-12 未収束状態

未実行、実行中、状態不明、または再実行待ちの対象を正常完了として扱わず、当該 stage の完了判定を行わないこと。

### AC-13 case-revise 経路

再合意済み Definition 変更では `case-revise` を stage 1 の代替入口として実行し、その完了後は通常経路と同じ stage 2 `case-ready` へ接続すること。

`case-revise` のためだけに別の stage 番号体系を新設しないこと。

### AC-14 Epic / Wave

Standard と Epic execution_unit が混在する場合でも、Epic 内部の Wave 状態遷移を case-auto 外側の stage 4 開始と誤認しないこと。

Epic execution_unit の stage 3 完了判定は既存 Epic / Wave workflow の完了状態に従い、case-auto が内部反復ロジックを複製しないこと。

### AC-15 中断再開

stage 2 で A の draft / RU が削除済み、B / C が未完了の状態で中断した場合でも、再開時に元の起動対象集合 A / B / C を識別できること。

A の完了済み処理を再実行せず、未完了対象だけを現在 stage で再開すること。

### AC-16 canonical state 非追加

stage 番号や対象集合を管理するためだけの新しい Git 管理対象 canonical state を導入しないこと。

正規成果物から再構成可能な情報を重複して永続化しないこと。

### AC-17 barrier 概念の除去

case-auto の active な契約・Design・Workflow Skill・command projection・reference に、case-auto 固有の独立状態管理モデルとして `stage barrier` を定義する記述が残存しないこと。

generic な同期技術用語としての barrier まで削除対象とはしない。

### AC-18 横断整合

case-auto の REQ、Command Design、Workflow Skill、runtime projection、関連 Foundation / Responsibility / Epic-Wave Design、reference 間で以下が一致すること。

* 4-stage 構造
* stage 内最大並列
* stage 間 fan-in
* 局所直列化
* cleanup
* 部分失敗
* resume
* Epic / Wave 接続

### AC-19 回帰検証

少なくとも以下のシナリオを個別に検証し、各結果を `pass / fail / blocked / not applicable` で記録すること。

* 複数対象の stage 1 並列
* stage 1 完了待ちから stage 2 への進行
* stage 2 並列 + Definition 共有更新
* blocked / failed 混在
* cleanup
* stage 3 上限超過
* stage 4 の並列事前処理 + 局所直列 merge
* Standard / Epic 混在
* draft / RU 削除後の中断再開
* 完了済み対象を含む再実行

### AC-20 既存検査

変更対象に対応する既存 docs / integrity / traceability 検査を実行し、変更によって新たな不整合を残さないこと。

AUTOGEN 対象が変更された場合は既存生成契約に従って再生成すること。

## 検証方法

単なる文言存在確認だけを受け入れ検証としない。

case-auto の複数対象実行について、実際の起動順序・同時実行・stage 完了待ち・部分失敗・共有書き込み・再開を観測可能な検証を行う。

特に「並列実行する」と記述されていることではなく、独立対象が実際に逐次処理へ退化していないこと、および次 stage が先行開始していないことを確認する。

既存検査で動的 orchestration を十分に検証できない場合は、本RUの受け入れ条件を直接検証できる回帰検証を追加する。
