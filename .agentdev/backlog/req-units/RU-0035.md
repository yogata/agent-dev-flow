# RU-0035: case-auto 複数対象 stage barrier と中断再開時の対象集合維持

## 目的

### 背景

`case-auto` は複数の要件 draft を一括処理でき、orchestration stage モデルとして `case-open`、`case-ready`、`case-run`、`case-close` を自走する。

2026-09-16 の14 draft を対象とした実行では、対象群全体を工程単位で進行させる意図に対し、実際には個々の draft が `case-open → case-ready → case-run → case-close` の方向へ縦切りで進行した。

現行 `REQ-034-025` は、stage 1 を `case-open・case-ready 順次`、stage 2 を `case-run 並列`、stage 3 を `case-close 順次` と定義し、前 stage 完了後に次 stage を開始することを要求している。一方、複数対象に対して「対象群全体の `case-open` が収束してから `case-ready` へ移る」のか、「各対象について `case-open → case-ready` を完了してよい」のかが明示されていない。

また、中断再開時には正規状態から現在位置を再構成する契約が存在するが、`case-ready` によって draft / RU が削除された対象を含め、case-auto 起動時に確定した対象集合を維持する契約が不足している。

### 問題

現行契約には、複数対象 case-auto に関して次の問題がある。

1. orchestration stage の適用単位が対象群全体であることが明確でなく、対象単位の縦切り実行を許容する解釈余地がある。
2. stage 1 が `case-open → case-ready` の一つの stage として表現され、`case-open` 全件収束と `case-ready` 全件収束の間の barrier が明示されていない。
3. 「全対象完了」を単純な成功条件として扱うと、一部 `blocked` / `failed` 時にも他対象を継続する既存契約と衝突する。
4. 再開時に stage cursor を保存しなくても現在 stage は各対象の正規状態から導出できるが、起動時対象集合そのものが draft 削除等によって失われる可能性がある。
5. 現行 command / Design / Workflow Skill / reference に同じ曖昧な stage 表現が存在し、局所修正では契約同期漏れが残る。

## Source Summary

チャット内で以下に合意した。

* 複数対象 case-auto は、対象単位の縦切りパイプラインではなく、対象群全体に対する orchestration stage barrier で制御する。

  * stage 1a: 対象群の `case-open`

## 統合理由

stage barrier と中断再開時の対象集合維持は別々の不具合ではない。

stage barrier を正しく再構成するためには、「どの対象群に対する barrier なのか」を再開時にも一意に識別できる必要がある。

stage cursor のみを修正して対象集合を保持しなければ、`case-ready` による draft 削除後の中断時に、完了済み対象が元の対象群から脱落し、異なる対象集合に対して barrier を評価する可能性が残る。

したがって、本件は「複数対象 case-auto の orchestration stage barrier と、その barrier を中断再開後も同一対象集合に対して維持する契約」を一つの Requirement Unit として扱う。

## 要件化の方向

### 1. orchestration stage の対象群適用

複数対象を処理する `case-auto` は、orchestration stage を対象ごとのパイプラインとして適用せず、起動時に確定した対象群に対する barrier として適用する。

通常経路は少なくとも以下の外部的進行順序を持つ。

1. stage 1a: `case-open`
2. stage 1b: `case-ready`
3. cleanup gate
4. stage 2: `case-run`
5. stage 3: `case-close`

例外経路の `case-revise` を含む場合も、対象ごとの縦切り実行ではなく、同等の対象群 barrier 原則を適用する。

### 2. stage の収束条件

次 stage への遷移条件は、単なる「全対象成功」ではなく、当該 stage に属する全対象が次のいずれかへ収束したこととする。

* 当該 stage を正常完了した。
* 既存契約上、当該 stage から後続へ進めない終端的な結果が確定した。

未実行、実行中、状態不明、再試行対象のままの対象が存在する間は、その stage の barrier は成立しない。

後続 stage へ渡す対象は、当該 stage を正常に完了し、後続実行条件を満たす対象のみとする。

`blocked` / `failed` 等によって後続不能となった対象の存在だけを理由として、独立した他対象の進行を停止しない。

### 3. stage 内 scheduling と barrier の分離

最大同時起動数、起動間隔、順次フォールバック等は stage 内の scheduling 制約とする。

これらによる batch 分割は orchestration stage の分割を意味しない。

例えば stage 2 の対象が7件で最大同時起動数が5件の場合、先行5件が完了しても残り2件が未収束である限り stage 3 を開始しない。

### 4. 再開時の stage 再構成

stage cursor 自体を新たな正規状態として保存しない。

再開時は以下から現在 stage を再構成する。

* 起動時に確定した対象集合
* 各対象の Issue / PR / Case 等の正規状態
* 既存契約上必要なローカル一時実行状態

現在 stage は、対象×stage の状態から「最も早い未収束 stage」として決定する。

完了済み stage / 対象を再実行せず、現在 stage の未収束対象のみを再実行対象とする。

同一対象だけを後続 stage へ先行させる縦切り再開を行わない。

### 5. 起動時対象集合の維持

case-auto 起動時に処理対象として確定した対象集合の安定識別子は、中断再開に必要であり正規成果物から完全には再構成できない期間に限り、ローカル一時実行状態として保持できる。

対象の draft / RU が後続工程で削除されても、その対象を実行中の対象集合から消失させない。

正規成果物から再構成できる情報を別の正規状態として重複管理しない。

全対象が終端状態となった後のローカル対象集合状態の保持は要求しない。

具体的な保存パス、ファイル名、データ形式は Design / 実装判断とし、本要件では固定しない。

## 決定的受け入れ条件

### 受け入れ条件

#### AC-01 対象群 barrier の契約

複数対象 A / B / C を処理する場合、A / B / C の stage 1a が収束する前に、いずれの対象についても stage 1b を開始しないこと。

#### AC-02 stage 1b barrier

A / B / C が stage 1a を収束した後、A の stage 1b が先に完了しても、B / C の stage 1b が未収束である間は A の stage 2 を開始しないこと。

#### AC-03 stage 2 barrier

stage 2 の対象が7件、同時起動上限が5件の場合、先行5件が完了しても、残る2件が未収束である間は stage 3 を開始しないこと。

最大5件の制約を stage 分割として扱わないこと。

#### AC-04 一部失敗時の継続

同一 stage の対象 B が `blocked` または `failed` 等の既存契約上後続不能な状態へ収束した場合、B を後続 stage の対象から除外すること。

A / C が正常完了している場合、B の存在だけを理由として A / C の後続 stage 進行を停止しないこと。

#### AC-05 未収束対象の barrier 維持

未実行、実行中、状態不明、または既存契約上再試行対象である対象が1件以上存在する場合、当該 stage の barrier を成立扱いしないこと。

#### AC-06 draft 削除後の対象集合維持

case-auto 起動時の対象集合に A / B / C が含まれ、A の `case-ready` により A の draft / RU が削除された後に中断した場合、再開時も A / B / C を同じ実行の対象集合として識別できること。

A を新規入力一覧から消失したことだけを理由として元の対象集合から除外しないこと。

#### AC-07 再開時の現在 stage 再構成

A が現在 stage を完了済み、B / C が同 stage 未完了の状態で再開した場合、A の完了済み処理を再実行せず、B / C のみを同一 stage の再実行対象とすること。

A だけを後続 stage へ先行させないこと。

#### AC-08 新しい正規状態の非導入

stage cursor または対象集合を保持するためだけの新しい Git 管理対象正規状態を導入しないこと。

正規成果物から再構成可能な情報を重複する正規状態として保存しないこと。

#### AC-09 ローカル一時状態のライフサイクル

対象集合のローカル一時実行状態は、中断再開に必要な期間のみ保持すればよく、全対象が終端状態となった後の恒久保持を要求しないこと。

#### AC-10 契約横断整合

`REQ-034`、case-auto Design、Epic / Wave 横断 Design、case-auto command projection、case-auto Workflow Skill、orchestration reference の stage barrier 表現が矛盾しないこと。

runtime projection に旧来の「stage 1 case-open → case-ready」を対象単位パイプラインとして解釈可能な記述を残さないこと。

#### AC-11 cleanup gate

cleanup gate は、stage 1b の対象群が収束した後、stage 2 開始前の barrier として評価されること。

一対象の `case-ready` 完了だけをもって対象群全体の cleanup gate 通過または stage 2 開始としないこと。

#### AC-12 検証

変更後に以下を確認すること。

* REQ / Design / Workflow Skill / command projection の参照整合
* AUTOGEN 索引に変更が生じる場合は再生成済みであること
* docs-check の該当検査が pass すること
* AC-01〜AC-11 の各状態遷移を個別に合否判定できる検証が存在すること

### 検証方法

検証結果は各受け入れ条件について `pass / fail / blocked / not applicable` のいずれかで記録する。

特に、単なる文言存在確認だけで完了とせず、複数対象に対する以下の状態遷移を検証対象とする。

* 全対象未完了
* 一部対象のみ完了
* 一部 blocked / failed
* stage 内上限による複数 batch
* draft / RU 削除後の中断再開
* 完了済み対象を含む再実行
* 全対象終端後の終了
