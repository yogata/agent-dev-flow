# RU-0122: Definition Package 生成手順への事前確認組込み（design 対応 coverage と finding domain 鮮度）

## Sources

- `existing-countermeasure-update-traceability-design-coverage-precheck.md`: Case #3123（PR #3124）で意味変更行 REQ-031-030 の baseline 既知 design 対応欠落が検出されず、case-ready lifecycle gate completeness（fail-closed）で停止。case-open の missing-design 0 件ゲートが増分ベース（新規行のみ）であるため、「既存行の意味変更」を対象に coverage --req による design 対応事前確認と欠落時の artifact_actions 組込みが手順に存在しない問題。
- `existing-countermeasure-update-inspect-finding-domain-freshness.md`: Case #3121（PR #3122）で draft-data の target_design.domain 宣言（responsibilities/）が実配置（foundations/）と不一致でも、slug・行番号・文言の3点機械照合で実配置を正と判定できた実例。finding の domain 記録が配置移動後に陳腐化し、機械的転記で誤パス更新を起こし得る鮮度確認（実パス実在照合）手順の欠落。

## Source Summary

req-define / case-open の Definition Package 生成・転記工程に、2種類の事前確認が手順として組込まれていない。(1) 意味変更対象 REQ 行の design 対応有無の事前確認（coverage --req 実査と欠落時の artifact_actions 組込み）。欠落行を含む Case は case-ready の lifecycle gate で必ず停止し得る（missing-design 既知債務 877 行の範囲で発生余地あり）。(2) finding 由来 draft の artifact_actions 転記前の target_design 実パス実在確認（grep による本文一意性確認込み）。宣言パスを正にすると不在パスへの誤変更が発生し得る。いずれも後段の gate・転記で失敗する前に、生成手順側で検出・対処する予防手順のギャップである。

## 統合理由

N:1。2件とも「Definition Package 生成・転記前の事前確認ステップの組込み欠落」という同一問題型であり、反映先も req-define / case-open の手順記述（workflow skill reference・case-open SKILL.md STEP-2/STEP-3・case-open Design）で共通する。「手順に事前確認ステップが明記されている」単一の受け入れテストで両方を検証可能なため統合する。確認対象が design coverage（REQ 行単位）と実パス実在（finding domain 記録単位）で異なるため、RU 内で論点を分離記載する。

## 要件化の方向

- req-define / case-open の Definition Package 生成手順に、意味変更対象行の design 対応事前確認ステップ（coverage --req、欠落時は artifact_actions へ design 対応追加を含めて合意）を追記する
- 同手順に、finding 由来 draft の転記前の実パス実在確認（slug・行番号・文言による機械的一意特定。不在パスを正にしない）を追記する
- 事前確認を省略した Case が case-ready ゲートで停止し得る旨の注記を手順側に置く
- 対象外: case-ready lifecycle gate completeness 契約自体の変更、traceability check / coverage の実装変更、inspect finding schema の変更、過去 finding の一括鮮度是正
- 暫定分類は挙動Design（手順・振る舞いの定義）。req-define で最終確定する
