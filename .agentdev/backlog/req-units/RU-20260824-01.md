# GitHub Issue を共通管理単位とする課題管理再設計

## 背景

AgentDevFlow では GitHub Issue を req/case パイプラインの Case 実行票として利用している一方、課題、ToDo、アイデア、リスク等の継続追跡には `docs/issue-list/` の課題ファイル方式が導入されている。

また、ローカルモードでは Case を `.agentdev/cases/` に保存する Case 専用モデルを持ち、GitHub I/O については 2026-08-24 時点で `REQ-011`、`REQ-052`、`DEC-022` により Markdown skill から Custom Tool へ移管する方向へ更新されている。

これらを踏まえ、追跡対象と Case 実行票を別々の保存基盤・操作経路で管理するのではなく、GitHub Issue とそのローカル相当物を共通 Issue 基盤として再構成する。

## 問題

現行構成では、追跡対象と Case が別基盤に分かれ、課題ファイル固有の文書分類、ID、検索・検査スクリプト、ローカル Case 専用保存、GitHub I/O の旧 Markdown skill 実装が併存している。

このまま追跡Issueだけを追加すると、追跡Issueの形式、状態、タグ・属性マッピング、GitHub/ローカル I/O、Case との関係が Command、Workflow Skill、Capability Skill、Tool、文書体系に重複定義される。さらに、既存 `ISL-001` が保持する未解決論点を失わずに旧方式を除去する必要がある。

## Source Summary

2026-08-24 の対話で、`agent-dev-flow-main_2026-08-24` を基準に新設された課題管理機構を見直した。

合意した最終方針は、GitHub Issue を Case 実行票だけに限定せず、追跡IssueとCase Issue を収容する共通Issue基盤へ拡張することである。追跡Issueは課題、ToDo、アイデア、リスク等を育てる管理単位とし、`/agentdev/issue` が自然言語操作入口となる。追跡Issueは実行票そのものではなく、実行が確定した場合は要件化・設計経路を経て別 Case Issue を生成する。

追跡Issueの論理フォーマット、種別、状態、タグ・属性へのマッピングは一元管理する。GitHub Issue Type / Issue Fields は利用可能な環境で写像として活用できるが、ADF の必須前提にはしない。

旧 `docs/issue-list/` 方式は完全に除去し、過去方式の経緯を現行文書へ残さない。課題ファイル専用 ID、文書分類、検索スクリプト、検査、テストも合わせて除去する。現在 `ISL-001` が保持している有効な未解決論点だけは新しい追跡Issueへ移す。

ローカルモードでは `.agentdev/cases/` の Case 専用保存モデルを `.agentdev/issues/` のローカルIssueの共通モデルへ一般化する。追跡IssueとCase Issue は同じローカルIssue基盤を利用し、`role` ごとの条件付きスキーマで差を表現する。

なお、8/24版では `REQ-011` と `DEC-022` により GitHub/Git I/O を Markdown skill から Custom Tool へ移管する方針が既に導入されているため、本 RU の GitHub/ローカル I/O 拡張はその Custom Tool 境界に実装する。上位層は GitHub版かローカル版かを意識せず、同一操作契約を利用する。

## 統合理由

本変更は、追跡IssueとCase Issue の論理モデル、GitHub/ローカル I/O、ローカル保存形式、公開コマンド、Capability Skill、文書体系、旧課題ファイル方式の除去を同時に整合させる必要がある。いずれかだけを個別変更すると複数の課題管理モデルと責務定義が併存するため、一つの Requirement Unit として横断的に扱う。

## 目的

AgentDevFlow の GitHub Issue 利用を、req/case パイプラインの実行票だけに限定せず、チームが継続して追跡する共通管理単位へ拡張する。

課題、ToDo、アイデア、リスク等を追跡Issueとして GitHub Issue 上で蓄積、検討、再評価、具体化し、実行が確定した仕事は req/case パイプラインから別の Case Issue として実行する。追跡IssueとCase Issue は同じ GitHub Issue 基盤を利用するが、役割とライフサイクルを明確に分離する。

`/agentdev/issue` は追跡Issueを自然言語で操作する公開入口とする。追跡Issueの論理フォーマット、種別、状態、GitHub上のタグ・属性への対応を一元管理し、各 workflow が個別に形式を定義しない。

ローカルモードでは GitHub Issue 相当の共通保存単位をローカルIssueとし、`.agentdev/issues/issue-{NNNN}.md` に保存する。追跡IssueとCase Issue は同じローカルIssue基盤を利用し、GitHub版と同一の Issue I/O 操作契約から差し替えられるようにする。

## 要件化の方向

### 1. GitHub Issue を共通Issue基盤にする

GitHub Issue を「人または Agent が、検討・判断・実行・追跡する必要のある事項の永続的な単位」と位置付ける。

Issueは `role` により追跡IssueとCase Issue を区別する。

- 追跡Issue: 課題、ToDo、アイデア、リスク等を蓄積し、検討、再評価、具体化、解決、反映確認まで追跡する。
- Case Issue: req/case パイプラインで確定した仕事を実行、検証、完了するための作業単位とする。

Issue が存在すること自体を Agent の実行許可としない。追跡Issueは実行対象へ直接変質させず、実行が確定した場合は req-define 等の正規要件化・設計経路を経由し、case-open が別の Case Issue を作成する。追跡Issueと生成された Case Issue の関係は後から追跡できるようにする。

### 2. 追跡Issueスキーマを一元管理する

追跡Issueの論理スキーマは `agentdev-issue-tracking` Design に集約する。少なくとも次を一元管理する。

- `role`
- `kind`
- 状態と状態遷移
- 件名、課題・アイデア・ToDo の内容、背景、影響
- 関連成果物
- 選択肢、判断材料、不足情報
- owner、期限、優先度等の任意メタデータ
- 保留理由、再評価条件
- 解決結論
- 反映先と反映状態
- 追跡IssueとCase Issue の関連
- GitHub上で使用するラベル、Issue Type、Issue Field 等への物理マッピング
- 追跡Issue本文の標準構造

物理マッピングの正は一箇所に置く。同一のラベル名、`kind`、状態、本文フォーマットを複数の Command / Skill / Template が独自定義しない。

検討経過は GitHub Issueコメントを正規の時系列履歴として利用し、Issue本文は現在状態を理解するための要約・構造化情報を中心とする。本文内へ独自の追記専用ログを二重保持しない。

### 3. `/agentdev/issue` を追跡Issue操作入口へ変更する

`/agentdev/issue` は自然言語入力から、起票、検索・参照、更新、コメント追加、保留、再評価、実行準備完了、解決、反映確認、クローズ、再オープンを判断して実行する。

ユーザーにサブコマンド、ラベル名、Issue Type、Field 名等の GitHub 実装詳細を要求しない。

新規起票時は、現在の作業で解決できる事項を先に解決し、既存追跡Issueを検索して重複を避ける。ユーザー合意が必要な設計判断を課題管理側だけで確定しない。

他 workflow も追跡Issue能力を利用できるが、各 workflow が追跡Issueスキーマや GitHub I/O を再実装しない。

### 4. I/O を Custom Tool の同一契約へ統合する

追跡Issue操作に必要な I/O を現行 Custom Tool 契約へ追加する。少なくとも次の能力を上位層から利用できるようにする。

- Issue 作成
- Issue単体読取（本文だけでなく title、state、labels、`role` / `kind` / 状態の写像に必要なメタデータを取得可能）
- Issue本文・メタデータ更新
- Issueコメント追加・読取
- Issue一覧・検索（role、kind、state、関連情報等による絞り込みに必要な構造化結果）
- Issueクローズ
- Issue再オープン
- Case workflow が既に利用する PR 操作

各 WRITE は Tool 内で VERIFY まで完了してから成功を返す。Command / Workflow Skill / Capability Skill の Markdown に gh CLI オプション、文字コード対策、一時ファイル実装等を復活させない。

### 5. ローカルモードをローカルIssue基盤へ一般化する

ローカル版 Custom Tool は通常版と同じ Issue操作契約を実装し、GitHub Issue を `.agentdev/issues/issue-{NNNN}.md` へ読み替える。

ローカルIssueは共通メタデータと `role` を持ち、`role` ごとに必要な本文・追加情報を条件付きで保持する。

- 追跡Issue: 追跡Issueスキーマに必要な情報とコメント相当履歴を保持する。
- Case Issue: 既存 Case 実行に必要な Issue本文、コメント相当情報、PR 相当セクション、マージ結果等を保持する。
- PR 関連操作は `role: case` のローカルIssueにのみ適用する。

ローカルIssueスキーマは追跡Issueを追加したことで Case 固有セクションを全 Issue の必須項目にしない。`role` ごとの必須項目・状態値・許可操作を検証できること。

ローカル版の上位 Command / Workflow / Capability は `.agentdev/issues/` を直接操作せず、通常版と同一の Tool 操作契約だけを利用する。

### 6. 文書体系と旧課題ファイル実装を除去する

`docs/issue-list/` をディレクトリごと削除する。`ISL-*` ID、課題ファイルの frontmatter、課題ファイルを docs/配下の正規文書として扱う分類、課題ファイル専用検索・一覧・検査スクリプトおよびテストを残さない。

`document-model.md` は課題追跡のために追加された8番目の文書分類を除去し、既存の文書7分類へ戻す。GitHubの追跡Issueは docs/配下の文書種別ではなく、管理単位・永続状態として責務表、Guide、System 説明を更新する。

`REQ-001` の文書種別一覧等、課題ファイルを docs/配下の文書種別として追加した箇所も整合させる。一方、「課題追跡に状態管理を集約する」等、GitHubの追跡Issueに読み替えて現在も成立する一般原則は新方式の意味で維持できる。

旧課題ファイル方式にのみ由来する `.agentdev/intake/inbox/2026-08-23-issue-list-docs-guard-profile-scope.md` と `.agentdev/intake/inbox/2026-08-23-req049-declaration-corpus-gap.md` は、新方式への移行で解消される古い前提の item として残さない。

### 7. 既存の未解決論点を追跡Issueへ移す

現行の `ISL-001` の実質的な論点は失わない。新しい追跡Issueとして、次の現在有効な情報だけを移す。

- サブエージェント間で探索責務を分割すべきかという未解決論点
- 改善前分析で read を伴う97論理実行単位のうち68単位で異なる子セッション間の同一 path 参照が確認されたこと
- REQ-048 と改善前分析 Report との関連
- 改善効果を観測する前に構造変更すると原因と効果を分離できないため現在は保留すること
- REQ-048 の改善を実運用へ反映した後、比較可能な OpenCode セッション履歴が十分蓄積したら再評価すること
- 再評価時に確認する残存重複、`source / projection` 由来重複、工程間文脈不足、独立検証として必要な重複、token 消費影響等

新しい追跡Issueには `ISL-001`、`docs/issue-list/`、課題管理機構の初期実装であったという経緯を記録しない。

## 受け入れ条件

1. `docs/issue-list/` が存在せず、現行成果物・配布物・検査コード・テスト・Guide・README・`.agentdev/intake/` に `docs/issue-list` または `ISL-` を現行仕様として参照する記述が残っていないこと。
2. `REQ-049` が GitHubの追跡Issueを正規管理先とし、追跡IssueとCase Issue の役割分離、課題・ToDo・アイデア・リスク、再評価、解決、反映確認、自然言語入口を現在要件として定義していること。
3. `DEC-020` が新しい GitHub Issueを共通管理単位とするモデルだけを記述し、`docs/issue-list/` を採用した経緯、却下案、移行前方式の説明を含まないこと。
4. `document-model.md` に課題追跡の8番目の文書分類がなく、文書7分類モデルが一貫していること。責務表・Guide でも追跡Issueを docs/配下の文書種別として扱っていないこと。
5. `/agentdev/issue` が GitHubの追跡Issueの自然言語操作入口となり、GitHub版では課題管理のためにリポジトリ内課題ファイルを作成・commit しないこと。
