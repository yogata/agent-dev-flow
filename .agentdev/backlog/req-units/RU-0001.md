# RU-0001: 実行定義層の責務境界再編と機械強制への移行

## 背景

AgentDevFlow の Command / Skill を横断して確認した結果、ガードレール番号 `Gxx` の欠番・非連番、同内容の重複記述、他の正規契約から導出可能な共通記述の再掲、決定的処理の Markdown 内残存が広範囲に存在することが確認された。

特に、公開 Command と専用 Workflow Skill の対応関係を全18組確認した結果、すべての組で、同一仕様を変更した際に Command と Workflow Skill の双方を同じ理由で変更する必要がある実質的な重複が存在した。

これは個別実装者による規約違反だけではなく、現行の正規設計自身が、

- Command は workflow 実装本体を所有しない
- Command は workflow の公開順序や高水準の実行構造を記述する

という両立しにくい責務を同時に要求していることに起因する。

また、`Gxx` には少なくとも以下の異なる性質が混在している。

- 利用者から見える実行拒否・副作用境界
- 成功時に満たすべき不変条件
- ファイル形式上の要求
- Git / GitHub 操作手順
- 文字コードやシェル等に依存する実装規則

そのため、`Gxx` の非連番は単なる採番不備ではなく、異なる責務を一つの記述体系へ集約していることの症候として扱う必要がある。

既存実装には、一方向生成による派生情報管理、配布境界を実行前に強制する Plugin / Hook、Skill 配下 Script への決定的処理分離など、今回の再編に利用できる既存パターンも存在する。

## 問題

現状には主として以下の4つの構造問題がある。

1. **正規責務モデルの自己矛盾**
   - Command を薄くする方針と、Command に workflow の順序・構造を再掲させる方針が併存している。
   - その結果、Command と Workflow Skill の二重管理が設計上誘発されている。

2. **決定的処理の Markdown 残存**
   - Git / GitHub 操作、文字コード制御、採番、形式検証等、本来プログラムとして決定的に処理可能な内容が Command / Skill / Reference の手順として記述されている。
   - モデルが文章を正しく解釈・遵守することに不要に依存している。

3. **型から継承可能な共通契約の再掲**
   - 同一種別の Command / Workflow Skill 等に、原本の扱い、拡張読込、単独実行禁止等の共通記述が繰り返されている。
   - 共通契約と個別差分の責務が分離されていない。

4. **Gxx への異種概念混在**
   - ローカルな利用者境界、横断ポリシー、実装手順、形式要求等が同一の番号体系で扱われている。
   - `G01` 起点・欠番なしへの再採番だけでは根本原因を解消できない。

- 旧 Gxx や旧 Command 記述形式への後方互換性は要求しない。
- Command の実行状態に依存する動的な書込み許可範囲の強制は今回の対象外とする。
- 同一規範の複数成果物による正規所有は認めず、独立利用上不可欠な場合に限り、正本を明示した非規範的な最小表現を許容する。

## 統合理由

各問題を個別の文章整理・採番修正として扱うと、現在の正規責務モデルと機械検査が旧構造を正しいものとして要求し続け、重複が再発する。

また、以下は相互依存する。

- Command / Workflow Skill の重複解消
- 型由来の共通記述削減
- Gxx の再定義
- 決定的処理の Script / Tool / Hook 化
- Tool / Plugin の配布境界
- 現行 checker の責務モデル変更

したがって、これらは「個々のファイルを短くする」複数の独立問題ではなく、**ADF の実行定義層における正規所有者を一意化する一つの責務境界問題**として統合して要件化する。

## 要件化の方向

### 1. 実行定義層の正規所有者

各層が正規所有できる内容を以下のように分離する。

| 層 | 正規所有する内容 |
|---|---|
| Command | 利用者向け入口、入力契約、最終出力、利用者から見える重大な副作用・確認境界、Workflow Skill への委譲 |
| Workflow Skill | 工程、分岐、状態遷移、再開、停止、Capability Skill の組合せ、副作用の実行順序 |
| Capability Skill | 複数 workflow で再利用可能な意味規則、判断、分類、方針 |
| Reference | 大きな説明、背景、例。新たな正規契約は所有しない |
| Script | 決定的な解析、変換、検証、生成 |
| Custom Tool | Git / GitHub 等に対する構造化された副作用操作 |
| Plugin / Hook | モデルの遵守判断へ委ねてはならない実行前禁止・強制 |
| Template | 固定的な成果物形状 |
| REQ / Design | 規範および設計契約 |

Command は workflow の工程や「公開順序の要約」を正規所有しない。

### 2. 標準継承と差分記述

成果物種別から継承可能な標準契約は、各 Command / Skill / Reference 等へ繰り返し記述しない。

個別成果物は、原則として以下のみを記述する。

- その成果物固有の契約
- 標準からの差分
- 必要な例外
- 正規所有者への名レベル参照

同一規範を複数成果物が正規所有することは禁止する。

独立利用上、正本の情報を再提示しないと利用者へ必要情報が届かない場合に限り、以下をすべて満たす非規範的な最小表現を許容する。

- 正規所有者が一意に特定できる
- 再提示側が正規契約を追加・変更しない
- 正本変更時に別の独立した仕様判断を必要としない
- workflow 工程を Command に再構成する用途では使用しない

### 3. 決定的処理の配置基準

Markdown 上の手順として保持する必要がない処理は、その性質に応じて以下へ移す。

| 性質 | 正規配置 |
|---|---|
| 同じ入力に対して決定的に解析・変換・検証・生成できる | Script |
| Git / GitHub 等への構造化された外部副作用を持つ | Custom Tool |
| 実行時に必ず拒否・強制すべき | Plugin / Hook |
| 意味判断・分類・方針判断を必要とする | Skill |
| 固定された成果物形状 | Template |

Tool / Hook へ移管した場合も、Command / Skill には必要な意味上の契約を残し、文字コード、シェル呼出方法、一時ファイル操作等の実装手順は残さない。

### 4. Tool / Plugin / Hook の配布境界

ADF で一般利用される機能と、agent-dev-flow 自己開発専用機能を区別する。

**ADF 配布対象**
- consumer でも必要となる汎用 Custom Tool
- consumer でも必要となる汎用 Plugin / Hook
- ADF 共通の副作用安全境界・実行時強制

**repo-local**
- agent-dev-flow 自己開発固有の整合性検査
- ADF の原本・投影構造にのみ依存する検査
- ADF 内部の文書体系・パス・REQ 等に依存する強制処理

ADF の実行時配布モデルは、必要な Tools / Plugins を正規配布物として扱えること。

### 5. 強制機能の失敗時動作

実行時禁止または副作用境界を強制する Tool / Hook は、安全性を確認できない場合に対象副作用を実行してはならない。

少なくとも以下を成功扱いしない。

- 設定を解釈できない
- 対象パス等を安全に解決できない
- 強制処理自体が異常終了した
- 必須検証が完了できない

一方、検索、診断、候補抽出等の補助能力については、その能力の契約で代替手段と継続可否を定義できる。

### 6. ガードレール識別体系

既存の `Gxx` は再採番して維持しない。

既存 `Gxx` は内容を分類し、正規所有先へ移す。

- Command 固有の利用者向け境界で、横断参照・機械強制を必要としないもの
  - ID を付与せず Command 契約として保持する
- 複数箇所から参照、検査または強制される共通ポリシー
  - 内容を示す安定した意味IDを付与する
- 決定的処理
  - Script 等へ移管する
- Git / GitHub 等の副作用手順
  - Custom Tool 等へ移管する
- 実行時禁止
  - Plugin / Hook 等による強制対象とする
- ファイル形状
  - Template / Design / 検査等の適切な正規所有者へ移す

意味IDは既存 `Gxx` との一対一変換を目的としない。

現行の G01 起点、欠番なし、連番を要求する制度および検査は、新しい責務体系への移行後に廃止する。

### 7. Command / Workflow Skill の正規化

確認済みの全18組の公開 Command と専用 Workflow Skill を、同一の新責務モデルで評価・正規化する。

局所的な数組だけを修正して新旧責務モデルを併存させない。

各組について少なくとも以下を満たすこと。

- Workflow Skill が所有する工程を Command が再掲しない
- Command は Workflow Skill の内部 STEP、reference パス等へ依存しない
- Command に型由来の共通 boilerplate を再掲しない
- Workflow Skill にも型から継承可能な共通契約を不要に再掲しない
- 個別差分と正規所有者が判別可能である

### 8. Capability Skill 等の責務競合解消

Command / Workflow Skill の組だけでなく、確認済みの以下のような横断的責務競合も同じ原則で解消対象とする。

- Command 執筆規約を複数 Skill が異なる内容で所有している状態
- Workflow Skill と Capability Skill の双方が同じ状態機械・実行制御を所有している状態
- 意味診断 Skill が機械判定可能な構造検査まで所有している状態
- 同じ派生情報を複数の表で手動同期している状態
- Capability Skill / Reference に実装手順が正規契約として残っている状態

派生可能な索引・逆引き表等は、一方向生成できる場合に複数正本を持たない。

## 主対象REQまたは変更対象候補

`req-define` では最新の正規文書を再確認し、既存 REQ への UPDATE と新規 REQ の必要性を確定する。

現時点の変更対象候補は以下。

- Command / Workflow Skill / Capability Skill の責務境界を所有する REQ 群
- 公開 Command の形式・thin Command 契約を所有する REQ 群
- ガードレール番号・integrity 検査を所有する REQ 群
- 実行時パッケージ・consumer 配布境界を所有する REQ 群
- Script / Tool / Plugin / Hook の正規配置および配布契約に不足がある場合の新規 REQ

関連 Design の変更対象候補は以下。

- Workflow Skill 責務モデル
- 成果物責務境界
- Command ファイル形式
- 実行時パッケージ境界
- integrity rule / checker 契約
- project extension 等、型由来共通記述を要求している正規設計

正確な REQ ID・変更行は `req-define` 時点の最新正本から確定する。

## 対象範囲

- 公開 Command と専用 Workflow Skill 全18組
- Command / Workflow Skill / Capability Skill の正規責務モデル
- Reference / Script / Custom Tool / Plugin・Hook / Template を含めた責務境界
- 型由来共通記述の継承・差分記述原則
- 既存 Gxx の分類と廃止
- 共通ポリシーの意味ID体系
- Gxx 連番検査および関連 baseline の最終解消
- 決定的処理の適切な実行層への移管
- ADF 汎用 Tool / Plugin / Hook の配布境界
- 強制機能の失敗時動作
- Command / Skill 横断で確認済みの責務競合
- 正規契約変更に追随する機械検査の整合

## 対象外

- OpenCode ハーネス本体の変更
- Command 実行状態に依存した動的な書込み許可範囲の強制
- 動的書込み許可範囲を実現できるかどうかの実証
- 既存 Gxx と新しい意味IDとの一対一対応維持
- 旧 Gxx または旧 Command 記述形式への後方互換層
- 単なる行数削減を目的とした文章短縮
- 責務変更を伴わない無関係な古い記述・dead code の一括整理
- 今回確認していない別機能の設計変更
- 実装を単一 worker に限定すること
- 実装時の Wave 構成、作業分割方法等の実装計画
- 本RUで必要性が確定していない公開 Command の追加・削除・rename
- 本RUで必要性が確定していない既存 scripts 公開入口の変更

## 作業仮定

以下は要件ではなく、後続工程で再確認可能な作業仮定とする。

- 既存の一方向生成、Skill 配下 Script、実行前 Hook の実装パターンは、適用可能な領域では再利用候補となる。
- 正規責務モデルの変更により既存 checker が不整合となる場合、checker は新しい正規契約へ追随させる。
- 新しい共通ポリシー意味IDの具体的な命名体系は、安定性・可読性・衝突回避を満たす範囲で後続設計に委ねる。
- Tool / Plugin の具体的なディレクトリ構造は、配布境界要件を満たす範囲で後続設計に委ねる。

## 受け入れ条件

### AC-01 正規責務モデル

Command / Workflow Skill / Capability Skill / Reference / Script / Custom Tool / Plugin・Hook / Template / REQ・Design について、それぞれが正規所有する内容と所有しない内容が正規文書上で一意に判別できること。

### AC-02 Command の責務

公開 Command が workflow の工程一覧、STEP、内部順序または「公開順序の要約」を正規所有せず、利用者向け入口、入力、最終出力、利用者から見える重大な副作用・確認境界、Workflow Skill への委譲に限定されていること。

### AC-03 18組の重複解消

確認対象の全18組の公開 Command と専用 Workflow Skill について、「同じ仕様変更を同じ理由で双方へ反映しなければならない workflow 契約の重複」が残っていないこと。

### AC-04 標準継承

型から一意に継承可能な標準契約が個別 Command / Skill 等へ必須記述として再掲されておらず、個別成果物が差分中心の記述になっていること。

### AC-05 正本の一意性

同一の規範について複数成果物が正規所有者となっていないこと。

非規範的な再提示が存在する場合は、正規所有者が識別でき、再提示側だけを変更して規範を変更できないこと。

### AC-06 決定的処理の分離

文字コード制御、採番、形式検証、定型変換等、機械的に決定可能な処理が、意味判断として Skill に残されていないこと。

### AC-07 副作用操作の分離

Git / GitHub 等への定型的な副作用操作について、モデルがシェル手順や文字コード等の実装詳細を逐次再現することを必須としない構造になっていること。

### AC-08 実行時強制

モデルの判断に委ねてはならない共通禁止事項について、機械強制可能なものは Plugin / Hook または同等の実行時強制境界で扱われること。

### AC-09 強制機能の異常系

安全性を確認できない状態で強制境界を担う Tool / Hook が異常終了または判定不能となった場合、対象副作用が実行されないこと。

### AC-10 配布境界

ADF 汎用 Tool / Plugin / Hook と agent-dev-flow 自己開発固有機能が区別され、consumer に必要な汎用機能だけをADF配布対象として扱えること。

### AC-11 Gxx 廃止

公開 Command に対する `G01` 起点・欠番なしという連番要件が新しい正規契約として残っていないこと。

### AC-12 共通ポリシー識別

複数箇所から参照、検査または強制される共通ポリシーがある場合、位置依存の連番ではなく、意味に基づく安定識別子で参照できること。

### AC-13 ローカル境界のID不要化

Command 固有で横断参照・機械強制を必要としない利用者向け境界について、識別子付与が必須になっていないこと。

### AC-14 旧制度の残存防止

Gxx 連番制度を前提とする checker、baseline、Design、REQ、参照導線が、新しい責務体系への移行完了後に現役の正規契約として残っていないこと。

### AC-15 checker 整合

機械検査が旧 Command / Workflow 重複構造への回帰を要求せず、新しい責務モデルと矛盾しないこと。

### AC-16 責務競合の解消

確認済みの Command 執筆規約、workflow 実行制御、意味診断と構造検査、派生情報の手動二重管理等について、正規所有者の競合が解消されていること。

### AC-17 対象外の維持

Command 実行状態に依存する動的書込み許可範囲の強制またはその実証が、本変更の成立条件へ追加されていないこと。

### AC-18 後方互換性

旧 Gxx や旧 Command 記述形式を維持するためだけの互換層・二重記述が追加されていないこと。

### AC-19 正常系回帰

責務再編後も既存公開 Command が本来提供していた利用者向け機能を実行でき、責務移管によって必要な処理が欠落していないこと。

### AC-20 実行環境差

Windows 固有の文字コード・シェル等への対処が必要な副作用処理について、その実装差異が利用者向け Command / Workflow Skill の手順複製を要求しないこと。

## 検証方法

後続工程では少なくとも以下を確認する。

- 正規 Design / REQ 間で責務定義が矛盾していないこと
