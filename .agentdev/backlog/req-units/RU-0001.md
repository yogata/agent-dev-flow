# Deep Review を対論型レビューへ再構成し、動的レビュー戦略・相互反証・合意収束を実現する

## 目的

現行 `agentdev-deep-review` が持つ「批判、反論、再検討、合意探索を自律反復する」基本構造を維持しつつ、根拠のない固定レビュー観点を廃止し、対象ごとにレビュー戦略を構成する対論型レビューへ再構成する。

標準 Skill は `agentdev-adversarial-review`、日本語名称は「対論型レビュー」へ完全移行する。

対論型レビューでは、Reviewer が対象案を正しいと仮定せず反証を試み、Reviewee はそのレビュー結果を正しいと仮定せず反証する。双方が相手の主張、前提、根拠、適用範囲、レビュー方法論を批判的に評価し、自身の主張も撤回、限定、修正できることを要求する。

一回のレビュー結果を最終回答として盲信せず、対論、合意候補形成、合意候補への再検証を反復し、利用可能な証拠から維持すべき本質的反論が残らない状態へ自律的に収束させる。

## 対象

- 標準対象は次の5領域とする。
  - 要件
  - 設計
  - 規格・仕様
  - 計画
  - 実装
- `agentdev-deep-review` を `agentdev-adversarial-review` へ完全移行する。
- 論理的役割を Orchestrator、Reviewer、Reviewee の3役とする。
- 評価前に対象、目的、制約、技術領域、想定失敗条件に応じたレビュー戦略を構成する。
- レビュー戦略は、必要に応じて次を含む。
  - 何を疑うか
  - どの立場から評価するか
  - どの既存知見・方法論を使うか
  - 何を証拠とするか
  - どの意味単位へ分解して検証するか
- レビュー戦略自体も未検証の判断として扱い、Reviewer / Reviewee が不足、過剰、誤適用、前提不成立を指摘できる。
- 審議中に新しい証拠や争点が生じた場合、レビュー観点、立場、方法論を追加、削除、再構成できる。
- Reviewer は対象案が正しいという前提を置かず、未発見の破綻条件、欠落、矛盾、不成立な前提、問題のある設計判断・実装方針・トレードオフを探索する。
- Reviewee は Reviewer の finding を未検証の主張として扱い、根拠、前提、対象理解、適用範囲、影響、方法論を反証する。
- Reviewer は Reviewee の反論を再評価し、自身の finding を撤回、維持、限定、修正できる。
- Reviewer / Reviewee の双方が自身の以前の主張を撤回、限定、修正でき、一方に恒常的な正解権限を与えない。
- finding は単なる懸念・指摘ではなく、可能な限り判定、根拠、適用条件を伴う。
- 問題が確認された結果だけでなく、限定条件下のみ成立、検証の結果成立しなかった、証拠不足で判定不能、十分な反証を試みても問題を確認できなかった、を正規結果として扱う。
- 問題を発見すること自体をレビューの成功条件としない。
- OpenAI/Codex `adversarial-review` 等、実装方針、設計判断、トレードオフ、前提を challenge する既存のレビュー知見を、観点、問い、failure mode、検証方法を構成する知識源として活用する。
- 外部知見を権威として自動採用せず、対象への適合性を評価する。
- 実行時の外部サービス・外部リポジトリへの必須依存にせず、必要な知見を ADF 側の配布可能なレビュー知識として保持する。
- Reviewer / Reviewee は双方とも、必要に応じて複数のサブエージェントを利用できる。
- 大規模対象では、観点、コンポーネント、failure mode、仮説、証拠源等の意味的に独立した単位へ分解し、必要に応じてワークフロー化・並列化できる。
- 小規模対象では物理的な複数サブエージェントを必須としない。
- 複数サブエージェントの結果は多数決しない。同一 finding の報告数を証拠の強さとして扱わず、重複統合、共通原因抽出、根拠・前提確認を行い、本質的争点へ正規化する。
- レビュー対象は、元案、レビュー戦略、finding、rebuttal、合意候補等の意味的な対象として管理し、「レビューのレビューのレビュー」という無制限の役割再帰ではなく、共通の challenge / counter-challenge プロトコルによる状態遷移として扱う。
- 合意は形式的全会一致、多数決、Reviewer / Reviewee が同じ文言を返した状態ではなく、本質的争点について相互反証が行われ、利用可能な証拠から維持すべき本質的反論が残らない状態として判断する。
- 合意結果は、元案維持、修正、部分修正、finding 撤回、適用範囲限定、代替案採用のいずれも許容する。中間案への機械的妥協を要求しない。
- 合意候補を形成しただけでは完了とせず、Reviewer / Reviewee が合意候補とその成立根拠を再度対論的に検証する。
- 合意候補の再検証で新しい本質的争点が見つかった場合、その争点について対論を再開する。
- 解決済み争点は、新しい証拠、新しい前提、異なる具体的破綻条件、未評価の適用範囲が示されない限り再開しない。
- 関連コンテキストと取得可能な証拠から判断可能な限り自律審議を続け、意見不一致だけを理由にユーザーへ返さない。
- 技術的に決着できない優先判断、ユーザー固有の目的・価値判断、両立不能要求、必要情報不足等、自律解決できない争点のみをユーザーへ返す。
- ユーザー回答後は影響を受ける争点から審議を再開し、必要な再検証を行う。
- レビュー完了時には、合意済み最終案または方針、採用した主要 finding と根拠、撤回・棄却した主要 finding と理由、限定 finding と適用範囲、主要なレビュー戦略・方法論、残留リスク・前提・不確実性、未解決事項を確認可能な形で返す。
- レビュー終了後、レビュー結果の対象への反映、ファイル保存等を必要に応じて追加指示できることをユーザーへ明示的に促す。

## 対象外

- 通常のコードレビュー、テスト、機械的検査、QG-1〜QG-4、inspect 系診断の代替。
- 固定5観点を別の固定観点集合へ置換すること。
- 固定された標準レビュー観点セットの新設。
- Reviewer または Reviewee の一方を恒常的な正解役・優先役とすること。
- finding 件数、Reviewer 数、サブエージェント数、多数決による正しさの決定。
- サブエージェント数、並列数、DAG 構造、モデル選択、timeout、最大ラウンド数、物理的状態保存形式の固定。
- 実行時の外部レビューサービス・外部リポジトリへの必須依存。
- OpenAI/Codex その他外部実装の全文複製。
- `agentdev-deep-review` の alias、互換入口、並存 Skill の維持。
- `agentdev-adversarial-review` 自身による対象ファイル変更、レビュー結果のファイル保存、commit、push、merge、Issue / PR 作成・更新・コメント、レビュー結果の自動適用、ユーザー承認代行。
- レビュー結果保存用の新しい正規成果物種別の導入。
- レビュー結果の適用・保存・後続工程への引き渡しを本 Skill の責務とすること。これらはレビュー完了後のユーザー責務とする。

### 検証方法

- 名称移行: 現行有効成果物・参照元を検索し、旧名の実行上有効な参照と互換 alias が残っていないことを確認する。
- REQ / SPEC 責務: `REQ-003` と新 Skill SPEC を比較し、利用者要求と成果物振る舞い・実行プロトコルが適切に分離されていることを確認する。
- 固定観点廃止: SPEC / SKILL / references を確認し、固定観点全実行が成立条件・完了条件でないことを確認する。
- Strategy: 対象種別が異なる複数ケースでレビュー戦略を構成し、対象に応じて異なる観点・方法論を選択できることを確認する。
- Strategy counter-review: 意図的に不足または過剰な戦略を与え、Reviewer / Reviewee が問題を指摘・修正できることを確認する。
- finding 反証: 誤った finding を含むケースで Reviewee が根拠付きで棄却・限定できることを確認する。
- Reviewer 再評価: 妥当な反論を返し、Reviewer が finding を撤回・限定・修正できることを確認する。
- 問題なし: 明確な破綻を確認できない対象で finding を捏造せず問題未確認を返せることを確認する。
- 合意再検証: 合意候補に新たな欠陥を含め、convergence audit で検出し対象争点へ戻ることを確認する。
- 並列レビュー: 重複 finding を複数サブエージェントから返し、件数で重み付けせず同一争点へ統合することを確認する。
- 自律審議: エージェント間で反論可能な争点を与え、ユーザーへ即時返却せず自律再検討することを確認する。
- ユーザー判断: 技術的に決着できない価値判断を残し、合意済み範囲と未解決争点を分離して返すことを確認する。
- 副作用境界: レビュー実行前後の対象、Git、Issue / PR 状態を比較する。
- 外部依存: 外部参考知見へアクセスできない環境でも ADF 内レビュー知識で標準レビューを実行できることを確認する。
- 各受け入れ条件の検証結果を `pass` / `fail` / `blocked` / `not applicable` のいずれかで整理する。`fail` は承認済みスコープ内で解決可能な場合のみ修正・再検証し、要件変更、対象範囲拡大、追加設計判断、外部依存解消が必要な場合は反復を停止して必要判断を報告する。未検証、`blocked`、`fail` が残る場合は完了と判定しない。

チャットで次を合意した。

- 現行 `deep-review` の相互レビュー、自律審議、合意探索という基本構造は維持する。
- 現行レビュー観点の固定5項目には妥当な根拠がなく、問題は個々の5項目ではなく固定観点モデル自体にある。
- 「観点を検討してから評価する」という流れまでは汎化するが、具体的観点は対象ごとに個別具体とする。
- Reviewer は対象案を、Reviewee はレビュー結果を、それぞれ批判的・敵対的にレビューする。レビュー結果を盲目的に信じること自体が本 Skill の解消対象である。
- 対論だけを目的にせず、相互反証を繰り返して合意点、修正案、限定案、代替案を探索する。
- 合意候補も再度対論的にレビューし、一回のやり取りで終わらせない。
- OpenAI/Codex `adversarial-review` のように「実装が正しい前提」を崩し、実装方針、設計判断、前提、トレードオフまで challenge する既存知見を活用する。
- 既存知見はレビュー戦略を構成する材料であり、固定レーンや権威として扱わない。
- Orchestrator / Reviewer / Reviewee の3論理役割とし、レビュー戦略、finding、反論、合意候補等を型の異なるレビュー対象として共通プロトコルで扱う。
- Reviewer / Reviewee は双方ともサブエージェントを利用でき、大規模対象では意味的分解と並列化・ワークフロー化によってスケールする。
- 複数エージェントの同意数を証拠強度とせず、重複 finding を本質的争点へ統合する。
- 対象範囲は要件、設計、規格・仕様、計画、実装とする。
- `agentdev-deep-review` は旧名を残さず `agentdev-adversarial-review` へ完全移行し、日本語名称は「対論型レビュー」とする。
- Skill 自身は read-only とし、レビュー結果の適用・保存はユーザー責務とする。ただしレビュー終了時に、必要なら結果の反映・保存等を追加指示できることをユーザーへ促す。
