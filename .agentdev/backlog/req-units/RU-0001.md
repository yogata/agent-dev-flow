# RU-0001: OpenCode セッション分析に基づく ADF 実行効率の第1次改善

## 1. 目的

OpenCode セッション履歴の分析で確認された ADF 実行上の重複に対し、品質、自律性、独立検証の価値を損なわずに第1次改善を行う。

同時に、改善後の実績を再分析した際に、削減された重複と品質保証上必要な重複を区別できる観測基盤を整備する。

本 RU は、サブエージェント、検証、文書等をトークン消費だけを理由に一律削減するものではない。

## 2. 背景と分析結果

直近30日間の ADF 実行を OpenCode の永続セッションデータから分析した結果、以下が確認された。

- 49,157 回のモデル呼出し、総計約 67.9 億トークンが記録され、その大半を cache read が占めた。
- read を伴う97論理実行単位のうち78単位で同一 path の複数回読込、68単位で子セッションをまたぐ同一 path 読込が確認された。
- 35論理実行単位で `src/opencode` と `.opencode` の対応する双方の経路が参照され、167正規化 path、931 read が該当した。
- case-run 側と case-close 側で同じ種類の検証が行われる実態が確認された。
- 委譲 prompt には目的、全工程、停止条件、成果物等の情報が含まれる場合があるが、統一された構造化契約にはなっていない。
- Case、GitHub Issue、PR、RU、OU、ADF 工程と OpenCode session の対応は自由文から再構成できる場合があるが、全 Case を安定して集計できる専用識別情報はない。
- 再検証や重複探索が新しい finding や品質向上へ寄与したかを判定する情報は構造化されていない。

一方、以下は現時点では確認できていない。

- compaction が主要な消費要因であること。
- 高トークン Case が ADF の非効率を意味すること。
- case-run / case-close の重複検証が無価値であること。
- サブエージェント数そのものが過剰であること。
- 特定モデルへの変更で同等品質をより低コストに実現できること。

以上から、現時点で原因と改善方向を比較的明確にできる以下4点を先行して改善する。

1. 実行追跡・評価可能性の向上。
2. 工程間の構造化された文脈引き継ぎ。
3. source / projection 参照経路の改善。
4. 検証・finding の追加価値の観測可能化。

サブエージェントの探索責務分割は原因分離が不十分であるため本 RU では実施せず、別途導入する課題管理で再評価待ちとして管理する。

## 3. 要求事項

### 3.1 実行追跡・評価可能性

ADF が生成、委譲、処理する実行について、後から OpenCode セッション履歴と ADF 成果物を安定して対応付けられること。

少なくとも、ADF が制御可能な範囲で以下の意味を機械的に識別できること。

- 対象 Case。
- GitHub Issue。
- GitHub PR。
- ADF 工程。
- 実行単位。
- 委譲目的。
- 実行結果。
- 親子実行関係の追跡に必要な識別情報。

自由文中に偶然出現する ID のみを根拠に対応付けないこと。

OpenCode 側に既に存在する token、model、tool call、message、part、compaction 等の詳細履歴を ADF 側へ重複保存しないこと。ADF 側は、OpenCode の実行履歴と ADF の Case、Issue、PR、工程、実行単位を結び付けるために必要な情報を優先して保持すること。

OpenCode または外部実行基盤から取得できない内部識別子を必須契約にしないこと。

### 3.2 工程間の構造化された文脈引き継ぎ

ADF の工程間、および親エージェントから実行担当サブエージェントへの委譲時に、後工程が必要とする解決済み文脈を構造化して引き継げること。

最低限、以下の意味を扱えること。

- 目的。
- 現在の ADF 工程。
- 現在の実行単位。
- 前工程で確定した事項。
- 未確定事項。
- 正規参照先。
- 停止条件。
- 期待する実行結果。
- 後続工程へ渡すべき成果。
- 計画が変更された場合に、その変更を識別するための情報。

全文履歴や巨大な計画本文の毎回複製を要求しないこと。

後工程は、引き継がれた確定済み事項を初期文脈として利用し、同じ情報をゼロから探索、再構築することを原則としないこと。

ただし、独立検証、鮮度確認、矛盾検出、正規成果物との整合確認を目的とする再確認は禁止しないこと。

引き継ぎ情報自体を REQ、Decision、Design、GitHub Issue、PR 等に代わる新たな正規情報源にしないこと。

### 3.3 source / projection 参照経路の改善

`src/opencode` と `.opencode` の双方を、目的を区別せず探索する状態を減らすこと。

実行目的に応じて、少なくとも以下を判別できること。

- 正規原本を確認すべき場合。
- 実行時 projection を確認すべき場合。
- source / projection 双方の整合確認が必要な場合。

工程間の文脈引き継ぎ等を利用して、その作業で使用すべき解決済み参照先を後工程へ渡せること。

「常に source のみ」「常に projection のみ」のような固定ルールにはしないこと。

source / projection 双方の確認が品質保証上必要な場合は、その確認を維持すること。

既存の source / projection 責務境界自体を変更する必要が生じた場合は、その変更を本 RU の暗黙事項として扱わず、正規の設計判断を行うこと。

### 3.4 検証・finding の追加価値の観測可能化

case-run、case-close、レビュー等で行われる検証について、検証を実行した事実だけでなく、前段階から何が変化したかを後から判定できること。

少なくとも以下を区別できること。

- 検証種別。
- 検証結果。
- 新規 finding。
- 修正済み finding。
- 既出 finding。
- 撤回または無効となった finding。

既存の PR 本文、GitHub Issue 本文、Issue コメント等、現在の ADF が正規情報源として利用している成果物を優先すること。

この目的だけのために独立した実行履歴 DB を新設しないこと。

同じ種類の検証が複数工程で行われた場合、後続検証が追加価値を持ったかを後から比較できること。

### 3.5 改善対象を一律削減しない

本 RU を根拠として以下を一律削減しないこと。

- サブエージェント数。
- 並列度。
- REQ、Decision、Design、Skill、reference 等の文書。
- case-run の検証。
- case-close の検証。
- 独立レビュー。

削減要否は、本 RU 実施後の観測結果から別途判断すること。

### 3.6 外部実行基盤との境界

以下の変更を本 RU の成立条件にしないこと。

- OpenCode 本体の変更。
- harness 内部の context 管理方式変更。
- provider の token 計測または課金方式変更。
- OpenCode DB スキーマ変更。

ADF が制御可能な委譲、参照解決、成果報告、識別情報の範囲で改善すること。

## 4. 実装後の再評価

本 RU 実装後は通常の ADF 開発を継続し、改善後の実行実績を蓄積する。

将来の再分析で、少なくとも以下を改善前後で比較できる状態にすること。

- 論理実行単位当たり token。
- token 分布。
- 同一 path 再読込。
- 子セッション間の同一 path 再読込。
- source / projection 重複参照。
- 工程間の同種検証。
- 新規 finding。
- 修正 finding。
- 既出 finding。
- Case、GitHub Issue、PR、実行単位、ADF 工程の対応付け率。
- 構造化された文脈引き継ぎの利用状況。

今回の分析で用いた定義との比較可能性を失わないこと。

## 5. 後続課題との関係

「サブエージェント探索責務分割の要否」は本 RU では実装しない。

課題管理機構の導入後、同事項を保留課題として登録する。

本 RU による改善を実運用へ反映し、通常の ADF 開発で比較可能な実績が十分に蓄積された時点で、OpenCode セッション履歴を再分析して当該課題を再評価する。

再評価の結果、探索責務分割が必要と判断された場合のみ、新規 RU として変更要求を要件化する。

## 6. 完了条件

以下をすべて満たすこと。

- ADF 実行と ADF 成果物を安定して対応付けるための情報が構造化されている。
- 工程間委譲に解決済み文脈を渡す契約が導入されている。
- source / projection の参照目的を区別し、不要な二重探索を抑制できる。
- 検証結果と finding の差分を後から分析できる。
- OpenCode 内部履歴を ADF 側へ無用に複製していない。
- 既存の正規情報源を新しい引き継ぎ情報で置き換えていない。
- サブエージェント、文書、検証を一律削減していない。
- 改善後データを今回の分析と比較できる。

## 7. テスト・検証観点

- 親から子への委譲で必要な構造化文脈が渡されること。
- 確定済み事項を後工程が初期文脈として利用できること。
- source のみ、projection のみ、双方確認の各経路を目的に応じて選択できること。
- case-run と case-close で同種検証を行った場合、その結果差分を後から識別できること。
- OpenCode DB と ADF 側識別情報から代表 Case を追跡できること。
- OpenCode 内部の一部情報が取得不能でも ADF workflow 自体が停止しないこと。

## 8. 非対象

- サブエージェント探索責務の分割実装。
- 検証工程の削除。
- 文書体系の一律削減。
- モデル選択最適化。
- provider 間の費用対効果評価。
- OpenCode / harness 自体の改修。
