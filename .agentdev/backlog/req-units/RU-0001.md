# overlap 要約生成の構造化警告結果反映（RU-0001）

## 目的

case-ready 受入検査 script（accept_definition_checks.ts）の overlap-cross-check step の要約生成が、engine 報告 JSON の構造化警告結果（`condition_a.warnings`、`detection_unavailable`）を正しく反映するようにする。consumer 側は要約だけでなく保存済み stdout 原証跡から警告を確定する規律を手順として明示する。

## 背景

Case #3682 の case-ready STEP-1 受入検査で、overlap-cross-check engine は `condition_a.warnings=1`（#3679 と #3686 の同一パス重複）を報告した一方、accept_definition_checks.ts の要約は常に `warnings=0` を表示した。要約は step detail（stdout 全文・終了コード）と併存する補助情報であり、gate 判定（終了コード 0・警告はゲート遷移に影響しない）は正しく機能する。ただし要約を読む消費者は警告の存在を取り逃し、横断依存検査の警告提示記録（case-ready 完了報告の記載要件）が欠落し得る。

## 問題

summary 生成側が存在しない top-level `warnings` を読む（`parsed.warnings?.length ?? 0`）。engine の報告契約（cross_dependency_types.ts の CrossDependencyInspectionReport）は警告を `condition_a.warnings` にネストしており top-level warnings は存在しないため、要約は engine が警告を返しても常に 0 件になる。intake-promote 実行時点（2026-10-15）の検証補足で不具合の存続を確認済み。detection_unavailable 状態も 0 件と誤表示し得る。

## 合意内容

learning「overlap警告を構造化結果から正しく要約する」と intake「accept_definition_checks の overlap 要約生成が報告 JSON の condition_a.warnings を読まず常に warnings=0 と表示する」は同一スクリプト（accept_definition_checks.ts）の同一不具合の観測であり、N:1 統合（α統合）とした。learning 側の受入条件・制約・原証跡確認規律と intake 側の修正方針・回帰テスト課題・Issue #3680 競合調整課題を、意味の選択・破棄なしに保存する。統合理由: 同一関心領域（同一スクリプト同一不具合）の複数成果物の統合であり、Jev 先行評価でも統合（L3 0.97 / I2 0.96）で合意。

## 要件化の方向

- 要約生成を `parsed.condition_a.warnings.length` と `parsed.detection_unavailable.length` から構成する（要約文字列の契約を報告 JSON 構造に合わせる）。修正方針は req-define の壁打ちで確定する。
- 回帰テスト（warnings 1 件の engine 報告を入力した要約生成）を accept_definition_checks.test.ts へ追加するかを req-define で判断する。
- consumer 側手順（case-ready reference 等）に、警告確認時に保存済み stdout 原証跡を検査する規律を明示する。
- 調整事項: Issue #3680（同一スクリプトの git status 列解析修正案件）との競合調整を実装計画に含める。depends_on は RU-ID のみ許容のため RU 間依存としては記録せず、要件化の方向の調整事項とする。
