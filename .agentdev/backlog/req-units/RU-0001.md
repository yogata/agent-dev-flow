# トレーサビリティ標準機能と producer / distribution 境界の再設計

## 目的

### 背景

AgentDevFlow（ADF）は、要件行と Design、実装成果物、検証手段の明示的な対応関係を扱う最小 Traceability Information Model（TIM）と、`agentdev-traceability` による coverage / impact / check を有している。

従来、この仕組みは主として ADF 自身の開発成果物を追跡する目的で構築されていた。一方、ADF は開発ワークフローを consumer project に提供する基盤であり、トレーサビリティも ADF 本体固有の自己管理機構ではなく、**ADF を利用して開発されるプロジェクトへ提供する標準機能**として位置付けることが適切である。

ADF 自身は、その標準トレーサビリティ機能を自己適用する self-hosting project の一つとして扱う。

また、ADF の開発管理情報と consumer に提供する製品内容の境界を再評価した結果、単純な「ADF成果物 / 配布物」の二分ではなく、以下の3層を区別する必要がある。

1. **開発管理成果物**

   * ADFまたはADF利用プロジェクトを設計、開発、検証、追跡するための内部成果物
   * REQ、Decision、Design、Report、トレーサビリティ情報、producer-only test 等を含む
2. **製品ソース**

   * consumer/runtime に提供する機能そのものの正規ソース
   * command、skill、tool、plugin、template、runtime script 等を含む
3. **配布成果物**

   * 製品ソースを特定 runtime 向けに投影・生成した成果物

トレーサビリティ情報は開発管理成果物であり、consumer に提供する製品ソースまたは配布成果物の内容ではない。

### 問題

現行のトレーサビリティ機構は、ADF自身のリポジトリ構造を前提として成立しており、ADF利用プロジェクトへ提供する標準機能として見ると、以下の問題がある。

#### 1. トレーサビリティ情報と製品ソースが混在している

現行の `ADF-COVERS` は、対応対象となる成果物自身のコメントとして保持される。

この方式では、consumer にそのまま提供される command、skill、tool、plugin、script 等にも producer 側の REQ ID と対応関係が埋め込まれる。

配布時に当該情報を除去する方式では、link projection のように変換工程を通さない配布形態を扱えず、また producer で検証した製品ソースと consumer に提供する内容が異なる。

#### 2. `ADF-COVERS` の物理表現が TIM 自体と結合している

論理的に必要なのは「Requirement と artifact の明示的な対応関係」であり、その対応関係が artifact 本文内のコメントで表現される必然性はない。

現行方式では、TIM の論理モデルと inline declaration の物理形式が結合している。

#### 3. `agentdev-traceability` が ADF 本体固有構造に依存している

現行実装は、ADF本体固有の要件ディレクトリ、要件表形式、特定ファイル拡張子、ADF内部の検証対応要否カタログ等を前提としている。

このため、ADF標準機能として consumer project に適用する際の一般性が不足している。

特に implementation / verification は本来成果物の「役割」であり、`.md` / `.ts` 等の特定ファイル種別に限定されるべきではない。

#### 4. verification policy が ADF 内部 Design に埋め込まれている

検証対応を必須とするか任意とするかは project-level policy である。

ADF 本体内部の Design 配下にあるカタログを標準機能が直接前提とすると、consumer project に同一モデルを自然に適用できない。

#### 5. TIM の完全性条件が新しい ADF 開発モデルと一致していない

新しいモデルでは以下を採用する。

* Decision 対応: 任意
* Design 対応: 必須
* implementation 対応: 必須
* verification 対応: project policy に従う

現行の Design 任意、Decision 対象外というモデルとは一致しない。

#### 6. fail-open の責務が一律である

coverage / impact は変更影響や対応関係を確認する補助能力であり、利用不能でも代替探索により継続できる。

一方、最終的な対応完全性を保証する `check` を品質ゲートとして使用する場合、check 自体が実行不能である状態を合格として扱うことはできない。

## 対象

- ADF標準TIMの再定義
- ADF利用projectへの標準トレーサビリティ機能の適用
- ADF自身へのself-hosting
- decision / design / implementation / verification の4 role
- Design必須化
- component / package 単位 sidecar
- top-level `traceability/`
- `traceability/policy.yaml`
- producer-only inline declaration
- `agentdev-traceability` の能力、知識、手順
- coverage / impact / check
- traceability completeness と workflow gate
- producer metadata と consumer distribution artifact の分離
- 現行配布対象に存在する inline producer metadata の最終状態是正
- 関連 REQ / Design / Skill / checker 間の矛盾解消

## 対象外

- 任意深度の成果物グラフ
- 一般的な依存関係探索
- ソースコード依存解析
- 意味類似検索
- Graph DB の導入
- 派生索引を標準必須要素とすること
- artifact revision / relation revision / digest による freshness 管理
- 要件変更時の stale artifact 自動判定
- OpenFastTrace、Capra、SysML、OSLC 等を runtime 依存として導入すること
- 任意の外部Requirements Management形式への汎用対応
- 個々の検証実行結果をTIMへ保存すること
- LLMによる対応関係の無承認自動確定
- トレーサビリティ情報のみから変更対象、依存関係、Wave、実行順序を確定すること
- 配布時stripを正規方式とすること
- 製品ソースの物理的正規配置そのものの再設計
- 実装計画、移行順序、コード差分

## 依存関係

本件を、ADF-COVERS除去、sidecar追加、TIM変更、配布境界変更、Skill変更、workflow変更に個別分割すると、以下の中間不整合が発生する。

* 配布物から宣言を除去したが traceability engine が sidecar を読めない

* Design を必須化したが case-ready が欠落を許容する

* ADF本体では sidecar、consumerでは inline declaration という二重モデルになる
* distribution boundary が ADF-COVERS を producer metadata としながら例外許容する

これらはすべて「ADF標準トレーサビリティモデルと producer / consumer 境界」という同一の契約変更から派生する。

そのため本RUでは、一つの整合した最終状態として扱う。

## 要件化の方向

### 1. ADF標準トレーサビリティ機能

ADF は、ADF利用プロジェクトの Requirement と成果物との明示的な対応関係を管理・検索・検査する標準トレーサビリティ機能を提供する。

ADF自身も同じ機能とデータモデルを使用する。

ADF固有の特殊なトレーサビリティ方式を別途設けない。

### 2. 最小TIM

Requirement line を最小単位とし、標準 role を次の4種とする。

| role             | 意味              | 完全性       |
| ---------------- | --------------- | --------- |
| `decision`       | 要件に関する正式な意思決定   | 任意        |
| `design`         | 要件を実現する現在の設計    | 必須        |
| `implementation` | 要件を実現する永続成果物    | 必須        |
| `verification`   | 要件を検証する永続的な検証手段 | policyに従う |

対応関係は Requirement と各 artifact の直接関係として保持する。

DesignまたはDecisionを経由して implementation / verification が成立したものと推定しない。

1 artifact が複数 Requirement を対象としてよく、1つのDesign文書が複数 Requirement line を担当してよい。

### 3. トレーサビリティデータの標準保存方式

配布対象となる成果物の対応関係は、repository top-level の producer/project-side `traceability/` に component / package 単位の sidecar として保持する。

概念例:

```yaml
component: workflow-case-close

implementation:
  src/.../SKILL.md:
    - REQ-032-027

verification:
  tests/.../case-close.test.ts:
    - REQ-032-027
```

sidecar は少なくとも次を識別可能とする。

* component
* artifact の repository-relative path
* role
* Requirement line ID

専用 artifact ID、graph node ID、edge ID、revision、digest 等を標準必須データとしない。

### 4. inline declaration

`ADF-COVERS` は標準TIMそのものではなく、producer-only artifact に対応関係をinline保持する場合の表現形式とする。

consumer distribution closure に含まれる成果物では使用しない。

sidecar と inline declaration は同じ論理的な対応関係へ正規化され、coverage / impact / check から同一に扱えること。

### 5. verification policy

`traceability/policy.yaml` を project-level verification policy の正規情報源とする。

基本契約は以下とする。

```yaml
verification:
  default: required
  optional:
    - REQ-xxxx-xxx
```

未指定 Requirement は required とする。

個々の component sidecar は verification policy を所有せず、対応関係のみを保持する。

### 6. artifact種別非依存

implementation / verification の成立可否を `.md`、`.ts` 等の拡張子で制限しない。

sidecar から有効な repository artifact として参照可能であれば、PowerShell、Python、Go、設定ファイル、IaC、Markdown その他の永続成果物を同じモデルで扱えること。

### 7. `agentdev-traceability`

`agentdev-traceability` は以下を提供する標準Skillとする。

* coverage
* impact
* check
* TIMの利用知識
* sidecar作成・更新知識
* verification policy の利用知識
* 要件・Design・実装・検証変更時のトレーサビリティ更新手順
* check結果の解釈と修正手順

Skill は ADF自身の個別REQと個別成果物との対応データを保持しない。

規範契約の正本は REQ / Design とし、Skill は利用に必要な最小知識と手順を提供する。

### 8. coverage / impact / check

`coverage` は Requirement 起点および artifact 起点で明示的対応関係を取得する。

`impact` は明示的な対応関係を用いて再確認候補を提示するが、結果のみから変更範囲、正規所有者、依存関係、実行順序を確定しない。

`check` は少なくとも以下を決定的に検査する。

* sidecar / inline declaration の構文不正
* 未知 role
* 存在しない Requirement line 参照
* 存在しない、または取得不能な artifact path
* Design 対応欠落
* implementation 対応欠落
* required verification 対応欠落
* verification policy の不正
* 同一論理関係の不整合な重複

Decision 対応欠落は不合格としない。

### 9. fail-open境界

coverage / impact を補助探索として利用している箇所では、機能の不在または実行失敗のみを理由として workflow を恒常停止させず、独立した正規成果物確認へfallbackできる。

一方、workflow が traceability completeness を完了条件として要求する時点では、check が正常に完全性判定できていない状態を pass として扱わない。

「対応関係が完全である」と「完全性を検査できなかった」を区別する。

### 10. workflow統合

REQの保存時点では Design 対応が未成立でも保存を許容する。

Design確定工程で Requirement と Design の対応を成立させる。

`case-ready` は、対象 Requirement line に Design 対応が1件以上存在することを実装着手条件とする。

`case-run` は実際に要件を実現する成果物へ implementation 対応を、永続的検証手段へ verification 対応を作成・更新する。

`case-close` は最終完全性検査として、対象 Requirement line について以下を確認する。

* Design 1件以上
* implementation 1件以上
* policy が required の場合 verification 1件以上
* traceability data 自体の整合性

Decision の有無は完了条件としない。

### 11. producer / distribution 境界

consumer distribution closure に含まれる製品ソースおよび配布成果物には、ADF自身または開発元project固有のトレーサビリティデータを含めない。

対象は command / skill だけに限定せず、consumer に配布される以下を含む全テキスト成果物とする。

* command
* skill
* reference
* tool
* plugin / hook
* template
* runtime script
* package付随ファイル
* その他 consumer distribution closure に含まれる成果物

配布処理における `ADF-COVERS` strip に依存せず、配布入力となる製品ソース自体を clean な状態とする。

distribution purity check では、distribution-bound artifact 内の producer-side traceability metadata を例外許容しない。

### 12. self-hosting

ADF自身も consumer project と同じTIM、sidecar、policy、coverage / impact / check を使用する。

ADF自身の個別対応関係は ADF repository の `traceability/` に保持し、ADFからconsumerへ配布しない。

これにより、

* ADFが提供するトレーサビリティ機能
* ADF自身のトレーサビリティデータ

を明確に分離する。

### 作業仮定

* sidecar の具体的 YAML schema、ファイル命名細則、カテゴリ分割の厳密な列挙は、上記の component / package 単位、最小データ、top-level `traceability/` という外部契約を変えない範囲で Design が定める。
* 製品ソースの物理的な正規配置変更は本RUでは決定しない。トレーサビリティ側は、配布入力となる clean canonical product source が存在するという境界契約のみを要求する。
* Requirement の標準ID体系は ADF の Requirement line ID を継続利用し、外部Requirements Management形式への汎用化は行わない。

## 決定的受け入れ条件

### AC-01: 標準機能としての位置付け

`agentdev-traceability` が、ADF本体専用機能ではなくADF利用プロジェクトのトレーサビリティを扱う標準配布機能として定義され、ADF自身が同機能のself-hosting対象として扱われている。

### AC-02: 4 role

TIM の標準 role が `decision / design / implementation / verification` の4種として定義されている。

### AC-03: 完全性規則

任意の現行 Requirement line について、

* decision は0件以上
* design は1件以上
* implementation は1件以上
* verification は policy が required の場合1件以上

という完全性規則を機械判定できる。

### AC-04: Design gate

REQ保存時点では Design 対応0件を許容し、実装着手前の `case-ready` では Design 対応0件の対象 Requirement line が存在する場合 ready へ遷移しない。

### AC-05: sidecar

consumer distribution closure に含まれる artifact の対応関係を、top-level `traceability/` 配下の component / package 単位 sidecar により保持できる。

### AC-06: sidecar最小データ

sidecar が artifact path、role、Requirement line ID により対応関係を表現でき、専用 artifact ID、graph node ID、edge ID、revision、digest を必須としない。

### AC-07: verification policy

`traceability/policy.yaml` により project-level verification policy を宣言でき、未指定 Requirement line は required と判定される。

### AC-08: inline declarationの限定

inline `ADF-COVERS` は producer-only artifact でのみ利用可能な対応関係表現として扱われ、consumer distribution closure 内では許容されない。

### AC-09: 同一論理モデル

sidecar と許可された inline declaration の双方が、coverage / impact / check から同一の Requirement-artifact relation として扱われる。

### AC-10: artifact種別非依存

implementation / verification artifact が `.md` / `.ts` 等の固定拡張子に限定されず、sidecar から参照可能な永続成果物を扱える。

### AC-11: coverage

Requirement 起点および artifact 起点で、明示された対応関係を role 付きで取得できる。

### AC-12: impact

Requirement または artifact 起点で再確認候補を取得できる一方、impact の結果または空結果だけから変更対象、依存関係、正規所有者、実行順序を確定しない。

### AC-13: check

check が少なくとも以下を個別に検出できる。

* 不正な対応関係記述
* 未知role
* 未知Requirement line
* 無効artifact path
* missing-design
* missing-implementation
* required Requirement の missing-verification
* verification policy 不正

Decision欠落は不合格としない。

### AC-14: check実行不能の扱い

最終完全性ゲートにおいて check が正常に完全性を判定できなかった場合、「対応完全性 pass」として扱われない。

### AC-15: advisory fail-open

coverage / impact を補助情報として利用する工程では、当該機能の利用不能だけを理由としてworkflowを恒常停止させず、独立した正規成果物確認へfallbackできる。

### AC-16: workflow

`case-run` が実際の implementation / verification 対応を作成・更新し、`case-close` が Design / implementation / required verification の完全性を独立して再検査する契約になっている。

### AC-17: Skill知識・手順

`agentdev-traceability` が少なくとも以下を利用知識または手順として提供する。

* TIMの基本概念
* 4 role の意味
* sidecar の作成・更新方法
* verification policy の扱い
* Requirement / Design / implementation / verification 変更時の対応関係更新
* coverage / impact / check の利用方法
* check finding の解釈

これらの規範契約の正本は REQ / Design に維持され、Skill に重複した独立規範を作らない。

### AC-18: ADF固有データ非配布

ADF自身の Requirement ID と ADF内部成果物との具体的対応データが `agentdev-traceability` の配布内容へ含まれていない。

### AC-19: distribution purity

consumer distribution closure 内の全対象テキスト成果物について producer-side traceability metadata が0件であり、配布時のstrip処理を前提とせずこの状態が成立する。

### AC-20: self-hosting

ADF自身の Requirement-artifact relations が、consumer project と同一のTIM、sidecar、policy、coverage / impact / check により管理・検査可能である。

### AC-21: 旧モデル矛盾の解消

以下の旧前提が現行契約として残っていない。

* Design対応は任意
* DecisionはTIM対象外
* 対応宣言は必ずartifact自身が保持する
* `.md` / `.ts` のみがtraceability対象
* ADF本体固有verification catalogが標準policy
* distribution-bound `ADF-COVERS` を配布境界検査で例外許容する
* 最終完全性checkが実行不能でも完全性passにできる

### AC-22: 最小TIM維持

再設計後も以下を導入しない。

* 任意深度グラフ探索
* Graph DB必須化
* 一般依存探索
* relation freshness管理
* artifact revision管理
* 個別検証実行結果のTIM保存

### 検証方法

要件化・実装完了時に少なくとも以下を検証する。

1. REQ / Design / Skill / checker / workflow の契約が新TIMで一致していること。
2. ADF自身について coverage / impact / check を実行できること。
3. sidecarのみで管理された artifact が coverage / impact / check に反映されること。
4. producer-only inline declaration が同じ問い合わせ結果へ統合されること。
5. Design欠落、implementation欠落、required verification欠落をそれぞれ独立して検出できること。
6. Decision欠落が完全性違反にならないこと。
7. optional verification が欠落していても完全性違反にならないこと。
8. `.ps1` 等、従来の直接走査対象外拡張子のartifactをsidecar経由で扱えること。
9. consumer distribution closure に producer-side traceability metadata が存在しないこと。
10. check自体の実行不能と、完全性passが区別されること。
11. ADF本体固有traceability dataを除いた状態で `agentdev-traceability` がconsumer projectへ配布可能であること。
12. 既存の Artifact Graph 相当機能や新たな中央グラフ管理が再導入されていないこと。

## Source Summary

本セッションで以下に合意した。

* ADF はトレーサビリティ追跡機能を標準機能として有し、ADF自身にもその機能を適用する。
* `agentdev-traceability` は ADF 本体専用ではなく、ADFを利用して開発するプロジェクトへ提供する標準Skillとする。
* ADF自身のトレーサビリティデータと、consumerへ配布するトレーサビリティ機能を分離する。
* ADFの成果物を「開発管理成果物」「製品ソース」「配布成果物」の3層で区別する。
* producer/project-management metadata は consumer distribution closure に含めない。
* 配布対象となる製品ソースに `ADF-COVERS` を保持しない。
* 配布対象成果物の対応関係は producer-only の sidecar metadata で保持する。
* sidecar は component / package 単位を基本とし、ファイル単位の大量sidecarや単一巨大中央台帳を採用しない。
* sidecar の正規領域は repository top-level の `traceability/` とする。
* sidecar は専用 artifact ID、graph node ID、edge ID、digest、revision 等を必須とせず、repository-relative artifact path、role、REQ line ID を基本情報とする。
* `ADF-COVERS` は TIM そのものではなく、producer-only artifact で使用可能な inline serialization と位置付ける。
* `traceability/policy.yaml` が project-level verification policy を所有する。
* verification の既定は required とし、optional な要件だけを明示する。
* 新しい標準 role は `decision / design / implementation / verification` の4種とする。
* decision は任意とする。
* design は全要件行について1件以上必須とする。
* implementation は全要件行について1件以上必須とする。
* verification は policy が required とする要件行について1件以上必須とする。
* REQ保存時点では Design 対応未成立を許容する。
* 実装着手前の `case-ready` では Design 対応成立を必須とする。
* `case-run` が implementation / verification 対応を作成・更新する。
* `case-close` が Design / implementation / required verification の完全性を最終検査する。
* coverage / impact は補助的・advisory な能力として fail-open を許容する。
* 最終完全性ゲートとしての check は、検査不能な状態を pass として扱わない。
* 個々の検証実行結果は TIM へ保持しない。
* 任意深度グラフ、派生Graph DB、一般依存探索へ機能を拡張しない。
* `agentdev-traceability` は、決定的な解析・検査能力だけでなく、新しいトレーサビリティモデルの利用知識と作成・更新・検査手順を提供する。
* REQ / Design は規範の正本、Skill は利用時の判断知識と操作手順を所有する。
* ADF自身の個別REQとADF内部成果物の対応データは、配布Skillへ含めない。
