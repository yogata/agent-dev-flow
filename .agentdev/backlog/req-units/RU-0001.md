# RU-0001: 最小TIMと要件対応モデルの確立

## 1. 背景

現行のトレーサビリティモデルは、Artifact Graph を中心に、成果物型、関係型、関係の意味、変更影響方向、拡張関係、派生索引などを広く扱っている。

今回、SysML、OSLC、OpenFastTrace 等の既存知見を起点に、仕様駆動開発で本当に必要なトレーサビリティをゼロベースで再検討した。その結果、ADF の中核で必要なのは、各要件について、どの Design 文書が設計を説明し、どの実装成果物が要件を実現し、どの検証手段が要件を検証するかを明示的に対応付け、その対応漏れや不整合を検出できることであると整理した。

OpenFastTrace の `coverage` / `covers` は概念上の参照元とするが、日本語本文では外部用語の直訳を正式用語とせず、「対応関係」「対応付け」「実装対応」「検証対応」を用いる。

## 2. 目的

ADF の Traceability Information Model（TIM）を、汎用成果物グラフではなく、要件を中心とした最小の対応モデルとして再定義する。

## 3. 要件

1. TIM の要件単位は REQ 文書全体ではなく、個別の `REQ-xxx-nnn` 要件行とする。
2. TIM の標準コア関係は、成果物が要件へ明示的に対応する `covers` とする。
3. 要件へ対応する成果物の役割は、`design`、`implementation`、`verification` の3種を標準とする。
4. 各現行要件には、その要件を実現する実装成果物が1件以上明示的に対応付けられていること。
5. 各現行要件には、その要件を検証する検証手段が1件以上明示的に対応付けられていること。
6. 要件と Design 文書の対応付けは任意とし、対応する Design 文書が存在しない要件を許容すること。
7. 実装成果物および検証手段は要件へ直接対応付けること。Design 文書との対応関係を経由して、要件に対する実装または検証が成立したものと推定しないこと。
8. 1つの成果物が複数の要件へ対応できること。
9. 1つの成果物が複数の役割を持てること。
10. `implementation` はソースコードという物理種別ではなく、要件を実現する永続成果物の役割として扱うこと。
11. `verification` は要件を検証する永続的な検証手段を表し、個々の検証実行結果は TIM に保持しないこと。
12. Decision は ADF の正式文書として維持するが、最小 TIM の標準成果物型には含めないこと。
13. 一般的な文書参照、Markdown リンク、言及を TIM の意味的なトレース関係として扱わないこと。
14. 関係ごとの変更影響方向を TIM の正規データとして保持しないこと。
15. 分解、具体化、依存、実現、実装、検証などの多数の関係型を標準 TIM へ持ち込まないこと。
16. 任意の成果物型や関係型を追加する汎用拡張機構を、最小 TIM の必須機能としないこと。
17. TIM は派生索引、グラフDB、物理保存形式を規定しないこと。
18. `coverage` / `covers` は機械識別子または外部標準との対応説明で使用できるが、日本語本文の正式用語は「対応関係」「対応付け」を用いること。

## 4. 作業仮定

- Design 文書の識別は現行どおりリポジトリ相対パスを利用する。
- 実装成果物および検証手段に専用の恒久IDを新設しない。
- 対応宣言の具体的な文字列表現は Design で確定する。

## 5. 対象範囲

- REQ-012 の全面再定義
- `docs/designs/foundations/traceability-model.md` の再設計
- DEC-017 の今回の最小 TIM 方針への再構成
- 要件対応の完全性規則
- TIM 用語の整理

## 6. 対象外

- 一般文書探索
- ソースコード依存解析
- 実行順序やワークフロー依存の表現
- Decision の理由探索
- 意味類似検索
- グラフDB
- 派生索引
- 個々の検証実行結果の保存
- 性能の数値基準

## 7. 受け入れ条件

| ID | 合否判定可能な条件 |
|---|---|
| AC-001 | 現行要件に実装成果物と検証手段が各1件以上直接対応している場合、要件対応の完全性を満たすと判定できること |
| AC-002 | Design 文書の対応が0件でも、それだけを理由に不完全と判定しないこと |
| AC-003 | 実装対応が0件の場合、実装対応の欠落として個別に検出できること |
| AC-004 | 検証対応が0件の場合、検証対応の欠落として個別に検出できること |
| AC-005 | Design 文書だけが対応している要件を、実装済みまたは検証済みと判定しないこと |
| AC-006 | 1成果物から複数要件、複数成果物から1要件の双方を正常に表現できること |
| AC-007 | 1成果物が複数役割を持つ場合も正常に表現できること |
| AC-008 | 存在しない要件への対応宣言を正常な対応関係として扱わないこと |
| AC-009 | Decision や一般文書参照が存在しなくても、要件対応の完全性を判定できること |
| AC-010 | 日本語の規範文書で `coverage` の直訳を TIM の正式用語とせず、「対応関係」「対応付け」を使用すること |

## 8. 検証方法

- 正常系: 実装対応1件、検証対応1件の要件を用いて完全性を確認する。
- 異常系: 実装対応欠落、検証対応欠落、存在しない要件参照を個別に確認する。
- 境界: Design 対応0件、1成果物が複数要件へ対応するケース、1成果物が複数役割を持つケースを確認する。
- 推移誤判定防止: Design → 要件の対応だけが存在する状態で、実装または検証が成立したと判定されないことを確認する。
- 用語検査: 更新対象の規範文書について `coverage` の直訳語を正式用語として使用していないことを確認する。

検証結果は各受け入れ条件ごとに `pass` / `fail` / `blocked` / `not applicable` で記録する。

## 9. 未決事項

要件化を妨げる未決事項はない。対応宣言の具体的な構文は Design で確定する。
