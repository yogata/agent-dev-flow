# RU-0001: 指摘事項の一般化と欠陥類型単位の修正・検証

## 1. 目的

実装レビューで確認された個別の失敗事例だけを修正し、同一の根本原因に属する兄弟事例が後続レビューで逐次発見される反復を抑制する。

ADF 側で、`agentdev-adversarial-review` が本質的な指摘事項を根本原因と欠陥類型へ可能な範囲で一般化し、`agentdev-case-run-execution-adapter` がその欠陥類型を修正単位として扱い、修正後も欠陥類型単位で検証する契約を持つ。

エージェント起動、反復回数、並列実行、コンテキスト管理等のハーネス実行機構は引き続き ADF の規範所有対象外とする。

## 2. 対象

### In Scope

- `agentdev-adversarial-review` における本質的な指摘事項の一般化
- レビュー上の指摘事項の解消判定と、実装修正完了の意味の分離
- `agentdev-case-run-execution-adapter` における修正範囲の一般化
- `agentdev-case-run-execution-adapter` における欠陥類型単位の検証
- 実装中のコードレビュー、QA、品質ゲート、試験等で確認された本質的な指摘事項への同一原則の適用
- 本質的な指摘事項と `completed-pr` / `blocked` / `failed` の関係
- 欠陥類型単位の検証結果を既存の完了証拠へ残すこと
- 関連する REQ / SPEC / Skill / reference の整合更新

### 本質的な指摘事項

未解消のままでは、次のいずれかの充足を主張できない指摘事項を本質的な指摘事項とする。

- Issue の完了条件
- Issue の受け入れ条件
- REQ
- Decision
- SPEC
- 当該 Issue に適用される必須品質条件

ハーネス固有の `critical`、`high`、`blocker` 等の重大度名称には依存しない。

### 欠陥類型

複数の具体的な失敗事例に共通する根本原因、破綻機構、または破られている不変条件によってまとめられる問題の意味的な集合とする。

### 作業仮定

- 指摘事項の一般化に必要な情報は既存の一時的な指摘事項状態で扱い、新しい正規成果物を導入しない。
- 欠陥類型の内部表現、フィールド名、保存構造は実装詳細とする。
- 欠陥類型単位で何件の事例を検証するかは固定せず、対象の性質と根拠から決定する。
- 現行の `case-run` 4状態契約を維持する。

## 3. 対象外

- 並列実行方式

- 新しい `case-run` 結果状態の追加
- 新しいレビュー結果用の正規成果物または永続スキーマの導入

## 5. 依存関係

必須の先行 RU はない。

既存の以下の契約を維持する。

- `agentdev-adversarial-review` は助言手段であり、実装修正や副作用を担わない。
- `case-run` 本体は実装せず、実行担当サブエージェントへ委譲する。
- Issue の対象範囲内の内部実装影響は自律処理し、Issue / REQ / Decision / SPEC 等の変更が必要な場合は `blocked` とする。
- `case-run` の結果状態は `completed-pr` / `blocked` / `failed` / `delegation-unavailable` の4状態を維持する。
- ハーネス実行機構は ADF 規範所有対象外とする。

## 6. 要件化の方向

### 6.1 `agentdev-adversarial-review` は本質的な指摘事項を一般化する

本質的な指摘事項が反証を経て維持、限定、または部分合意された場合、具体的な失敗事例だけで終わらせず、可能な範囲で次を明らかにすること。

- 根本原因または破綻機構
- 破られている前提または不変条件
- 欠陥類型
- 適用範囲
- 同種事例または隣接事例
- 適用外となる条件
- レビュー上の解消条件

一般化の根拠が不足する場合は推測で範囲を確定せず、「一般化範囲不明」または証拠不足として扱うこと。

### 6.2 レビュー上の解消と実装修正完了を分離する

`agentdev-adversarial-review` における指摘事項の解消は、指摘事項の妥当性、根本原因、適用範囲等について審議上の決着が得られたことを意味する。

コード修正、試験完了、品質ゲート通過を意味してはならない。

本質的な指摘事項は、元の具体的な再現事例について結論が出ただけではレビュー上の解消扱いにせず、次のいずれかまで確認すること。

1. 欠陥類型と適用範囲を合理的に特定できた。
2. 具体例固有の問題であり、一般化不要である根拠を確認できた。
3. 一般化に必要な証拠不足を明示し、未解決事項として残した。

### 6.3 `agentdev-case-run-execution-adapter` は欠陥類型を修正単位とする

実行中に本質的な指摘事項が確認された場合、報告された個別事例のみを修正単位としてはならない。

修正前に利用可能な証拠から次を整理すること。

- 根本原因
- 欠陥類型
- 同じ原因の影響を受ける範囲
- 必要な修正範囲
- 必要な追加検証範囲

この原則は `agentdev-adversarial-review` 由来の指摘事項だけでなく、実装中のコードレビュー、QA、品質ゲート、試験等で確認された本質的な指摘事項にも適用すること。

### 6.4 Issue 対象範囲を越える修正は自律実行しない

一般化した修正範囲が既確定 Issue の対象範囲内の内部実装変更だけで完結する場合は自律的に修正してよい。

次の変更が必要になる場合は現行 Issue 内で勝手に変更せず `blocked` とすること。

- Issue の対象範囲
- Issue の完了条件
- Issue の受け入れ条件
- REQ
- Decision
- SPEC
- 必須品質条件

### 6.5 本質的な指摘事項は欠陥類型単位で検証する

本質的な指摘事項を修正した場合、元の再現事例だけの再検証をもって完了としてはならない。

欠陥類型に応じて合理的に必要な検証対象を選定すること。適用可能な候補には次を含む。

- 元の再現事例
- 同種事例
- 境界条件
- 対称となる事例
- 適用外であるべき事例
- 既存の回帰試験

これらを固定的な全項目必須チェックリストにはしない。

### 6.6 追加の失敗事例は根本原因で再分類する

欠陥類型単位の検証中に新たな失敗事例を発見した場合、直ちに独立した新規指摘事項として扱ってはならない。

既存の指摘事項と根本原因が同一の場合は、既存の欠陥類型の適用範囲不足として修正範囲を再設定し、修正と欠陥類型単位の検証を再実行すること。

根本原因が異なる場合のみ、新しい指摘事項として扱うこと。

### 6.7 本質的な指摘事項は記録だけで完了扱いにしない

本質的な指摘事項は、PR の Findings 等へ記録したことだけを理由として未解消のまま `completed-pr` にしてはならない。

Issue の対象範囲内で修正可能な場合は、修正および欠陥類型単位の検証が成功した後にのみ `completed-pr` を許可すること。

非本質的な指摘事項は既存契約に従い Findings 記録による継続を許可する。

### 6.8 根本原因または欠陥類型を特定できない場合は `failed` とする

本質的な指摘事項について、利用可能なリポジトリ情報、実装差分、試験結果、関連する Issue / REQ / Decision / SPEC / docs を十分に調査しても、安全な修正範囲を正当化できる根本原因または欠陥類型を確立できない場合、局所的な推測修正によって `completed-pr` へ進んではならない。

この場合は `failed` とすること。

「十分な調査」を固定回数や固定時間では定義しない。

### 6.9 既存4状態を維持する

本変更のために新しい結果状態を追加しないこと。

- Issue 内で安全に修正可能: 修正継続
- Issue / REQ / Decision / SPEC 等の変更が必要: `blocked`
- 本質的な問題は確認できたが安全な修正範囲を確立できない: `failed`
- 実行基盤が利用不能: `delegation-unavailable`

### 6.10 欠陥類型単位の検証証拠を残す

本質的な指摘事項を修正して `completed-pr` とする場合、少なくとも次を既存の PR 本文または品質ゲート完了報告から確認できること。

- 対象となった本質的な指摘事項
- 特定した根本原因または欠陥類型
- 採用した修正範囲
- 実施した欠陥類型単位の検証
- 検証結果

新しい正規成果物種別を追加しないこと。

## 7. 決定的受け入れ条件

1. 本質的な指摘事項について、具体的な再現事例だけでレビュー上の解消にならないことを確認できる。
2. 一般化可能な指摘事項について、根本原因または欠陥類型と適用範囲をレビュー結果から確認できる。
3. 一般化できない指摘事項について、推測で欠陥類型を確定せず、証拠不足または一般化範囲不明として扱われる。
4. `agentdev-adversarial-review` 上の解消と実装修正完了が別概念として定義されている。
5. 本質的な指摘事項の修正時、報告された個別事例だけでなく欠陥類型に基づいて修正範囲が決定される。
6. 欠陥類型単位の追加検証で同一根本原因の失敗を発見した場合、新規指摘事項化せず既存指摘事項の適用範囲不足として再修正される。
7. 異なる根本原因の失敗を発見した場合、新しい指摘事項として区別される。
8. Issue 内で修正可能な本質的な指摘事項が未解消の場合、`completed-pr` にならない。
9. Issue / REQ / Decision / SPEC 等の変更が必要な場合、`blocked` となる。
10. 十分な調査後も根本原因または欠陥類型を確立できない本質的な指摘事項は `failed` となる。
11. 非本質的な指摘事項について、既存の Findings 記録による継続を妨げない。
12. 新しい `case-run` 結果状態が追加されていない。
13. 欠陥類型単位の検証内容と結果を既存の完了証拠から確認できる。
14. 新しい正規成果物または永続スキーマが導入されていない。
15. ハーネス固有の重大度名称、レビュー回数、モデル、並列方式等へ ADF 契約が依存していない。
16. 一般化可能な事例、具体例固有の事例、証拠不足の事例について、それぞれ期待されるレビュー結果を検証できる。
17. 同一根本原因を持つ複数の失敗事例について1つの欠陥類型として修正・検証され、別原因の失敗は別指摘事項として扱われることを検証できる。
18. 各受け入れ条件の検証結果を `pass` / `fail` / `blocked` / `not applicable` のいずれかで個別に判定できる。

## 8. Source Summary

実装レビューが10ラウンドまで反復した事例を分析した結果、主な原因はレビューが厳格だったこと自体ではなく、報告された具体的な再現事例を修正単位として扱い、同じ根本原因に属する欠陥類型まで一般化して修正・検証する契約が不足していたことである。

具体的には、ある区切り文字、符号化表現、境界条件の失敗を個別に修正した後、次ラウンドで同じ破綻機構に属する別表現が発見される反復が生じた。また、分類対象の範囲と所有・抑止対象の範囲が異なるといった概念上の分離もレビュー中に明確化された。

この学びから、ハーネス側の探索能力だけに依存せず、ADF 側で次の2実装単位を強化する方針に合意した。

1. `agentdev-adversarial-review`: 指摘事項の一般化とレビュー上の解消判定を強化する。
2. `agentdev-case-run-execution-adapter`: 修正範囲を欠陥類型へ一般化し、欠陥類型単位で修正後検証を行う。

本質的な指摘事項は、未解消のままでは Issue の完了条件・受け入れ条件、REQ / Decision / SPEC、または必須品質条件の充足を主張できない指摘事項とする。本質的な指摘事項は Findings への記録だけでは `completed-pr` にせず、Issue 内で修正可能なら修正と欠陥類型単位の検証を必須とする。Issue 等の変更が必要なら `blocked`、十分な調査後も安全な修正範囲を確立できなければ `failed` とする。
