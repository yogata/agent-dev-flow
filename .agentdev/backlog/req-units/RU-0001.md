# プロジェクト知識の独立管理と判断への利用基盤

## 背景

AgentDevFlow では、learning から得られたプロジェクト固有の知見を後続の判断へ再利用する仕組みが導入されている。

現行構造では、現在のシステム事実は Design、再利用可能な判断知識は project-local Capability Skill が所有し、Project Extension を経由して workflow から利用する構成となっている。

一方、検討の結果、Capability Skill と知識は異なる責務を持つものとして整理した。

- Capability Skill は「どのように判断するか」を所有する。
- 知識は「判断するときに何が分かっているか」を所有する。
- learning は経験や観測から知識候補を生成する入口の一つであり、知識そのものではない。
- 知識は REQ、Decision、Design 等とは異なり、複数の判断処理から横断的に利用される。

また、プロジェクト固有の知識だけでなく、外部仕様、調査結果、設計時の発見、利用者が明示した知識も将来の判断材料となるため、知識の生成経路を learning のみに限定しない。

初期導入では対象をプロジェクト知識に限定し、標準知識の共有・配布や ADF基盤知識の物理管理などは、必要性が顕在化した時点で検討する。

## 問題

現行ADFには、プロジェクト知識を独立した正規資産として保持する場所がない。

そのため、再利用可能な判断知識を Capability Skill が所有しており、能力と判断材料の責務が混在している。

また、次の不足がある。

1. プロジェクト知識を正規文書として保存する場所と文書契約がない。
2. learning から得られたプロジェクト知識を独立した知識へ保存する経路がない。
3. learning 以外で得られた知識を明示的に登録する入口がない。
4. command / skill がプロジェクト知識の所在を共通前提として利用する契約がない。
5. 知識文書について最低限の構造整合性を検査する仕組みがない。

知識探索についてADF独自の検索機構を導入する必要はない。関連知識の探索は、利用環境のハーネスが提供するリポジトリ探索能力を前提とする。

ADFは、知識がどこにどのような単位で存在するかを明確にし、command / skill がその所在を認識できる状態を提供する。

## 統合理由

今回の変更は、個別のリスク分析機能やlearning経路だけの変更ではない。

プロジェクト知識の正規所有場所、生成経路、利用方法、文書体系を一体として変更しないと、Capability Skillから知識を分離しても後続判断から利用できず、learning側だけを変更しても保存先が成立しない。

そのため、以下を一つの要件単位として扱う。

- 知識の正規所有
- 知識文書の最小契約
- learningからの知識化
- learning以外からの明示的な知識化
- 判断処理からの知識利用
- 知識文書の最低限の整合性検査

## 要件化の方向

### 1. プロジェクト知識の正規所有

プロジェクト固有の再利用可能な知識は、Capability Skill、Project Extension、learningの一時状態ではなく、`docs/knowledge/` 配下の正規文書として所有する。

現在のシステム構造・動作そのものを記述する内容は引き続き Design が所有し、将来の判断で再利用する知識を知識文書が所有する。

Capability Skill は判断能力を所有し、プロジェクト知識そのものを正規所有しない。

### 2. 知識文書の単位

1つの知識を1つの Markdown ファイルとして保存する。

1つの知識は、単独で意味を持ち、適用可否を独立して判定できる最小の再利用単位とする。

ファイル名は内容を簡潔に表す kebab-case の slug とし、初期実装では知識専用の固定ID、採番機構を導入しない。

### 3. 知識文書の最小内容

各知識文書は少なくとも以下を保持する。

- 知識内容
- 適用条件
- 適用対象
- 根拠
- 関連知識

状態、信頼度、有効期限、利用回数等は初期契約に含めない。

### 4. learningからの知識化

learning は経験・観測からプロジェクト知識候補を生成できる。

プロジェクト知識候補は、後続の承認工程を経て `docs/knowledge/` の知識文書へ保存できる。

現行の「project-local Capability Skillへ判断知識を追加する」経路は、プロジェクト知識について `docs/knowledge/` を正規所有先とする経路へ変更する。

知識文書として保存された後も、元のlearning項目そのものを知識として扱わない。

### 5. learning以外からの知識化

外部仕様、調査結果、設計時の発見、利用者が明示した内容を、learningを経由せずプロジェクト知識候補として登録できる明示的な入口を提供する。

具体的な公開command名、Skill構成は後続Designで決定する。

intake は具体的な作業候補の受付という現在の責務を維持し、知識登録入口として使用しない。

### 6. 利用者承認

プロジェクト知識としての新規保存、既存知識の更新、置換、削除は利用者承認を経て確定する。

learning由来の知識化について、既存のbacklog-review承認境界を利用できる場合は、その承認契約を再利用する。

### 7. 判断時の知識利用

プロジェクト知識を必要とするcommand / skillは、`docs/knowledge/` がプロジェクト知識の正規領域であることを認識できるようにする。

関連知識の探索は、利用環境のハーネスが持つ探索能力を利用する。

ADFは特定のエージェント名、モデル名、探索API、探索アルゴリズムを固定しない。

ADF独自の検索エンジン、意味検索、検索索引を初期要件として導入しない。

変更誘発境界リスク分析を行う要件分析能力は、初期の具体的な知識利用箇所として `docs/knowledge/` のプロジェクト知識を判断材料として利用できるようにする。

### 8. Project Extensionとの境界

Project Extension はプロジェクト固有の文脈、規則、検査、受け入れゲート、禁止事項等を既存契約に従って扱う。

プロジェクト知識の正規所有先は Project Extension または project-local Capability Skill としない。

知識利用のために、すべての知識とCapability Skillの対応関係をProject Extensionへ事前登録することを要求しない。

### 9. TIMとの境界

知識をTIMの標準対象へ追加しない。

TIMは要件とDesign、実装成果物、検証手段の明示的対応付けという現在の責務を維持し、一般的な知識探索や意味検索を担わない。

### 10. 構造整合性検査

`docs/knowledge/` 配下の知識文書について、決定的に判定可能な最低限の構造を機械検査できるようにする。

少なくとも以下を検査対象とする。

- 正規配置
- ファイル命名規則
- 必須内容の存在

知識内容そのものの正しさ、適用条件の意味的妥当性は機械検査で確定せず、LLMによる判断および利用者承認の対象とする。
