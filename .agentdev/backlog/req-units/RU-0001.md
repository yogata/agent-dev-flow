# Decision・Design 状態評価の正規工程化と状態乖離検出

## 背景

2026-09-10、対応する REQ、Design、実装が既に現行状態となっている一方で、Decision が `proposed`、Design が `draft` のまま残っていた事例を一括是正した。

確認の結果、個別文書の更新漏れではなく、Decision と Design の状態評価を必ず実行する発火点が正規工程上で不足していることが構造要因であると判断した。

現行の状態評価には次の性質がある。

- Decision は `proposed → accepted` の状態遷移を持ち、`accepted` の Decision のみが現行判断の根拠となる。一方、実装 Case を開始するまでに関連 Decision の状態を必ず評価する正規工程が存在しない。
- Design は `draft → accepted` の状態遷移を持ち、実装との整合を確認して確定する。case-close に Design 確定工程は存在するが、PR 本文の `## Design確定候補` への申告を入力としており、当該欄が空の場合は対象 Design 自体の棚卸しを行わない。
- draft Design の長期放置や proposed Decision の不適切な権威引用を検出する既存検査は存在するが、状態評価工程そのものの欠落を補うものではなく、発見後の事後処置に依存する。

Decision と Design は状態確定の意味が異なる。

- Decision の `accepted` は、技術判断が正式に受理されたことを示し、実装完了を意味しない。このため、実装開始前に評価される必要がある。
- Design の `accepted` は、現在採用する内部構造として実装・検証との整合を確認できたことを示す。このため、当該 Design に関係する実装・検証を行った Case の完了時に評価される必要がある。

## 問題

Decision と Design の状態評価が、それぞれ本来必要な工程で必須化されていない。

### Decision

req-save により Decision と REQ が保存された後も、Decision は `proposed` のまま実装工程へ進むことができる。

この状態では、関連 REQ の Case が実装されても Decision の受理判断が後回しとなり、実装済みの現行状態と Decision status が乖離する。

Decision の受理判断は実装完了後ではなく、実装 Case の開始前に実行される必要がある。

### Design

case-close の Design 確定処理は、PR 本文の `## Design確定候補` に候補が申告されていることを前提としている。

実装対象 REQ に関係する draft Design が存在していても、申告がなければ評価対象にならない。このため、実装・検証済みの内部構造を記述する Design が `draft` のまま残る。

Design 確定候補の申告は補助情報として利用できるが、棚卸し自体の発火条件としてはならない。

### 事後検出

既存の draft 放置検出は時間経過を検出できるが、今回必要なのは単なる `draft` / `proposed` 状態の検出ではない。

後続工程が進行しているにもかかわらず、前段成果物の状態評価だけが未実施であるというライフサイクル上の乖離を検出する必要がある。

- Design の正規確定工程は case-close に存在するが、PR 本文 `## Design確定候補` の申告に依存し、空の場合は確定対象の棚卸しを行わない。

## 統合理由

Decision の実装開始前評価、Design の Case 完了時評価、inspect-docs による事後検出は、実行工程は異なるが、いずれも「成果物の状態評価が正規工程から漏れ、実態と status が乖離する」という同一問題を解消する。

本 RU では状態ライフサイクルを横断した一つの Requirement Unit として入力し、req-define では既存 REQ の責務境界に従って以下へ分離して要件化できるものとする。

- case-open における Decision 状態評価
- case-close における Design 状態評価
- inspect-docs における状態乖離診断

Decision↔REQ のトレーサビリティモデル自体は本問題とは分離し、別要件として扱う。

## 要件化の方向

### Decision 状態評価

case-open は実装 Case の作成前に、対象 REQ に関連する Decision の状態を確認する。

関連する Decision が `proposed` の場合、Case を開始する前に受理可否を評価し、`accepted` への状態遷移または Case を開始できない理由を確定する。

Decision の状態が未確定のまま実装 Case を開始しない。

関連 Decision の特定には正規に取得可能な関係情報のみを使用する。Decision と REQ の関係が一意に取得できない場合、本文の意味、文字列類似、周辺参照等から推測して関連 Decision を確定しない。

### Design 状態評価

case-close は PR 本文の `## Design確定候補` の有無とは独立して、当該 Case の対象 REQ に関係する draft Design を棚卸しする。

`## Design確定候補` は追加候補や補助情報の入力として利用できるが、セクション不存在または空を理由として Design 状態評価を省略しない。

棚卸しされた各 draft Design は個別に評価し、次のいずれかを確定する。

- 実装・検証との整合が確認できる場合は `accepted` へ遷移する。
- 当該 Case では確定できない場合は、見送り理由と再評価契機を記録する。

候補を未評価のまま case-close を完了しない。

### 状態乖離診断

inspect-docs は、単に `proposed` Decision または `draft` Design が存在すること自体を異常としない。

次のように、後続状態との組合せによって状態評価漏れが疑われる状態を DRIFT として診断できるようにする。

- 実装 Case の対象となる REQ に関連する Decision が、受理評価されないまま `proposed` である。
- 実装・検証との整合を評価できる段階に達した Design が、状態評価されないまま `draft` である。

この診断は正規工程の代替ではなく、case-open / case-close の取りこぼしを発見する第二層とする。

既存の「一定期間 draft のまま放置されている Design」を検出する観点とは責務を分離する。

## 外部依存

Decision の case-open 前評価には、対象 REQ と関連 Decision の関係を正規情報から一意に取得できることが必要である。

この関係モデルの変更は本 RU の対象外とする。

正規関係を取得できない状態では、Decision 状態評価を意味推測で代替せず、その Case の開始を停止して取得不能理由を報告する。

TIM 側の別変更が必要な場合、本 RU の Decision 部分はその依存が解消されるまで `blocked` として扱い、Design 棚卸しや inspect-docs の独立実施可能な部分まで不必要に拡張しない。

## 受け入れ条件

1. **Decision 候補なし**

   - case-open の対象 REQ に関連する `proposed` Decision が存在しない場合、既存と同様に Case 作成を継続できる。

2. **Decision 候補あり**

   - case-open の対象 REQ に関連する `proposed` Decision が存在する場合、GitHub Issue 作成または実装開始より前に当該 Decision の状態評価が実行される。

3. **Decision 受理**

   - 評価結果が受理の場合、Decision が既存ライフサイクル規則に従って `accepted` へ遷移したことを確認してから Case 作成を継続する。

4. **Decision 未確定**

   - Decision を受理できない、または判断に必要な情報が不足する場合、`proposed` のまま Case を開始せず、停止理由を報告する。

5. **Decision 関係取得不能**

   - 対象 REQ と Decision の正規関係を一意に取得できない場合、本文内容、文字列一致、類似度その他の意味推測によって関連 Decision を確定せず、Case 作成前に停止して取得不能を報告する。

6. **Design 申告なし**

   - PR 本文に `## Design確定候補` が存在しない、または空であっても、case-close の Design 棚卸し処理が実行される。

7. **Design 候補なし**

   - 対象 REQ に関係する draft Design が0件の場合、0件であることを確認した上で Design 状態評価を正常完了できる。

8. **Design 候補複数**

   - draft Design が複数存在する場合、各 Design を独立して評価し、候補全件について評価結果を得られる。

9. **Design 昇格**

   - 当該 Case の実装・検証結果から Design の現在構造との整合を確認できる場合、既存ライフサイクル規則に従って `draft → accepted` へ遷移する。

10. **Design 見送り**

    - 当該 Case だけでは Design を確定できない場合、見送り理由と再評価契機を記録する。見送りと未評価を区別できる。

11. **Design 未評価残存**

    - 棚卸し対象として列挙された Design に、昇格または見送りのいずれの評価結果もない項目が残る場合、case-close を完了扱いにしない。

12. **PR 申告との統合**

    - `## Design確定候補` に記載された候補は棚卸し結果と統合して評価され、重複候補を二重処理しない。

13. **再実行**

    - case-open / case-close を再実行した場合、既に `accepted` の Decision / Design に対して同じ状態遷移や承認記録を重複生成しない。

14. **Decision DRIFT**

    - inspect-docs は、単なる `proposed` Decision と、実装 Case の対象となる状態まで後続工程が進んでいるにもかかわらず受理評価されていない `proposed` Decision を区別して診断できる。

15. **Design DRIFT**

    - inspect-docs は、単なる `draft` Design と、実装・検証との整合を評価できる段階を通過しているにもかかわらず状態評価されていない `draft` Design を区別して診断できる。

16. **既存放置検出との分離**

    - 状態乖離診断は、draft の経過時間のみを根拠とする既存放置検出と同一判定を重複保持しない。

17. **診断の副作用**

    - inspect-docs は状態乖離を検出・報告するが、Decision / Design の status を直接変更しない。

18. **TIM変更非依存**

    - 本 RU の実装によって新しい Decision↔REQ 関係型、TIM 成果物型、グラフまたは派生索引が暗黫に追加されない。
