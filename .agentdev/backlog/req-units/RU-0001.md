# REQ・Decision・SPEC・コマンド・スキル・検査基盤の横断整合性を回復する

## 目的

AgentDevFlow の REQ、Decision、SPEC、コマンド、スキル、検査基盤、配布物が同一の契約を実装する状態へ統一する。

監査では、文書間の契約差異、現行識別体系と検査器の不一致、ADR から Decision への移行残り、コマンドとスキルの責務重複、配布物から開発リポジトリ内部への依存、GitHub 操作の環境依存、adversarial-review の起動条件差異、case-auto と case-run の責務差異、Epic 更新責務の競合、検証失敗を記録しただけで完了できる経路、Artifact Graph の検証不足、日本語品質・禁則違反等が確認された。

個別ファイルの局所修正では同種不整合が再発するため、正規契約から配布物・検査基盤までを一つの体系として是正し、同種欠陥を機械検査で検出できる状態を実現する。

## 対象

- `docs/requirements/**`
- `docs/decisions/**`
- 現行 `docs/specs/**`
- 文書体系を規定する foundation、responsibility、workflow、integrity 関連文書
- `src/opencode/commands/agentdev/**`
- `src/opencode/skills/agentdev-*/**`
- 上記を生成・解析・検査するスクリプトとテスト
- Artifact Graph
- Artifact Validation
- GitHub 操作境界
- 日本語品質・禁則検査
- 上記に関係する fixture

対象範囲では、個別ファイルだけでなく、同一原因または同一契約差異から生じる箇所を横断的に検索し、欠陥類型単位で是正する。

## 対象外

- AgentDevFlow と無関係なアプリケーションコードの変更
- 本件の整合性回復に不要な新機能追加
- 本件に不要な UI 変更
- 正規契約で要求されていない後方互換層の新設
- superseded 文書を現行仕様として復活させること
- ハーネス固有のプロセス起動方式を外部仕様として固定すること
- 本件と無関係なリファクタリング

## 依存関係

- 他 RU への必須依存はない。
- 要件化時は、既存 REQ・Decision・accepted SPEC の内容を最新 `main` から再読込し、監査後に変更された箇所を反映する。
- 実装時の内部依存順は、正規契約の確定、検査基盤の更新、SPEC の整合、配布物への投影、全体回帰の順とする。ただし、この順序自体を利用者向け外部仕様にはしない。

## 要件化の方向

### 1. 正規文書間の整合性

REQ、Decision、SPEC は同一機能について相互に矛盾する契約を保持しないこと。

REQ は利用者から見た要求を記述し、実装方式、移行作業、過去 Issue、変更履歴、一時的な作業工程を正規要求として保持しないこと。

SPEC は REQ を具体化する成果物仕様として記述し、REQ と異なる利用者向け挙動を独自に定義しないこと。

### 2. 現行識別体系

現行 REQ 識別子は 3 桁形式を正とし、REQ の生成、解析、検査、fixture、参照検証を含むすべての現行処理が 3 桁 REQ を扱うこと。

4 桁 REQ を前提とする旧処理により現行 REQ が検査対象外になることを許容しないこと。

ADR を現行の正規文書種別として扱わず、Decision 体系へ統一すること。

### 3. コマンドとスキルの責務分離

コマンドは利用者向け公開インターフェースとワークフローへの入口を担うこと。

処理手順、分岐、並列制御、中断・再開等のワークフロー実装はワークフロースキルが所有すること。

能力スキルは再利用可能な能力を提供し、特定コマンドの Step 番号やワークフロー固有の実行位置を契約として持たないこと。

同一の処理規則をコマンドとワークフロースキルの双方で独立定義しないこと。

### 4. 配布物の自己完結性

配布されるコマンドおよびスキルは、AgentDevFlow 開発リポジトリ内部の正規文書や開発管理情報を実行時依存先としないこと。

少なくとも、開発リポジトリ固有の REQ / Decision / Issue / PR 識別子、内部 SPEC パス、他スキルの内部 `references` / `scripts`、開発時のみ存在する成果物、能力スキルからのコマンド固有 Step 番号依存を排除すること。

必要な契約は配布物自身または正式な公開インターフェースとして保持すること。

### 5. GitHub 操作境界

GitHub との入出力は定められた GitHub 操作境界を経由すること。

配布物の標準動作として、特定 OS、特定シェル、特定文字コード処理を必要としないこと。

PowerShell 固有処理、`chcp`、cp932 / Shift-JIS 変換、BOM 操作、一時ファイルを介した本文受け渡し、`--body-file` 必須方式を標準契約の前提としないこと。

Issue、PR、コメント等について書き込み後の結果確認を可能とすること。

### 6. adversarial-review の起動契約

adversarial-review は無条件にすべての処理へ適用しないこと。

ユーザーが明示的に要求した場合、または呼出元工程が対象の重要性・意味的リスクから必要と判断した場合に適用可能とすること。

上位オーケストレーターが、下位工程で既に決定された適用要否を独自に上書きしないこと。

ユーザー判断を必要とする結果が返された場合は自律的に採否を決定せず、ユーザーへ制御を戻すこと。

### 7. case-auto / case-run / harness の責務

case-auto は複数処理単位のオーケストレーションを担い、依存関係管理、実行対象選択、並列化、中断・再開、結果集約を扱うこと。

case-run は単一 Issue の実行を担うこと。

エージェントプロセスの具体的な起動方法や並列実行機構そのものはハーネス側の責務とし、ADF の外部仕様として固定しないこと。

### 8. handoff の挙動

`agentdev_handoff` による停止は ADF 適用先で有効とすること。

AgentDevFlow 自身を AgentDevFlow で変更する自己適用環境では、handoff 設定だけを理由として実行を停止しないこと。

この例外を REQ、SPEC、ワークフロー実装で一致させること。

### 9. Epic の単一書き手

Epic 本文の実行状態更新を行う正規の書き手を一つに限定すること。

case-run 等の下位処理は正規の書き手を迂回して Epic 本文を直接更新しないこと。

並列処理、中断、再開、失敗を含めて単一書き手原則を維持すること。

### 10. 検証失敗時の完了条件

検証で本質的な問題が検出された場合、検出事項を記録しただけで成功または完了としないこと。

承認済み対象範囲内で解消可能な問題は修正後に再検証すること。

要件変更、対象範囲拡大、新たな設計判断、ユーザー判断、外部依存解消が必要な場合は自律的に対象を拡大せず処理を停止すること。

未解決の `fail` または `blocked` が存在する場合は完了と報告しないこと。

### 11. Artifact Graph の検証

Artifact Graph は正規文書から生成されたグラフ自体の欠陥を独立して検証できること。

少なくとも欠落ノード、余剰ノード、欠落エッジ、余剰エッジ、グラフ構造上の欠陥、原文側の参照欠陥を区別して検出可能とすること。

代表質問による回帰検証は REQ-020 で定める 10 件を実行し、評価指標数と代表質問数を同一概念として扱わないこと。

### 12. 日本語品質および禁則検査

正規文書および利用者へ配布・表示される文章に、定められた日本語品質検査と禁則検査を適用すること。

禁則語を検出した場合、対象語だけの機械的置換を基本処理とせず、その表現を含む文全体を意味的に適切な形へ修正すること。

一箇所で同一種類の問題を検出した場合、同じ欠陥構造が他ファイルに存在しないか横断検査すること。

### 13. 検査器自身の整合性

正規文書や配布物を検査する検査器は、現行文書体系および契約に追従すること。

現行ファイルを識別形式の不一致等によって黙って検査対象外にしないこと。

検出対象となる欠陥ごとに正常 fixture と異常 fixture を設け、意図した欠陥が実際に検出されることを確認すること。

### 14. 欠陥類型単位での是正

監査で発見された個別ファイルだけを修正対象としないこと。

一つの欠陥を確認した場合、同一原因または同一契約差異から生じる箇所をリポジトリ全体から探索し、一つの欠陥類型として是正すること。

少なくとも、4 桁 REQ、ADR 残存、禁則表現、環境依存、コマンド Step 番号依存、内部 SPEC 参照、他スキル内部参照、review 起動条件、case-auto / case-run 責務、Epic 書き込み責務、検出事項と完了判定を横断対象とすること。

### 作業仮定

- 修正は実行開始時点の最新 `main` を起点とする。
- superseded 文書は現行動作の正規根拠として使用しない。
- 既存の利用者向け機能を不要に変更せず、契約矛盾の解消を優先する。
- 同一契約を複数箇所へ複製するより、単一の責務所有者へ集約する。
- 利用者から見える挙動を変えない可逆的な内部詳細は、必要最小限の再構成を許容する。

## 決定的受け入れ条件

各項目を個別に `pass` / `fail` / `blocked` / `not applicable` で判定する。

1. 全現行 REQ が現行の 3 桁識別体系として生成・解析・検査される。
2. 現行 REQ ファイルが識別子形式の不一致により検査対象から除外されない。
3. 現行契約に ADR を正規文書種別として必要とする参照が残っていない。
4. 全 accepted SPEC から参照される REQ が実在し、参照内容が当該 REQ の意味と一致する。
5. REQ と accepted SPEC の間に既知の外部挙動の矛盾が残っていない。
6. コマンドと対応ワークフロースキルが同一処理手順を独立して定義していない。
7. 能力スキルが特定コマンドの Step 番号へ依存していない。
8. 配布コマンドおよびスキルが ADF 開発リポジトリ内部の SPEC、Issue、他スキル内部ファイルを実行時依存先としていない。
9. GitHub 操作の標準契約が PowerShell、特定文字コード、一時ファイル、`--body-file` を必須としない。
10. adversarial-review の起動条件が REQ、SPEC、呼出元ワークフローで一致する。
11. case-auto、case-run、ハーネスの責務が相互に重複せず、定義どおり実装されている。
12. 自己適用環境と ADF 適用先で `agentdev_handoff` がそれぞれ定義された挙動を示す。
13. Epic 本文について複数の実行主体が競合して書き込む経路が存在しない。
14. 検証失敗を検出事項として記録しただけで成功扱いになる経路が存在しない。
15. 未解決の `fail` または `blocked` がある処理を完了として報告しない。
16. Artifact Graph の欠落・余剰ノード、欠落・余剰エッジ、グラフ構造上の欠陥、原文参照欠陥を意図的に壊した fixture で検出できる。
17. Artifact Graph の代表質問回帰を 10 件実行する。
18. 禁則辞書による全対象ファイル検査が 0 件となる。
19. 禁則語修正後に同一欠陥類型を横断再検索し、残存がないことを確認する。
20. README 等に記載された公開コマンド一覧と実在コマンド一覧が一致する。
21. 存在しない公開コマンドへの参照が 0 件となる。
22. REQ、Decision、SPEC、コマンド、スキル、検査器の全体回帰検証がすべて `pass` または適切な `not applicable` となる。

検証では、適用可能な項目について、不正 REQ 識別子、存在しない参照、空入力、中断後の再実行、外部 GitHub 操作失敗、検証失敗後の再検証、`user-decision-required`、consumer / self-hosting 差、並列子処理の一部失敗、Artifact Graph の意図的な欠落・余剰、特定 OS に依存しない GitHub 操作、禁則語を含む fixture を確認する。

`fail` が承認済み対象範囲内で解決可能な場合は修正して再検証する。要件変更、対象範囲拡大、追加設計判断、外部依存解消が必要な場合は反復を停止し、必要な判断事項を報告する。未検証、`blocked`、未解消の `fail` が一つでも残る場合は完了としない。

## Source Summary

2026-08-15 に AgentDevFlow の文書・配布物・検査基盤を横断監査した結果、REQ、command SPEC、skill SPEC、全配布コマンド、全トップレベル `SKILL.md`、Artifact Graph の主要スクリプト等で多数の不整合を確認した。

主要な共通原因は、文書体系変更が各層へ一貫して投影されていないこと、検査器自体が旧契約を保持していること、公開インターフェースとワークフロー実装の責務が重複していること、配布物が producer 内部情報へ依存していることにある。

個別修正では再発可能性が高いため、正規契約を先に整合させ、検査器を現行契約へ追従させた後、SPEC、コマンド、ワークフロースキル、能力スキル、GitHub 操作境界、Artifact Graph、日本語品質検査へ順次投影し、最後に全体回帰で完了判定する方針で合意した。
