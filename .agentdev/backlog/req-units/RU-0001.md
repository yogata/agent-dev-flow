# TIM準拠トレーサビリティモデル・派生索引・目的別探索の再構成

## 背景

現行の Artifact Graph は、REQ、Decision、SPEC 等の成果物とその関係を抽出し、派生索引としてグラフ化することで、関連成果物探索、変更影響候補取得、経路探索、根拠追跡等を提供している。

再評価の結果、扱っている問題の大部分は AgentDevFlow 固有ではなく、システム開発におけるトレーサビリティ管理として既に体系化されていることが判明した。

今後は独自概念・独自語彙・独自探索規則を極力減らし、Traceability Information Model（TIM）を基本概念として採用する。成果物型、トレースリンク型、関係の意味については、SysML、OSLC、OpenFastTrace 等で確立された概念・語彙を優先して採用する。

ADF 固有概念としては、ADF の思想上必要な `Decision` を成果物型として追加する。ただし、Decision から他成果物への関係についても、既存の標準的な関係語彙で表現可能な場合は独自関係を追加しない。

Artifact Graph は上位概念ではなく、TIM に基づく正規成果物間のトレーサビリティ情報から生成される、再生成可能な派生索引として位置付ける。

また、現行利用で確認された以下の問題を解消する。

- README 等の索引・集約成果物を経由して無関係な候補が大量に取得される
- 関係の意味と単なる文書参照が十分に区別されていない
- 変更影響、依存、実装等の探索規則が個別実装になり得る
- 古い派生索引を問い合わせに利用できる
- AI へ渡す候補数を制御できない
- ADF のワークフロー固有規則と汎用トレーサビリティ機能が混在している

## 基本構造

トレーサビリティ機能を以下の4層へ分離する。

```text
Traceability Information Model
        ↓
Trace Index
        ↓
Trace Query
        ↓
ADF Integration
```

| 層 | 責務 |
|---|---|
| TIM | 成果物型、トレースリンク型、関係の意味、関係制約 |
| Trace Index | TIM に基づく派生索引の生成、鮮度、決定論性 |
| Trace Query | トレース、変更影響、依存、実現関係、構造診断等の問い合わせ |
| ADF Integration | ADF 各ワークフローでの問い合わせ利用方法、独立確認、判断責務 |

## 要件

### RU-TIM-001: TIM をトレーサビリティの正規モデルとする

Artifact Graph 固有のノード型・関係型定義を上位モデルとせず、TIM を成果物間トレーサビリティの論理モデルとすること。

TIM は少なくとも以下を表現できること。

- 成果物型
- トレースリンク型
- リンク元成果物型
- リンク先成果物型
- 関係の意味
- 変更影響方向
- 必要な関係制約
- 根拠情報への関連付け

グラフの物理保存形式は TIM そのものとみなさないこと。

### RU-TIM-002: 標準語彙の優先

成果物型およびトレースリンク型は、SysML、OSLC、OpenFastTrace 等で確立された概念・語彙を優先して採用すること。

少なくとも以下に相当する意味を独自語彙として重複定義しないこと。

- 分解
- 具体化
- 仕様化
- 制約
- 依存
- 実現
- 充足
- 実装
- 検証
- 妥当性確認
- 置換・改訂
- 一般参照

既存語彙で ADF の意味を十分に表現できない場合のみ ADF 固有関係を追加すること。

### RU-TIM-003: Decision の ADF 拡張

`Decision` は ADF 固有の成果物型として TIM へ追加すること。

Decision と他成果物との関係は、既存の標準的な関係型で表現可能な場合、その関係型を利用すること。

Decision という成果物型が ADF 固有であることを理由として、Decision 専用の関係型を無条件に追加しないこと。

### RU-TIM-004: 意味的トレースリンクと一般参照の分離

Markdown リンク等から取得できる一般的な文書参照と、変更影響・依存・実現・検証等の意味を持つトレースリンクを区別すること。

単に参照関係が存在することだけを理由に、以下の探索へ参加させないこと。

- 変更影響
- 依存
- 実現
- 充足
- 検証

一般参照は、関連成果物確認、所在確認、低位問い合わせ等では利用可能とすること。

### RU-TIM-005: 関係意味から探索を導出

変更影響、依存、実現関係等の探索方向を、問い合わせごとの個別ハードコードだけで決定しないこと。

TIM に定義された関係の意味から、目的別問い合わせの探索方向・参加可否を導出できること。

少なくとも変更影響について、関係ごとに以下を区別できること。

- リンク方向へ影響
- 逆方向へ影響
- 双方向へ影響
- 変更影響なし

リンクの記述方向と変更影響方向を同一視しないこと。

### RU-TIM-006: 拡張関係の意味定義

プロジェクト拡張によって新しい関係型を追加可能とすること。

新しい関係型を高位問い合わせへ参加させる場合は、その関係型について必要な意味情報を明示すること。

未知の関係型について、名前や LLM 推論等から意味を自動推定しないこと。

意味定義が存在しない関係型は、低位問い合わせでは利用可能とし、高位問い合わせへ自動参加しないこと。

### RU-IDX-001: Artifact Graph の位置付け

Artifact Graph は TIM に基づくトレーサビリティ情報を探索するための派生索引とすること。

Artifact Graph を正規情報源としないこと。正規情報は引き続き各正規成果物とすること。

### RU-IDX-002: 既存低位問い合わせ

以下に相当する低位問い合わせ能力を維持すること。

- 隣接関係
- ノード間経路
- 根拠・出典

既存の `neighbors`、`path`、`provenance` の公開動作は、必要な互換性評価を行わずに全面変更しないこと。

### RU-IDX-003: 索引・集約成果物の役割識別

README、INDEX、CATALOG 等の名称そのものではなく、成果物の役割として索引・集約成果物を識別可能とすること。

索引・集約成果物は以下の用途で利用可能とすること。

- 索引構造の検査
- 索引漏れ・参照漏れの検査
- 所在確認
- 一般参照探索
- 明示的な索引構造問い合わせ

索引・集約成果物であることだけを理由として、成果物またはその関係をグラフから削除しないこと。

変更影響等から除外する主たる判断は、成果物名ではなくトレースリンクの意味に基づくこと。

### RU-IDX-004: 鮮度判定

鮮度保証を必要とする問い合わせの実行前に、派生索引の鮮度を判定すること。

鮮度判定には少なくとも以下を使用すること。

```text
input_digest
graph_config_digest
generator_version
schema_version
```

意味は次のとおりとする。

- `input_digest`: 派生索引生成対象となる正規入力の相対パスおよび内容
- `graph_config_digest`: 派生索引生成結果へ影響する適用後設定
- `generator_version`: 生成・解析結果の意味が変化する生成処理の版
- `schema_version`: 派生索引の物理構造の版

すべて一致する場合のみ既存索引を再利用すること。

### RU-IDX-005: 鮮度と問い合わせ設定の分離

派生索引生成結果へ影響しない問い合わせ時設定は、索引の再生成条件に含めないこと。

少なくとも以下は索引鮮度から分離すること。

- `discovery_roots`
- 候補数上限
- 問い合わせ結果の表示設定

これらの変更のみを理由として派生索引を再生成しないこと。

### RU-IDX-006: 利用時再生成

正規入力ファイルの更新ごとに常時派生索引を再生成しないこと。

鮮度保証を必要とする利用の直前に鮮度を確認し、不一致または索引不在の場合のみ再生成すること。

生成不能の場合の動作は ADF Integration 層の障害時方針に従うこと。

### RU-QRY-001: 高位問い合わせの提供

低位問い合わせとは別に、TIM の意味を利用した高位問い合わせを提供すること。

初期提供対象は少なくとも以下とする。

```text
related
impact
dependency
implementation
diagnostics
```

各問い合わせは TIM の意味を利用する問い合わせプロファイルとして扱い、独立した関係モデルを持たないこと。

### RU-QRY-002: related

`related` は、起点成果物と明示的なトレースまたは一般参照を持つ関連成果物候補を取得すること。

`related` の結果を、変更影響または依存関係として解釈しないこと。

### RU-QRY-003: impact

`impact` は、起点成果物を変更した場合に影響を受ける可能性がある成果物候補を取得すること。

探索方向は TIM に定義された関係の変更影響意味から導出すること。

一般参照または変更影響なしと定義された関係を、単にリンクが存在することだけを理由に探索経路として使用しないこと。

### RU-QRY-004: dependency

`dependency` は、起点成果物が成立、実現または実行されるために依存する成果物候補を取得すること。

依存関係として定義されていない一般参照を依存関係として扱わないこと。

### RU-QRY-005: implementation

`implementation` は、要件、仕様、設計等を実現・実装する成果物候補を取得すること。

`implementation` は TIM 上の実現・実装・充足系列の関係を利用する問い合わせプロファイルとして扱うこと。

将来、より一般的な coverage 問い合わせへ統合または上位化できる設計とすること。

### RU-QRY-006: diagnostics

構造上の注目候補は、通常の関連探索とは分離して診断問い合わせとして扱うこと。

診断対象には必要に応じて以下を含める。

- 孤立候補
- 未解決関係
- 廃止成果物への関係
- 関係制約違反
- 循環候補
- 複数経路
- 関係集中
- 根拠欠落

構造的特徴だけから異常を確定しないこと。

関係型ごとに TIM で制約が定義されている場合は、その制約に基づいて判定すること。

ADF 固有の所有・統制構造等は ADF Integration 層の診断規則として扱うこと。

### RU-QRY-007: 候補数上限

各高位問い合わせは、標準候補数上限を持てること。

標準上限値はコードへ直書きせず、問い合わせ設定として管理すること。

プロジェクト拡張は候補数上限を上書き可能とすること。

候補数上限の変更によって TIM 上の関係意味または探索意味を変更しないこと。

### RU-QRY-008: 候補数上限の決定

標準候補数上限は代表ケースによる回帰検証結果に基づいて決定すること。

少なくとも以下を満たすこと。

- 正常な代表ケースの必須候補を欠落させない
- AI へ渡す候補量を実用的な範囲に抑える

索引成果物等による候補増幅を候補数上限だけで抑制しないこと。

正常ケースと候補増幅ケースを上限値だけで分離できない場合は、関係意味または問い合わせ規則を見直すこと。

### RU-QRY-009: 候補過多時の動作

問い合わせ結果が候補数上限を超えた場合、候補を黙って切り捨てないこと。

問い合わせプロファイルに定義された決定論的な優先・除外規則を適用すること。

それでも上限を超える場合は、少なくとも以下を返すこと。

- 候補過多であること
- 全候補数
- 返却候補数
- 適用した絞り込み規則
- 独立探索へ移行可能であること

候補過多のみを理由として ADF ワークフロー全体を停止させないこと。

### RU-QRY-010: 問い合わせ結果

高位問い合わせは候補ごとに少なくとも以下を確認可能とすること。

- 候補成果物
- 候補となった理由
- トレースリンク型
- 探索方向
- 到達経路

詳細な根拠箇所は根拠問い合わせの責務とし、高位問い合わせへ根拠詳細を重複保持しないこと。

### RU-QRY-011: discovery_roots

成果物発見処理は、通常実行時に適用後設定から `discovery_roots` を自動解決すること。

明示的な実行時上書きが指定された場合のみ、その実行に限って変更できること。

通常の利用側ワークフローは探索範囲を重複して保持しないこと。

### RU-ADF-001: ADF ワークフローとトレーサビリティ層の分離

ADF 固有ワークフローは、TIM、派生索引、問い合わせ内部規則を独自に再定義しないこと。

ADF 側は必要な問い合わせ目的を指定し、返された候補を利用して判断すること。

### RU-ADF-002: ワークフロー割り当て

初期の利用方針は少なくとも次のとおりとする。

| ワークフロー | 主な問い合わせ |
|---|---|
| `req-define` | `related`、`impact`、必要に応じて `dependency` |
| `spec-save` | `related` |
| `case-open` | `impact`、`dependency` |
| `case-run` | `implementation` |
| `case-close` | 必要に応じて整合性確認 |
| `adversarial-review` | `diagnostics`、論点に応じた他問い合わせ |
| `inspect-docs` 等 | `diagnostics` |

この割り当ては ADF の責務分担を表すものであり、TIM そのものへ組み込まないこと。

### RU-ADF-003: case-run の責務境界

通常の `case-run` はトレーサビリティ問い合わせを利用して、新規の依存関係、実行構成、Wave 構成、実行順序を設計しないこと。

依存関係および実行構成の決定責務は、既存の ADF 責務分担に従い上流工程に維持すること。

`case-run` は既に決定された実装対象と正規成果物の実現関係確認を主用途とすること。

### RU-ADF-004: 独立確認

トレーサビリティ問い合わせ結果を最終判断として扱わないこと。

必要な判断では少なくとも以下のいずれかで確認可能とすること。

- 正規成果物本文
- `rg` 等の文字列探索
- ファイル探索
- その他の独立した正規情報確認手段

派生索引の不在、生成失敗、空結果、候補過多だけを理由として「関係なし」「影響なし」と判断しないこと。

### RU-ADF-005: 障害時動作

派生索引が存在しない、破損している、生成できない、問い合わせできない場合でも、ADF 標準ワークフローは代替探索が可能な限り継続すること。

トレーサビリティ基盤の障害だけを理由として、ADF ワークフローを恒常的に停止させないこと。

正規成果物そのものの異常と、派生索引側の異常を区別すること。

## 作業仮定

以下は要件ではなく現時点の作業仮定とする。

- 現行 Artifact Graph の物理形式は、TIM に基づく派生索引として再利用可能と仮定する。
- `nodes.jsonl`、`edges.jsonl`、`provenance.jsonl` 等の全面廃止は不要と仮定する。
- 高位問い合わせは既存問い合わせ実装を拡張して実現可能と仮定する。
- `generator_version` は生成結果の意味が変化する変更時に更新する版管理方式を基本とする。
- 現行の低位問い合わせについて、必要性のない破壊的変更は行わない。
- SysML、OSLC、OpenFastTrace 間で完全に同一の語彙が存在しない場合、意味の一致度と ADF の利用目的を基準に採用語彙を決定する。

## 対象範囲

- TIM の導入
- 成果物型の再整理
- トレースリンク型の再整理
- SysML、OSLC、OpenFastTrace 等への語彙寄せ
- Decision 成果物型の ADF 拡張
- 一般参照と意味的トレースリンクの分離
- 変更影響方向等の関係意味定義
- 拡張関係型の意味定義方式
- Artifact Graph の派生索引への位置付け変更
- 鮮度保証
- 利用時再生成
- 高位問い合わせ
- 候補量制御
- トレーサビリティ診断
- `discovery_roots` の自動適用
- ADF ワークフローとの責務分離
- 現在の候補増幅問題に対する回帰検証

## 対象外

- Artifact Graph または派生索引の正規情報源化
- LLM によるトレースリンク意味の自動確定
- 未知関係型の名前からの自動分類
- README 等の索引成果物そのものの削除
- 正規成果物保存時の常時索引再生成
- ADF ワークフロー固有責務の TIM への組込み
- `case-run` による依存関係・実行構成の再設計
- SysML、OSLC、OpenFastTrace の実装そのものへの全面置換
- ReqIF 等による外部要求管理ツールとの交換機能
- 意味的類似度によるトレースリンク自動生成

## 受け入れ条件

### AC-01 TIM 構造
成果物型、トレースリンク型、リンク元・リンク先、関係意味を TIM として表現できること。

### AC-02 標準語彙対応
採用した主要な成果物型・関係型について、既存標準・実装との対応または ADF 固有である理由を確認できること。既存語彙と意味が重複する ADF 独自語彙が残っていないこと。

### AC-03 Decision
Decision が ADF 拡張成果物型として利用できること。Decision という理由だけで不要な専用関係型が追加されていないこと。

### AC-04 一般参照分離
README 等から生成された一般参照が、関係意味を持たない状態で `impact`、`dependency`、`implementation` の経路へ参加しないこと。

### AC-05 変更影響方向
順方向影響、逆方向影響、双方向影響、影響なしを個別に検証できること。

### AC-06 拡張関係
意味定義された拡張関係が該当する高位問い合わせへ参加できること。意味定義されていない未知関係が高位問い合わせへ自動参加しないこと。未知関係が存在しても低位問い合わせが破綻しないこと。

### AC-07 索引・集約成果物
通常の変更影響探索等において、一般参照しか持たない索引・集約成果物を経由して無関係な成果物群へ展開しないこと。索引構造を明示的に問い合わせる場合は利用可能であること。

### AC-08 鮮度
正規入力変更、索引生成設定変更、`generator_version` 変更、`schema_version` 変更を個別に検出し、必要な場合に派生索引を再生成すること。

### AC-09 再生成不要条件
候補数上限、`discovery_roots`、問い合わせ結果表示設定のみの変更では派生索引を再生成しないこと。

### AC-10 索引不在
派生索引が存在しない状態で鮮度保証対象問い合わせを実行した場合、生成可能なら生成して問い合わせること。生成不能の場合は代替探索へ移行可能な状態を返すこと。

### AC-11 索引破損
既存派生索引が読み込み不能または現在のスキーマと互換性がない場合、その索引を正常な索引として利用しないこと。

### AC-12 高位問い合わせ
`related`、`impact`、`dependency`、`implementation`、`diagnostics` がそれぞれ定義された意味に従って動作すること。

### AC-13 空結果
候補が存在しない場合、正常な空結果として扱うこと。空結果を派生索引障害として扱わないこと。

### AC-14 候補数上限
各高位問い合わせに設定された候補数上限が適用されること。

### AC-15 候補過多
候補数上限超過時に候補を黙って切り捨てないこと。絞り込み後も超過する場合、候補過多と候補数を確認でき、ADF ワークフローが代替探索へ移行可能であること。

### AC-16 問い合わせ理由
各高位問い合わせ結果から、候補、関係型、探索方向、到達経路、候補となった理由を確認できること。

### AC-17 根拠分離
詳細な根拠情報を必要とする場合、根拠問い合わせから取得できること。高位問い合わせが同じ根拠詳細を別管理していないこと。

### AC-18 discovery_roots
実行時上書きがない場合は適用後の `discovery_roots` が自動利用されること。明示的な上書きはその実行に限り有効であること。

### AC-19 ADF 責務分離
ADF 各ワークフローが問い合わせ目的を利用し、探索方向、関係意味、TIM 定義を独自に保持していないこと。

### AC-20 case-run
通常の `case-run` がトレーサビリティ問い合わせによって新規の依存関係、Wave 構成、実行順序を決定しないこと。

### AC-21 障害時継続
派生索引不在、派生索引破損、派生索引生成失敗、高位問い合わせ失敗、候補過多の場合でも代替探索へ移行可能であること。

### AC-22 回帰品質
代表ケースについて、必須候補の見逃し、誤候補、候補総数、一般参照経由の候補増幅、索引・集約成果物経由の候補増幅、探索方向、変更影響なし関係の誤通過、拡張関係の参加可否、派生索引側だけの見逃し、独立探索側だけの見逃しを確認すること。README 等を経由した既知の候補増幅を再現する回帰試験を含めること。

各受け入れ条件は個別に `pass / fail / blocked / not applicable` で判定できること。

## 検証方法

最低限、以下を検証する。

### 正常系
- 標準成果物型・関係型
- Decision 成果物型
- `related`
- `impact`
- `dependency`
- `implementation`
- `diagnostics`
- 鮮度一致時の索引再利用
- `discovery_roots` 自動解決

### 関係意味
- 順方向影響
- 逆方向影響
- 双方向影響
- 変更影響なし
- 一般参照
- 意味定義済み拡張関係
- 意味未定義拡張関係

### 異常系
- 索引不在
- 索引破損
- 索引生成失敗
- 問い合わせ失敗
- 候補過多
- 未知の拡張関係

### 境界値
- 探索深度境界
- 候補数が上限直前
- 候補数が上限一致
- 候補数が上限超過

### 空状態
- 空索引
- 候補0件
- `discovery_roots` 内に対象なし

### 再実行
- stale 検出後の再生成
- 再生成後の同一問い合わせ
- 候補過多後の絞り込み

### 回帰
- README 経由候補増幅
- 索引・集約成果物経由候補増幅
- 一般参照と意味的関係の分離
- 既存低位問い合わせ
- 独立探索との比較

`fail` が承認済み範囲内の実装不備で解決可能な場合のみ修正・再検証する。

要件変更、対象範囲拡大、追加の意味定義、標準語彙選択、外部依存解消が必要になった場合は反復を停止し、必要な判断事項を報告する。

未検証、`blocked`、未解決の `fail` が残る場合は完了と判定しない。
