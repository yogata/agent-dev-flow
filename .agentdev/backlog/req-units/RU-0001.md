# SPEC成果物のDesign再定義と文書体系再構成

## 目的

ADFの現行SPEC成果物を、実際の責務に一致するDesign成果物へ再定義する。
Designは、REQを満たすために現在採用している内部構造、内部動作、責務分担、データ構造、処理方式、規則、パラメータを記述する正規成果物とする。

現行SPECは実体として内部設計を記述している一方、SPECという名称は仕様一般を意味し、Requirementとの関係やTIM上のDesignとの対応に不要な用語変換を生じさせている。
この機会に名称だけでなく、Designへ混在しているReport、実測値、検証実体を分離し、SPEC固有に蓄積された不要な分類、状態、互換構造もDesignへ持ち込まない。

## 対象

### Designの意味境界

- DesignはREQを満たすために現在採用している内部構造、内部動作、責務分担、データ構造、処理方式、規則、パラメータを記述する。
- Designは現在のHOWを記述する。
- 将来案、採用理由、却下理由、作業履歴、監査結果、評価結果、実測値、実装コードそのもの、検証実行結果はDesignに保持しない。
- ArchitectureはDesignに含まれる一部として扱い、Designを高位設計だけに限定しない。

### 文書体系と物理配置

- SPEC成果物型を廃止し、Design成果物型へ置換する。
- `docs/specs/` を `docs/designs/` へ変更する。
- `docs/designs/` は現在有効なDesignだけを保持する正規領域とする。
- `docs/reports/` をReportの正規配置として新設する。
- 旧 `docs/specs/` の `authoring`、`commands`、`foundations`、`integrity`、`local`、`quality`、`responsibilities`、`skills`、`workflows` は、Designとして妥当な内容を `docs/designs/` へ移行する。
- `integrity/audits/**`、人間向けbaseline、Artifact Graph効果評価、DOC-MAP監査等の監査・評価・観測記録はReportへ移す。
- チェッカーが使用する実行時データはDesignから外し、既存のリポジトリローカル検証スキル配下の `data/`、`baselines/` 等へ配置する。
- Design文書に保持している再計算可能なAUTOGEN実測表は永続化をやめ、必要時に実体から算出する。

### 正規語彙と保存系

ADF成果物を意味する正規語彙を次へ変更する。

- `SPEC` → `Design`
- `docs/specs/` → `docs/designs/`
- `spec-save` → `design-save`
- `agentdev-workflow-spec-save` → `agentdev-workflow-design-save`
- `agentdev-spec-file-manager` → `agentdev-design-file-manager`
- `artifact: spec` → `artifact: design`
- `target_spec` → `target_design`
- `related_spec` 等はADFのSPEC成果物を意味する場合にDesign語彙へ変更する。

外部API仕様、プロトコル仕様等、一般名詞として正しい「仕様」「specification」は変更しない。

### Design操作

- Design保存操作は `create`、`append`、`update` の3値を正規値とする。
- `spec-create`、`spec-update`、`spec-append` 等の旧別名は廃止する。
- `design-create`、`design-update`、`design-append` 等の新しい別名も導入しない。
- `target_area` による既存セクション更新、追加位置判断等の現行機能はDesign保存機能へ責務を引き継ぐ。

### Design frontmatterとライフサイクル

- Designの基本frontmatterは `title`、`status`、`created`、`updated` とする。
- `status` は `draft`、`accepted` の2値とする。
- 新規Designは `draft` とし、確定時に `accepted` へ遷移する。
- `superseded`、`superseded_by` をDesignライフサイクルから廃止する。
- 置換済みDesignは現行Designツリーへ保持せず、履歴はGit、Issue、Decision等の既存履歴手段から確認する。
- `spec_logical_division` を廃止し、Design用の代替分類メタデータは追加しない。
- 正規所有者という設計原則は維持するが、各Designに `canonical_owner` frontmatterを要求しない。
- Design専用の安定ID体系は本変更では導入しない。

### 既存機構の追従

- REQ、Decision、Design、Guide、Reportの文書境界を文書モデルへ反映する。
- req-define、req-save、design-save、一時成果物契約、inspect-docs、docs-check、targeted docs guard、索引生成、健全性計測をDesign語彙へ追従させる。
- case-closeのDesign確定処理を `draft` → `accepted` に追従させる。
- Artifact Graphは `docs/designs/` と `design` 型を認識するための追従修正だけを行う。

## 対象外

- TIMの最終モデル確定。
- TIM用Design単位IDの導入。
- `DES-*` 等の新規ID体系。
- Design内のトレース対象粒度の確定。
- DecisionのTIM参加判断。
- Artifact Graphの関係型、関係意味、高位問い合わせの再設計。
- OpenFastTrace等の外部ツール採否。
- Report専用の保存コマンド、ライフサイクル、独立ワークフローの新設。
- 新しい検証基盤の導入。
- 旧 `spec-save` の互換コマンド、互換aliasの維持。
- release互換等、本変更と無関係な後方互換機構の追加。

## 正規所有者とアンカー

- 文書種別の意味境界、配置、優先順位: 現行 `docs/specs/foundations/document-model.md` の責務を移行後 `docs/designs/foundations/document-model.md` が継承する。
- 執筆時の文書種別配置判定: 現行 `docs/specs/responsibilities/document-type-responsibilities.md` の責務をDesign側へ移行する。
- Design保存ワークフロー: `design-save` と `agentdev-workflow-design-save`。
- Designファイル操作: `agentdev-design-file-manager`。
- draft-data成果物契約: 現行 `docs/specs/responsibilities/artifact-contracts.md` の責務をDesign側へ移行する。
- 文書整合性検査: 既存 `repo-agentdev-integrity` とdocs-check経路を維持し、Design語彙へ追従する。
- 正規所有者という一般原則: 現行成果物責任表の責務を維持する。各Designの `canonical_owner` メタデータは正規所有原則そのものとは分離して廃止する。

## 依存関係

別RUへの依存はない。

実装内部では次の順序依存を持つ。

1. 文書モデル、配置、ライフサイクルをDesignへ再定義する。
2. req_draft、artifact_actions、Design操作契約を再構成する。
3. `design-save`、Workflow Skill、file-managerを一括移行する。
4. Report分離、integrity、index、健全性計測を整理する。
5. Artifact GraphをDesign名称とパスへ追従させる。
6. 旧SPEC語彙、旧パス、旧状態、混在成果物の残存を横断検証する。

これらは単一の横断変更として扱い、中間状態で旧語彙と新語彙を併存させない。

## 要件化の方向

- REQ-001を更新し、仕様成果物をDesignへ再定義し、Reportを正式な文書種別として扱い、Designの意味境界、配置、ライフサイクルを今回の合意へ変更する。
- REQ-001に存在する仕様の安定ID必須、`superseded`、主論理区分、各仕様の正規所有対象宣言等の過剰要求はDesignへ継承せず削除または縮小する。
- REQ-004を更新し、req-define / req-save / `design-save` の責務境界とREQ / Design境界へ用語を統一する。
- REQ-008を更新し、永続成果物、direct consumer、`artifact_actions`、operation契約をDesignへ変更する。
- REQ-036を更新し、inspect系診断をREQ / Design境界へ変更する。
- 新規REQは作成せず、既存関心の再定義として既存REQを更新する。
- 新規Decisionは原則作成しない。実装中に既存Decisionと矛盾する独立した新しい長期判断が判明した場合だけ別途判断する。
- Artifact GraphのTIM意味論変更は本変更へ混ぜず、Design移行完了後のTIM再検討へ戻す。

### 作業仮定

以下は利用者向け要件ではない。

- 旧SPECファイルの個別移動先はDesign境界に従って機械的に一括決定せず、Report、Verification実体、Designのいずれかへ内容を確認して分類する。
- 既存相対リンク、IRのaffected_artifacts、検査fixture等は物理移動に合わせて更新する。
- 旧語彙検出では、外部仕様や検出fixture等の正当な `spec/specification` 使用を誤検出しない。

## 決定的受け入れ条件

1. 現行正規成果物としてSPEC種別が存在しない。
2. `docs/designs/` が存在し、現在有効なDesignだけを保持する。

4. Design本文に実測スナップショット、監査結果、完了済み作業履歴が混在しない。
5. 新規Designの基本frontmatterが `title`、`status`、`created`、`updated` で構成される。

10. Design専用の新規ID体系が導入されていない。
11. 公開保存コマンドが `design-save` であり、`spec-save` 互換コマンドが存在しない。

20. targeted docs guardとdocs-checkが `docs/designs/**` と `design-save` を正しく扱う。
21. Report分離後、`audits/`、`baselines/` をDesignではないものとして扱う専用例外が不要になる。
22. Artifact Graphの標準入力パスが `docs/designs/`、対応ノード型が `design` へ追従する。
23. Artifact GraphのTIM関係型、関係意味、高位問い合わせに本変更由来ではない変更が入っていない。
24. 現行成果物と実装に、ADF成果物SPECを意味する `docs/specs/`、`artifact: spec`、`target_spec`、`spec-save`、`agentdev-workflow-spec-save`、`agentdev-spec-file-manager`、`spec_logical_division` が残っていない。履歴資料、外部仕様の一般名詞、検出fixture等の正当使用は除外する。
25. 通常のREQ形成、Design保存、Case実行、Case確定、docs-checkの主要経路がDesign移行後も完遂できる。
