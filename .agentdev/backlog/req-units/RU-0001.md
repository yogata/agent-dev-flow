# 配布コマンド・スキルの文章品質是正を実ファイル検証で完遂する

## 背景

配布コマンド・スキルの文章品質について、これまで複数回の是正を実施したが、実ファイル上の不備が十分に減っていないにもかかわらず「全件 pass」と判定される事象が発生した。

直近の是正では、全対象を確認したと報告されているものの、実際の変更は未完結文の末尾へ「である」を補う等の限定的な修正が中心であった。

その結果、是正要求の起点となった `req-define.md` の

`工程上の選好を肯定形の不変条件として示す:`

が現在も残っている。

同様に、以下のような既知不備も残存している。

- 完成成果物に残った執筆者向けメタ指示
- `durable state`、`resume source` 等の不要な英語混在
- 「〜を正とする」「〜が正」「〜の正」等の不自然な規範表現
- `查読` 等の意図しない異言語文字
- 未完結文
- 過剰な名詞連結
- 多数の条件・例外・処理を一文へ連結した文
- 既知の参照残骸

既存の `REQ-053 配布物の文章品質契約` は、文章品質の基準自体を既に規定している。

一方、実行側が一部の違反だけを修正した後に、ファイル全体を再評価せず pass と判定できる余地が残っている。

したがって、文章品質基準を追加するだけではなく、**最終HEADの実ファイルをファイル単位で再査読し、その証拠が存在しなければ完了できない契約**が必要である。

## 問題

現在の問題は、文章品質基準の不足だけではない。

主な問題は、是正と完了判定の間に次の抜け道が存在することである。

1. 一つのファイルに複数の不備があっても、そのうち一件を修正しただけでファイル全体を pass と判定できる。
2. 変更差分だけを確認し、変更後ファイル全文を再確認しなくても完了できる。
3. 既知不備が残っていても、「全件確認した」という自己申告だけで合格扱いにできる。
4. 既知の不自然な英語表現を、是正時に根拠なく「許容語」と再分類することで違反件数を減らせる。
5. 修正を行った実行主体と最終合否判定が同一の判断結果だけに依存し、誤った自己評価を検出できない。
6. 最終検証結果と最終HEADの実ファイルが一致していることを要求する契約が弱い。
7. 対象ファイルの一部が未変更でも、初期不合格理由を解消した証拠なしに pass とできる。
8. `fail` または `blocked` が残っていても、別課題への移送だけで本件を完了扱いにできる余地がある。

このため、要求上は「全件是正」であっても、実態としては限定的な修正だけで完了できてしまう。

## Source Summary

本セッションでは、次の事実と方針を確認した。

- 配布コマンド・スキルの文章品質是正を複数回実施しても、実ファイル上の改善が不十分である。
- 直近実行では「全件 pass」と報告されたが、独立再確認では多数の既知不備が残っていた。
- `req-define.md` の起点となったメタ指示が現在も残っている。
- `agentdev-doc-writing` に意図しない異言語文字が残っている。
- `agentdev-command-authoring`、`agentdev-skill-authoring`、`agentdev-inspect-skills` も、自ら規定する文章品質基準を完全には満たしていない。
- 一部の文だけを修正してファイル全体を pass と判定する方式では不十分である。
- 最終HEADの各ファイル全文を再査読しなければならない。
- 既知不備を分類変更だけで消してはならない。
- 実ファイル上の改善を証明できない場合は完了扱いにしない。

## 統合理由

本件を再度単なる「文章修正」として扱うと、これまでと同じ失敗を繰り返す可能性が高い。

根本原因は、

- 是正対象の特定
- 是正
- 最終検証
- 完了判定

の間に、実ファイルとの対応を強制する契約が不足していることである。

したがって、本RUでは次を一つの要求単位として扱う。

1. 現在残っている文章品質不備の全件是正
2. 既知不備を初期未解決事項として固定
3. 最終HEADを基準とした全ファイル再査読
4. ファイル単位の合否証拠
5. 誤った pass 判定を防ぐ完了条件
6. 改善がない状態での完了禁止

## 要件化の方向

### 1. 既存文章品質契約を置き換えず、完了検証契約を強化する

主対象は既存 `REQ-053` の強化とする。

既存の文章品質観点は維持し、本RUでは特に、

- 対象確定
- 既知不備管理
- 是正後全文確認
- ファイル単位判定
- 最終HEADとの一致
- 完了判定

を強化する。

### 2. 初期不合格を勝手に消さない

本セッションで不合格と確認したファイルと不備は、是正開始時点の初期未解決事項として扱う。

初期不合格は、次のいずれかを満たすまで解消扱いにしてはならない。

- 実ファイルを修正し、該当不備がなくなったことを確認した。
- 既存の文章品質規範または既存用語政策により、当該指摘が明確に許容されていることを根拠付きで確認した。
- 意味または許容可否が一意に判断できず、`blocked` とした。

実行中に新しい許容解釈を作り、既知不備を pass へ変更してはならない。

文章品質規範または用語政策そのものを変更しなければ許容できない場合、本件の文章是正とは分離して扱う。

### 3. ファイルの一部修正をファイル全体の pass とみなさない

一つのファイルについて一件以上の修正を行っても、それだけでは当該ファイルを pass と判定してはならない。

各ファイルは、最終状態の全文について少なくとも次を再確認する。

- メタ指示残留
- 未完結文
- 不要な英語混在
- 規範関係のあいまいさ
- 過剰な名詞連結
- 条件・例外・処理の過剰連結
- Markdown・Unicode・参照等の決定的破損

すべての観点に合格した場合だけ、そのファイルを pass とする。

### 4. 最終HEADの実ファイルを検証対象とする

合否判定は、修正途中の内容、変更差分、作業用メモ、過去の査読結果だけを根拠としてはならない。

最終合否判定では、提出対象となる最終HEADから対象ファイルを読み直す。

変更差分が正しいことと、ファイル全体が正しいことを別に扱う。

### 5. 初期不合格ファイルの未変更passを禁止する

初期不合格となったファイルについて、実ファイルに変更がないまま pass とする場合は、初期指摘そのものが誤検出だったことを既存規範に基づいて証明しなければならない。

根拠のない「問題なし」「許容語」「技術用語である」等の説明だけでは pass としない。

### 6. ファイル単位の検証証拠を必須にする

最終検証結果には、対象ファイルごとに少なくとも次を含める。

- ファイルパス
- 初期判定
- 修正有無
- 確認した文章品質観点
- 最終判定
- 残存不備
- `blocked` の場合の判断が必要な事項

全件をまとめた件数だけでは完了証拠としない。

「全件確認済み」「違反0件」という集計値は、ファイル単位の結果と一致する場合にだけ有効とする。

### 7. 修正判断と最終合否判定を同じ自己評価だけに依存させない

最終合否判定は、修正時に作成した「修正済み」という判断をそのまま継承してはならない。

最終HEADの実ファイルを再入力として、文章品質基準を改めて適用する。

修正時の判断と最終確認結果が異なる場合、最終確認結果を優先する。

### 8. 改善量を確認する

本件の開始時点と終了候補時点について、少なくとも次を比較する。

- 不合格ファイル数
- 残存する既知不備数
- `blocked` 数
- 決定的破損数

終了候補時点で不合格ファイル数または既知不備数が開始時点から減少していない場合、本件を完了扱いにしてはならない。

最終的には、対象ファイルの `fail` と `blocked` を0件にする。

### 9. `blocked` の別課題移送だけで完了しない

意味を一意に復元できない場合は推測修正を禁止し、`blocked` とする。

ただし、`blocked` を別課題へ記録しただけで本RUを完了扱いにしてはならない。

本RUの対象ファイルに文章品質上の `blocked` が残る限り、本RUは未完了とする。

ユーザー判断により対象外化または現状維持が明示的に合意された場合のみ、対象から除外できる。

### AC-14 改善実績

開始時点と終了候補時点を比較し、

- fail ファイル数
- 既知不備数
- 決定的破損数

が減少していること。

改善が0である場合は、他の検証結果にかかわらず `fail` とする。

### AC-15 全件合格

最終的な対象コマンド・スキルの結果が、

- `pass`: 全件
- `fail`: 0件
- `blocked`: 0件

であること。

1件でも `fail` または `blocked` が残る場合は、本RUを完了扱いにしない。

### AC-16 完了報告と実ファイルの一致

完了報告の件数、ファイル単位結果、最終HEADの実ファイル内容が一致すること。

完了報告で `pass` とされたファイルから文章品質違反が一件でも再現できた場合、最終検証全体を `fail` とする。

## 検証方法

検証では、実行者の「全件確認した」という自己申告を証拠としない。

最終HEADの実ファイル、ファイル単位の検証結果、決定的検査結果を突き合わせる。

検証結果は各受け入れ条件について `pass / fail / blocked / not applicable` で記録する。

`fail` が承認済み範囲内の文章修正で解消可能な場合は、修正して同じ条件を再検証する。

意味の確定、対象範囲変更、規範変更が必要な場合は `blocked` とし、ユーザー判断なしに pass へ変更しない。

すべての対象ファイルと受け入れ条件が `pass` になるまで完了としない。
