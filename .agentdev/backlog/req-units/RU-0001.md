# コマンド・スキル自然言語記述の全件是正と再発防止

## 背景

AgentDevFlow の全コマンド・全スキルについて、内容そのものを正しいものと仮定したうえで、完成成果物としての文章品質を確認した。

2026年8月30日時点の `main` を対象に、現行のコマンド19件とスキル51件、計70ファイルを一つずつ確認した結果、コマンドは19件すべて、スキルは51件中50件が文章品質基準を満たしていなかった。

特に、検討の起点となった `req-define.md` の

`工程上の選好を肯定形の不変条件として示す:`

という記述が現在も残っており、完成したコマンド定義に執筆者向けのメタ指示が残留する問題が解消されていない。

文章品質契約、作成時の品質基準、査読・診断観点自体は追加されているが、それらを規定するスキル自身にも同じ種類の違反が残っている。

## 問題

現状は、文章品質に関する規範を定義しただけで、既存の配布物全体への適用と最終検証が完遂されていない。

確認された主な問題は次のとおりである。

1. 完成成果物に執筆者・LLM向けのメタ指示が残っている。
2. 主語・述語が完結しない断片的な文が残っている。
3. 日本語で自然に表現できる説明まで英単語へ依存している。
4. 「〜を正とする」「〜が正である」「〜の正」のような不自然な規範表現が残っている。
5. 名詞を過剰に連結した表現や、一文に多数の条件・例外・動作を詰め込んだ表現が残っている。
6. 簡体字、誤字、参照残骸、Markdown・パス・コードスパンの破損など、機械的に検出可能な不備が残っている。
7. 文章品質を定義・査読・診断するスキル自身が、自ら定めた文章品質基準を満たしていない。

したがって、現状を文章品質是正完了とは扱えない。

## 統合理由

確認された不備は特定のコマンドやスキルに限定された個別誤記ではなく、同一の文章品質問題が配布物全体へ横断的に存在している。

そのため、69件の個別修正要求へ分割するのではなく、

- 配布物全体に適用する文章品質契約
- 現行配布物の全件是正
- 作成時、査読時、診断時の再発防止

を一つの変更単位として扱う。

各ファイル固有の文意は個別に保持する必要があるが、合否基準は共通化する。

## 要件化の方向

### 1. 完成成果物としての文章品質を満たす

コマンドおよびスキルの自然言語記述は、利用者または実行エージェントがそのまま読んで解釈できる完成文章とする。

完成成果物では、文章を書かせるためのメタ指示を残さず、その指示によって表現すべき実際の規則・状態・制約を直接記述する。

### 2. 意味を保持したまま文章単位で是正する

既存の振る舞い、責務、状態遷移、識別子、CLI/API 契約を変更せず、文章表現のみを是正する。

不自然な語だけを別の語へ置換する方法を基本とせず、必要に応じて文全体を再構成する。

元の意味を一意に復元できない場合は推測で書き換えず、未解決事項として扱う。

### 3. 英字表記の必要性を区別する

次のように英字で保持する意味があるものは、文章品質違反として一律に扱わない。

- 識別子
- 状態値
- 操作名
- CLI オプション
- ファイル・ディレクトリパス
- API 名
- コード上の名称
- 固有の技術名称
- `worktree` など、プロジェクト内で英字表記を維持することが明確な用語

一方、日本語で自然に記述できる説明語まで英語へ依存する記述は是正対象とする。

### 4. 規範関係を明示する

「〜を正とする」「〜が正」「〜の正」のように、何が定義元で何が参照側なのかが文法上不明瞭な表現を避ける。

必要に応じて、次のような関係を明示する。

- 規範となる定義がどこに存在するか
- どの定義に従うか
- どの成果物・スキルが当該定義を所有するか

### 5. 決定的な破損を機械的に検出可能にする

少なくとも次の不備は、人間またはLLMの目視だけへ依存せず検出できる状態にする。

- 制御文字
- 意図しない異言語文字
- 壊れた Markdown
- 壊れたコードスパン
- 壊れたリンク・パス表現
- 既知形式の参照残骸
- 機械的に判定可能な構文破損

具体的な検出手段の実装方式は本 RU では固定しない。

### 6. 作成・査読・診断の各責務で再発を防止する

文章品質基準を、少なくとも次の責務へ一貫して反映する。

- コマンド作成時の品質基準
- スキル作成時の品質基準
- 文書査読時の品質基準
- コマンド・スキル横断診断時の品質基準

これらの基準を定義するファイル自身も同じ基準を満たす。

- 意味が一意に判断できない記述を推測で確定すること

## 既知の不備類型と実例

### メタ指示残留

- `工程上の選好を肯定形の不変条件として示す:`
- `硬い境界…に限定する:`
- `Decision保存の直前に妥当性を再検証する:`

完成成果物では、このような「どのように書くか」の指示ではなく、実際の規則を直接記載する。

### 未完結文

例:

- `レビュー完了フェーズ。`
- `人間向け公開入口。`
- `AgentDevFlow 標準配布スキル。`
- `workflow 実装本体。`
- `要件分析のための知識ベース。`

見出し・表ラベルなどを除き、通常本文は文として完結させる。

### 不自然な英語混在

例:

- `fast path`
- `durable state`
- `resume source`
- `runtime artifact`
- `finding disposition`
- `silent skip`
- `partial result`
- `child task recovery`
- `current STEP`
- `source-of-truth priority`

英字で保持する契約上の必要性がない場合、日本語として自然な表現へ再構成する。

### 不自然な規範表現

例:

- `〜を正とする`
- `〜が正である`
- `順序の正`
- `操作知識の正`
- `非破壊性の正`

定義元・参照先・所有関係を明示する文章へ変更する。

### 文字・構造破損

確認済みの例:

- `status 维持`
- `查読`
- `docs/decisions<README>.md`
- 壊れたテンプレート参照記法
- `-066`
- `-151 相当`
- Markdown 強調記法の不整合

### 過剰な名詞・条件連結

複数の責務、条件、例外、停止条件、復旧条件を一文へ連結し、読点だけで接続している記述を分解する。

特に workflow 系スキルでは、この問題が広範に存在するため、単一の既知箇所だけでなく全文を対象に確認する。

## 受け入れ条件

### AC-1 全件是正

実施時点の全対象コマンド・スキルを一つずつ確認し、文章品質違反が0件であること。

一部ファイルの抜き取り確認では合格としない。

### AC-2 既知不備の解消

2026年8月30日の全件確認で検出した既知不備について、すべて解消済みであること。

少なくとも、起点となった `req-define.md` のメタ指示が残っていないこと。

### AC-3 メタ指示残留なし

完成したコマンド・スキル本文に、実行時の意味を持たない執筆者・LLM向けメタ指示が残っていないこと。

作成方法を説明すること自体が責務である authoring 系スキル内の正当な作成指示は対象外とする。

### AC-4 未完結文なし

通常本文に主語・述語等が欠落した未完結文が残っていないこと。

見出し、表のセル、項目名、識別子等、文章である必要がない箇所は対象外とする。

### AC-5 不要な英語混在なし

識別子、状態値、CLI/API 名、ファイルパス、コード上の名称、固有技術名称等を除き、日本語で自然に表現可能な説明語の不要な英語混在が残っていないこと。

### AC-6 規範関係の一義性

規範となる定義を参照する文章について、定義元、参照元、所有関係のいずれかが一義的に読み取れること。

「〜を正とする」等の表現を使用する場合も、その関係が曖昧でないこと。

### AC-7 文構造の可読性

過長な名詞連結や、一文への過剰な条件・例外・処理の連結が残っていないこと。

独立して判定・理解できる条件または処理は、必要に応じて別文または箇条書きへ分離されていること。

### AC-8 決定的破損0件

対象ファイルについて、少なくとも次の決定的破損が0件であること。

- 制御文字
- 意図しない異言語文字
- 壊れた Markdown
- 壊れたコードスパン
- 壊れたリンク・パス表現
- 既知形式の参照残骸

### AC-9 意味保持

文章是正によって、既存の次の内容が変更されていないこと。

- コマンド・スキルの振る舞い
- 責務境界
- 状態遷移
- 停止条件
- 識別子
- CLI/API 契約
- 入出力契約

文章から元の意味を一意に復元できない箇所は、推測で修正せず `blocked` として扱うこと。

### AC-10 再発防止側の自己適合

文章品質の作成・査読・診断を担うファイル自身についても同じ文章品質基準を適用し、違反が0件であること。

少なくとも以下を個別に再確認する。

- `agentdev-command-authoring`
- `agentdev-skill-authoring`
- `agentdev-doc-writing`
- `agentdev-inspect-skills`

### AC-11 新規配布物への適用

新規または更新されたコマンド・スキルについて、作成時・査読時・横断診断時に同一の文章品質観点を適用できること。

### AC-12 最終検証

修正後に再度、対象となる全コマンド・全スキルを一つずつ確認する。

検証結果はファイルごとに `pass / fail / blocked` で記録し、`fail` または `blocked` が1件でも残る場合は完了としない。

## 検証方法

1. 対象となるコマンド・スキルの一覧を確定する。
2. 決定的破損について機械検査を実施する。
3. 各ファイルを一つずつ文章品質観点で査読する。
4. 既知不備だけでなく、同じ不備類型が別箇所へ残っていないか横断確認する。
5. 各ファイルを `pass / fail / blocked` で記録する。
6. 全対象が `pass` となった場合のみ完了と判定する。
