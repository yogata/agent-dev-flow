# RU-0014: case-open と case-run の実行契約責務境界の明確化

## 目的

`case-open → Issue → case-run` の責務境界を整理し、Issue 作成時点で確定可能な実行条件、受け入れ条件、検証方法を `case-open` が Issue の execution contract として確定する。

`case-run` は Issue 作成時点で確定可能な事項を再判断、追加設計せず、Issue に記録された契約に基づく実装、実行時観測、検証を担当する。

これにより、成果物種別に応じた authoring/review skill の適用漏れ、実装フェーズでの受け入れ条件や test strategy の追加判断、Issue scope の黙示的拡張を防止する。

## 対象

### In Scope

- `case-open` が Issue 作成時点で確定可能な execution contract の確定
- Issue の以下の情報の確定および後工程への引き渡し
  - 対象範囲、変更対象成果物
  - 関連する REQ / ADR / SPEC
  - 完了条件
  - test strategy
  - 成果物種別から決まる必須 quality control
  - Issue scope に影響する変更影響候補
  - ユーザーが明示した任意 review の発動契約
  - work_type / scale / Issue structure
- 成果物種別と必須 quality control の対応を共通ルールとして扱うこと
- 少なくとも以下の artifact-specific quality control を対象とすること
  - document の変更に対する `agentdev-doc-writing`
  - Skill の作成、変更に対する `agentdev-skill-authoring`
  - Command の作成、変更に対する `agentdev-command-authoring`
- 同じ性質を持つ他の artifact-specific authoring/review/check が存在する場合、同一責務境界に従わせること
- `case-run` が実行中に Issue contract の不足、矛盾、scope 拡大の必要性を発見した場合の停止、`case-update` 連携
- 新規 Issue および本変更適用後に更新される Issue への新契約適用

### 責務境界

`case-open` は **what / required verification** を確定する。

- 何を変更対象とするか
- 何を満たせば完了か
- 何を検証しなければならないか
- どの品質統制が必須か

`case-run` は **how / execute / observe / verify** を担当する。

- 既確定契約を実現する内部実装方式
- 実装
- test strategy の実行
- fix-and-reverify
- 実行時にしか取得できない状態の観測
- 実 diff と契約の適合確認

## 対象外

- `case-run` から内部実装方式の判断を除去すること
- 関数配置、内部データ構造、命名、実装順序等の可逆的な内部実装判断を `case-open` で事前確定すること
- worktree precondition、staleness check、実 diff 検査等、実行時状態を必要とする検査を `case-open` へ移管すること
- `case-run` が実装結果の REQ / ADR / SPEC / Issue contract 適合性を検証する責務の除去
- `case-close` の完了条件最終評価、PR merge、Issue close 責務の変更
- 既存の未更新 Issue を一括変換または遡及更新すること
- req_draft を case-run の入力として復活させること
- artifact-specific quality control の個々の品質基準そのものを本要件で再定義すること

## 依存関係

必須の先行 RU はない。

ただし実装時には、既存の以下の契約を維持する必要がある。

- case-open 成功後は Issue / Epic が後続工程の SSoT であること
- test strategy は `verification` / `pass_criteria` / `on_failure` を持つこと
- QG-2 は Issue 作成前に完了条件と test strategy の妥当性を検証すること
- case-run が既確定 Issue / REQ / ADR / SPEC の変更を必要とした場合、自律変更せず blocked とすること
- case-run の実装方針は既確定契約内の内部選択に限定すること

## 要件化の方向

### 1. case-open が execution contract を完成させる

case-open は Issue 作成前に、Issue 作成時点で合理的に確定可能な実行条件を確定すること。

少なくとも以下を含む。

- 実装対象成果物
- 関連 REQ / ADR / SPEC
- 完了条件
- test strategy
- 必須 artifact-specific quality control
- scope-affecting impact candidate
- ユーザー明示指定に由来する review 発動契約
- work_type / scale / Issue structure

### 2. 完了条件と検証方法を分離する

Issue の完了条件には成果物が満たすべき状態を記録する。

実行手段や検証手段は test strategy に記録する。

例:

- 完了条件:
  - 変更対象 Skill が Skill authoring 品質基準を満たすこと
- test strategy:
  - verification: `agentdev-skill-authoring` によって変更対象 Skill をレビューする
  - pass_criteria: 対象基準に未解決違反がない
  - on_failure: fix-and-reverify

Skill 名の使用自体が利用者要求でない限り、「特定 Skill を呼ぶこと」を成果状態として完了条件化しない。

### 3. artifact-specific quality control の選択を case-open に集約する

変更予定成果物の種別から必須 quality control を導出できる場合、その適用要否を case-run に委ねないこと。

artifact type と quality control の対応は個別 command に散在させず、再利用可能な共通規則として管理すること。

少なくとも document / Skill / Command を対象とし、同種の quality control が存在する場合は横断的に確認すること。

### 4. 完了条件品質の再設計を case-run から除外する

case-run は Issue に確定済みの完了条件を実行契約として扱うこと。

case-run が完了条件の不足、曖昧さ、矛盾、実現不能を検出した場合は、完了条件を自律補完せず blocked とすること。

単なる構造破損や staleness の検出は case-run の安全検査として維持できる。

### 5. 関連 ADR の拘束関係を case-open で確定する

case-open は Issue の実装を拘束する関連 ADR を Issue 作成前に特定し、必要な制約を完了条件または test strategy へ反映すること。

case-run は既確定 ADR への適合を確認すること。

case-run 実行時に新たな拘束 ADR または契約変更の必要性が判明した場合、自律的に Issue contract を拡張せず blocked とすること。

### 6. 条件付き test strategy の追加判断を case-open へ移す

「関数削除時は全利用箇所を検査する」等、Issue の予定変更内容から事前に判断可能な検証条件は case-open が test strategy へ展開すること。

case-run は当該条件を見て test strategy を新規設計せず、記録済み項目を実行すること。

### 7. scope-affecting impact candidate を case-open で処理する

case-open は Issue 作成前に変更影響候補を探索し、Issue scope、完了条件、test strategy に影響する候補を execution contract へ反映すること。

case-run が実装中に新たな impact candidate を発見した場合、以下を区別すること。

- 既存 Issue scope 内で処理可能な内部実装上の影響:
  - case-run が処理可能
- Issue scope、完了条件、REQ / ADR / SPEC、必須 quality control の追加変更が必要:
  - blocked
  - Issue 更新は case-update に委譲

### 8. work_type / scale を case-run で再決定しない

case-run 到達時点で work_type / scale / Issue structure が確定済みである場合、case-run はこれらを再分類して実行契約を変更しないこと。

case-run は Issue metadata、構造、実態の矛盾を検出した場合に停止できるが、新たな分類を正として処理を継続しないこと。

### 9. adversarial-review の発動契約と実行を分離する

ユーザーによる adversarial-review の明示指定が Issue 作成前に判明している場合、case-open は発動契約を Issue に永続化すること。

実装方針そのものの生成および review 実行は case-run / execution adapter の責務とする。

case-run は一時会話コンテキストだけを根拠として、Issue に存在しない発動契約を新規追加しないこと。

### 10. 既存 Issue の互換運用

本変更は、新規作成する Issue および本変更適用後に更新された Issue から適用する。

本変更以前に作成され、その後更新されていない既存 Issue に対し、新 execution contract の項目欠落だけを理由として一律 blocked にしない。

既存 Issue が `case-update` 等によって新契約へ更新された場合は、更新後の execution contract を適用する。

この互換運用のために、case-run へ新しい契約判断責務を残してはならない。

## 決定的受け入れ条件

1. **Issue 作成時契約**
   - 新規 Issue の作成時に、予定成果物から事前判定可能な必須 quality control が case-open によって判定され、必要な検証が Issue の test strategy に記録されること。

2. **document quality control**
   - document 変更を予定する新規または新契約へ更新済み Issue では、document quality control の必要性を case-run が初めて判断する構造になっていないこと。

3. **Skill quality control**
   - Skill 作成、変更を予定する新規または新契約へ更新済み Issue では、`agentdev-skill-authoring` 相当の必須検証が Issue 作成時に確定されること。

4. **Command quality control**
   - Command 作成、変更を予定する新規または新契約へ更新済み Issue では、`agentdev-command-authoring` 相当の必須検証が Issue 作成時に確定されること。

5. **完了条件と検証方法の分離**
   - 完了条件には成果状態を、test strategy には検証方法、合格基準、不合格時処置を記録し、必須 Skill 名の呼出自体が利用者要求でない場合は Skill 呼出を完了状態として扱わないこと。

6. **QG-2 境界**
   - 完了条件の網羅性、測定可能性、REQ / ADR / SPEC 反映等の Issue 作成前に確定可能な品質判断が case-open / QG-2 で完了し、case-run が同じ基準を用いて完了条件を再設計しないこと。

7. **ADR 境界**
   - Issue 作成前に判明する関連 ADR の拘束条件が execution contract に反映され、case-run はその適合確認を行うこと。
   - case-run で追加 ADR 制約が必要と判明した場合、Issue contract を黙示的に拡張せず blocked になること。

8. **条件付き test strategy**
   - 関数削除等、変更予定から事前判定できる追加検証条件が case-open により test strategy へ展開され、case-run に当該 test strategy の新規追加判断が残っていないこと。

9. **変更影響候補**
   - case-open が Issue scope に影響する変更影響候補を Issue 作成前に扱うこと。
   - case-run 中に scope 拡大が必要と判明した場合は自律拡張せず blocked / case-update 経路へ移行すること。

10. **work_type / scale**
    - case-run が work_type / scale を再決定して execution contract または workflow を変更しないこと。
    - metadata 等の矛盾検出時は、再分類による継続ではなく停止または既定の更新経路を使用すること。

11. **adversarial-review**
    - Issue 作成前に存在するユーザー明示指定は Issue に永続化されること。
    - 実装方針に対する review 実行自体は case-run / execution adapter に残ること。

12. **runtime-only 判断維持**
    - worktree 状態、staleness、実 diff、実装結果、test 実行結果など実行時にしか確定できない判断は case-run に維持されること。

13. **既存 Issue 互換性**
    - 本変更以前に作成され新契約へ更新されていない Issue は、新項目欠落のみを理由に一律停止しないこと。
    - 新規 Issue および新契約へ更新済み Issue では新しい execution contract 境界が適用されること。

14. **SSoT**
    - case-open 成功後の case-run は req_draft を参照して不足契約を補完せず、Issue / Epic を SSoT として処理すること。

15. **契約変更時停止**
    - case-run で Issue / REQ / ADR / SPEC の追加、変更、撤回が必要になった場合、実装を継続して黙示的に契約変更せず blocked として処理すること。

## 作業仮定

- 本 RU は `case-open → Issue → case-run` の責務再配置を主目的とし、個別 quality control の品質基準自体は既存の各 Skill/SPEC を利用する。
- artifact-specific quality control の具体的な内部表現方法は SPEC で決定できる。利用者可視の execution contract と責務境界を変えない限り、専用フィールド、test strategy への展開、共通 resolver 等の内部形式は本 RU では固定しない。
- 新契約適用済み Issue を識別するためだけの恒久的 schema version 導入は前提としない。

## 検証方法

- case-open の正常系テスト
  - document / Skill / Command の各変更 Issue を生成し、必要な完了条件および test strategy が case-run 前に存在することを確認する。
- case-run の正常系テスト
  - 新契約 Issue を入力し、case-run が quality control の適用要否を再判断せず記録済み test strategy を実行することを確認する。
- scope 拡大テスト
  - 実装中に Issue 外の成果物変更、追加 ADR 制約等が必要となるケースで blocked となり、黙示的に Issue scope を拡張しないことを確認する。
- staleness テスト
  - Issue 作成後のファイル消失、件数変化等について、case-run の既存 staleness check が維持されることを確認する。
- 互換性テスト
  - 本変更以前に作成された未更新 Issue が、新契約項目欠落のみを理由として一律停止しないことを確認する。
  - case-update 後の Issue には新契約が適用されることを確認する。
- SSoT テスト
  - case-run が req_draft を参照せず Issue / Epic の情報のみで実行できることを確認する。

## Source Summary

ユーザーとの要件壁打ちにより、`doc-writing` / `skill-authoring` の適用漏れを起点として、現行 `case-run` が Issue 作成時点で確定可能な判断を一部保持している構造を横断確認した。

個別 Skill の適用漏れ修正ではなく、以下を共通原則として扱うことで合意した。

- case-open は Issue 作成時点で確定可能な execution contract を完成させる。
- Issue は case-open 成功後の後続工程に対する SSoT とする。
- case-run は execution contract を新規設計せず、実装、実行時観測、検証を担当する。
- 実装時に契約変更、scope 拡大が必要と判明した場合は blocked / case-update とする。
- artifact-specific quality control は個別例外ではなく共通 routing concern とする。
- 既存 Issue には遡及適用せず、新規または更新 Issue から新契約を適用する。
