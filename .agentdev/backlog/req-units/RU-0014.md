# RU-0014: adversarial-review 強化・原則適用・case-auto 自走統合

## 目的

adversarial-review の独立性、finding 単位の審議状態管理、semantic stagnation / convergence control を強化し、対象ワークフローでは adversarial-review を原則適用する。

同時に、最大自走を目的とする case-auto と adversarial-review を両立させる。req-define を case-auto 開始前の重点的な意味確定フェーズとして扱い、case-auto 実行中に下位 command の adversarial-review が未決事項を検出しても、既に合意済みの正規情報または許容された可逆的内部裁量で解決できる場合はユーザーへ再確認せず自走を継続する。

真に新しいユーザー判断が必要な場合だけユーザーへエスカレーションし、finding の解釈・採否・候補反映は各 caller command に維持することで、case-auto を中央 review engine にしない。

## 対象

- `agentdev-adversarial-review` の review protocol、SPEC、SKILL、reference
- REQ-015 で定義される adversarial-review caller integration の発動方針
- req-define における case-auto 前の重点 review と既存 auto_gate との接続
- case-auto における下位 command 由来 decision の bounded parent decision resolution
- decision_context / parent_decision_required / resume point を用いた下位 command と case-auto 間の判断委譲
- caller command が自身の review finding を解釈・採否・反映する責務の維持
- default-on 導入後の QG / HITL / workflow / delegation contract との整合
- 必要な command / skill / workflow / checker / test の整合更新

## 対象外

- adversarial-review を QG、承認ゲート、恒久統制ゲートへ変更すること
- adversarial-review の全 finding を case-auto に集約すること
- case-auto が raw finding を解釈、採用、棄却、候補へ直接反映すること
- 新しい正規 review artifact または永続 finding schema の導入
- REQ-015 の caller 対象 command 集合そのものの変更
- `manual / recommended / automatic` の別発動モード体系の導入
- case-auto 対象工程へ req-define を追加すること
- case-auto がユーザー合意なしに外部仕様、互換性、データ保持、セキュリティ、対象範囲、受け入れ条件を変更すること
- 特定モデルの組み合わせ、物理 subagent 数、timeout、最大 round 数等の実装固定

## 依存関係

- 本 RU は、現行 adversarial-review caller integration（REQ-014 / REQ-015）が存在することを前提とする。
- RU-0015 の caller 対象集合不整合是正とは論理的に関連するが、本 RU の意味要件は RU-0015 の完了に依存しない。実装・検証時は caller 集合の正を REQ-015 として扱う。
- case-auto の decision resolution は、既存 `decision_context` / `parent_decision_required` / resume point 契約を拡張利用することを前提とし、新規永続結果型を要求しない。
- req-define と case-auto の境界は、req-define が case-auto 対象外であり、case-auto 開始前にユーザー合意を十分に形成できる現行ワークフローを前提とする。

## 要件化の方向

### 1. 独立初期レビュー

- adversarial-review は初期 challenge を複数の独立した論理 review stream で実施できること。
- 初期 challenge 中、各 stream は他 stream が生成した finding を参照しないこと。
- 独立性はモデル差や物理 agent 差ではなく、初期 finding 生成時の相互 finding 非共有によって定義すること。
- 初期 review stream は最低2系統とすること。
- 対象、目的、制約、確定済み review strategy は共有してよいこと。
- 各 stream は共通 strategy に不足を認めた場合、兄弟 stream の finding を見ずに補足観点を追加できること。
- 初期 challenge 後に finding を統合し、duplicate を整理して既存 counter-challenge / convergence へ進むこと。

### 2. finding 単位の構造化状態管理

- 各 finding を個別に識別し、審議状態を追跡できること。
- 少なくとも、主張、evidence、assumptions、scope / applicability、falsification condition、現在状態、直近 disposition、解決根拠、duplicate 関係を意味的に区別できること。
- finding 状態は審議中の一時状態とし、新しい正規 artifact または永続 schema を導入しないこと。
- 具体的 field 名、保存形式、内部データ構造は実装詳細とすること。

### 3. semantic stagnation / convergence control

- 審議の進展を文章表現や単純 round 数ではなく、finding の意味状態の変化で判定すること。
- 新しい substantive finding、撤回、scope 限定、修正、candidate consensus、完了、新 evidence、新 premise、新 falsification condition、duplicate 統合等は意味的進展として扱えること。
- 言い換え、同一 evidence の反復、根拠のない同一 finding 再起票を進展として扱わないこと。
- stagnation 検出時、直ちにユーザーへエスカレーションせず、duplicate 統合、非本質論点終了、追加 evidence 探索、scope 限定等の自律解決を試みること。
- 固定 round 数を REQ / SPEC 上の収束条件にしないこと。timeout や最大 round は実装詳細として設定可能とすること。

### 4. default-on + skip policy

- REQ-015 で定義される adversarial-review caller 対象 command では adversarial-review を原則実行すること。
- ユーザー明示指定を通常発動の必須条件から外すこと。
- review 価値が明確に低い経路では skip を許容すること。
- skip 条件は当該経路の正規所有者で明示的かつ判定可能に定義すること。
- skip 判断のためだけに新しい HITL / 承認点を追加しないこと。
- skip 対象でもユーザーが明示的に adversarial-review を要求した場合は実行すること。
- adversarial-review は QG / HITL の代替にしないこと。

### 5. req-define を case-auto 前の重点 review 地点とする

- req-define は case-auto 対象外の対話的な要件確定フェーズとして adversarial-review を原則実施すること。
- adversarial-review finding を要件候補へ反映し、必要なら壁打ちを再開すること。
- case-auto へ引き渡せる状態では、ユーザー固有の目的、対象範囲、外部契約、重要制約その他 case-auto が新たに決定できない本質的事項を未決のまま残さないこと。
- adversarial-review により本質的未決事項が検出された場合、既存 auto_gate の未解決事項として扱い、別の新規承認ゲートを作らないこと。
- req-define でユーザーと確定した意味を、後続の正規 REQ / ADR / SPEC / Issue へ継承すること。

### 6. 各 caller command の責務

- 各 caller command は自身が所有する候補について adversarial-review を実施すること。
- finding の意味解釈、採否、候補への反映は caller command の責務として維持すること。
- caller command は、自身の責務と利用可能な合意済み情報で解決できない判断事項だけを親へ返すこと。
- case-auto 固有の finding 採否ロジックを各 caller command に重複実装しないこと。

### 7. case-auto の bounded parent decision resolution

- case-auto は adversarial-review を中央集約的に直接実施・解釈する review engine とならないこと。
- 下位 command から raw finding ではなく、解決不能な判断事項を構造化した decision context として受領すること。
- 受領した判断事項について、その時点で有効な REQ、ADR、SPEC、Issue その他の正規な合意済み情報から回答可能か確認すること。
- 既決事項から一意に回答できる場合はユーザーへ再確認せず回答し、下位 command を resume させること。
- 外部仕様、互換性、データ保持、セキュリティ、対象範囲、受け入れ条件等を変更しない可逆的内部詳細は、既存契約で許容された範囲に限り合理的な作業仮定で自走できること。
- 上位合意そのものの欠落、矛盾、曖昧性が finding の対象である場合、その問題のある上位合意を根拠に finding を自動解決しないこと。
- 既存合意または許容内部裁量で解けない新しいユーザー価値判断、対象範囲変更、外部契約変更等が必要な場合のみユーザーへエスカレーションすること。
- case-auto は回答と根拠または作業仮定を下位 command へ返し、既存 resume point から処理を継続すること。
- adversarial-review の再実行要否は adversarial-review 側の再 review 契約に従い、case-auto 独自の再 review 条件を持たないこと。

### 8. 権威関係

- req-define の draft ファイル自体を恒久的な最上位 SSoT としないこと。
- req-define でユーザーと確定した意味を後続正規成果物へ継承し、各時点ではその時点の有効な正規成果物を判断根拠とすること。
- 下位工程は既に確定済みのユーザー判断を理由なく再決定しないこと。
- 一方、確定内容自体の矛盾、欠落、不整合を adversarial-review が発見することを妨げず、その場合は新しい finding として扱うこと。

### 作業仮定

- REQ-015 の caller 対象集合は本 RU では変更しない。
- `decision_context` / `parent_decision_required` / resume point 等の既存概念を利用できる。
- case-auto の parent decision resolution は manager-orchestrator 責務の拡張として配置できる。
- exact schema、物理 agent 構成、モデル構成、timeout、最大 round は実装詳細である。

## 決定的受け入れ条件

- AC-01: 初期 review が最低2論理 stream で実行され、各 stream の初期 finding 生成完了前に兄弟 stream の finding が共有されない。
- AC-02: 複数 stream が同一 substantive finding を生成した場合、統合後に duplicate として一つの審議対象へ整理できる。
- AC-03: 表面的に類似していても failure condition または scope が異なる finding を誤って同一化しない。
- AC-04: finding ごとに撤回、限定、修正、candidate consensus、完了、未解決等の状態遷移を独立して追跡できる。
- AC-05: 同内容の言い換え反復を semantic progress として扱わない。
- AC-06: 新 evidence、scope 変更、premise 変更、falsification condition 変更等を semantic progress として認識できる。
- AC-07: stagnation 時、利用可能な自律解決手段を試さず直ちにユーザー質問へ遷移しない。
- AC-08: REQ-015 caller 対象 command で、ユーザー明示指定がなくても原則 adversarial-review が実行される。
- AC-09: 各経路で明示された skip 条件に該当する場合、adversarial-review を省略して従来フローを継続できる。
- AC-10: skip 対象でユーザーが明示指定した場合、adversarial-review が実行される。
- AC-11: req-define で adversarial-review が本質的未決事項を検出した場合、未解決のまま case-auto へ引き渡さず、壁打ちまたは既存 auto_gate 解決経路へ戻せる。
- AC-12: case-auto 配下の caller command が自身で解決可能な finding を case-auto へ raw finding として転送せず、自身で採否・反映できる。
- AC-13: 下位 command から未決 decision を受領した case-auto が、現行正規成果物から一意に回答可能な場合、ユーザー停止せず回答して resume できる。
- AC-14: 可逆的内部詳細で既存契約内の裁量に収まる場合、case-auto が作業仮定と根拠を明示した上で自走継続できる。
- AC-15: 上位 REQ / ADR / SPEC / Issue 等の矛盾そのものが finding である場合、case-auto が当該矛盾した情報を根拠として一方を勝手に採用しない。
- AC-16: 新しいユーザー価値判断、対象範囲変更、外部契約変更等が必要な場合、case-auto が自動決定せず既存停止経路でユーザーへ返す。
- AC-17: case-auto が decision 解決またはユーザー判断を受けた後、記録済み resume point から再開できる。
- AC-18: adversarial-review が利用不能な場合、その事実を silent skip せず扱い、既存 QG / HITL 契約を破壊しない。
- AC-19: 新しい正規 review artifact または永続 finding schema が生成されない。
- AC-20: default-on 導入後も adversarial-review が QG / HITL の代替または新しい恒久承認ゲートになっていない。
- AC-21: case-auto 固有の finding 採否ロジックが各 caller command へ重複実装されていない。
- AC-22: 通常単体実行と case-auto 配下実行で、各 caller command の review 対象、finding 解釈、採否、反映責務が変化しない。

検証では各 AC を `pass / fail / blocked / not applicable` で個別評価する。少なくとも独立 stream 隔離、duplicate / non-duplicate 統合、finding lifecycle、semantic stagnation、default-on / skip / user override、req-define → auto_gate、case-auto decision resolution、上位合意矛盾時停止、新規ユーザー判断時停止、resume、review 利用不能 fallback、通常実行と case-auto 実行の互換性、新規永続 artifact 非生成、QG / HITL 責務非重複を確認する。

fail が承認済みスコープ内で解決可能な場合のみ修正・再検証し、要件変更、対象範囲拡大、追加設計判断または外部依存解消が必要な場合は blocked として停止する。

## Source Summary

本セッションでは、既存 adversarial-review の blind independent review、finding lifecycle、semantic stagnation control を強化する方針に合意した。

発動方針については、当初検討した `recommended` 層ではなく、adversarial-review を基本適用する `default-on + skip policy` を採用することで合意した。懸念点は default-on 自体ではなく、無条件必須化による QG / HITL との二重統制、低価値経路での過剰コスト、case-run での上流判断再審議、review 機構障害による全体停止であり、明確な skip 条件と責務分界で回避する。

case-auto との関係では、最大自走と adversarial-review の停止要求をそのまま組み合わせるのではなく、req-define を case-auto 前の重点的な対話・意味確定地点とする。req-define で adversarial-review を原則実行して本質的未決事項を解消し、その合意済み意味を後続 REQ / ADR / SPEC / Issue へ継承する。

case-auto 中も各 caller command が自身の責務範囲で adversarial-review を原則実施する。finding の解釈・採否・反映は各 command に残し、解決できない判断事項のみ decision context として case-auto へ返す。case-auto は既決事項または許容された可逆的内部裁量で回答可能なら自走解決し、上位合意そのものの欠落・矛盾や新しいユーザー判断が必要な場合だけユーザーへエスカレーションする。この設計により adversarial-review を case-auto の自走性を落とす機構ではなく、合意済み裁量境界内で継続的に再検証する機構として扱う。
