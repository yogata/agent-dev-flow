# 評価ブランチを用いた実証・評価・正式化ワークフロー

## 目的

方式比較、技術選定、性能評価、AIエージェント方式、アーキテクチャ等について、調査や設計だけでは重要な採否判断を確定できない場合に、正式な `main` へ未確定成果を入れず、評価ブランチ上で構築・実行・測定・評価して知見を得られるようにする。

実証で得た知見は評価ブランチを `main` へ昇格させるのではなく、実証完了後に `req-define <実証Issue>` から最新 `main` に対して改めて正式化する。

## 対象

### 実証Caseの判定

- 実証か否かを `work_type` と別の性質として扱う。
- feature / bugfix / maintenance / docs_chore のいずれでも実証を利用可能とし、`work_type` に `experiment` 等を追加しない。
- `req-define` は、調査・設計だけでは重要な採否判断を確定できず、実行・測定・観察が必要な場合に実証Caseを推奨する。
- 単なる追加調査だけを理由に実証Caseとしない。
- ユーザーが実証を明示している場合は再確認せず実証Caseとして扱う。
- ユーザーが実証を明示していない場合は、`req-define` が実証を推奨する理由を提示し、ユーザーとの壁打ちで実証Caseへの移行を確定する。
- 実証Caseとして確定した後は評価ブランチ利用を別途確認せず、実証Caseなら評価ブランチ、通常Caseなら `main` と決定的に導出する。

### 評価契約

`req-define` は実証開始前に、必要に応じて次を確定する。

- 評価対象・仮説
- 比較対象
- 比較条件
- 評価方法
- 評価観点
- 評価シナリオ
- 測定・観察項目
- 判定基準
- 必要証拠
- 採用条件
- 不採用条件
- 判定不能条件
- 中止条件
- 再実行条件
- 比較条件逸脱時の扱い

評価契約とテスト戦略を分離する。テスト戦略は実証手段・計測手段・実証環境が正常に動作したかを扱い、評価契約は評価対象から得られた結果と採否を扱う。評価対象が採用基準を満たさなかったことを実装不具合として自動修正しない。

### 評価契約の変更

- 実証開始後、実行側の自律判断では評価契約を変更しない。
- ユーザーが評価契約の変更を明示的に指示した場合のみ変更できる。
- 変更時は変更内容、変更理由、既存評価結果への影響を追跡可能にする。
- 変更後の契約に影響する既存評価について、必要な再評価または再実行を行う。
- 変更前の契約と結果を失わず、後から変更履歴を確認できるようにする。
- 実証全体の最終完了後は当該実証の評価契約および最終結果を書き換えない。
- 完了後に異なる条件で評価する場合は新しい実証として扱う。

### 実証開始とdraft引き継ぎ

- `req-define` 自身にはGit副作用を追加しない。
- 実証Case確定後、最初の保存処理より前に当該実証専用の評価ブランチと必要なworktreeを準備する。
- `req-define` が生成したdraftを内容欠落なく評価環境へ引き継ぎ、`req-save` / `spec-save` が継続利用できるようにする。
- 評価ブランチ作成だけの新しい公開コマンドは追加しない。

### 評価ブランチ上の成果物と正式性

評価ブランチ上では通常のADF工程を利用し、REQ、SPEC、Decision、実証コード、評価基盤、評価用データを必要に応じて作成・更新できる。

評価ブランチ上で文書が `status: accepted` 等になっても、それだけで `main` の正式成果物とはみなさない。ADFの正式状態は `main` 上に存在することを含めて判断する。

### ADF制御状態

- 評価ブランチによる隔離によって `main` 側のADFワークフロー状態が巻き戻らないようにする。
- 実証Issue作成・VERIFYが成功したRUは、評価ブランチ削除後に `main` 側で未処理RUとして再出現しないようにする。
- RU消費等のADF制御状態と、評価ブランチ上の一時的な実証内容を分離する。

### 実証状態の永続識別

- 実証Issueに対象評価ブランチを記録する。
- 会話コンテキストが失われてもIssue等の永続情報から、実証Caseであること、対象評価ブランチ、所属する実証単位を復元できるようにする。
- Epic実証ではEpic Issueから共有評価ブランチを特定できるようにする。

### case-open / case-run / case-close

- `case-open` はIssue本文に評価契約と対象評価ブランチを記録する。
- `work_type` と実証の組み合わせごとに専用Issueテンプレートを増殖させず、既存テンプレートへ条件付き評価情報を追加する。
- `case-run` は評価ブランチを作業起点およびPR baseとし、必要な実証手段の準備、実行、測定、観察、証拠生成、評価を行う。コード作成が不要な実証も許容する。
- PRには実際の実行条件、測定結果、観察結果、証拠、評価結果を記録する。
- 各Caseの `case-close` はPRを評価ブランチへsquash mergeする。
- 最終 `case-close` は実行・計測エンジンとして新しい評価を始めず、事前の評価契約と蓄積済み証拠から最終結果を導出する。

### Standard / Epic

- StandardとEpicの双方を初版対象とする。
- 実証のEpic要否をfeature-onlyの現行規模判定に限定しない。
- Standard実証は1実証につき1評価ブランチ、Epic実証は1 Epicにつき1評価ブランチを利用する。
- 異なる実証は別の評価ブランチを利用し、複数実証を同時進行可能とする。
- Epicでは各Waveが同じ評価ブランチを統合状態として継承する。
- 複数Waveの統合状態を実際に動かさなければ評価できない場合、`case-open` は統合状態を実行・測定するChild IssueまたはWaveを計画へ含める。
- 各Childで必要十分な評価が完了する場合は不要な統合評価Waveを強制しない。

### 評価結果

Case実行状態と評価結果を別概念として扱う。

Case実行状態は既存の completed / blocked / failed / delegation-unavailable 等を利用し、評価結果は採用 / 不採用 / 判定不能 / 未確定を区別する。

- completed + 採用
- completed + 不採用
- completed + 判定不能
- blocked / failed + 未確定

`判定不能` は計画どおり評価を完遂したが証拠から採否を区別できない場合に限る。実行失敗、必要データ不足、外部依存失敗は blocked / failed として扱う。

最終結果には必要に応じて結論、選択方式、適用条件、除外条件、根拠を記録する。

### 記録と追跡

- Issue本文を実行前の評価契約の正規記録とする。
- PRを実行条件、測定結果、技術証拠、評価結果の記録とする。
- Issue最終コメントを最終評価結果の正規記録とする。
- 初版では専用評価成果物ファイルを追加しない。
- 評価ブランチ削除後もIssue/PRから必要な結果と証拠を追跡できるようにする。

### mainとの関係

- 評価開始時の `main` commitを固定契約としない。
- `main` が進んだことだけを理由に評価結果を失効させたり再実証を要求したりしない。
- 評価結果がどのような前提・実行状態から得られたかを既存PR/Git証跡等から追跡可能にする。
- 実証中に `main` の変更を取り込むことを一律禁止しない。評価条件へ影響する場合は必要な再評価を行う。
- 正式化時には、評価結果が依存した前提が最新 `main` でも成立するかを改めて確認する。

### 中断・失敗・再開

- blocked / failed / ユーザー中断時に、再開可能な実証は評価ブランチを保持する。
- 保持された評価ブランチとIssueの永続情報から実証を再開できるようにする。
- 実証を明示的に終了・放棄した場合は、必要な記録を残した後に評価ブランチを破棄できる。
- blocked / failed を理由に自動的に評価ブランチを破棄しない。

### 実証完了と正式化

- 実証完了時に評価ブランチを `main` へmergeしない。
- 実証結果・証拠を永続記録してから評価ブランチを削除できる。
- 評価ブランチ上の実装をそのまま正式実装へ昇格しない。
- 最終実証 `case-close` は次の正式化経路として `req-define <実証Issue>` を利用者へ明示する。
- StandardではStandard Issue、EpicではEpic Issueを指定し、Epic中間Waveでは正式化案内を出さない。
- `case-close` は後続 `req-define` を自動実行しない。
- `req-define <実証Issue>` は評価契約、最終評価結果、参照証拠を入力として扱い、最新 `main` に対して知見の適用可能性を再評価したうえでRequirement、SPEC、Decision、Implementation、追加実証の必要性を判断する。

## 対象外

- 実証専用公開コマンド。
- 評価専用の新しい正規成果物。
- 評価ブランチから `main` への直接昇格。
- 実証コードの自動正式化。
- LLM専用評価基盤。
- 任意評価ブランチ同士の依存関係管理。

## 依存関係

- RU-0002: Case統合先の一般化と評価ブランチを利用可能にする基盤。

## 要件化の方向

- `req-define` に実証必要性の推論・提案と評価契約定義を追加する。
- `req-save` / `spec-save` / `case-open` / `case-run` / `case-close` を評価ブランチ上でも既存責務を保ったまま動作させる。
- Issue/PRを実証の永続的な契約・証拠・最終結果の正規記録として利用する。
- 評価ブランチの一時性とADF制御状態の永続性を分離する。

### 作業仮定

以下は公開要件ではない。

- 評価ブランチの命名規則は実装設計で決定する。
- draftの具体的な引き継ぎ方式は実装設計で決定する。
- 評価契約の変更履歴を識別する具体的な形式はIssueの既存履歴・コメント等を優先し、専用の版管理機構を前提としない。
- 評価ブランチから正式実装への通常のcherry-pickは行わないことを原則とする。

## 決定的受け入れ条件

1. `req-define` が実証必要性を推論し、ユーザーが実証を明示していない場合は理由を提示してユーザー合意後に実証Caseを確定する。
2. 実証Case確定後に評価ブランチ利用を再確認しない。
3. 1実証単位につき1評価ブランチが割り当てられ、独立した複数実証を別々の評価ブランチで同時進行できる。
4. `req-define` のdraftを評価環境へ欠落なく引き継ぎ、`req-save` / `spec-save` を継続実行できる。
5. REQ/SPEC/Decisionを評価ブランチ上へ保存でき、それらを `main` の正式成果物と誤認しない。
6. 評価ブランチ削除後も `main` 側のRU消費状態が巻き戻らない。
7. Issueから実証種別、対象評価ブランチ、所属実証単位を復元できる。
8. 評価契約が実証開始前に確定し、実行側が自律変更しない。
9. ユーザー明示指示による評価契約変更が可能で、変更内容、理由、既存結果への影響が記録され、必要な再評価または再実行が行われる。
10. 完了済み実証の評価契約と最終結果が後から書き換えられない。
11. Standard実証が評価ブランチ上で完結する。
12. Epic実証の各Waveが同一評価ブランチを継承し、必要な場合は統合後の状態を実際に実行・測定する。
13. feature以外の実証でも必要に応じてEpicを利用できる。
14. 採用、不採用、判定不能を正常な評価完了として区別でき、blocked / failed を未確定として扱う。
15. blocked / failed / 中断時に再開可能なら評価ブランチが保持され、明示的な終了・放棄時のみ必要な記録後に破棄できる。
16. 評価ブランチを `main` へmergeせず実証を完了できる。
17. 評価ブランチ削除後もIssue/PRから結果と証拠を追跡できる。
18. 最終 `case-close` が `req-define <実証Issue>` を案内し、Epic中間Waveでは案内しない。
19. `req-define <実証Issue>` が最新 `main` に対して評価結果の依存前提と適用可能性を再評価する。

## 検証方法

少なくとも、Standard実証の採用・不採用・判定不能、blocked、failed、中断・再開、明示的放棄、コード変更なし実証、独立した2実証の同時進行、Epic複数Wave、統合評価が必要・不要なEpic、feature以外のEpic実証、ユーザー指示による評価契約変更と再評価、完了後の契約変更要求、評価ブランチ削除後の証拠参照、`main` 側RU状態維持、実証Issueから正式化への引き継ぎを個別に検証する。
