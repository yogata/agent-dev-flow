# RU-0003: ADF決定論的実行中核と構造改善ループ

## 1. 背景

AgentDevFlowでは、CommandからWorkflow Skillへの処理手順移管、STEP単位の再開、Capability Skillの分離、Case実行の並列化などが既に導入されている。

一方、現状では次の責務が十分に統一されていない。

- LLMによる意味判断と、機械的・決定論的に実行可能な処理の境界
- 状態遷移、依存関係判定、並列分岐・合流、再開位置復元をADFと実行基盤のどちらが所有するか
- 全公開処理に共通する実行状態・実行結果
- 中断・再開用のローカル状態とIssue / PR / Caseファイル等の正規状態との関係
- 並列実行における処理単位とworktreeの責務
- 学習を蓄積するだけでなく、ADFの構造改善へ昇華する仕組み

Noodleの設計上の考え方を参考にするが、ADF固有のREQ / Decision / SPEC / Issue / PRを中心とした開発プロセスは維持する。

## 2. 目的

ADFの既存開発プロセスを原則変更せず、処理実行の下位層を次の原則で再構成する。

1. LLMが担う判断と、決定論的に処理できる機械処理を分離する。
2. ADF自身が決定論的な実行中核を持つ。
3. 中断・再開を会話記憶や特定の実行基盤へ依存させない。
4. 処理単位、依存関係、状態遷移を明示し、安全な並列実行を可能にする。
5. 全公開処理に共通する実行結果契約を導入する。
6. 学習を記録で終わらせず、再発防止につながる構造改善候補へ昇華する。

## 3. 要件

### 3.1 判断処理と決定論的処理の分離

- ADFは、意味解釈、要件分析、設計判断、分類、レビュー結果の採否などの判断をLLM側の責務とすること。
- 状態遷移、依存関係評価、形式検査、結果集約など、入力と規則から一意に決定可能な処理を決定論的処理として分離すること。
- 決定論的に処理できる事項を、理由なくLLMの推論だけへ委ねないこと。
- Workflow Skill / Capability Skillは判断または処理手順を所有できるが、決定論的処理は可能な限りテスト可能なscript等へ委譲すること。

### 3.2 ADFが所有する決定論的な実行中核

ADFは少なくとも次の処理を、自身の決定論的な実行中核として所有すること。

- 実行状態の遷移
- 処理単位間の依存関係判定
- 実行可能な処理単位の判定
- 不正な状態遷移の拒否
- 再開位置の再構成
- 並列分岐後の合流可否判定
- 処理結果の集約
- 実行中に守るべき不変条件の検査

次は実行基盤側の責務として維持すること。

- エージェントやモデルの選択
- セッションの起動・終了
- 文脈管理
- バックグラウンド実行の具体的手段
- プロセス監視
- 生存確認
- 実行基盤固有の再試行機構

並列処理について、並列可否、依存関係、合流条件等の意味判断・決定論的判定はADFが所有し、実際の並列起動機構は実行基盤へ委譲すること。

### 3.3 共通実行契約

全公開処理は、処理の複雑さにかかわらず、共通して次を表現できる実行契約を持つこと。

- 実行状態
- 処理固有の結果
- 停止した場合の理由
- 再開可能か否か

実行状態と処理固有の結果を別概念として扱うこと。

「処理自体は完了したが警告あり」と「処理が中断され結果未確定」を区別できること。

既存処理が持つ複数次元の結果を、共通実行状態へ押し潰さないこと。

### 3.4 決定論的な実行中核の適用基準

共通実行契約は全公開処理に適用すること。

ただし、決定論的な実行中核による状態機械制御は、次のいずれかを必要とする処理に限定すること。

- 複数段階からなる
- 中断・再開を必要とする
- 複数の処理単位を持つ
- 並列分岐・合流を持つ
- 処理単位間の依存関係を持つ
- 外部処理の完了待ちを持つ
- 一部成功・一部失敗を扱う

単純な収集処理や読み取り専用診断へ、一律に重い状態機械を導入しないこと。

### 3.5 中断・再開用のローカル状態

中断・再開に必要な一時状態はローカルに永続化すること。

この状態について次を満たすこと。

- Git管理を要求しない。
- 他端末との共有を要求しない。
- 実行履歴としての恒久保存を要求しない。
- 会話コンテキストだけを唯一の情報源にしない。
- 保存場所の具体的なパスは要件として固定しない。
- Issue / PR / Caseファイル等から再構成できる情報を、別の正規状態として重複管理しない。
- 正規成果物へまだ反映されていない、中断・再開に必要な最小情報だけを保持する。
- 正規成果物上で処理単位が終端状態になった後、その処理単位のローカル状態保持を要求しない。

`.agentdev/` のGit管理対象ドメイン状態と、Git管理しないローカル一時実行状態を区別できること。

### 3.6 再開時の正規状態優先

再開時は、ローカル一時状態だけを信用して続行しないこと。

少なくとも次の順序で再開位置を決定すること。

1. ローカル一時状態から再開対象を特定する。
2. Issue / PR / Caseファイル等の正規状態を再取得する。
3. 正規状態から現在位置を再構成する。
4. 既に完了している処理を再実行しない。
5. 未完了部分のみを続行する。

ローカル一時状態と正規状態が矛盾する場合は正規状態を優先し、安全に自動解消できない場合は停止すること。

### 3.7 処理単位を一級概念として扱う

並列実行は「複数エージェントを起動すること」ではなく、独立した処理単位を定義した結果として可能になるものとすること。

処理単位は少なくとも次の意味を持てること。

- 安定した識別子
- 入力
- 出力
- 依存関係
- 所有対象
- 現在状態
- 完了条件
- 検証結果
- 必要な場合のworktreeとの対応

具体的な格納形式はSPECで定義すること。

### 3.8 並列実行とworktree隔離

- 依存関係上独立した処理単位は並列実行可能とすること。
- Git上の変更を伴う並列処理では、処理単位をworktreeで隔離する既存方針を維持すること。
- ADFは、実行可能な処理単位、並列可能性、合流条件、一部失敗時の全体状態遷移を判断すること。
- 実際に起動するエージェント数、起動API、実行基盤固有の並列化手段はADFの正規契約へ固定しないこと。

### 3.9 Workflow Skill / Capability Skillとの責務接続

既存のCommand / Workflow Skill / Capability Skill責務分離を維持すること。

決定論的処理は、その下位または公開能力として接続し、概念上次の責務分離を成立させること。

- Command: 利用者向け入口、公開契約、Workflow Skillへの委譲
- Workflow Skill: 処理手順、分岐、停止条件、処理手順上の状態遷移
- Capability Skill: 複数の処理手順で共通する判断基準・能力
- 決定論的処理: 規則に基づき一意に判定・変換できるテスト可能な処理

Capability Skillが決定論的処理を公開能力として所有することは許容するが、処理順序そのものをCapability Skillへ移さないこと。

### 3.10 学習を構造改善へ昇華する

learning pipelineは学びを保存するだけでなく、再発防止のために「どこへ反映すべきか」を評価すること。

候補には少なくとも次を含めること。

- 既存REQ / Decision / SPECへの反映
- Skillの改善
- 決定論的な検査・ガードレールへの移管
- 既存処理手順の改善
- 通常のIssueによる修正
- 重複・陳腐化した知識の削除
- 現時点では反映不能なものの保留

learning-promoteがこれらを直接変更してはならない。

現行の `learning-promote → backlog-review → RU → req-define` という承認・要件化経路を維持し、構造改善先の分類結果を後続工程へ渡すこと。

### 3.11 実行状態の利用者向け報告

実行状態は利用者から確認できる正式な概念とすること。

ただし、状態確認だけを目的とする専用Commandは今回追加しないこと。

既存処理が、次の場面で共通実行契約に基づく状態を必要な範囲で報告すること。

- 停止したとき
- 中断状態から再開するとき
- 正常終了または異常終了するとき

報告では、実行状態、停止理由、再開可否、処理固有結果を意味的に区別できること。

### 3.12 公開プロセスの維持

今回の変更は原則として内部実行アーキテクチャの再構成とすること。

次を原則維持すること。

- `/agentdev/*` の公開処理体系
- REQ / Decision / SPECの役割
- Issue / PR中心の構造的実行
- 既存のユーザー判断・承認境界
- 標準開発工程
- case-autoが標準工程を置換しないという位置づけ

本RUで明示した共通実行結果と状態報告については外部契約変更を許容する。

その他に外部仕様変更の必要性が判明した場合は、実装側で独自変更せず、追加の設計判断を要求すること。

## 4. 作業仮定

以下は要件ではなく、現時点の作業仮定とする。

- ローカル一時実行状態の物理配置は実装時に決定し、本RUでは固定しない。
- 決定論的な実行中核の実装言語・ライブラリは固定しない。
- 既存scriptやCapability Skillで再利用可能なものは、新しい仕組みを増やすより再利用を優先する。
- 共通実行状態の具体的な列挙値はSPECで確定する。
- 処理単位の具体的な保存形式はSPECで確定する。

- ADF側の決定論的実行中核

## 6. Out of Scope

## 7. 成果物への反映方針

本RUを単一の新REQへ集約せず、既存の責務所有者へ分配することを基本方針とする。

- REQ-005: 共通実行契約、選択的な状態機械適用、再開時の正規状態優先を追記する。
- REQ-006: 処理単位、依存判定、分岐・合流、並列実行、worktree隔離を追記・精製する。

- Decision: ADFが決定論的実行中核を所有し、実行基盤は起動・セッション・プロセス機構を所有するという横断設計判断を新規Decision候補として扱う。
- workflow-contracts SPEC: 共通実行状態、実行結果、状態遷移契約を更新する。
- input-resolution-and-durable-state SPEC: ローカル一時状態、正規状態優先、再開再構成を更新する。

- learning系SPEC: 構造改善先分類を更新する。

既存DEC-010 / DEC-011は置換せず、新しいDecisionから精製・拡張することを基本とする。

## 8. 受け入れ条件

1. 代表的な複雑処理について、LLM判断と決定論的処理が分類され、決定論的処理がLLM推論だけに依存していないこと。
2. 状態遷移、依存判定、実行可能判定、分岐・合流、結果集約をADFが所有し、エージェント起動、セッション、バックグラウンド実行機構を実行基盤が所有すること。
3. 対象となる全公開処理が、実行状態、処理結果、停止理由、再開可否を一貫した意味で扱えること。
4. 状態機械を必要としない収集・診断処理へ不要な再開・並列制御が強制されていないこと。
5. 複雑処理が正常終了した場合、終端状態と処理固有結果が区別して報告されること。
6. 外部依存失敗、処理失敗、ユーザー判断待ち等を正常完了と誤認しないこと。
7. 実行中断後、会話記憶だけに依存せず、ローカル一時状態と正規状態から安全に再開できること。
8. ローカル一時状態とIssue / PR / Caseファイルが矛盾した場合、正規状態を再取得して処理位置を決定すること。
9. 正規成果物から再構成可能な処理完了状態を、別の正規情報源としてローカル一時状態へ保持しないこと。
10. 中断・再開用ローカル状態をGitへcommitしなくても再開機能が成立すること。
11. 独立した複数処理単位がworktreeを分離して同時実行でき、依存先未完了の処理単位は実行可能と判定されないこと。
12. 並列処理の一部が失敗・中断した場合、完了済み処理を未完了へ戻さず、全体の次状態を規則に従って判定できること。
13. 必須処理単位が揃っていない状態で後続処理へ進まないこと。
14. 同じ処理を再実行した場合、Issue / PR / Caseファイル上で既に終端状態の処理単位を重複実行しないこと。
15. learning-promoteが学びについて構造改善先を評価できる一方、直接REQ / Decision / SPEC / Skill / checker等を書き換えず、既存の承認・RU化経路を維持すること。
16. 本RUで明示した実行状態・実行結果報告以外について、既存公開処理、成果物体系、主要ユーザー判断点が維持されること。
17. 実行状態確認だけを目的とした新規公開Commandが追加されていないこと。
18. 実行基盤固有の起動方法やモデル名をADFの正規契約へ固定せず、異なる実行基盤でも同じADF側状態遷移契約を適用できること。

## 9. 検証方法

各受け入れ条件を `pass / fail / blocked / not applicable` で個別評価すること。

最低限、次のシナリオを実行検証すること。

- 単一処理の正常終了
- 中断後の再開
- Issue / PR側だけが先に更新されている状態からの再開
- ローカル一時状態消失時の正規状態からの復元可能範囲
- 不正な状態遷移
- 外部依存取得失敗
- 複数処理単位の並列実行
- 依存先待ち
- 一部処理単位の失敗
- 並列処理の合流
- worktree削除後に、完了済み処理をIssue / PRから認識できること
- learningの構造改善先分類
- 単純な収集・診断処理が過剰な状態機械を要求されないこと
- 実行基盤を変更してもADF側契約が特定の起動APIへ依存しないこと
