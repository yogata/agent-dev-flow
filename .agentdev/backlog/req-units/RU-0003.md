# RU-0003: トレーサビリティのADFワークフロー統合

## 1. 背景

ADF の主ワークフローでは、req-define が要件と変更影響候補を整理し、req-save が要件を保存し、design-save が Design 文書を保存し、case-open が実行契約を Issue へ投影し、case-run が実装を委譲し、case-close が最終受け入れ判定を専任している。

トレーサビリティを有効にするために各工程へ独自判断を追加すると、同じ対応関係を複数工程が再推論し、case-run や case-close の責務が肥大化する。新しい最小 TIM は、既存の責務境界に沿って、対応関係を作成する工程と検査する工程を明確に分離する必要がある。

## 2. 目的

要件と Design 文書・実装成果物・検証手段の対応関係を、既存 ADF ワークフローの責務境界を崩さずに作成・利用・検査できるようにする。

## 3. 要件

### req-define

1. req-define は、既存の明示的な対応関係と `impact` を変更影響候補の確認に利用できること。
2. req-define は、トレーサビリティ情報だけで変更対象、正規所有者、対象範囲を確定しないこと。
3. req-define は、`impact` が空結果であることを「影響なし」の根拠としないこと。
4. req-define は、将来作成される実装成果物または検証手段との対応関係を推測して正規情報として保存しないこと。

### req-save

5. req-save は正式な要件IDの保存を担当し、実装対応または検証対応を作成する責務を持たないこと。
6. 新規要件の保存時点で実装対応または検証対応が存在しないことを理由に req-save を失敗させないこと。

### design-save

7. req-define で Design action と対象要件の対応が明示的に確定している場合、design-save はその情報を利用して Design 文書と要件の対応関係を保存できること。
8. design-save は、Design 本文の自由記述から対象要件を再推論して正規の対応関係を生成しないこと。
9. Design 文書の対応付けが任意であることを維持し、Design action が存在しない要件の処理を妨げないこと。

### case-open

10. case-open は、上流工程で確定した対象要件と実行契約を Issue へ引き継ぐこと。
11. case-open は、req-define と重複して一般的な変更影響探索や依存関係探索を行い、対象範囲を再決定しないこと。

### case-run

12. case-run の実行担当は、実際に要件を実現する成果物へ実装対応を明示すること。
13. case-run の実行担当は、実際に要件を検証する永続的な検証手段へ検証対応を明示すること。
14. 単に変更されたファイルであることを理由に、そのファイルを要件へ自動的に対応付けないこと。
15. 実行担当は PR 作成前に対象要件について `check` を実行し、実装対応、検証対応、対応宣言の整合性を検査すること。
16. `check` の不合格が承認済み対象範囲内で修正可能な場合、実行担当は修正して再検証すること。
17. `check` の不合格を解消するために要件変更、対象範囲拡大、追加設計判断、外部依存解消が必要な場合、実行担当は反復を停止し、blocked として必要な判断事項を報告すること。

### case-close / QG-4

18. case-close は QG-4 の一部として、対象要件の実装対応と検証対応の完全性を正規成果物から独立して再検査すること。
19. 対象要件に実装対応または検証対応の欠落が残る場合、case-close はマージせず停止すること。
20. case-close は不足する対応関係を自動追加または修正しないこと。
21. case-close の検査失敗は case-run 側の修正対象として差し戻せること。

### 検証手段と実行結果の分離

22. TIM は「何が要件を検証するか」という検証手段との対応関係を保持すること。
23. Issue、PR、QG は「今回その検証を実行して合格したか」という実行結果を扱うこと。
24. 特定時点の検証結果を TIM の恒久的な対応関係として保存しないこと。

## 4. 作業仮定

- Design action と要件IDの対応は、既存の draft-data / artifact_actions / operation_units の伝播機構を利用して引き継げる。
- case-run の具体的な `check` 呼出位置は Workflow Skill / adapter の Design で決定する。
- case-close の具体的な QG-4 挿入位置は既存の最終受け入れフローを崩さない範囲で Design で決定する。

## 5. 対象範囲

- req-define の変更影響候補確認
- req-save の責務境界
- design-save の Design 対応保存
- case-open の引き継ぎ責務
- case-run の実装対応・検証対応作成と事前検査
- case-close / QG-4 の最終検査
- 検証手段と検証実行結果の責務分離
- REQ-021 の大幅な再定義

## 6. 対象外

- case-open への新しい対象範囲決定権の追加
- case-run 本体による意味判断の追加
- case-close による自動修正
- 変更ファイルからの対応関係自動推定
- LLM による恒久的な対応関係の自動確定
- 個々の検証結果を TIM へ保存する仕組み

## 7. 受け入れ条件

| ID | 合否判定可能な条件 |
|---|---|
| AC-001 | 新規要件保存直後に実装対応・検証対応が0件でも req-save が正常に完了できること |
| AC-002 | Design action がない要件でも design-save の必須処理により停止しないこと |
| AC-003 | req-define が `impact` の空結果だけを根拠に「影響なし」と確定しないこと |
| AC-004 | case-open がトレーサビリティを利用して対象範囲を再決定しないこと |
| AC-005 | case-run の実行担当が変更ファイル全件を要件へ自動対応付けしないこと |
| AC-006 | case-run の PR 作成前に対象要件の実装対応と検証対応を `check` で確認できること |
| AC-007 | 承認済み対象範囲内で解消可能な対応漏れは修正後に再検証されること |
| AC-008 | 要件変更または対象範囲拡大が必要な対応漏れでは自動補完せず blocked となること |
| AC-009 | case-close が実装対応・検証対応の欠落を独立検査し、欠落時にマージしないこと |
| AC-010 | case-close が対応漏れを自動修正しないこと |
| AC-011 | 検証手段との対応関係と、今回の検証実行結果が別の情報として管理されること |
| AC-012 | 中断後の再実行でも、正規成果物に保存済みの対応関係を再利用し、同じ対応宣言を重複生成しないこと |

## 8. 検証方法

- 正常系: 新規要件 → Design 保存 → case-open → case-run → case-close の一連で対応関係が段階的に成立することを確認する。
- Design なし: Design action がない要件でも case-run まで進めることを確認する。
- 異常系: case-run で実装対応欠落、検証対応欠落を個別に発生させ、不合格と再検証を確認する。
- 範囲外判断: 対応漏れ解消に要件変更が必要なケースで blocked となることを確認する。
- 最終ゲート: case-run 側の検査を意図的に回避した状態でも case-close が独立して欠落を検出し、マージを停止することを確認する。
- 中断・再実行: 対応宣言作成後に処理を中断し、再実行して重複宣言が発生しないことを確認する。
- 検証結果分離: 検証手段との対応は維持しつつ、実行結果だけが PR / QG 側で更新されることを確認する。

検証結果は各受け入れ条件ごとに `pass` / `fail` / `blocked` / `not applicable` で記録する。

## 9. 未決事項

要件化を妨げる未決事項はない。各工程での具体的な呼出位置と内部データ形式は Design で確定する。
