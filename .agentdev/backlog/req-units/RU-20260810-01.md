# RU: Artifact Graph の実ワークフロー活用再構成

本 RU は AgentDevFlow self-hosting において、Artifact Graph が実装済みであるにもかかわらず実ワークフローで十分に活用されていない状態を是正し、Artifact Graph を成果物間の探索・影響分析・構造診断・レビュー証拠探索・変更後検証に実効的に利用できる構造へ再構成する要求を扱う。

## 背景・問題

AgentDevFlow は `agentdev-artifact-graph` を標準 skill として持ち、REQ / ADR / SPEC を中心とする明示的な成果物関係について、Graph の生成、検査、問い合わせ、provenance 取得、verification feedback を提供している。

self-hosting augmentation ではさらに command、skill、integrity_rule、extension、source_file、および `delegates_to`、`governs` を扱える。

一方、現状には次の問題がある。

1. Artifact Graph を利用する既存 Project Extension の一部が、廃止済みの旧 skill 名 `repo-agentdev-artifact-graph` を参照しており、標準 skill への移行と実行時委譲が整合していない。
2. Artifact Graph の利用先が定義されていても、実行エージェントが Graph を主要な候補探索手段として利用せず、従来の glob / grep / rg 等のみで探索を完結する経路が残っている。
3. Artifact Graph の利用責務が `case-run` など実装工程にも広く配置されており、変更対象・必要 skill・検証対象を事前に確定すべき `req-define` / `case-open` との責務境界が弱い。
4. Artifact Graph と特に相性のよい `inspect-docs` / `inspect-skills` の構造診断へ十分統合されていない。
5. 現行の効果検証は Artifact Graph 自身の extension 接続確認に偏っており、実際の要件分析・影響分析・診断における効果を十分に検証していない。

## 目的

Artifact Graph を、単独で問い合わせ可能な補助機能ではなく、AgentDevFlow における次の4用途の共通探索基盤として実効的に利用する。

1. Discovery / Impact
2. Diagnostics
3. Review Evidence
4. Verification

ただし Artifact Graph は派生索引のままとし、正規成果物を代替する SSoT または意味判断エンジンにはしない。

## 要求事項

### R1. Artifact Graph 委譲先の現行標準 skill への統一

Artifact Graph を利用する現行 command / skill / Project Extension は、委譲先を現行標準 skill `agentdev-artifact-graph` へ統一すること。

廃止済み `repo-agentdev-artifact-graph` および superseded となった旧 local Artifact Graph 仕様への実行時依存を残さないこと。

委譲先 skill の不存在を正常な Artifact Graph 利用状態として扱わないこと。

### R2. Discovery / Impact 用途

Artifact Graph を次の工程における関連成果物候補の探索へ利用すること。

- `req-define`
- `spec-save`
- `case-open`
- `backlog-review`

#### req-define

Artifact Graph は少なくとも次の候補探索に利用できること。

- 既存 REQ
- 関連 ADR
- 関連 SPEC
- canonical owner が関連する成果物
- 構造的な所有者重複候補
- downstream の変更影響候補

Graph による候補取得後、正規成果物本文および Graph 以外の探索手段による確認を行ってから最終判断すること。

CREATE / APPEND / UPDATE、SPLIT / MERGE、意味的重複、canonical owner を Graph 単独で確定しないこと。

#### spec-save

Artifact Graph は少なくとも次の候補探索に利用できること。

- 対応 REQ
- 同一または関連 canonical owner を持つ SPEC
- 関連 command
- 関連 skill
- 関連 integrity rule

SPEC の正規配置先、追記先、target_area 等の最終判断権限は既存の SPEC 管理責務へ残すこと。

#### case-open

case-open は Issue の対象範囲、完了条件、test strategy、必要な skill・検証事項を確定する前に、Artifact Graph を変更影響候補の探索へ利用すること。

候補には self-hosting 環境で少なくとも以下を含められること。

- REQ
- ADR
- SPEC
- command
- skill
- extension
- integrity rule
- 関連 source_file

Graph 候補は正規成果物または独立した探索手段で確認した上で、少なくとも次へ分類すること。

- in scope
- verification only
- out of scope

必要な document-writing / skill-writing 等の適用要否、関連 integrity rule、downstream verification 等、case-run の実行方針を左右する事項は、可能な限り case-open 時点で確定し Issue の受け入れ条件または実行条件へ反映すること。

#### backlog-review

backlog-review は promoted artifact 自体を Artifact Graph の正規 node とすることを必須としない。

入力成果物に含まれる REQ / ADR / SPEC / canonical owner 等の明示情報を起点として、既存正規成果物との関係候補を取得できること。

Graph は統合・分割・depends_on の補助 evidence として使用できるが、その判断を Graph 単独で確定しないこと。

### R3. Diagnostics 用途

Artifact Graph を次の診断工程へ利用すること。

- `inspect-docs`
- `inspect-skills`

#### inspect-docs

Artifact Graph は構造的な診断候補として、適用可能な範囲で次を検出できること。

- unresolved reference
- superseded artifact への現行参照
- dangling relation
- provenance 欠落
- orphan candidate
- 不自然な relation path
- structural duplicate candidate

Artifact Graph による構造診断と、`inspect-docs` が行う意味診断を区別すること。

SPLIT / MERGE / MOVE / DUPLICATE / RETIRE / DRIFT 等の意味判断を Graph の構造情報だけから確定しないこと。

#### inspect-skills

self-hosting augmentation が利用可能な場合、Artifact Graph を少なくとも次の構造診断へ利用できること。

- command → skill 関係
- command → extension → skill 関係
- 存在しない skill への委譲
- 不自然または予期しない delegation
- orphan skill candidate

consumer 環境に対応 node type / relation type が存在しない場合、それ自体を異常とせず、従来の診断経路を継続すること。

### R4. Review Evidence 用途

`agentdev-adversarial-review` は Artifact Graph を、レビュー結論の確定ではなくレビュー対象候補・evidence の探索に利用できること。

少なくとも次を論点候補として利用できること。

- 複数の規範的成果物から到達する対象
- 複数経路
- cycle
- relation 集中ノード
- isolated node
- 複数 owner / governing relation を持つ候補

Graph から得た情報は未検証 evidence として扱い、Reviewer / Reviewee の対論または正規成果物確認を経ずに finding を確定しないこと。

### R5. Verification 用途

`case-close` は Artifact Graph を変更後の関係整合性検証へ利用できること。

少なくとも次を確認可能とすること。

- Graph の生成・鮮度
- Graph integrity
- unresolved relation
- dangling relation
- provenance defect
- Graph と独立確認結果との差異

Graph defect と canonical defect を区別すること。

Graph 自体の生成・問い合わせ失敗のみを理由に case-close を失敗させないこと。

正規成果物側の実不整合が確認された場合は、既存の品質ゲート・受け入れ条件に従って fail とすること。

### R6. case-run の Artifact Graph 責務縮小

`case-run` を Artifact Graph による主要な変更影響決定工程としないこと。

case-run での Artifact Graph 利用は、少なくとも次の補助用途に限定すること。

- Issue に記録された対象から予期しない依存・参照が見つかった場合の補助探索
- acceptance criteria の検証根拠への到達
- case-open 時点からの関係差異確認

case-run は Graph の探索結果だけを根拠として、次を行わないこと。

- Issue scope の自律拡大
- 新しい artifact action の追加
- 新たな必須 skill の決定
- Issue に存在しない新規要件の実装

case-open の前提を変更する必要が生じた場合は、既存の finding / case-update 等の上位経路へ戻すこと。

### R7. Artifact Graph の判断防護

すべての consumer で以下を共通原則とすること。

- Graph は派生索引であり SSoT ではない。
- Graph の結果から変更対象、要件充足、責務重複を単独で確定しない。
- Graph 取得結果の根拠となる canonical source を確認可能であること。
- 必要に応じて rg、filesystem scan 等の独立手段で補完・反証すること。
- Graph 不在を「関連なし」「影響なし」の根拠にしない。
- 意味的類似・意味的責務重複を Graph の明示関係と同一視しない。

### R8. Fail-open と互換性

Artifact Graph が次の状態であっても、Artifact Graph が既存 workflow の必須成立条件でない経路では従来手段へ fallback できること。

- missing
- stale
- invalid
- regeneration failure
- consumer に対象 node / relation が存在しない

Artifact Graph 導入によって、Artifact Graph を使用しない既存 consumer または ADF 正規成果物モデルを採用しない consumer の正常動作を壊さないこと。

### R9. 効果検証の二層化

Artifact Graph の検証を少なくとも次の2種類へ分離すること。

#### Parser / Graph regression

Graph parser、augmentation、relation extraction、provenance 等の正確性を検証する。

既存 extension 構造等を用いた代表 fixture はこの目的で維持してよい。

#### Workflow effectiveness

実際の AgentDevFlow workflow で発生する質問を対象とする。

例:

- REQ の変更影響候補
- 同一 owner の SPEC
- 関連 command / skill / integrity rule
- command から実際に委譲される skill
- superseded artifact への現行参照
- 変更後の dangling relation

少なくとも次の観点で Graph 利用時と独立探索時を比較できること。

- 必要候補の recall
- false candidate
- canonical source 到達可否
- Graph-only miss
- independent-search-only miss
- 探索操作量

Artifact Graph 自身の接続確認だけを workflow effectiveness の成立根拠としないこと。

## 作業仮定

以下は本 RU の要件ではなく、要件定義・実装を進める際の作業仮定とする。

1. `agentdev-artifact-graph` の標準コア、augmentation、`prepare_graph`、`check_graph`、`query_graph`、`verify_graph` の現行基本モデルは維持する。
2. self-hosting 固有情報は `.agentdev/artifact-graph.yaml` による augmentation で扱う。
3. Artifact Graph の query API を全面的に再設計することは本 RU の成立条件ではない。
4. consumer 追加は Project Extension または既存 command / skill 責務境界に沿って実装する。

- `agentdev-artifact-graph`
- Artifact Graph の self-hosting augmentation
- `req-define`

- intake / learning / promoted artifact の新規 node type 化
- case-run への新しい scope 決定権付与
- Artifact Graph を利用しないプロジェクトへの強制適用

## 受け入れ条件

### AC-001: 旧委譲先除去

現行の実行経路および Project Extension に、廃止済み `repo-agentdev-artifact-graph` を実行時委譲先とする参照が存在しないこと。

### AC-002: 現行 Artifact Graph 利用成立

Artifact Graph を利用する consumer が、現行標準 skill `agentdev-artifact-graph` を通じて Graph の準備・問い合わせ・検証を実行できること。

### AC-003: req-define 候補探索

req-define が Artifact Graph を既存 REQ / ADR / SPEC / owner / 影響候補の探索に利用でき、Graph 単独で CREATE / APPEND / SPLIT / MERGE / semantic duplicate を確定しないこと。

### AC-004: case-open 事前 impact analysis

case-open が Issue scope・acceptance criteria・test strategy の確定前に Artifact Graph による変更影響候補を評価できること。

### AC-005: case-run scope 防護

case-run が Artifact Graph の結果だけを根拠として Issue scope または artifact action を拡大しないこと。

### AC-006: inspect-docs 構造診断

inspect-docs が Graph 由来の構造 finding と意味診断結果を区別できること。

### AC-007: inspect-skills delegation 診断

self-hosting 環境において、command → extension → skill の委譲関係および存在しない委譲先 skill を診断できること。

### AC-008: adversarial-review evidence 境界

adversarial-review が Artifact Graph の結果を未検証 evidence として利用し、Graph の結果だけで finding を確定しないこと。

### AC-009: case-close 変更後検証

case-close が変更後の Graph integrity、未解決関係、dangling relation、provenance 等を確認できること。

### AC-010: defect 分類

Artifact Graph と独立確認結果に差異がある場合、少なくとも Graph 側の欠陥と canonical source 側の欠陥を区別して扱えること。

### AC-011: fail-open

Graph が missing / stale / invalid / regeneration failure のいずれかでも、Graph failure 自体を停止条件としない consumer では代替探索へ移行できること。

### AC-012: consumer 互換性

Artifact Graph 対象成果物を持たない consumer、または self-hosting 固有 node type / relation type を持たない consumer が異常終了しないこと。

### AC-013: parser regression 分離

Graph parser / extraction / augmentation の回帰検証が workflow effectiveness 検証と独立して実行・判定できること。

### AC-014: workflow effectiveness

実運用を代表する変更影響・依存・参照・検証質問について、Graph と独立探索結果を比較でき、必要候補の見逃しおよび誤候補を判定できること。

### AC-015: canonical verification

Graph により変更対象・関連成果物候補を取得する workflow では、最終判断前に canonical source または独立した確認手段による検証が行われること。

## 検証方法

| 対象 | 検証 | 合格条件 |
|---|---|---|
| AC-001 | repository 全体の旧 skill 名参照検索 | 現行実行時参照 0 件 |
| AC-002 | Graph build / prepare / query の consumer 経路テスト | 現行 skill 経由で成功 |
| AC-003 | req-define targeted test | Graph 候補利用と意味判断境界を確認 |
| AC-004 | case-open targeted test | Issue 作成前に impact 候補が評価される |
| AC-005 | case-run scope expansion negative test | Graph のみを根拠とした scope 拡大が発生しない |
| AC-006 | inspect-docs fixture | structural / semantic finding を区別 |
| AC-007 | 存在・不存在 skill を含む extension fixture | 不存在委譲先を検出 |
| AC-008 | adversarial-review test | Graph evidence が未検証候補として処理される |
| AC-009 | change 後 Graph check / verify | 関係不整合を観測可能 |
| AC-010 | graph defect / canonical defect fixture | 原因分類が一致 |
| AC-011 | missing / stale / invalid / regeneration failure test | fallback して workflow 継続 |
| AC-012 | consumer fixture | Graph 空状態・self-hosting augmentation 不在が正常 |
| AC-013 | parser regression suite | workflow test と独立して合否判定可能 |
| AC-014 | representative workflow query suite | recall / false candidate / miss を比較可能 |
| AC-015 | consumer integration test | Graph-only の最終確定経路が存在しない |

検証結果は各受け入れ条件について `pass` / `fail` / `blocked` / `not applicable` のいずれかで報告する。

`fail` は承認済みスコープ内で解決可能な場合のみ修正・再検証する。要件変更、対象範囲拡大、追加設計判断、外部依存解消が必要な場合は反復を停止し、必要な判断事項を報告する。

未検証、`blocked`、`fail` が残る状態を完了としない。
