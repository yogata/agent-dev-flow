# ADF本体版タグのGitHub Release記録対応

## 目的

ADF本体の版タグそれぞれにGitHub Releaseを対応させ、記録が抜けることと、やり直し時に同じ記録を二つ作ることを防ぐ。

## 対象

- `yogata/agent-dev-flow` 本体で確認したSemVer版タグ37件と、今後 `STEP-11: stage 7: リリース` が作る正式な版タグ。
- 37件には `v4.0.0-rc.1` と `v4.0.0-rc.2` を含む。RCにもRelease草稿を作り、GitHubの `prerelease` を有効にする。版の基準からRCを除くDEC-059の規則は変えない。
- Releaseがない33件の草稿を作る作業を、今回だけ行う既存タグの補完に含める。
- 対象はADF本体に限り、ADFを使う他のプロジェクトには一律に適用しない。

## 対象外

草稿を自動で公開すること、既存タグを動かす・作り直すこと、版の番号付け規則を変えること、すでにある4件のRelease本文や公開の有無を変えること、新しいリリースノート形式、常に動く監視。

## 正規所有者とアンカー

`REQ-114-010`、承認された `DEC-059` の「公開操作」「タグ権威・不移動」、backlog-auto の `STEP-11: stage 7: リリース` と「公開操作の実行経路」。DEC-059の意味を変える場合は、Decision文書を直接書き換えず、Decisionのライフサイクルに従う。

## 依存関係

他のRUの成果を待つ作業はない。タグを動かさないDEC-039の規則と、REQ-102のGit送信方法を維持する。

## 要件化の方向

ADF本体の版タグごとに、タグ名が一致するGitHub Releaseを一件だけ対応させる。stage 7はタグをリモートへ送った後、現在あるすべての版タグを確認し、対応するReleaseがないものに草稿を作る。すでにある草稿・公開Releaseはそのまま使い、公開の有無と本文を変えない。GitHubから読み戻してタグとの対応を確かめるまでRelease工程を完了としない。草稿を作る操作はADF本体で選んだ方式に含め、公開は別にユーザーが明確に認めない限り行わない。GitHubへの書き込みはADFが認めた経路だけを使い、直接 `gh release create` を実行して現在の制限を迂回しない。草稿を作り、結果を読み戻す操作がまだない場合は、既存の経路に必要な機能だけを加える。`REQ-114-010` で要件を満たせるなら重複する要件を作らず、必要なDecisionとDesignを更新する。

## 決定的受け入れ条件

1. 既存タグを補った後、37件すべてに同名のGitHub Releaseが一件ずつある。すでにある4件は変えず、足りない33件だけ草稿を作る。
2. `v2.9.0`、`v3.2.0`、`v3.3.0` はGitHubにタグがない。注釈のある元のタグを通常の `git push` で送り、`--force` は使わず作り直さない。送った後、リモートのタグ識別子がローカルと一致することを確かめてから草稿を作る。
3. `v4.0.0-rc.1` と `v4.0.0-rc.2` は草稿かつプレリリースとして記録する。すでに公開されている3件と `v5.1.2` の草稿は、公開の有無・本文を変えない。
4. 今後の `STEP-11: stage 7: リリース` は、タグとReleaseの対応を読み戻してから完了する。草稿作成に失敗した場合はタグを動かさず、Releaseがないため工程を完了できないと報告して停止する。やり直しても既存タグ・Releaseを使い、同じReleaseを二つ作らない。
5. どの工程も草稿を自動で公開しない。公開はユーザーが別に明確に認めた後に限る。
