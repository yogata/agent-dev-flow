# RU-0032: REQ 行追加を伴う Definition 生成時の verification-scope-catalog 追随工程の規定

## Sources

- **REQ 行追加時のカタログ追随工程の不在（Case #2822〜#2858 バッチ、Issue #2867 / #2870 関連）**: case-ready STEP-6 検証ゲートで、直前に merge した Definition PR の新規 REQ 行 36 行（REQ-057-026..029・REQ-036-027・REQ-047-010・REQ-010-077・REQ-021-026/027・REQ-031-029/030・REQ-082-001..025）が verification-scope-catalog 未登録で verificationClassification: unclassified となり、対象 10 Case が ready 保留した（36 行は Issue #2867 で解消済み。本要件は再発防止の工程規定が対象）。REQ 行追加を伴う Definition Package 生成時にカタログへのエントリ追加（または追随）を Definition に含める工程規定が存在しない。現行 case-open は未分類行の残存を許容し、#2870 で追加された横断依存検査ゲートは同一パス重複・共有領域未登録行の重複需要は検出するが「カタログ更新の不在」そのものを検出しない。case-ready での unclassified 検出時に case-open へ差し戻す経路も規定されていない（fix gap / application miss）。

## Source Summary

REQ 行追加と verification-scope-catalog 分類の追随を工程として接続し、REQ 行追加を伴うバッチ投入で case-ready STEP-6 の ready 保留が反復しないようにする。分類機能・最終ゲート・事後棚卸し手順は既存であり、欠落しているのは工程接続（前置・検出・差し戻し）である。

## 統合理由

1:1。単一成果物・単一論点（追随の工程規定）であり、統合・分割不要。

## 要件化の方向

work_type: maintenance。次の予防策のいずれか（または組み合わせ）を選択する（実現方法の選択は req-define の変更影響分析に委譲）:

1. case-open（および req-define）の工程へ検証対応要否分類ゲートを明示する（REQ 行追加時は verification-scope-catalog 更新を Definition Package に含める）
2. case-ready STEP-2 の canonical 再取得時に traceability check を機械実行し、unclassified 検出時に case-open へ差し戻す経路を明記する
3. REQ 移動・分割時にカタログの範囲表現追随を Definition 変更の必須構成とする

制約: 検証対応要否の最終ゲートの case-ready 所有（case-open SKILL の現行明記）を前提とし、本要件は追随の工程接続に留める。カタログ編集は実変更（main 直接変更を伴う）であるため Definition PR 経由以外の適用経路を取らない。traceability check の unclassified と missing-verification は同一行集合の単一導出である（計上仕様を変更しない）。対象 36 行の分類確定自体は対象外（Issue #2867 で解消済み）。

受け入れ条件: REQ 行追加を伴う Definition 生成時、カタログ追随の要否が工程上明示されること（Definition 構成への包含または上位工程での明示）、case-ready で unclassified を検出した際の差し戻しまたは保留の経路が reference に明記されていること、バッチ投入で新規 REQ 行の unclassified による ready 保留が構造的に防止または早期検出されること。
