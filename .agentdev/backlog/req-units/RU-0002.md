# RU-0002: adversarial-review の成立条件・重要指摘モデル強化

## 1. 背景

`agentdev-adversarial-review` は、レビューアー、レビュイー、オーケストレータの3論理役割による対論型レビューとして、レビュー戦略の構成、独立した初期レビュー、相互反証、収束、収束後再検証を行う。

現行方式では、レビュー対象を正しいと仮定せず破綻条件、欠落、矛盾、不成立な前提等を探索し、レビューアーの指摘も未確定の主張としてレビュイーが反証する構造を既に持つ。また、問題発見そのものを成功条件とせず、固定された反復回数も収束条件としていない。

一方、レビューアーに欠陥探索を強く求めるだけでは、実際には問題のない対象についても指摘を作り続ける危険がある。対論型レビューの目的は指摘件数を増やすことではなく、対象が妥当であるための条件を明確化し、その条件に対する反証を通じて、判断に影響する重要な問題を解消することである。

## 2. 目的

対論型レビューの既存構造を維持したまま、レビュー判定モデルを次の流れとして明確化する。

レビュー論点
→ 成立条件
→ 反証
→ 指摘
→ 重要性の判定
→ 重要指摘
→ 相互反証、統合、限定
→ 本質的争点
→ 解消
→ 収束後再検証

これにより、無差別な欠陥探索ではなく、成立条件に対する反証と重要指摘の解消を中心としたレビューとする。

## 3. 用語

### 3.1 レビュー論点

何について対象の妥当性を確認するかを示す審議上の観点。

### 3.2 成立条件

そのレビュー論点について、対象を妥当と判断するために成立すべき条件。

### 3.3 指摘

レビューアーが提示する、根拠、前提、適用範囲、反証条件を伴う未確定の主張。

### 3.4 重要性

指摘の採否が、対象の妥当性、要求充足、設計判断、採否または受け入れ判定へ影響する性質。

### 3.5 重要指摘

採否によって、対象の妥当性、要求充足、設計判断、採否または受け入れ判定が変わり得る指摘。

### 3.6 本質的争点

一つ以上の重要指摘を、相互反証するための意味単位へ整理したもの。

### 3.7 解消

指摘が採用、撤回、棄却、限定、またはユーザー判断によって未決状態でなくなったこと。

## 4. 要件

### 4.1 レビュー論点と成立条件

- 対論型レビューは、評価開始時にレビュー論点を設定すること。
- 各レビュー論点について、その論点で対象を妥当と判断するために成立すべき条件を導出すること。
- 成立条件は固定チェックリストではなく、対象、目的、制約、正規成果物、技術領域、想定される破綻に応じて動的に構成すること。
- レビュー中に新しい根拠または問題が発見された場合、レビュー論点および成立条件を追加、削除、修正できること。
- レビュー論点と成立条件を同一概念として扱わないこと。

### 4.2 反証を中心としたレビュー

- レビューアーは、一定数の問題を発見することを目的としてはならない。
- レビューアーは、設定された成立条件が成立しない具体的な条件、根拠、矛盾、欠落、不成立な前提等を探索し、反証を試みること。
- 十分な反証を試みても問題を確認できなかった場合、それを正常なレビュー結果として扱うこと。
- 初期の成立条件では捉えられない重要な問題を発見した場合、新しいレビュー論点または成立条件を追加して審議対象とできること。

### 4.3 指摘

- 指摘は、レビューアーが提示する未確定の主張として扱うこと。
- 指摘は少なくとも、主張、根拠、前提、適用範囲、反証条件を意味的に区別して扱えること。
- レビュイーは指摘を正しいものとして自動的に採用せず、根拠、前提、対象理解、適用範囲、影響、方法論を反証できること。
- レビューアーはレビュイーの反証を再評価し、自身の指摘を撤回、維持、限定、修正または部分的に採用できること。

### 4.4 重要性と重要指摘

- 各指摘について重要性を判定すること。
- 採否によって対象の妥当性、要求充足、設計判断、採否または受け入れ判定が変わり得る指摘を重要指摘とすること。
- 重要性と重大度を同一概念として扱わないこと。
- 好み、表現改善、対象の妥当性に影響しない軽微な改善、対象範囲外の理想論、具体的影響を示せない抽象的懸念は、原則として重要指摘としないこと。
- 重要性の有無についても、レビューアーとレビュイーの相互反証対象とすること。

### 4.5 指摘と本質的争点の関係

- 指摘と本質的争点を別概念として扱うこと。
- 一つ以上の重要指摘を、相互反証するための意味単位へ整理したものを本質的争点として扱うこと。
- 複数のレビュー系統またはレビューアーが同じ問題を別々に指摘した場合、重複を統合して一つの本質的争点として扱えること。
- 同一指摘の件数を、その指摘の妥当性または重要性の強さとして扱わないこと。

### 4.6 収束条件

- 固定された反復回数をレビューの収束条件としてはならない。
- 未解決の重要指摘が存在しないことを、レビュー完了の中心条件とすること。
- 重要指摘は、少なくとも次のいずれかによって解消できること。
  - 指摘を採用し、対象案へ必要な修正を反映した。
  - 反証が成立し、指摘を撤回または棄却した。
  - 適用範囲を限定し、限定された範囲で結論を確定した。
  - 自律解決できない事項についてユーザー判断を得て解決した。
- 重要でない指摘だけが残っていることを理由として対論を継続しないこと。
- 重要指摘が一件も発生しないことを正常なレビュー結果として許容すること。

### 4.7 収束後再検証

- 重要指摘が解消され収束候補が形成された後、最終案とその成立根拠を再検証すること。
- 収束後再検証では少なくとも次を確認すること。
  - 各成立条件が引き続き成立している。
  - 採用した指摘への対応によって別の成立条件が破壊されていない。
  - 新たな重要指摘が発生していない。
- 新たな重要指摘が確認された場合、その争点について対論を再開すること。

### 4.8 レビューアーの判断独立性

- レビューアーは、対象を作成した側の自己評価、正当性の主張、未検証の前提または結論を、それ自体を理由として正しいものと扱わないこと。
- 対象作成者が提示した設計理由、判断理由、前提等は必要に応じて参照できるが、検証対象として扱うこと。
- レビューアーの判断独立性を確保するために、別のモデルまたは別の物理エージェントを必須としてはならない。
- 既存の初期2系統の独立レビューにおける、初期指摘生成前の相互指摘非共有による独立性を維持すること。

### 4.9 ユーザー判断

- 関連する正規成果物および取得可能な根拠から自律解決できる限り、レビューアーとレビュイーの審議を継続すること。
- 単なる意見不一致を理由としてユーザーへ判断を返さないこと。
- 技術的に一意に決着できない優先判断、ユーザー固有の価値判断、両立不能な要求、新たな対象範囲判断、必要情報不足等、自律解決できない事項のみユーザー判断へ付議すること。
- ユーザー回答後は、その判断の影響を受ける争点から審議を再開し、必要な再検証を行うこと。
- 対論型レビューにおけるユーザー判断への返却を、組織上の上位者へのエスカレーションとは区別すること。

### 4.10 呼出元との責務分界

- 成立条件の導出、指摘の重要性判定、本質的争点への整理、収束判定は対論型レビュー側が所有すること。
- `case-open`、`case-run`、`req-define`、`inspect-promote`、`intake-promote`、`learning-promote`、`backlog-review` 等の呼出元に、これらの判定ロジックを重複定義しないこと。
- 呼出元は対論型レビューの結果を受領し、既存契約に従って採用済み指摘の反映、未解決事項の伝播、後続処理判断を行うこと。
- 既存の原則実行・スキップ可能という位置付け、QG・HITL非代替、副作用境界を変更しないこと。

## 5. 作業仮定

- 内部的なフィールド名、状態保持形式、プロンプトの分割方法は、利用者から見える振る舞いおよび正規契約を変更しない範囲で実装側が決定できる。
- 別モデル、別物理エージェント、並列数、タイムアウト、最大反復回数は実装詳細とし、本要件では固定しない。
- 既存のレビューアー、レビュイー、オーケストレータの3論理役割、および現行の対論状態遷移は維持する。

4. 指摘件数をレビュー成功条件としていない。

10. レビュイーの反証によって誤った指摘を撤回できる。
11. 指摘の適用範囲を限定して解消できる。
12. 重要でない指摘だけを理由に審議を継続しない。
13. 未解決の重要指摘が存在しないことを収束条件の中心としている。
14. 固定された反復回数を収束条件としていない。
15. 重要指摘が0件でも正常完了できる。
16. 収束後再検証で成立条件を再確認する。
17. 修正によって別の成立条件が破壊された場合、新しい重要指摘として審議を再開できる。
18. レビューアーが対象作成者の自己評価を正当性の根拠として扱わない。

22. ユーザー判断が必要な争点だけをユーザー判断へ付議できる。
23. 呼出元へ成立条件導出、重要性判定、収束判定のロジックが重複していない。
24. 新しいレビュー結果用正規成果物または永続スキーマを導入していない。
25. 既存のQG・HITL・副作用境界を変更していない。

## 9. 検証方法

以下のシナリオを用いて、各受け入れ条件を個別に検証する。

- 問題が存在しない対象をレビューし、重要指摘0件で正常完了できること。
- 実際に要求充足へ影響する問題を含む対象をレビューし、重要指摘として扱えること。
- 好みまたは軽微な改善だけを提示した場合、重要指摘として扱わず審議を不要に継続しないこと。
- レビューアーが誤った指摘を提示した場合、レビュイーの反証によって撤回できること。
- 一部条件下のみ成立する指摘について、適用範囲を限定して解消できること。
- 独立した複数レビュー系統が同一問題を別表現で指摘した場合、一つの本質的争点へ統合できること。
- 初期レビュー論点に含まれない重要な破綻を途中で発見した場合、新しいレビュー論点または成立条件を追加できること。
- 指摘への修正対応によって別の成立条件を破壊した場合、収束後再検証で検出し審議を再開できること。
- 正規成果物から一意に解決できる争点について、ユーザー判断へ付議せず自律解決できること。
- 新しい価値判断等が必要な争点についてのみ、ユーザー判断へ付議できること。
- 対論型レビューを呼び出す各経路について、判定ロジックが呼出元へ重複していないこと。
- 新しい正規成果物、永続スキーマ、QG、HITL、承認ゲートが追加されていないこと。

検証結果は各項目について `pass` / `fail` / `blocked` / `not applicable` のいずれかで整理する。

`fail` は承認済み対象範囲内で解決できる場合のみ修正して再検証する。要件変更、対象範囲拡大、新たな設計判断、外部依存の解消が必要な場合は反復を停止し、その理由と必要な判断事項を報告する。
