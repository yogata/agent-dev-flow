# ADFブランチモデルとCase統合先の一般化

## 目的

ADFが暗黙に前提としてきた「Caseの統合先は常に `main`」という制約を見直し、正式状態の正規ブランチである `main` を維持しながら、必要な場合に一時的な評価ブランチをCaseの統合先として利用できるようにする。

評価ブランチは新しいGitサブシステムとして導入せず、既存Caseの統合先を `main` 固定から一般化することで実現する。

## 対象

### ブランチモデル

- `main` は1本のみとし、正式状態の唯一の正規ブランチとする。
- 評価ブランチは必要な場合のみ作成し、同時に0本以上存在できる。
- 原則として1つの実証単位につき1つの評価ブランチを割り当てる。
- Standard実証では当該実証が1つの評価ブランチを利用する。
- Epic実証ではEpic全体が1つの評価ブランチを共有する。
- 異なる実証単位が同一の評価ブランチを共有しない。
- 評価ブランチ同士を通常の依存・派生関係として扱わない。
- 先行実証の未正式成果を前提に後続実証が必要な場合は、同一Epic/Waveとして扱うか、先行実証を正式化した後に別実証として開始する。

### Case統合先の一般化

現在の `統合先 = main` という固定前提を、`統合先 = Caseに割り当てられた統合先`、既定値 `main` へ一般化する。

少なくとも次を同じ統合先基準へ一般化する。

- worktreeの作成元
- PRのbase
- rebase・同期基準
- 鮮度確認
- `case-close` のsquash merge先
- Epic後続Waveの作業起点

通常Caseでは既定統合先を `main` とし、評価を利用しない既存Standard / Epic Caseの利用者向け操作と挙動を維持する。

### case-close

- `case-close` の公開コマンドを維持する。
- マージ処理を新しい公開コマンドへ分離しない。
- QG-4は引き続きIssue完了条件の最終判定とする。
- QG-4合格後、Caseに割り当てられた統合先へsquash mergeする。
- Case完了と `main` への反映を同一概念として扱わない。

### 評価ブランチの位置づけ

- 評価ブランチを正規成果物としない。
- 評価ブランチ専用の公開Gitコマンド体系を追加しない。
- 評価ブランチの作成・削除には既存Git/worktree能力を再利用する。
- 初版で許容する統合先の種類は `main` と評価ブランチに限定する。
- release branch等の一般的な複数ブランチ運用へ先回りして拡張しない。

## 対象外

- 実証を行うかの判断。
- 評価契約、評価結果、実証Issueの意味契約。
- `case-auto` の実証対応。
- release branch等の汎用的な複数ブランチ運用。
- 任意のGit branchを利用者が自由に統合先へ指定する機能。

## 依存関係

別RUへの依存はない。

本RUは、後続の実証・評価ワークフローが利用するブランチ基盤を先に成立させる。

## 要件化の方向

- Caseの統合先を表す共通概念を導入し、既定値を `main` とする。
- `agentdev-git-worktree`、`case-run`、`case-close`、Epic/Waveの `main` 固定処理を必要最小限の範囲で統合先基準へ変更する。
- 通常Caseの外部仕様を変えず、評価ブランチを第一級成果物や独立したGit管理機構にしない。

### 作業仮定

以下は公開要件ではない。

- 統合先を表現する内部フィールド名は実装設計で決定する。
- 評価ブランチの命名規則は実装設計で決定する。
- 評価ブランチの具体的な作成・削除担当Skillは既存責務との整合を見て決定する。

## 決定的受け入れ条件

1. `main` が正式状態の唯一の正規ブランチとして維持される。
2. 通常Standard Caseが従来どおり `main` へsquash mergeされる。
3. 通常Epic Caseが従来どおり `main` を介してWaveを進められる。
4. Caseの統合先を `main` 以外の評価ブランチへ設定できる。
5. worktree、PR base、rebase・同期、鮮度確認、`case-close` のmerge先、Epic後続Waveの起点が同一の統合先を参照する。
6. 複数の異なる評価ブランチを同時に扱ってもCase状態や統合先が混在しない。
7. 評価ブランチ利用のための新しい公開Gitコマンドが追加されていない。
8. QG-4の意味が変更されていない。
9. `main` 以外を統合先にしてCaseを完了しても、それを `main` 反映済みとは扱わない。

## 検証方法

- 通常Standard Caseでworktree起点、PR base、merge先が従来どおり `main` であることを確認する。
- 通常Epic Caseで後続Waveが従来どおり `main` 上の前Wave成果を参照できることを確認する。
- 評価ブランチを統合先とするCaseで、worktree起点、PR base、同期基準、merge先が評価ブランチへ一貫して切り替わることを確認する。
- 異なる評価ブランチを利用する複数Caseを並行実行し、相互に状態が混在しないことを確認する。
