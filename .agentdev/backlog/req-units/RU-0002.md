# RU-0002: ADF 課題管理機構の導入

## 1. 目的

ADF へ、一般的なシステム開発で用いられる課題管理の仕組みを導入する。

要件定義、方式設計、HLD、LLD、パラメータ設計、実装、レビュー、検証、外部確認等で生じた未解決事項を、発生から検討、保留、解決、正規成果物への反映確認まで継続して追跡できるようにする。

課題管理は、Intake / Learning 等の AI 駆動開発におけるループエンジニアリングとは別系統として扱う。

## 2. 基本原則

### 2.1 課題の対象

システム開発中に課題として認識された未解決事項を原則として対象とする。

対象を設計判断だけ、実装課題だけ、特定の成果物粒度だけに限定しない。

課題の解決結果は、内容に応じて例えば以下のいずれにもなり得る。

- Decision。
- REQ。
- HLD。
- LLD。
- その他の Design。
- パラメータ設計。
- RU。
- 実装。
- 検証方法。
- 対応不要という結論。

課題起票時点で反映先を決め打ちしないこと。

### 2.2 他成果物との境界

課題管理は「まだ解決していない問い、問題、確認事項、判断待ち事項」を管理する。

Decision は、課題を解決した結果のうち、将来にわたり判断理由を保持すべきものを扱う。

RU は、課題解決後に変更実施が必要と判断された場合の変更要求を扱う。

GitHub Issue は、req/case パイプラインで実装対象となった作業単位であり、本 RU の課題管理とは別概念とする。

Intake / Learning は AI 駆動開発の改善循環を扱い、本 RU の課題管理とは別系統とする。

## 3. 課題成果物

### 3.1 配置

課題の正規配置先を以下とする。

`docs/issue-list/`

### 3.2 管理単位

1課題につき1ファイルとする。

課題の状態によってディレクトリを移動しない。

各課題ファイル自身が状態を保持する。

解決済み、クローズ済みの課題も課題管理の履歴として同じ体系内で追跡できること。

### 3.3 識別

各課題は一意な課題 ID を持つこと。

GitHub Issue 番号と明確に識別できること。

具体的な接頭辞、採番規則、ファイル名規則は Design で確定してよい。

### 3.4 状態

少なくとも次の意味を表現できること。

- 未着手。
- 検討中。
- 保留。
- 解決済み。
- クローズ済み。

具体的な保存値は Design で確定してよい。

「解決済み」と「クローズ済み」は区別すること。

- 解決済み: 課題に対する結論が出た状態。
- クローズ済み: 必要な正規成果物への反映、または反映不要の確認まで完了した状態。

### 3.5 課題に保持する情報

少なくとも以下の意味を保持できること。

- 課題 ID。
- 件名。
- 状態。
- 課題内容。
- 背景。
- 影響。
- 関連成果物。
- 現時点の選択肢。
- 判断材料、証拠。
- 不足情報。
- 担当。
- 期限。
- 再評価条件。
- 検討経過。
- 結論。
- 反映先。
- クローズ確認。

担当、期限等、課題によって不要な項目は空値または省略可能としてよい。

保留状態では、原則として「なぜ現在判断できないか」と「何が成立すれば再評価するか」を識別できること。

解決済みでは結論を保持すること。

クローズ時は、反映先または反映不要の理由を確認できること。

## 4. エージェンティックな課題管理能力

課題管理は単なるファイル形式ではなく、ADF エージェントが利用可能な共通能力として提供する。

少なくとも次の操作能力を持つこと。

- 課題の検知。
- 新規起票。
- 検索、参照。
- 更新。
- 検討経過の追加。
- 保留。
- 再評価。
- 解決。
- 反映確認。
- クローズ。
- 再オープン。

内部実装については、操作単位に Skill を分割しても、1つの課題管理 Skill の `references/` 等に分割してもよい。

単なる操作差だけを理由として Skill を不必要に細分化しないこと。

現行 ADF の Command / Workflow Skill / Capability Skill の責務分離に従い、最終的な Skill 分割は Design で確定すること。

課題管理能力は特定の単一 workflow に閉じず、要件定義、設計、レビュー、実装、検証等の複数 workflow から利用可能であること。

## 5. `/agentdev/issue`

### 5.1 公開入口

課題管理の人間向け公開入口として `/agentdev/issue` を提供する。

### 5.2 自然言語による操作

ユーザーに `add`、`list`、`update`、`resolve`、`close`、`reopen` 等のサブコマンド、引数、操作文法の暗記を要求しないこと。

ユーザーは自然言語で意図を伝えればよく、課題管理側が現在の会話文脈、対象課題、状態等から必要な操作を判断すること。

例:

- `/agentdev/issue この論点を課題として残して`
- `/agentdev/issue 未解決の課題を確認したい`
- `/agentdev/issue サブエージェント探索重複の課題を再検討して`

内部実装で明示的な操作種別を持つことは禁止しない。

### 5.3 コマンド非依存

課題管理能力の利用に `/agentdev/issue` の明示実行を必須としないこと。

要件定義、設計、レビュー、実装、検証等の ADF workflow が未解決事項を認識した場合、必要に応じて課題管理能力を利用できること。

ユーザーが明示的に課題登録を指示しなかったことだけを理由に、将来の設計、実装、検証に影響する未解決事項を会話コンテキストだけへ残さないこと。

### 5.4 課題化判定

すべての疑問、TODO、一時エラーを課題化しないこと。

少なくとも、現在の作業で解決できず、かつ将来の設計、実装、検証、合意等に影響する未解決事項を課題化候補とすること。

正規成果物の確認等によってその場で解決可能な疑問は、原則として課題化前に解決を試みること。

### 5.5 自律性の境界

エージェントによる課題管理は、既存の承認、判断境界を迂回してはならない。

ユーザー合意が必要な設計判断を課題管理能力自身が勝手に確定しないこと。

一方、既に正規成果物または現在の会話で結論が確定している場合は、その結果を課題へ反映可能とすること。

## 6. 課題の再評価

保留課題を単に保存して忘れる状態にしないこと。

再評価条件を持つ課題について、関連する作業、設計、レビュー、分析等を行う際に条件成立を確認できること。

ただし、すべての ADF コマンド実行時に `docs/issue-list/` 全文を読み込むことを要求しないこと。

課題 ID、状態、関連成果物、再評価条件等を利用し、必要な課題へ効率的に到達できる設計とすること。

再評価後は次のいずれかを選択できること。

- 結論が出た場合は解決済みとする。
- まだ判断できない場合は、理由と不足情報を更新して保留を継続する。
- 課題自体が消滅した場合は、対応不要という結論で解決できる。
- 必要な変更が確定した場合は、解決結果を正規成果物へ反映し、必要に応じて RU 化する。

## 7. 課題解決後の反映

課題管理能力自身が、Decision、REQ、HLD、LLD 等すべての成果物更新責務を直接所有する必要はない。

課題管理では少なくとも以下を追跡すること。

- 何が結論となったか。
- どこへ反映すべきか。
- 実際に反映されたか。

成果物更新そのものは、その成果物を所有する ADF 能力へ委ねてよい。

課題をクローズする前に、必要な反映が完了していること、または反映不要であることを確認すること。

## 8. 初期課題の登録

本 RU の実装時に、課題管理機構の最初の実課題として「サブエージェント探索責務分割の要否」を `docs/issue-list/` に登録すること。

### 8.1 初期状態

保留とする。

### 8.2 課題

OpenCode セッション分析では、複数の子セッション間で同じ path を参照する重複探索が広く確認された。

サブエージェントごとに探索対象または探索責務を明示的に分割することで、この重複を削減すべきかを判断する必要がある。

### 8.3 判断材料

改善前分析では、read を伴う97論理実行単位のうち68単位で、異なる子セッション間の同一 path 参照が確認された。

### 8.4 現時点で判断しない理由

現在観測されている重複には、少なくとも以下が混在している可能性がある。

- 工程間の文脈引き継ぎ不足。
- source / projection の二重探索。
- 必要な独立検証。
- サブエージェントの探索責務自体の重複。

RU-0001 では前二者を含む改善と、検証価値の観測可能化を実施する。

その効果を観測する前にサブエージェントの構造を変更すると、原因と効果を分離できない。

### 8.5 再評価条件

RU-0001 の改善を実運用へ反映した後、通常の ADF 開発を一定量継続し、改善前と同じ観点で比較可能な OpenCode セッション履歴が十分に蓄積したこと。

単に時間が経過したことではなく、改善後の実行実績を比較可能になったことを条件とする。

### 8.6 再分析事項

少なくとも以下を再分析すること。

- 子セッション間の同一 path 再読込。
- source / projection 由来の重複を除いた残存重複。
- 工程間の文脈引き継ぎ不足による重複。
- 独立検証として必要な重複。
- 同種検証による新規 finding の有無。
- 残存する不要な探索重複。
- 残存重複の token 消費への影響。

### 8.7 再評価結果

再分析後、以下のいずれかとすること。

- 不要: 必要な重複である、または RU-0001 によって十分改善された場合、探索責務分割を実施せず課題を解決、クローズする。
- 判断不能: 原因分離または実績が不足する場合、理由を追記して保留を継続する。
- 必要: 不要な探索重複が有意に残り、探索責務分割が有効と判断した場合、課題を解決し、その変更を新規 RU として要件化する。

課題管理から直接実装へ進めないこと。

## 9. 完了条件

以下をすべて満たすこと。

- `docs/issue-list/` が課題管理の正規配置先として定義されている。
- 1課題1ファイルで管理される。
- 状態を各課題ファイル自身が保持する。
- 解決、クローズ後も履歴を追跡できる。
- 課題の結果を Decision、HLD、LLD 等の特定成果物へ限定していない。
- `/agentdev/issue` が自然言語の単一公開入口として利用できる。
- ユーザーがサブコマンドや引数体系を覚える必要がない。
- ADF の他 workflow から課題管理能力を利用できる。
- 課題の検知、起票、検索、更新、保留、再評価、解決、反映確認、クローズ、再オープンを扱える。
- 既存の承認境界を迂回しない。
- Intake / Learning / GitHub Issue / Decision / RU との責務が明確に分離されている。
- 「サブエージェント探索責務分割の要否」が最初の課題として登録されている。

## 10. テスト・検証観点

- 自然言語だけで新規課題を起票できること。
- 自然言語だけで未解決課題を検索、確認できること。
- 自然言語だけで既存課題を更新、保留、解決、クローズできること。
- `/agentdev/issue` の明示実行なしに、他の ADF workflow から課題管理能力を利用できること。
- 同一課題を不必要に重複起票しないこと。
- 保留課題の再評価条件を後から取得できること。
- 解決結果を Decision へ反映する Case を扱えること。
- HLD、LLD 等へ直接反映する Case も扱えること。
- 変更不要で終わる課題も扱えること。
- 解決済みだが未反映の課題をクローズ済みと誤認しないこと。
- GitHub Issue と課題 ID を混同しないこと。
- `docs/issue-list/` 全文読込を毎回要求しないこと。
- 初期課題「サブエージェント探索責務分割の要否」が保留状態で正しく登録されること。

## 11. 非対象

- Intake / Learning パイプラインへの統合。
- GitHub Issue による課題管理への置換。
- すべての課題を Decision 化すること。
- 課題起票時点で反映先を固定すること。
- 課題管理から直接実装を開始すること。
- ユーザーに課題管理用 CLI 構文の暗記を要求すること。
