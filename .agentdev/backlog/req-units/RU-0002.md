# RU-0002: Artifact Graphから最小トレーサビリティ機能への再構成

## 1. 背景

現行 `agentdev-artifact-graph` は、汎用ノード・関係モデル、派生索引、根拠情報、拡張定義、鮮度管理、複数の問い合わせ種別などを持つ。最小 TIM ではこれらの大半を必要としない。

外部実装についても比較した結果、OpenFastTrace は TIM の概念・検査方法の参照実装として有用だが、Java 実行環境や独自記法への適合が必要となるため、ADF の標準実行依存として採用しない。Eclipse Capra、専用グラフDB等も今回の最小機能に対して過大である。

## 2. 目的

`agentdev-artifact-graph` を廃止し、要件と成果物の明示的な対応関係だけを扱う小規模な標準機能 `agentdev-traceability` へ再構成する。

## 3. 要件

1. 標準配布スキル名は `agentdev-traceability` とし、`artifact-graph` を新しい標準機能名として引き継がないこと。
2. 標準公開能力は `coverage`、`impact`、`check` を基本とすること。
3. `coverage` は、要件を指定して対応する Design 文書、実装成果物、検証手段を取得できること。
4. `coverage` は、成果物を指定してその成果物が対応する要件を取得できること。
5. `coverage` は明示された対応関係を全件返し、候補数上限、ランキング、探索深度によって黙って切り捨てないこと。
6. `impact` は、要件を起点に、その要件へ明示的に対応する成果物を変更時の再確認候補として取得できること。
7. `impact` は、成果物を起点に、その成果物が対応する要件を経由して、同じ要件へ対応する他成果物を再確認候補として取得できること。
8. `impact` は任意深度のグラフ探索を行わず、成果物 ↔ 要件 ↔ 成果物の範囲を超えて探索しないこと。
9. `impact` の空結果を「影響なし」の証明として扱わないこと。
10. `check` は、少なくとも不正な対応宣言、未知の成果物役割、存在しない要件への参照、実装対応の欠落、検証対応の欠落、対応宣言の根拠箇所を取得できない状態を決定的に検査できること。
11. 標準実装は正規成果物を直接走査し、対応関係をその場で解決できること。
12. `.agentdev/graph/` のような派生 Graph を標準動作の必須入力または必須生成物としないこと。
13. 派生索引の鮮度判定、再生成、生成バージョン、設定ダイジェスト等を TIM の必須契約としないこと。
14. `neighbors`、`path`、`provenance`、`related`、`dependency`、`implementation`、`diagnostics` の旧公開動作との互換性を必須としないこと。
15. 一般文書探索、任意経路探索、構造診断、依存関係探索を `agentdev-traceability` の責務へ取り込まないこと。
16. OpenFastTrace、Eclipse Capra、専用グラフDBを標準実行依存として導入しないこと。
17. 性能について数値の受け入れ基準を設けないこと。
18. 将来、直接走査が実運用上の問題として観測された場合、`coverage`、`impact`、`check` の外部契約を変えずにキャッシュまたは索引を追加できる構造とすること。
19. 具体的な対応宣言の表記は Design で確定し、要件では文字列形式を固定しないこと。

## 4. 作業仮定

- 対応宣言は、対応する成果物自身を正規情報源として保持する。
- 中央の `traceability.yaml` 等を正規台帳として新設しない。
- 対応成果物の所在はリポジトリ相対パスを基本とし、必要な場合のみファイル内位置を根拠として扱う。
- 現行 Artifact Graph のファイル探索、Markdown 解析、要件ID解決、存在確認等の小さな実装資産は、設計に適合する場合のみ再利用する。

## 5. 対象範囲

- `agentdev-artifact-graph` から `agentdev-traceability` への標準機能再構成
- `coverage`、`impact`、`check` の公開契約
- 正規成果物の直接走査
- 対応宣言の解析・検査
- 現行 Artifact Graph 実装の再利用可否判定

## 6. 対象外

- 旧公開APIの互換層
- 一般文書グラフ
- 任意深度の経路探索
- 意味類似検索
- LLM による対応関係の自動確定
- 派生 Graph の常設
- 専用グラフDB
- OpenFastTrace の本番依存化
- 性能最適化の先行実装

## 7. 受け入れ条件

| ID | 合否判定可能な条件 |
|---|---|
| AC-001 | 派生 Graph が存在しない状態で `coverage`、`impact`、`check` の3能力が利用できること |
| AC-002 | `coverage` が明示された対応関係を欠落なく返すこと |
| AC-003 | `coverage` が対応関係を候補数上限によって黙って切り捨てないこと |
| AC-004 | `impact` が成果物 ↔ 要件 ↔ 成果物の範囲を超えて探索しないこと |
| AC-005 | `impact` が空結果の場合でも「影響なし」と断定する情報を返さないこと |
| AC-006 | `check` が不正な対応宣言、未知の役割、存在しない要件参照を個別に検出できること |
| AC-007 | `check` が実装対応の欠落と検証対応の欠落を個別に検出できること |
| AC-008 | `check` が正常な Design 対応0件を異常としないこと |
| AC-009 | 旧 Artifact Graph の公開APIを呼び出さずに標準機能が成立すること |
| AC-010 | `.agentdev/graph/` の生成・鮮度管理を実行せずに標準機能が成立すること |

## 8. 検証方法

- 正常系: 1要件に複数役割の対応成果物を用意し、`coverage` と `check` を確認する。
- 逆引き: 1成果物から複数要件への対応を `coverage` で確認する。
- 変更影響候補: 要件起点、成果物起点の双方で `impact` の到達範囲を確認する。
- 異常系: 不正な宣言、未知の役割、存在しない要件ID、実装対応欠落、検証対応欠落を個別に確認する。
- 空状態: 対応宣言がない成果物・要件を照会し、空結果と基盤障害を区別できることを確認する。
- 旧依存排除: 旧 Graph 生成物を削除した状態で3能力が成立することを確認する。

性能は明確な利用者要件が存在しないため `not applicable` とする。
検証結果は各受け入れ条件ごとに `pass` / `fail` / `blocked` / `not applicable` で記録する。
