# RU-0006: Command / Workflow Skill アーキテクチャ再編

## 目的

AgentDevFlow の全公開 Command を横断的に分析し、Command が workflow 実装本体を抱える現行構造を、公開 Command、Workflow Skill、STEP reference、Capability Skill、Harness runtime の責務へ再編する。

本再編では、Command をユーザー向け公開インターフェースとして薄く保ち、workflow 実装を Workflow Skill へ移す。Workflow Skill は compaction 後も Harness の ToDo / task state と GitHub / Git / repository artifact 等の durable state から再開可能な STEP モデルを持ち、STEP 詳細は `references/` へ段階的に分離する。

個別 Command を順番に Skill 化して局所最適化するのではなく、現行全 Command の workflow architecture inventory を先に作成し、workflow 境界、STEP 境界、Capability 境界、Extension 境界の妥当性を横断検証した上で、一体的に新体系へ移行する。

公開 Command の名称、主要入力、主要出力、ユーザーから見た workflow の意味は原則維持し、今回の変更では内部実装アーキテクチャを再構成する。

## 対象

- 現行全公開 Command の workflow architecture inventory 作成。
  - 公開入力、公開出力、ユーザーから見た責務
  - 主要処理段階、主要分岐
  - side effect
  - HITL 境界
  - parallelism / fan-out / fan-in
  - resume point
  - durable state / SSoT
  - Harness runtime state 依存
  - 利用 Capability Skill
  - internal workflow 分割候補
- Command を user-facing interface / entrypoint / dispatcher へ縮退し、workflow 手順本体を Workflow Skill へ移すこと。
- `1 Command = 1 Workflow Skill` を前提とせず、制御構造、resume model、side-effect model、HITL、parallelism、完了条件が実質的に異なる場合は 1:N Workflow Skill 分割を許容すること。
- Workflow Skill の `SKILL.md` を control plane とし、workflow purpose、input/output、global invariant、STEP 一覧、branch/loop、transition、ToDo 運用、resume protocol、stop/complete condition、STEP reference 導線を所有させること。
- STEP は既存 Command の見出し番号を機械的に分割せず、独立して開始、完了判定、再開できる resume point 単位として再定義すること。
- STEP 詳細を Workflow Skill 配下の `references/` へ分離し、各 STEP reference が少なくとも Purpose、Input Resolution、Preconditions、Procedure、Result、Evidence / Durable Outputs、Completion Verification、Resume / Idempotency を持つこと。
- STEP reference は次 STEP を決定せず local result のみを返し、result に対する transition は `SKILL.md` が所有すること。
- STEP 間 handoff は会話コンテキストを正とせず、後続 STEP が必要な情報を GitHub、Git、repository artifact、Harness ToDo、Harness task state 等から再取得、再導出、再検証する Input Resolution モデルへ移行すること。
- STEP 間 state は、(1) durable SSoT から再構成、(2) identifier のみ保持して再取得、(3) 再構成不能な最小 scalar state を Harness runtime に保持、(4) 大容量かつ再生成不能な場合のみ runtime artifact を使用、の優先順位とすること。
- Harness ToDo を workflow execution の program counter / checkpoint として使用し、STEP identifier、STEP status、workflow/domain correlation identifier、必要時のみ再構成不能な最小 runtime scalar を保持すること。ToDo を domain state の SSoT や大規模 workflow database としないこと。
- compaction 後は会話履歴ではなく Harness ToDo から current STEP を決定し、当該 STEP reference を再読込して Input Resolution に従い必要状態を再取得・再検証すること。
- 対象 Harness は、ToDo の作成・状態復元、background / parallel child task の起動、domain identifier と child task identity の対応保持、compaction 後の child task status 取得、child result 回収を提供できることを前提とすること。
- 並列 workflow の実行中 child state は Harness task state を用い、完了済み child の最終状態は可能な限り GitHub 等の durable domain state から再構成すること。fan-in を LLM の会話記憶や一時 result 配列のみに依存させないこと。
- 複数 workflow で再利用される能力は Capability Skill として全 Command 横断分析後に抽出すること。workflow 固有 STEP の類似性だけを理由に reference を過剰共通化せず、capability 共通化を優先すること。
- Project Extension を現行の command / skill ファイル種別中心モデルから、Workflow Extension / Capability Skill Extension の責務モデルへ再編すること。
  - Public Workflow Extension は当該公開 workflow execution scope の context / rules / checks / acceptance gates / must_not を所有し、配下の internal workflow / STEP 全体を拘束する。
  - 1:N 分割で internal workflow 固有の project-local 拡張が必要な場合のみ internal Workflow Extension を許容する。
  - Capability Skill 固有の project-local 拡張は Capability Skill Extension が所有し、その Capability を利用する全 workflow に適用する。
  - Workflow Extension を呼び出した全 Capability Skill の extension として暗黙継承・コピーしない。
  - 標準 workflow → public Workflow Extension → internal Workflow Extension の順で追加・制約強化として適用し、標準挙動の暗黙上書きを行わない。
- 既存 `.agentdev/extensions/commands/*.yaml` との後方互換性は必須としない。ただし、公開 Command 単位の project-local 制約が内部 workflow 全体へ効く有用な意味は Workflow Extension として維持すること。互換性だけを目的とした旧 extension model の恒久二重運用を行わないこと。
- 代表ケースとして少なくとも以下の異なる workflow 特性で新モデルの妥当性を検証すること。
  - `case-run` / `case-auto`: orchestration、resume、single / Epic Wave、parallel fan-out / fan-in、child task recovery、compaction
  - `req-define`: interactive workflow、HITL、reasoning loop、Decision、adversarial review、session context dependency
  - `req-save` / `spec-save`: deterministic processing、file mutation、validation、idempotency、commit / push
  - `intake-promote`: classification、review、HITL approval、state transition、destructive / irreversible action
- `case-run` は single Issue と Epic Wave を代表的な internal workflow 分割候補として評価し、1:N 分割の妥当性を全体 architecture の観点から確認すること。
- `case-auto` の最終 workflow 設計は、少なくとも req-save、spec-save、case-open、case-run、case-close の新 workflow 契約確定後に行い、下位 workflow の詳細実装を複製しない sequence / parallel execution / result handling の上位 orchestrator として再評価すること。
- 実装は専用 worktree 内で段階的に進めてよいが、全体 architecture inventory と workflow 境界の横断評価が完了する前に個別 Command の Skill 移行実装を開始しないこと。
- worktree 内の移行途中では旧新混在を許容するが、main 反映時点では全対象 Command / Workflow Skill / STEP reference / Extension が新体系へ移行済みであること。main への反映を体系切替境界とし、部分移行状態を完成状態として残さないこと。
- 移行完了時、Workflow Skill へ移管した workflow 実装を Command 本文へ重複して残さず、不要となった旧 workflow implementation、旧 extension contract、重複規則を正規経路として残さないこと。
- 関連する REQ / Decision / SPEC、documentation、checker、tests を新責務モデルへ整合させること。

## 対象外

- 公開 Command 名の積極的な統廃合。
- 公開 Command のユーザー向け責務そのものの再設計。
- 公開 IF 変更を内部実装都合で暗黙に行うこと。
- OpenCode 自体への機能追加。
- Harness の ToDo、compaction、background task recovery 機能そのものの実装。
- compaction 後に child task identity / status を復元できない Harness 向け fallback 実装。
- OpenCode 1.18.15 に存在しない hidden Skill 機構の新設。
- Workflow Skill の discovery / direct invocation を技術的に完全遮断する仕組み。意図しない利用リスクは description、invocation contract、guard 等の soft guard で許容する。
- Runtime state 用の新規永続データベース。
- Runtime artifact の AgentDevFlow 正規成果物化。
- 後方互換性だけを目的とした旧 command-extension model の恒久維持。

## 要件化の方向

req-define では本 RU を単一 Command のリファクタリングではなく、AgentDevFlow の Command / Skill / Workflow / Extension 責務モデルを横断的に再構成する要件として扱う。

要件化では少なくとも以下を区別する。

1. 利用者視点の要件
   - 公開 Command の名称、主要入力、主要出力、ユーザーから見た workflow 意味を原則維持する。
   - 長時間 workflow が compaction 後も安全に再開できる。
   - workflow の部分完了、停止、並列 child の状態を誤認せず再開できる。
   - project-local extension が責務に沿った範囲へ一貫して適用される。
2. 成果物視点の仕様候補
   - Workflow Skill / Capability Skill / STEP reference の物理構造。
   - SKILL.md と STEP reference の詳細責務分界。
   - ToDo / Input Resolution / transition / result の実行契約。
   - Workflow Extension / Capability Skill Extension の配置、適用順序、schema。
   - command-to-workflow dispatch、1:N internal workflow 構造。
   - checker、tests、migration procedure の具体化。
3. Decision 候補
   - Command = public interface、Workflow Skill = workflow implementation、Capability Skill = reusable capability とする責務モデル。
   - 1 Command = 1 Workflow を固定しない方針。
   - STEP を resume point 単位とし、handoff を conversation memory に依存させない方針。
   - Extension を file-kind 中心から workflow / capability responsibility 中心へ再編する方針。
   - worktree 内で全体移行し、main 反映を体系切替境界とする方針。

req-define は上記分類を最終確定し、既存正規成果物への APPEND / UPDATE と新規 CREATE の妥当性を横断評価する。現行 Command の Step 番号や `case-run` / `case-auto` の代表構造を他 Command へ機械適用しない。

## 決定的受け入れ条件

1. 全公開 Command が architecture inventory に含まれ、各 Command の public contract、主要処理段階、分岐、side effect、HITL、parallelism、resume、durable state、Harness dependency、Capability dependency、internal workflow 候補を確認できる。
2. 個別 Workflow Skill の移行実装開始前に、全公開 Command の Workflow Architecture Map が作成され、workflow boundary、STEP boundary、Capability boundary、Extension boundary の横断レビューが完了している。
3. 既存公開 Command の名称、主要入力、主要出力、ユーザーから見た workflow の意味が原則維持される。変更が必要な場合は実装都合で暗黙変更せず追加判断として停止・報告される。
4. 対象 Command から workflow 手順本体が除去され、公開 interface / dispatch を中心とした構造となる。Workflow Skill へ移した手順が Command に重複して残らない。
5. 各 Command について 1:1 / 1:N Workflow Skill の選択理由を説明でき、制御構造等が実質的に異なる経路は分割評価され、単なる operation 差だけで不必要に分割されていない。
6. 各 Workflow の STEP が独立した開始、完了判定、resume point として成立し、旧 Command の見出し番号を機械的にファイル分割しただけの構造になっていない。
7. 各 STEP reference が過去会話なしで Input Resolution、実行、検証、再開を行える。STEP transition は `SKILL.md` が所有し、reference に重複定義されていない。
8. 代表 workflow で、前 STEP までの会話内容を失った状態を想定しても Harness ToDo と durable state から current STEP と必要入力を復元できる。
9. STEP 間で必要な durable 情報は SSoT から再取得・再検証され、自然言語の前 STEP result のみに依存していない。
10. 再構成不能な runtime state は必要最小限に限定され、ToDo または Harness runtime state に保持される。ToDo が大規模 domain state storage として利用されていない。
11. 並列 child task を持つ代表 workflow で、compaction 後も child identity / status を Harness から復元でき、完了済み child の状態を durable domain state と併せて再構成して fan-in 判定できる。
12. 複数 workflow で共通する能力が Capability Skill として横断的に評価され、workflow 固有 STEP が過剰に共通 reference 化されていない。
13. Workflow Extension / internal Workflow Extension / Capability Skill Extension の責務、配置、適用範囲、適用順序が定義され、public Workflow Extension が internal workflow / STEP 全体を拘束しつつ Capability Skill extension へ暗黙コピーされない。
14. 既存 command-extension との後方互換性のためだけの二重 extension model が正規状態として残っていない。
15. Workflow Skill の意図しない discovery / invocation リスクに対し、OpenCode 1.18.15 で実現可能な soft guard が導入される。
16. `case-run` / `case-auto` により orchestration、resume、single / Epic Wave、parallelism、compaction モデルが検証される。
17. `req-define` 等により interactive / HITL / loop を持つ workflow でも STEP / resume / compaction モデルが成立する。
18. `req-save` または `spec-save` 等により deterministic mutation / verification / commit を持つ workflow でも新モデルが成立する。
19. `intake-promote` 等により classification / review / approval / irreversible action 境界を持つ workflow でも新モデルが成立する。
20. `case-auto` は下位 workflow 契約確定後に再設計され、下位 workflow の詳細処理を複製しない上位 orchestrator となる。
21. 正常系では既存公開 IF を通じて代表 workflow が完了する。
22. blocked / failed / validation failure では未完了 STEP を completed と誤認せず、定義された停止状態を保持する。
23. 中断・再実行では completed STEP の会話コンテキストを前提とせず current STEP から安全に再開できる。
24. GitHub、Git、Harness child task 等の外部依存取得失敗時に状態を推測して後続 STEP へ進まず、定義された blocked / failed として扱う。
25. 入力対象なし、artifact action なし、処理対象 child なし等、既存 workflow が持つ no-op / empty state の外部挙動が維持される。
26. 配布元リポジトリと consumer repository の責務境界、および project extension 境界が新 architecture でも維持される。
27. worktree 内の実装・検証が完了するまで main に部分移行状態を反映せず、main 反映時点では全対象 Command / Workflow Skill / STEP reference / Extension が新体系へ移行済みである。
28. 移行完了時に旧 workflow implementation、不要な旧 extension contract、重複規則が正規経路として残っていない。保持が必要なものは新 architecture 上の責務と理由が明示されている。
29. 関連 checker / test を更新し、全受け入れ条件の検証結果を `pass / fail / blocked / not applicable` で記録する。fail が承認済みスコープ内の修正のみで解消可能な場合は修正・再検証し、公開 IF 変更、スコープ拡大、新規 architecture 判断、追加 Harness capability、外部依存変更が必要な場合は反復を停止して判断事項を報告する。
30. blocked / fail / 未検証項目が残る状態を完了として扱わない。

## Source Summary

ユーザーとの壁打ちでは、現行 Command の workflow 実装が厳格化・機能追加により肥大化していることを起点に、Command を公開 IF とし workflow 実装を Skill へ移す構造を検討した。

`case-run` / `case-auto` を代表ユースケースとして、Workflow Skill の `SKILL.md` を control plane、`references/<step>.md` を STEP 詳細、Harness ToDo を program counter とするモデルを掘り下げた。STEP は既存の Markdown 見出し単位ではなく、独立して開始・完了判定・再開できる resume point とすることで合意した。

STEP 間 handoff は LLM の会話記憶へ任せず、後続 STEP が必要情報を GitHub / Git / repository artifact / Harness task state 等から再取得する Input Resolution を中心とすることで合意した。ToDo は current STEP と最小 correlation 情報を保持する checkpoint とし、domain state の SSoT にはしない。対象 Harness は ToDo と実行中 child task の identity / status を compaction 後も復元可能なものを前提とすることで合意した。

`case-run` の検討では `Resolve / Analyze / Prepare / Preflight / Execute / Finalize` の6 STEP を代表案として採用し、single Issue と Epic Wave は同一公開 Command の背後で internal workflow を 1:N 分割できることを確認した。ただし、この具体構造を他 Command へ機械適用せず、全 Command を横断分析して workflow 境界を確定する方針とした。

さらに Project Extension について、現行 command / skill というファイル種別への対応ではなく、Workflow Extension / Capability Skill Extension の責務モデルへ再編することで合意した。既存 command-extension の後方互換性は必須としない一方、公開 Command 単位の project-local 制約が内部 workflow 全体へ適用される有用な意味は Workflow Extension として維持する。

移行は全 Command の architecture inventory と新構造を先に確定し、専用 worktree 内で一体的に実装・横断検証する。worktree 内では移行途中の新旧混在を許容するが、main への反映を体系切替境界とし、main 上に部分移行状態を完成状態として残さないことで合意した。
